# Phase 4: Skills Distribution - Context

**Gathered:** 2026-09-09
**Status:** Ready for planning

<domain>
## Phase Boundary

The five curation skills reach every configured runtime from a brew-installed binary that
carries their content itself — installed in a runtime's native skill format where one exists,
and indexed into a delimited, re-detectable block in AGENTS.md (with the skill files written
beside it) where none does. The embedded content is byte-identical to what the Claude plugin
ships, and a mechanical gate proves it, so a plugin-free install teaches an agent to curate
and the two copies cannot drift.

**In scope:** the `skill/` → `internal/skills/data/` vendor step and its drift gate; the
`//go:embed` package and its skill-inventory walk; a declarative `SkillTarget` on `Plan`
authored per runtime; `internal/skills`' `Install` and its filesystem seam; the AGENTS.md
delimited-block splice (append / replace / fail); the aggregated per-row `Outcome` and the
new `registration=` / `skills=` / destination / digest row fields; `generic`'s skills payload;
a new one-line `summary:` frontmatter key on each shipped SKILL.md.

**Out of scope:** the plugin's hooks and its `/engram-setup` command — this phase distributes
the five *skills* only; Phase 5's `/engram-setup` delegation gate and `internal/setupgen`;
Phase 6's install documentation; Cursor (REQ-register-cursor, deferred to v2); any change to
the five-value `Outcome` vocabulary, to `Classify`, or to `exit.go` (all pinned in Phase 2 and
deliberately left alone by Phase 3's D-16); `REQ-setup-reconcile-hand-edits` and
`REQ-setup-drift-detection` (both explicitly v2).

**Requirements:** REQ-skills-embedded-in-binary, REQ-skills-native-format,
REQ-skills-agents-md-fallback.

<decisions>
## Implementation Decisions

### Embedding and the anti-drift gate

- **D-01:** `skill/engram/skills/` stays **canonical**; a Taskfile target (`task skills:vendor`
  or equivalent) copies it wholesale into `internal/skills/data/`, which `//go:embed` reads.
  This mirrors `internal/webauth/static` (vendored from `ui/` by `task ui:build`) exactly, and
  leaves plugin authorship untouched: an author edits the file `claude plugin install` reads,
  and the Go tree follows.
  Rejected: **inverting the direction** (skills canonical in `internal/skills/data/`, `skill/`
  generated by `internal/surfacesgen`). It would reuse the existing `interface-surface drift`
  CI job — which already diffs `skill/` — for zero new CI, but it makes the plugin's own
  directory generated output, and the plugin dir is what `claude plugin install` consumes.
  Rejected: **a symlink** — `//go:embed` does not follow symlinks.
  — **Reversibility:** costly — flipping the canonical side later means rewriting the vendor
  task, the drift gate, and every embedded path, while the plugin's on-disk layout is a
  published consumption surface.

- **D-02:** Drift is proven by **a Go test in `internal/skills` that byte-compares the embedded
  FS against the on-disk `../../skill/engram/skills/` tree** — set-equality over discovered
  paths, then byte-equality per path. **Not** a CI-only `git diff --exit-code` job.
  A vendored SPA needs a pnpm build to verify, which is why backlog Phase 999.1 proposes a
  commit-timestamp *proxy* for it. A skills vendor is a plain file copy, so exact content
  equality is checkable with no toolchain, in milliseconds — so this gate lives in
  `go test ./...` and therefore fires on `task`, on a local run, and on **every feature-branch
  push**. That is precisely the coverage 999.1 records `ui-drift` as lacking
  (`pull_request` / `push: main` only), and it is a better answer than the proxy for this tree.
  It also catches an edit made directly to the vendored copy, which a one-directional
  regenerate-then-diff would not.
  **Invariant: set-equality, never containment.** A containment assertion passes vacuously on
  a superset — the failure class memories `bqhy5v5hq9` and `8583e0yqa1` both record.
  Rejected: **a CI drift job mirroring `ui-drift`** (inherits 999.1's hole verbatim: a whole
  phase can edit `skill/` and stay green until PR time). Rejected: **both** (for a plain copy
  the CI job proves nothing the test does not, so it is two mechanisms asserting one property).

- **D-03:** The binary satisfies success criterion 1 ("can produce the full content") through
  **the existing preview, with the full bytes in the `--output json` lane only**. The text row
  stays dense: destination path(s), a per-skill content digest, and a byte count. No new verb,
  no new flag, no golden churn.
  This is the only shape that honors REQ-setup-previews-by-default ("shows the exact command or
  **content** that would be issued, not a summary of it") without putting 58KB into a
  `key=value` row — D-15 of Phase 3's one-serialization-plus-a-view, unchanged.
  Rejected: **a `--show-skills` flag** (a 7th flag on an already-six-flag command; both goldens
  move; a `destructive_test.go` row; a conditional-rule entry). Rejected: **a dedicated
  `engram skills list|show` command** — and note its Phase 5 justification is weaker than it
  looks: `internal/setupgen` can import `internal/skills` in-process and never needs a CLI verb.
  — **Reversibility:** costly — once a machine consumer reads the json `content` field,
  removing it is a breaking change to the report's published shape.

- **D-04:** The vendor step copies the **whole subtree**, the embed directive uses
  **`//go:embed all:data`**, and the skill inventory is **whatever the embedded FS walks** —
  nothing anywhere hardcodes "five".
  A sixth skill, or an existing skill gaining a `references/` file, ships with zero code change,
  and D-02's set-equality gate covers it automatically. This is the repo's stated preference for
  structural predicates over enumerations that fail by absence (`operatorCommands()`,
  `cmdwalk.go:118`; memory `zcev96ng18`).
  **The `all:` prefix is load-bearing, not decoration:** `internal/webauth/static_test.go:38`
  records a bare `//go:embed` silently excluding `_`-prefixed subtrees. That test exists because
  this repo already lost that one.
  Rejected: **enumerating the five** in the vendor step and a Go var (adding a sixth skill and
  forgetting the list means it silently never ships). Rejected: **structural discovery plus a
  pinned five-name canary** (a loud tripwire on intentional additions, at the cost of churn per
  addition; not taken, but the cheapest thing to add later if silent scope growth ever bites).

### Where the writes live

- **D-05:** `internal/setup` **declares**, `internal/skills` **installs**, `cmd/engram`
  **composes**. `Plan` grows a declarative `SkillTarget` (destination + format), authored in
  each runtime's own file — the same AUTHORED-HERE invariant `Probe` follows (Phase 3 D-09).
  `internal/skills` owns the embed and an `Install` with its own injectable filesystem seam.
  `cmd/engram/setup.go` wires `plan.SkillTarget` → `skills.Install`.
  This is forced as much as chosen: `leafpurity_test.go` fails on **any** same-module import, so
  `internal/setup` can never import `internal/skills`. This split keeps `internal/setup` a
  zero-file-I/O stdlib leaf and keeps threat **T-02-01 closed**, while putting the write logic
  next to the content it writes.
  Rejected: **`internal/setup` doing it all** via `Environment` gaining
  `ReadFile`/`WriteFile`/`MkdirAll` and `Action` gaining a file-write variant — simplest call
  graph, but the vendored skills would have to move into `internal/setup/data/` (contradicting
  D-01) and T-02-01's zero-file-reads property would be deliberately reopened. Rejected: **the
  write loop in `cmd/engram`** with `internal/skills` content-only — it keeps `internal/skills`
  as pure as `internal/setup` but splits the apply path across the `cmd`/`internal` boundary and
  makes `cmd/engram` grow its own FS seam.
  — **Reversibility:** costly — undoing it moves `Install` across a package boundary and
  reopens the leaf-purity gate's premise.

- **D-06:** A runtime row keeps **exactly one `Outcome`**, aggregated by an **authored,
  documented precedence: `failed` > `wrote` > `already-correct` > `would-write` >
  `not-present`**. Per-facet detail rides as ordinary row fields
  (`registration=already-correct skills=wrote`) — D-15's one-more-`key=value` shape with no new
  rendering code.
  `exit.go`, `Classify`, and `TestClassifyExhaustiveOutcomeCombinations` are **untouched** —
  the same posture D-16 of Phase 3 took, and for the same reason.
  **Invariant, generalizing D-08 of Phase 3:** mixed state resolves **up** to `wrote`, never
  down to `already-correct`. Falsely reporting convergence is the failure this milestone keeps
  designing against.
  Rejected: **two rows per runtime** (nothing is lost to precedence, and `Classify`'s table is
  over outcome combinations rather than row counts so it still holds — but
  REQ-setup-partial-failure-legible says outcome is reported "per runtime", and the summary's
  "N/M present" count would need redefining). Rejected: **a second `Result.SkillsOutcome` field
  consumed by `Classify`** (most precise; reopens the pinned pure function and its exhaustive
  table for a marginal gain).
  — **Reversibility:** costly — the aggregated `Outcome` and the facet field names are the
  observable report contract scripts and coding agents read.

- **D-07:** Failure is **fully independent at every level, and accumulates**. Registration and
  skills are attempted independently per runtime; every skill is attempted; each failure
  accumulates into the row's `Reason` via `internal/migrate`'s `errors.Join` idiom (the
  precedent Phase 3 D-03 already adopted). Nothing is skipped because something else failed.
  This is REQ-setup-partial-failure-legible's "no runtime's failure silently discards another's
  success" applied one level down.
  Rejected: **atomic all-or-nothing skills via stage-and-rename** (a runtime never ends up with
  a half-populated skills dir — but rename-based atomicity does not generalize to the AGENTS.md
  single-file path, so the two install shapes would carry different failure semantics; and see
  D-16, where rename is independently rejected). Rejected: **registration gating skills** (skills
  instructing an agent to call `mcp__engram__*` tools are arguably misleading with no
  registration — but a transient auth or network failure would then cost the skills too, and
  "skipped" is a sixth state the pinned vocabulary does not have).

- **D-08:** A destination skill file is **overwritten unconditionally**, and **byte-comparing
  the existing file against the embedded content** decides the reported outcome: equal →
  `already-correct` with no write; differing or absent → write and report `wrote`, naming the
  path.
  No provenance header, no marker. The consequence is the point: **the installed bytes, the
  vendored bytes, and the plugin's bytes are one identity**, which is the most literal reading
  of "sourced from the same files the plugin ships" and keeps D-02's gate meaningful end to end.
  `setup` is already `Destructive: true` (Phase 2 D-13), and the milestone states plainly that
  idempotent re-install **is** the update path. `REQ-setup-reconcile-hand-edits` stays v2.
  Rejected: **a provenance header gating overwrite** (protects hand edits, but the installed file
  stops being byte-identical to the plugin's, so the drift identity needs a strip-then-compare
  step). Rejected: **refusing to overwrite anything that differs** — decisive flaw: a skill
  engram itself wrote from an older release differs from the new embedded content, so it would
  block its own update, breaking the update path for exactly the case that matters most.
  — **Reversibility:** costly — `already-correct` versus `wrote` for skills is an observable
  contract, the same one REQ-setup-idempotent pins for registration.

### Native targets and scope

- **D-09:** `engram setup --apply` **writes to the native destination unconditionally**. Whether
  a runtime tolerates a plugin-supplied copy and a loose copy of the same skill — dedupes,
  shadows, or surfaces both — is a **third-party behavior the researcher must establish**, not
  something engram asserts or gates on.
  This keeps Phase 2's **D-12 intact** (detection is `LookPath` only, never a config-directory
  stat).
  Rejected: **detecting the engram plugin and standing down** — no duplicates by construction,
  but it reverses P2 D-12 the way P3 D-10 reversed its preview posture, and it makes
  `internal/skills` read a third-party config layout, the exact dependency every REQ-register-*
  deliberately avoided. Rejected: **delegating to `claude plugin install`** (one source of truth
  and consistent with the shell-out posture, but it needs network and a reachable marketplace,
  and it undercuts this phase's own goal that a plugin-free brew binary works).

- **D-10:** Skills install at **user scope only**, with every destination derived from
  `Environment.HomeDir` — the seam that already exists. This mirrors Phase 3's
  `claude mcp add --scope user` exactly, so the server and the guidance that teaches its use
  live at the same scope, and `engram setup`'s result never depends on cwd.
  It also sidesteps a concrete footgun: this repo's own `./AGENTS.md` is a symlink to
  `CLAUDE.md`, so a cwd-scoped fallback would write straight through into a project's real
  instruction file.
  Rejected: **project scope** (guidance travels in version control with the repo, but the MCP
  server would be registered globally while its skills are per-repo, and nothing about the
  command signals a cwd dependency). Rejected: **a `--scope` flag** (a 7th flag, both goldens,
  a `destructive_test.go` row, and a conditional-rule entry, for a knob no requirement asks for).
  — **Reversibility:** costly — changing scope later orphans every previously-installed copy at
  the old path, and nothing in this phase revisits or cleans up an old destination.

- **D-11:** `generic` **carries the skills in its deliverable**. Its row grows a skills payload
  alongside `Config`: destination-agnostic content, nested in `--output json` per D-03 while the
  text row stays dense. `generic`'s `Outcome` stays `would-write` in both lanes and `exit.go` is
  not reopened — Phase 3 D-16, unchanged.
  REQ-register-generic-mcp exists so an unsupported client is "a documented manual path rather
  than a dead end"; a dead end for the curation guidance is still a dead end, and a user on an
  unsupported client is the one class with no other way to obtain it.
  Rejected: **registration-only `generic`** (smallest change, keeps `generic`'s deliverable
  exactly as Phase 3 scoped it).
  — **Reversibility:** costly — same published-report-shape argument as D-03.

- **D-12:** There is **no opt-out**. `engram setup` does registration and skills, always;
  `--runtime` remains the only selector. No new flags, no golden movement, no
  `destructive_test.go` row, no conditional-rule entry.
  The overwrite contract already makes a re-run cheap and honest (`already-correct` when nothing
  changed), which answers the usual reason to want a skip.
  Rejected: **a `--skills=false` opt-out**, and rejected: **`--skills-only` plus `--skills=false`**
  (full independence in both directions, matching D-07's failure model; the v0.13.x Phase 1
  flag-group machinery makes the mutual exclusion cheap to express, but it is still new pinned
  surface). Promotion to a flag later is purely additive — same disposition, and same reasoning,
  as Phase 3's D-12 gave `--timeout`. See Deferred Ideas.
  — **Reversibility:** reversible — adding a flag later is additive and breaks no caller.

### The AGENTS.md fallback

- **D-13:** The delimited block carries **an index — one line per skill (name, trigger hint, and
  the on-disk path)** — and the **full `SKILL.md` files are written verbatim beside it**. The
  agent fetches a skill's procedure on demand.
  This is the progressive-disclosure pattern engram already ships for rules (session start
  renders a one-line index; full text arrives via `get_memory`), and it preserves D-08's
  byte-identity: the files on disk **are** the plugin's bytes.
  The alternative's cost is concrete: all five inlined is 58,522 bytes — roughly 15K tokens
  added to **every** session on that runtime, permanently, for five skills of which a typical
  session needs zero or one.
  Rejected: **full text inlined** (most literal reading of the requirement; one location,
  nothing to fetch, trivially replaceable — at that context cost). Rejected: **a derived
  condensation inlined** — decisive flaw: a condensation is a second authored artifact, so
  "sourced from the same files… so the two cannot drift" stops being true unless the
  condensation is itself generated and drift-gated, which means a summarizer whose faithfulness
  nobody can mechanically verify.
  — **Reversibility:** costly — the on-disk layout is written into someone else's home
  directory, so changing it later orphans the old directory on every machine already set up.

- **D-14:** Each shipped `SKILL.md` gains **a new authored one-line frontmatter key** (working
  name `summary:`) alongside `name`/`description`, and **that is the index line, verbatim**.
  It mirrors engram's own contract, where a rule's `summary` must be a single line and *is* the
  index entry — authored, never truncated.
  **Research precondition:** confirm that Claude Code, and any other native consumer, tolerates
  an unknown frontmatter key without warning or rejecting the skill.
  Rejected: **`description` verbatim** (zero new keys and drift-proof by construction, but these
  are exhaustive trigger lists written for a skill matcher, not index lines —
  `curating-memory`'s is ~1,400 characters and the five total ~3.4KB). Rejected: **`description`
  mechanically truncated** — truncation is exactly what engram's own summary guidance warns
  against ("preserve negations/identifiers"), and `curating-spine`'s description carries a
  load-bearing "never mutates a record without consent" clause a first-sentence cut discards
  silently.
  — **Reversibility:** costly — the key ships inside the plugin's own files and any consumer
  that learns to read it.

- **D-15:** Exactly **two** AGENTS.md states are writable: **zero blocks** (append one) and
  **one well-formed block** (replace it in place). **Two or more blocks, an unmatched `begin`,
  or an unmatched `end` is `OutcomeFailed`** — with the offending marker offsets named in
  `Reason` — and **not one byte is written**.
  This generalizes D-08 of Phase 3's own invariant (ambiguity resolves to the safe report, never
  to a guess) and honors "content outside the block is left byte-for-byte untouched" in the one
  case where honoring it is hard.
  Rejected: **repair and converge** (collapse duplicates, treat unmatched markers as absent) —
  always converges and never blocks an operator, but engram would silently rewrite a region of a
  file it did not author, which is the exact promise the requirement exists to make. Rejected:
  **fail on duplicates, tolerate unmatched** (handles the likeliest accident without a hard
  stop, but leaves a stray marker orphaned in the file forever and appends past it on every run).

- **D-16:** The AGENTS.md write is **in place and follows symlinks**: read the whole file,
  splice the block in memory, write it back with one `os.WriteFile` call.
  This is a deliberate choice **against** the stage-and-rename idiom, and the reason must not be
  rediscovered: `os.WriteFile` on an existing symlink writes **through** it, while temp-file +
  `os.Rename` **replaces** it with a regular file — silently breaking a stow/chezmoi/yadm
  dotfiles setup, which is a common way a `~/.codex/AGENTS.md` exists at all. (This repo's own
  `./AGENTS.md` is a symlink to `CLAUDE.md`.)
  Accepted cost, stated plainly: **the write is not atomic**. A crash mid-write truncates the
  file. Bounded to a single write syscall of a few KB.
  Rejected: **atomic rename onto the `EvalSymlinks`-resolved target** (atomic *and*
  dotfiles-preserving, but the path written is not the path the operator named — so the row must
  report both — and the resolved target may sit on another filesystem where rename fails and
  needs a documented fallback). Rejected: **atomic rename refusing symlinks** (never silently
  replaces one, but hard-fails a very common setup whose only remedy is to un-manage the file).

### Claude's Discretion

The user chose a concrete option on every question; nothing was answered "you decide". These
remain the planner's, bounded by the decisions above:

- The exact delimiter syntax for the AGENTS.md block, subject to D-15's requirement that it be
  unambiguously detectable and that an unmatched half be diagnosable by offset.
- `SkillTarget`'s type shape. Note the repo's own idiom, stated in `plan.go`'s `Outcome` doc
  comment: a state is "a REAL, explicit value — never modeled as an absence or the zero value".
  An explicit `Kind` discriminator (including an explicit "no skills" case for `generic`) is the
  aligned shape; presence-inference over two optional string fields is the fails-by-absence one.
- `internal/skills`' filesystem seam signature, following `Environment`'s struct-of-func-fields
  precedent (`environment.go`) rather than an interface.
- Field names and `json` tags for the new row keys (registration facet, skills facet,
  destination, digest, byte count), subject to D-03, D-06 and D-11 each being reported.
- The exact `summary:` key name in D-14 and its length bound.
- File modes and directory permissions for created skill directories, and umask handling.
- Whether `internal/skills` gets its own leaf-purity gate; `//go:embed` is stdlib, so the
  package can be one.
- Where D-06's aggregation precedence lives and how it is tested exhaustively without reopening
  `exit.go`.

<specifics>
## Specific Ideas

- **The rules index is the model for D-13.** engram's own session-start behavior — render a
  one-line index per rule, fetch full text on demand — is exactly what the AGENTS.md block
  should do for skills. Build it to look like that, not like a documentation dump.
- **`summary` in engram's memory contract is the model for D-14.** A rule's `summary` "must be a
  single line (the index entry)", authored rather than truncated. The new frontmatter key is
  that same idea applied to a skill.
- **`codex`'s `--bearer-token-env-var` was the reference shape for Phase 3's D-05; the analogue
  here is `internal/webauth/static`.** When in doubt about vendoring, embedding, or the `all:`
  prefix, copy what that package already does rather than inventing a second way.
- **Standing user principle, restated from Phase 1 D-11, Phase 2, Phase 3, and rule
  `m45p2b4bp7`:** do not test or red-gate third-party behavior. Verify engram's own vendoring,
  embedding, splicing, path authoring, outcome aggregation, report shape and exit codes. Drive
  the filesystem seam with a fake.
- **The two research preconditions are genuine unknowns, not placeholders.** Treat them the way
  Phase 3's D-05 treated the env-var expansion syntax — a shape to establish, never a spec to
  assume:
  1. Which runtimes have a native skill or rules format, where it lives at user scope, and what
     a runtime does with a plugin-supplied *and* a loose copy of the same skill.
  2. Whether Claude Code and every other native consumer tolerate an unknown `summary:`
     frontmatter key without warning or rejecting the skill.
- **`digest=` in the text row should be a content digest of what would be written**, so an
  operator can compare two machines without diffing files. Exact algorithm and truncation are
  the planner's.

<deferred>
## Deferred Ideas

- **`--skills=false`, or `--skills-only` plus `--skills=false`.** Rejected under D-12 on
  surface cost, not difficulty — the v0.13.x flag-group machinery would express the mutual
  exclusion cheaply. Purely additive later. Revisit on evidence: an operator or CI job that
  actually needs registration without skills, not by anticipation. Same disposition, and the
  same reasoning, Phase 3's D-12 gave `--timeout` — which is itself still deferred.
- **A dedicated `engram skills list|show` command.** Rejected under D-03. Revisit only if
  Phase 6's install docs show operators need the guidance without `jq`, or if a consumer appears
  that cannot use `--output json`.
- **A `--show-skills` flag on `setup`.** Same rejection, same trigger to revisit.
- **Atomic all-or-nothing skills install via stage-and-rename.** Rejected under D-07 (it does
  not generalize to the AGENTS.md single-file path) and independently under D-16 (rename
  replaces a symlink). Revisit if partially-installed skill sets prove genuinely confusing in
  practice, with real reports rather than by anticipation.
- **Detecting the engram plugin and standing down for claude-code.** Rejected under D-09; it
  reverses Phase 2's D-12. Revisit **only if** research shows a runtime actually mishandles a
  duplicate skill — and if so, prefer a reported warning over a config-directory read.
- **Delegating to `claude plugin install`.** Rejected under D-09: needs network and a reachable
  marketplace, and undercuts the plugin-free goal that motivates the whole phase.
- **A provenance header on installed skill files.** Rejected under D-08 — it breaks the
  installed-bytes-equals-plugin-bytes identity that makes D-02's gate meaningful end to end.
- **A pinned five-name inventory canary alongside D-04's structural discovery.** Not taken.
  It is the cheapest thing to add if silent distribution-scope growth ever bites.
- **Repairing a malformed AGENTS.md** (collapsing duplicate blocks, treating unmatched markers
  as absent). Rejected under D-15. Revisit only with real reports of operators blocked by the
  hard failure.
- **Distributing the plugin's hooks and its `/engram-setup` command through the binary.** Out of
  scope: the ROADMAP fixes this phase to the five curation skills, and `/engram-setup` is
  Phase 5's subject.
- **Backlog Phase 999.1 itself** (a feature-branch staleness gate for the vendored SPA, and the
  same question for `surfaces:gen`). Unchanged and still open. D-02 does **not** close it — it
  takes a different and stronger route available only because a skills vendor is a plain copy
  with no build step. Worth noting in 999.1 when it is promoted.
