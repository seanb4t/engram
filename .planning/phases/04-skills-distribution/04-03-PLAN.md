**One routing question needs your answer before any destination is authored.**

### What research changed

`04-CONTEXT.md` was written before research returned. Its D-16 names a user-scope `AGENTS.md` under
the Codex home as the concrete dotfiles case the in-place write protects — which reads as though
Codex was the AGENTS.md-fallback runtime at the time the decisions were locked.

Research then found that **all three native runtimes have a native skill format**:

| Runtime | Native skills destination | Evidence |
|---|---|---|
| claude-code | `~/.claude/skills/<name>/SKILL.md` | official docs, plus live observation |
| codex | `$HOME/.agents/skills/<name>/SKILL.md` | official docs (USER scope); **locked this session** |
| opencode | `~/.config/opencode/skills/<name>/SKILL.md` | official docs, plus live observation |
| generic | none — it is not a machine | D-11 gives it a previewed payload, never a write |

REQ-skills-agents-md-fallback and ROADMAP success criterion 3 are both written for the case where a
runtime has **no** native skill format. On the research findings, no v1 runtime trips that condition
— yet success criterion 3 says plainly that `engram setup --apply` **writes** the guidance into
AGENTS.md inside a delimited block, and re-running replaces that block.

The mechanism is already built and proven (plan 04-02). What is undecided is where it points.

### Why this is not cheap to reverse

Whatever is chosen is written into someone else's home directory, and this phase deliberately never
revisits or cleans up an old destination (D-13's own stated reversibility). Changing it later leaves
an orphaned directory, or an orphaned marker block, on every machine already set up.

### What is NOT on the table

Codex's skills destination itself. `$HOME/.agents/skills` is locked from this planning session, and
`$CODEX_HOME/skills` is explicitly excluded. No option below changes that, and no option writes two
skills destinations for one runtime.

| Boundary | Description |
|----------|-------------|

| the operator's environment -> a destination path | `XDG_CONFIG_HOME` is operator-controlled input that participates in building a filesystem destination |
| a third-party runtime's loader -> engram's own report | engram can report a truthful `wrote` for a file the runtime never reads, which is a requirement failure invisible to the report |
