<objective>
Add the `chainVerifier` combinator and its structural JWT-vs-opaque discriminator inside
`internal/auth` (SC1 / D-01 / D-02 / D-03 / D-04). The chain composes over the existing
`mcpauth.TokenVerifier` function type — no new interface — and is the single value `withAuth`
(Plan 06) wraps in place of the lone human verifier today. It routes each bearer by shape BEFORE
running any verifier (never "try all, take first success"), tries the OIDC branch in the D-02 order
(human → client-credentials), sends opaque bearers to the static comparator, and denies by default.

`chainVerifier` takes its three lane verifiers as `mcpauth.TokenVerifier` arguments (any of which may
be nil when its mechanism is unconfigured, D-03), so this plan is independent of the concrete
verifier constructors (Plans 01/02) and the config (Plan 04) — those are wired together in Plan 06.

Purpose: keep the two mechanisms' security properties unblended (Pitfall 9) and make human-only
deployments byte-for-byte unchanged (Pitfall via D-03 independent enablement).
Output: `chain.go` (`chainVerifier`, `looksLikeJWT`) + routing/order/deny tests.
</objective>

<assumption_delta_decision>
The assumption-delta checkpoint FIRES for this phase — a genuine singular→plural transition: one
OIDC `Verifier` becomes a CHAIN of user / client-credentials / static mechanisms, and one owner-claim
source becomes per-lane owner claims.

- Now-primary noun (verification layer): the **verifier chain** (was: the single `Verifier`).
- Primary noun (identity model): stays `store.Subject{authenticated{owner}}` — UNCHANGED (DEC-12c).

Decision = **promote-to-chain for verification, no-change for the Subject identity model.** A service
principal is a VARIANT of the existing `authenticated` subject (a non-email namespaced owner), not a
new primary — so the sealed 2-variant `store.Subject` sum is NOT widened (D-06 / anti-Pattern-1) and
no promote/add-alongside debt is incurred at the identity layer. Only the verifier layer pluralizes.

Rationale: the sealed Subject already generalizes over any non-email namespaced owner (DEC-g37x's
`namespacedOwner`), so the chain feeds it new owners through an UNCHANGED contract
(`TokenInfo.Extra[owner_claim]` → `SubjectFromTokenInfo`).

Suggested invariant test (satisfied across Plans 01/03): every enabled mechanism in the chain resolves
to a non-empty `authenticated` owner OR is rejected — never anonymous (the service lanes fail closed;
the human lane's fail-open-to-anonymous is the explicit no-issuer exception, not a chain mechanism).
</assumption_delta_decision>
