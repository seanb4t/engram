<objective>
Build the write-lane Connect transport as two composed interceptors and expose a dedicated `engramWrite` client:

- `attachCsrf` reads the JS-readable `engram_csrf` cookie and sets the `X-CSRF-Token` header on every outgoing write request (SC2, D-08 discretion — one choke point, not per-call).
- `retryOnce` catches a `ConnectError` whose code is `Unauthenticated` or `PermissionDenied`, retries `next(req)` exactly once, and rethrows the second failure unchanged (SC3, D-08).

**Retry mechanism — accurate framing (Codex HIGH, verified against `connectreseal.go:39`):** the retry is an **opportunistic single retry for a cookie/CSRF-freshness race**, NOT a "retry through re-seal." A *failed* request cannot itself trigger a server re-seal — `newConnectResealInterceptor` explicitly skips re-sealing when the handler returns an error or a nil response (`connectreseal.go:39-41`: `if err != nil || resp == nil ...`). The retry succeeds only when the browser's cookie state changed between the two attempts — e.g. a concurrent successful read re-sealed the `engram_csrf`/`engram_session` cookies, or a freshly-opened tab's CSRF cookie value wasn't yet observed at first request-build time — and the inner `attachCsrf` re-reads it on the retry. A truly hard-expired session (`resolver.go` rejects the cookie) will deterministically fail the retry too → terminal, drives D-09. Do NOT describe this as re-seal-on-retry anywhere in code comments or the SUMMARY.

Purpose: centralize CSRF attachment and the retry-once semantics in transport, so no mutation wrapper reimplements them and the retry stays invisible to the operator.
Output: two interceptors + a write-only `engramWrite` client, each unit-tested against `createRouterTransport`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser JS → same-origin Connect API | Untrusted client attaches X-CSRF-Token; server (connectcsrf.go) is the authoritative verifier |
| engram_csrf cookie (non-HttpOnly) → JS | Cookie is deliberately JS-readable so the SPA can echo it; this is the double-submit design |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-19-11 | Tampering | retryOnce double-submitting a non-idempotent create (StoreMemory/StoreDiscovery) | high | mitigate | Retry only on Unauthenticated/PermissionDenied — both are rejected before the write handler mutates state (session Resolve at `connectauth.go` + CSRF verify at `connectcsrf.go` precede `next()`; business errors never map to these two codes per `connecterror.go`), so a retry cannot double-create; retry limited to exactly one attempt (Task 2 tests assert exactly-twice). **Codex+grok confirmed this mitigation HOLDS against live source.** Recommended future hardening (out of this UI plan's file scope — do NOT add a Go file here): a server-contract test proving both retry codes stay pre-handler for all six write procedures — file as a follow-up so a future handler returning either code post-mutation cannot silently make create-retries unsafe |
| T-19-12 | Information Disclosure | engram_csrf cookie readable by page JS (XSS could exfiltrate it) | medium | accept | Non-HttpOnly is required by the double-submit design (server mints/refreshes it); token is per-request and short-lived; XSS-hardening is out of this phase's scope (server-owned). Never cache the token beyond a single request |
| T-19-13 | Spoofing | Missing/forged CSRF header on a write | low | mitigate | attachCsrf echoes the server-minted cookie value; server verifies the double-submit and binds token to Subject.Owner — client cannot forge a valid pair |
</threat_model>
