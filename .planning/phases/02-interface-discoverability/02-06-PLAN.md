<task type="checkpoint:human-action" gate="blocking">
  <name>Checkpoint: rotate the Cloudflare API token for the docs-site deploy</name>
  <action>
Issue a replacement Cloudflare API token and set it as the `CLOUDFLARE_API_TOKEN` repository secret.

This step is human-only, deliberately rather than by oversight: issuing a Cloudflare API token
requires an authenticated dashboard session, and setting a GitHub repository secret requires an actor
with admin rights on the repository. Neither has a CLI or API path reachable from a coding session.
Everything downstream — the `gh run rerun`, the run watch, and the live-page verification — IS
automatable and is handled by Task 1 rather than handed back to the developer.

The failure is already diagnosed: `.github/workflows/docs-site.yaml`'s `deploy` job has failed on
every `main` push since 2026-08-02 with `Invalid access token [code: 9109]` on the bare `/accounts`
call. The token is invalid or revoked, not merely under-scoped, so re-scoping the existing token will
not help — it must be reissued.
  </action>
  <instructions>
1. Open the Cloudflare dashboard for the account that owns the `engram-docs` worker:
   Manage Account -> API Tokens.
2. Create a token with the permission `Workers Scripts: Edit`, scoped to that single account. Do not
   grant broader account-wide or zone-wide permissions.
3. Copy the token value once. Do not paste it into a file, a commit, a shell that records history, or
   this conversation.
4. In GitHub: Settings -> Secrets and variables -> Actions -> update the `CLOUDFLARE_API_TOKEN`
   repository secret with the new value.
5. Revoke the old token in the Cloudflare dashboard, so there is no window in which two tokens are
   valid.
6. Reply when steps 1-5 are done.
  </instructions>
  <verification>
The developer confirms the new `Workers Scripts: Edit` token is set as the `CLOUDFLARE_API_TOKEN`
repository secret and the old token is revoked. Task 1 then proves the rotation worked by re-running
the failed workflow and asserting the PUBLISHED `reference/errors.md` returns HTTP 200 with the
hint-code table present — a green job over a stale page is the failure mode this checkpoint exists to
catch, so the workflow conclusion alone is not accepted as evidence.
  </verification>
  <resume-signal>Type "token rotated" once the new token is set as the repository secret and the old one is revoked, or describe what blocked you</resume-signal>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer → Cloudflare account | a long-lived API token granting write access to a published worker |
| GitHub Actions secret → deploy job | the token is handed to a workflow that publishes the public docs site |
| local git state → deletion | irrecoverable removal of the only copy of three commits |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-23 | Elevation of Privilege | the replacement Cloudflare API token | high | mitigate | The token is scoped to `Workers Scripts: Edit` on the single account owning the `engram-docs` worker — not account-wide, not zone-wide. The old token is revoked in the same session, closing the window in which two tokens are valid. |
| T-02-24 | Information Disclosure | token value handling | high | mitigate | The checkpoint instructs the developer to paste the token only into the GitHub secret field — never into a file, a commit, a shell history, or the conversation. No task echoes, reads, or logs `CLOUDFLARE_API_TOKEN`; the verification reads only the published page and the workflow conclusion. |
| T-02-25 | Spoofing | a green deploy job over a stale published page | medium | mitigate | Verification asserts the LIVE page returns HTTP 200 and contains the hint-code content, not merely that the workflow concluded `success`. This is the failure mode CONTEXT.md explicitly warns about. |
| T-02-26 | Repudiation | irrecoverable loss of the three branch-only commits | high | mitigate | Deletion is gated on a per-commit, content-based (not path-based) verification recorded in the SUMMARY before any `git branch -D` runs. Any unaccounted content halts the deletion and the branch is preserved for the developer. Path-based comparison is explicitly rejected because paths moved during the milestone close. |
| T-02-27 | Tampering | over-broad branch cleanup | medium | mitigate | Only the one named branch is in deletion scope; every other stranded branch is reported, never removed. An acceptance criterion bounds the session to at most one branch deletion. |
| T-02-SC | Tampering | npm/pip/cargo/go installs | low | accept | This plan installs nothing and modifies no repository file. RESEARCH.md's Package Legitimacy Audit records no new external packages for this phase, so no legitimacy checkpoint applies. |

Canon-referral breadcrumb (not minted as a prohibition): API-token scoping and secret-rotation
hygiene are canon — covered by `/gsd-secure-phase`; not minted here.
</threat_model>
