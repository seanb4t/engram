<objective>
Prove ROADMAP success criterion 5: the sweep runs with no collection lock because the write path
stamps the current version before the sweep runs, so new writes arrive already-current and never
create new backlog — demonstrated by writing new records WHILE the sweep is in flight and confirming
they are never re-processed.

Purpose: "no lock needed" is the kind of claim that is easy to assert and hard to earn. The property
that makes it true is an ordering dependency on Phase 2, not a property of the sweep itself, and a
test that merely showed the sweep finishing would prove nothing about it. So this test does three
things a weaker one would not: it triggers the concurrent write deterministically from inside the
sweep's own Scroll request, it observes at the wire which point ids the sweep actually wrote, and it
includes the complementary control — a below-target mid-sweep write that DOES enter the backlog —
without which "never re-processed" would also be satisfied by a filter that matches nothing.

It also states its own limits at full strength, because both reviewers found the earlier framing
claimed more than the mechanics deliver: with `CurrentVersion` pinned at 0 this phase, the mid-sweep
record reaches the target through a caller-supplied `Memory.SchemaVersion`, so what is proven is
strict-filter exclusion plus production write-path plumbing, CONDITIONAL on the stamp==target invariant
that Phase 2's `TestEveryFullWriteMethodStampsSchemaVersion` pins. The literal causal claim is deferred
to Phase 4 behind a greppable marker (PA-10a).

Output: `internal/store/migrate_converge_test.go` against the pinned `qdrant/qdrant:v1.18.2`
testcontainer, plus two committed RED patches: one widening the backlog filter to include
already-current records, one skipping the mid-sweep write to prove the non-vacuity guard is live.
</objective>

**PA-10 (how "already-current" is produced this phase — read this before writing a line).**
`migrate.CurrentVersion` is pinned at `0` and must stay there, but the sweep needs a target of at
least `1` to have any backlog at all (03-01 PA-4). So a mid-sweep `Store.Upsert` of an ordinary
`Memory` stamps `schema_version: 0`, which is BELOW a target of 1 — the opposite of what SC5 needs to
demonstrate. The resolution is `payload()`'s monotonic maximum
(`p[schemaVersionKey] = int(max(migrate.CurrentVersion, m.SchemaVersion))`, `store.go:646`): a
mid-sweep `Store.Upsert` of a `Memory` whose `SchemaVersion` is `migrate.Version(1)` stamps `1`
through the completely unmodified production write path.

What that substitutes and what it does not: the *value* the write path claims is supplied by the
caller instead of by the constant, but the *path* — `payload()` as the only door, the stamp as
monotonic, the write as atomic-per-record — is the real one, and Phase 2 already proved all three
(`TestEveryPointWriteRoutesThroughPayload`, `TestEveryFullWriteMethodStampsSchemaVersion`). State this
substitution explicitly in the test's doc comment. Do NOT use `injectRawPayload` for the
already-current record: that would bypass `payload()` and make the test about a filter rather than
about the stamp-then-sweep ordering, which is the entire content of SC5.

**PA-10a (what SC5 is and is not discharged by, after review cycle 1 — both reviewers flagged this,
Codex at HIGH and Opencode at MEDIUM).** SC5's production claim is causal: *because* the write path
stamps the current version, new writes arrive already-current. In production that holds because both
sides are the SAME CONSTANT — `payload()` stamps `CurrentVersion` and the sweep targets
`CurrentVersion`. In this test the stamp comes from caller-supplied `Memory.SchemaVersion` and the
target comes from `MigrateOptions.Target`, so their equality is BY CONSTRUCTION, not derived from a
shared source of truth. Record the consequence honestly and completely, in the test's doc comment and
in the SUMMARY, in these three parts:

1. **What is proven here.** The backlog filter's strict bound excludes a record already at the target;
   the production write path (`Store.Upsert` -> `payload()`) is the mechanism that puts it there; and
   the sweep converges under a live concurrent writer with no lock.
2. **The invariant the proof is conditional on, named.** `payload()`'s stamp must equal the sweep's
   target. That invariant is pinned by Phase 2's `TestEveryFullWriteMethodStampsSchemaVersion`
   (`internal/store/schemaversion_stamp_test.go:27`) together with
   `TestEveryPointWriteRoutesThroughPayload`. Write the sentence Opencode asked for, close to verbatim:
   *this test proves SC5 conditional on `payload()`'s stamp equalling the sweep target, an invariant
   pinned by `TestEveryFullWriteMethodStampsSchemaVersion`; if that gate is ever weakened, SC5's proof
   here must be revisited.* Naming that test is required — it is what makes the condition checkable by
   a verifier instead of a caveat.
3. **The Phase 4 forward-pointer, as a greppable `// PHASE4:` marker** in the same doc comment: when
   Phase 4 pairs `CurrentVersion = 1` with the registered v0->v1 step, this same concurrency test must
   be re-run with an ORDINARY `Memory` carrying NO `SchemaVersion` at all, and `MigrateOptions.Target`
   left at zero so it resolves to `CurrentVersion`. That run is the only direct proof of SC5's causal
   statement, and it is blocking for Phase 4 — not optional polish.

Do not let the SUMMARY report SC5 as fully discharged. Report it as: strict-filter exclusion and
write-path plumbing PROVEN this phase; the causal ordinary-write claim DEFERRED to Phase 4 with the
condition named and a marker in the code.

**PA-11 (the mid-sweep write must fire exactly once — proven by a counter, not a boolean).** The
trigger fires on the sweep's SECOND observed `*qdrant.ScrollPoints`, guarded by a `sync.Once`. A writer
that re-fired on every pass would insert a fresh below-target record each pass and the sweep would
never converge — the test would then be measuring livelock, not the property.

Review cycle 1: `sync.Once` ENFORCES at most one execution and a boolean proves at least one, so the
pair can only ever establish "exactly one" by trusting `sync.Once` rather than observing it. Replace
the boolean with an integer `fires` counter incremented INSIDE the `Once` body, and assert `fires == 1`.
Additionally record `triggerMatches` — the number of times the scroll-ordinal condition evaluated true —
and log it. If `triggerMatches` is greater than 1 while `fires` is 1, that is `sync.Once` doing its job
and worth recording in the SUMMARY; if `triggerMatches` is 0 the trigger never armed and every negative
assertion downstream is vacuous, so assert it is at least 1 as well.

**PA-11a (no assertions from inside the interceptor).** The hook must NOT call `t.Fatal`, `t.Fatalf`,
`t.Error` or `t.Errorf` from inside the interceptor callback. gRPC's unary client interceptor is invoked
on the calling goroutine — which here is the sweep's, i.e. the test's — so in practice this would work;
but the test must not DEPEND on that, because the guarantee is a property of the current
`grpc-go`/`go-client` call path rather than of the test, and `t.Fatalf` from a non-test goroutine
silently fails to fail the test. Instead the hook holds a mutex-guarded `[]error` (or `[]string`), the
in-hook checks append a described failure and return, and the test drains that slice immediately after
`Store.Migrate` returns and before any subtest, failing with every recorded entry. Note in a comment
that `t.Logf` remains safe and is fine for diagnostics.

**PA-12 (no deadlock, and why).** The mid-sweep write is issued through a SECOND `*Store` built on a
plain, non-intercepting client, so it does not re-enter the interceptor and does not contend with the
sweep's own connection. Do not perform the write through the intercepted client.

**PA-13 (backlog arithmetic must keep the shrink guard satisfied — and what that bounds the claim to).**
03-01's termination guard errors when a freshly-counted backlog fails to shrink between passes.
Inserting one below-target record mid-run must not stall that. With six seeded legacy records,
`Batch: 2` and a single insertion on the second scroll, each pass still removes two and adds at most
one once — so the count strictly decreases every pass. If the executor changes the seed count or the
batch size, re-derive the per-pass counts by hand before running, and record the derivation in the
SUMMARY.

Both reviewers noted the consequence, and it must be labelled rather than left implicit: hand-selected
arithmetic plus exactly ONE inserted laggard proves TOLERANCE OF ONE BOUNDED BELOW-TARGET INSERTION,
not the finite-backlog theorem under arbitrary concurrent writers. Call the `laggard` case a

"already-current records are excluded" from "the filter matches nothing" — and do not present it as
evidence that the sweep converges against any writer. The general statement rests on the
stamp-then-sweep ordering (D-08), which is an argument, not something this test measures.
