<objective>
Prove ROADMAP success criterion 5: the sweep runs with no collection lock because the write path
stamps the current version before the sweep runs, so new writes arrive already-current and never
create new backlog — demonstrated by writing new records WHILE the sweep is in flight and confirming
they are never re-processed.

Purpose: "no lock needed" is the kind of claim that is easy to assert and hard to earn. The property
that makes it true is an ordering dependency on Phase 2, not a property of the sweep itself, and a
test that merely showed the sweep finishing would prove nothing about it. So this test does three
things a weaker one would not: it triggers the concurrent write deterministically from inside the
sweep's own Scroll request, it observes at the wire which point ids the sweep actually wrote, and it
includes the complementary control — a below-target mid-sweep write that DOES enter the backlog —
without which "never re-processed" would also be satisfied by a filter that matches nothing.

Output: `internal/store/migrate_converge_test.go` against the pinned `qdrant/qdrant:v1.18.2`
testcontainer, plus two committed RED patches: one widening the backlog filter to include
already-current records, one skipping the mid-sweep write to prove the non-vacuity guard is live.
</objective>

<planner_assumptions>

**PA-10 (how "already-current" is produced this phase — read this before writing a line).**
`migrate.CurrentVersion` is pinned at `0` and must stay there, but the sweep needs a target of at
least `1` to have any backlog at all (03-01 PA-4). So a mid-sweep `Store.Upsert` of an ordinary
`Memory` stamps `schema_version: 0`, which is BELOW a target of 1 — the opposite of what SC5 needs to
demonstrate. The resolution is `payload()`'s monotonic maximum
(`p[schemaVersionKey] = int(max(migrate.CurrentVersion, m.SchemaVersion))`, `store.go:646`): a
mid-sweep `Store.Upsert` of a `Memory` whose `SchemaVersion` is `migrate.Version(1)` stamps `1`
through the completely unmodified production write path.

What that substitutes and what it does not: the *value* the write path claims is supplied by the
caller instead of by the constant, but the *path* — `payload()` as the only door, the stamp as
monotonic, the write as atomic-per-record — is the real one, and Phase 2 already proved all three
(`TestEveryPointWriteRoutesThroughPayload`, `TestEveryFullWriteMethodStampsSchemaVersion`). State this
substitution explicitly in the test's doc comment. Do NOT use `injectRawPayload` for the
already-current record: that would bypass `payload()` and make the test about a filter rather than
about the stamp-then-sweep ordering, which is the entire content of SC5.

**PA-11 (the mid-sweep write must fire exactly once).** The trigger fires on the sweep's SECOND
observed `*qdrant.ScrollPoints`, guarded by a `sync.Once`. A writer that re-fired on every pass would
insert a fresh below-target record each pass and the sweep would never converge — the test would then
be measuring livelock, not the property. Guard it, and assert afterwards that it fired exactly once.

**PA-12 (no deadlock, and why).** The mid-sweep write is issued through a SECOND `*Store` built on a
plain, non-intercepting client, so it does not re-enter the interceptor and does not contend with the
sweep's own connection. Do not perform the write through the intercepted client.

**PA-9 (carried forward, helper-name ownership).** Plan 03-04 lands a second interceptor in the same
package during the same wave. This plan owns `midSweepInterceptor`, `dialMidSweepTestClient` and
`midSweepHook`; it must not declare `setPayloadFaultInjector`, `faultMode` or
`dialFaultInjectingTestClient`, and must not redeclare anything from
`internal/store/schemaversion_recallgate_test.go` or `internal/store/migrate_test.go`.

**PA-13 (backlog arithmetic must keep the shrink guard satisfied).** 03-01's termination guard errors
when a freshly-counted backlog fails to shrink between passes. Inserting one below-target record
mid-run must not stall that. With six seeded legacy records, `Batch: 2` and a single insertion on the
second scroll, each pass still removes two and adds at most one once — so the count strictly decreases
every pass. If the executor changes the seed count or the batch size, re-derive the per-pass counts by
hand before running, and record the derivation in the SUMMARY.

</planner_assumptions>
