<planner_assumptions>

**PA-1 (fixtures live in `_test.go`, not `testdata/`).** CONTEXT.md leaves this to discretion. The
fixtures are Go `ApplyFunc` closures, not data — expressing them as `testdata/` JSON would require a
second interpreter layer whose bugs would be indistinguishable from the checker's. They stay in the
test file.

**PA-2 (`CheckAdditive` sees keys, not values).** The check compares key SETS. A step that overwrites
an existing key's VALUE in place is additive by key set and passes. That is a real limit of D-04's
chosen mechanism, not a defect in this implementation — the restricted-writer alternative that would
close it (a `PayloadAdder` with no set/delete surface) is in CONTEXT.md's Deferred Ideas, explicitly
not chosen for this phase. Write the limit into the test file's doc comment so no future reader infers
a stronger guarantee than the code provides.

**PA-3 (this table does not run against `Registry`).** D-06 is explicit: the production registry is
empty this phase, so a table iterating it would scan nothing and pass. Any acceptance criterion here
that mentions `Registry` is about asserting it is EMPTY, never about iterating it for coverage.

</planner_assumptions>

    Create `internal/migrate/additive_test.go` (SPDX header, `package migrate`) with

    **Table shape.** Each row carries: a name, a `before` payload map, a declared `addsKeys` slice, a
    `Reversibility`, an `ApplyFunc`, a `wantConforming` bool, and — for non-conforming rows — the list
    of key names the error must mention. Build each row's step with `NewStep(0, 1, declared, rev,
    apply)` so no fixture can carry a declaration shape a real registered step could not.

    **The seven rows.** The first three must be classified conforming, the last four non-conforming:
    1. `conforming additive` — `before` has `content`; declares `schema_version`; the apply sets
       exactly that one key. Reversible with a real inverse.
    2. `conforming additive, irreversible with a stated reason` — same shape, but carrying
       `Irreversible("...")` with a concrete reason string. This row exists to pin that reversibility
       and additive compliance are ORTHOGONAL: an irreversible step is still held to the same key-set
       discipline, and a conforming verdict here must not depend on which `Reversibility` variant the
       step carries.
    3. `conforming no-op` — declares nothing and adds nothing. Legal: CONTEXT.md states steps may have
       side effects, and a pure-side-effect step touches no key. This row exercises the empty-set
       against empty-set edge, where a naive implementation using a nil-vs-empty-slice comparison
       breaks.
    4. `removes a key` — `before` has `content` and `legacy_field`; declares nothing; the apply
       deletes `legacy_field`. Non-conforming: `before` is not a subset of `after`. The error must
       name `legacy_field`.
    5. `adds an undeclared key` — declares `schema_version`; the apply sets `schema_version` AND
       `undeclared_extra`. Non-conforming by set equality even though it is additive and even though
       the declared key IS among those added. This is D-04's load-bearing row: a superset check would
       call it conforming. The error must name `undeclared_extra`.
    6. `declares a key it never adds` — declares `schema_version` and `never_written`; the apply sets
       only `schema_version`. Non-conforming by set equality — the mirror of row 5, which a subset
       check would call conforming. The error must name `never_written`.
    7. `removes one and adds an undeclared one` — both directions violated at once. The error must
       name BOTH the vanished key and the undeclared key, proving the two directions are reported
       independently rather than collapsed into one generic message.

    **Drive each row identically:** clone `before` (the fixture map must not be mutated in place, or a
    later row inherits an earlier row's damage), call `step.Apply` on the clone, then call
    `CheckAdditive(step, before, after)`. `err == nil` is the conforming verdict. For non-conforming
    rows assert that every expected key name appears in the error text, using `strings.Contains`.

    **The two anti-vacuity guards, both before the loop:**
    - `if len(fixtures) == 0 { t.Fatal(...) }` — D-05, copied literally from RESEARCH.md's example.
    - Count the rows by expected verdict and fail unless BOTH classes are non-empty. A table of only
      conforming rows passes a checker that always returns nil; a table of only violating rows passes
      one that always returns an error. Neither guard alone is sufficient, so assert both.

    **One more assertion after the loop, and it is the strongest one here:** collect the names of the
    rows that were actually classified non-conforming and assert that set is SET-EQUAL to the expected
    non-conforming name set, with both difference directions printed on failure. This single assertion
    is what an always-nil checker and an always-error checker both fail, and it does not depend on any
    row's error text.

    **Assert the shipped registry is empty** (PA-3): `if len(Registry) != 0 { t.Fatalf(...) }`, with a
    message stating that this phase ships an empty production registry and that this table deliberately
    runs against fixtures instead, because iterating an empty registry would pass for the wrong reason.

    Write PA-2's limit into the test file's doc comment: this check compares key sets only and cannot
    see a step that overwrites an existing key's value in place; the restricted-writer alternative that
    would close that gap is a recorded Deferred Idea, not an oversight.
