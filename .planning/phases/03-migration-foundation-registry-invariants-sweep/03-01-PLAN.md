**PA-1 (carried forward from RESEARCH A1; strengthened after review cycle 1).** D-03's claim that
`Irreversible("")` "panics at package init, before any test runs" holds only if the call appears in a
package-level `var`/`init()`, not inside a function called later. This phase's production `Registry`
is EMPTY, so nothing exercises the init-time half at all. This plan proves only the
panics-on-bad-input half (plan 03-02), which is the half this repo already has an idiom for
(`TestRemapFromPanicsOnEmptyValue`).

Both reviewers flagged that a doc comment is not an enforcement mechanism: nothing would fire if
Phase 4 built the registry inside a function instead. So the deferral is made LOAD-BEARING TODAY
rather than left as prose. `Registry`'s doc comment carries a greppable `// PHASE4:` marker stating
the package-level-`var` obligation and why it is load-bearing for D-03, and plan 03-02 adds an AST
assertion that (a) `Registry` is declared as a package-level `var` — true today with the empty
literal, and therefore a gate that fails the moment Phase 4 moves it into a function — and (b) the
marker is present. A ROADMAP Phase 4 note was considered and NOT taken: `ROADMAP.md` is a
GSD-generated, GSD-parsed artifact and inventing an obligations subsection under a phase entry is
prohibited (`planning-artifacts` rule). The in-repo AST gate is strictly stronger anyway, because it
runs on every `go test ./internal/migrate/...`.

**PA-2 (per-point SetPayload, resolving RESEARCH A3).** The sweep issues **one `SetPayload` per
point**, not one per chunk — mirroring `BackfillShortIDs` (`store.go:2782-2789`), and diverging from
RESEARCH.md's Pattern 4 sketch, which selects a whole chunk of ids. The reason is correctness, not
taste: a step's added values are derived from the record's OWN payload (Phase 4's first customer mints
a per-record `short_id`), so a single multi-ID `SetPayload` would write one record's values onto
every id in the chunk. Consequence to keep consistent everywhere downstream: "the Nth SetPayload" in
plan 03-04's fault injection means the Nth POINT of a pass, and "partial" means
some-points-of-a-pass-landed, not some-ids-within-one-call-landed. This is a strictly stronger
position with respect to qdrant/qdrant#9371, not a weaker one: within-call ambiguity is removed by
construction, and cross-call ambiguity is handled by unconditional per-pass re-derivation.

**PA-3 (termination guard).** D-07's loop-to-zero has no stated termination condition for a
persistently failing backend. This plan adds one, and derives it the same way D-09 requires
everything else to be derived — from a **fresh re-derivation**, never from a write call's error: if
a pass's freshly-counted backlog is not strictly smaller than the previous pass's, `Migrate` returns
an error wrapping the last write error. This guard assumes D-08's stamp-then-sweep ordering (no
writer is producing below-target records faster than the sweep drains them). That assumption is
exactly what plan 03-05 proves; state its dependence in the doc comment.

**The error must not overclaim** (review cycle 1). A non-shrinking backlog is not proof of a backend
failure: a concurrent writer inserting below-target records at the sweep's own drain rate produces
exactly the same observation. The error therefore says what was OBSERVED and names the precondition
it rests on — "backlog did not shrink between passes N and N+1 (%d -> %d); under the stamp-then-sweep
precondition (D-08) that means writes are not landing" — and wraps the last write error when there
was one. When there was NO write error at all, the message must say so explicitly, because that case
is the concurrent-writer case rather than the failing-backend case and an operator reading it needs
to know the difference.

**PA-14 (accepted scope debt: one exact `Count` per pass).** The sweep performs a fresh exact `Count`
before every bounded scroll. Every other sweep in this file (`Reindex`, `store.go:3133`;
`BackfillShortIDs`, `:2741`) pages a cursor and never counts. The exact count is what makes PA-3's
termination guard a re-derivation rather than an inference from write signals, which is D-09's whole
point — so it is deliberate, not an oversight. It is also repeated full-backlog accounting: cost is
O(passes x backlog) where the siblings are O(backlog). This is ACCEPTED as Phase 3 scale debt. Write
it into `Store.Migrate`'s doc comment in those terms — deliberate, its reason, its cost, and that a
large-collection optimization (an approximate count with an exact confirmation on the final pass, or
a count only every K passes) is a Phase 4 / large-collection follow-up, not a Phase 3 defect. Do not
optimize it in this phase; a cheaper guard that is not a fresh re-derivation would silently undo
D-09.

**PA-4 (`target <= 0` short-circuit).** `backlogFilter`'s `IsEmpty` arm matches every legacy record
unconditionally, so it is only correct for `target >= 1`. At `target == 0` a legacy record is
already at v0 and needs nothing. `Migrate` therefore short-circuits at `target <= 0`. Without this,
`engram migrate` against today's `CurrentVersion = 0` would stamp a semantically-meaningless
`schema_version: 0` across the whole collection.

**PA-5 (`CheckAdditive`'s signature).** `CheckAdditive(s Step, before, after map[string]any) error`
takes both maps rather than applying the step itself, so the sweep — which must compute `after`
anyway in order to write — and the fixture table in plan 03-03 drive exactly the same function. A
signature that re-applied the step internally would mean the sweep validates a *different* execution
than the one it writes.

**PA-5a (the aliasing hazard this signature creates, and its mandatory discipline).** Because
`CheckAdditive` receives two maps it did not produce, EVERY caller owns the discipline that keeps
them independent. An `ApplyFunc` is free to mutate the map it is handed and return that same map —
nothing in the type prevents it, and a real step is likelier to do this than not. If a caller clones
once and then passes the same backing map as both `before` and `after`, the diff is a map against
itself: `AddedKeys` and `RemovedKeys` are both empty and `CheckAdditive` returns nil for ANY step
whose declaration is also empty — a vacuous pass on the exact enforcement path this phase exists to
build. The discipline is therefore PER-STEP RE-CLONING, written out literally in Task 1's action and
grep-pinned in its acceptance criteria, and proven by a fixture whose `ApplyFunc` mutates its input
in place (Task 3 here, and plan 03-03's mirror row for the table driver).

**PA-6 (error wording).** `internal/migrate` is a stdlib-only leaf with no access to the repo's
`field=<name> hint=<code>` envelope machinery (which lives in `internal/server`). Its errors are
plain `fmt.Errorf` values prefixed `migrate: `, naming the offending index/version/keys. CONTEXT.md
leaves error-envelope wording to discretion; this is the resolution. Phase 4 wraps these into the
operator envelope at the CLI boundary.
