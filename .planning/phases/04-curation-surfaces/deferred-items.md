Root cause traced via `~/.claude/gsd-core/bin/lib/milestone.cjs`'s `cmdRequirementsMarkComplete`: the checkbox regex DOES match `- [ ] **CUR-01**`, but the traceability-row write only flips `Status` when the current cell reads `Pending` or `Gaps Found` (case-insensitive); this project's REQUIREMENTS.md has `Mapped` in that column for every one of its 40 rows, which the verb does not recognize, so the row write is rejected — and per `#2788 defect 2`'s checkbox/row divergence guard, the checkbox flip is then rolled back too, leaving the requirement reported `not_found` even though it plainly exists in the file. This affects every requirement in the milestone: `grep -c '| Complete |'` and `grep -c '^\- \[x\]'` both return `0` across the whole file, even though Phases 1-3 are already shipped per STATE.md (`completed_phases: 2`, current_phase 04) -- so this is a pre-existing, milestone-wide gap between this project's REQUIREMENTS.md and the tool's own vocabulary (confirmed against `~/.claude/gsd-core/templates/requirements.md`, whose traceability table and "Status Values" section document exactly `Pending | ... | Complete`, with no `Mapped` state and no per-project override documented in this file).
  **Why not fixed here:** Per the project's `planning-artifacts.md` rule, a tool-owned generated file (REQUIREMENTS.md is written and re-read by `gsd-tools`) must never have custom structure invented into it by hand -- a shape the tool doesn't recognize (`Mapped`) is an upstream gap to report, never a local workaround (hand-editing 40 rows from `Mapped` to `Pending`, or hand-flipping this plan's 3 rows to `Complete`, would both be exactly that). It is also out of this plan's scope under the executor's own Scope Boundary rule: the defect predates plan 04-12, affects all 40 requirements across every phase (not files this plan touched), and reproducing/fixing it correctly is a milestone-level (likely `gsd-tools` upstream) question, not a plan-level one.
