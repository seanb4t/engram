In a NEW file `internal/store/migrate_status.go`:

1. Define the histogram type. Prefer a small struct with an explicit present/absent split; do NOT return a bare scalar. Suggested shape (executor discretion per D-08): `type VersionBucket struct { Version int; Count uint64 }` and `type MigrateStatusResult struct { Buckets []VersionBucket; Absent uint64; Total uint64 }`. Whatever the shape, present bucket key = `schemaVersionKey` (`schema_version`, store.go:370).
2. `func (s *Store) MigrateStatus(ctx context.Context) (MigrateStatusResult, error)`:
   - Wrap with `tracer.Start(ctx, "store.MigrateStatus")`, a `defer span.End()`, and the `telemetry.RecordStoreOp(ctx, "MigrateStatus", start, err)` + error→span-codes pattern shown by the other store methods.
   - Request present buckets with one `s.client.Facet(ctx, &qdrant.FacetCounts{CollectionName: s.collection, Key: schemaVersionKey, Exact: qdrant.PtrOf(true)})`; read each `FacetHit.Value`'s IntegerValue as the version int and `Count` as the bucket count. Sort buckets by version ascending for a stable/deterministic report (edge: equal-valued facets are merged by Qdrant; output order is NOT specified by the backend, so sort on this side).
   - Request the absent/legacy bucket with one exact `s.client.Count(ctx, &qdrant.CountPoints{CollectionName: s.collection, Filter: &qdrant.Filter{Must: []*qdrant.Condition{qdrant.NewIsEmpty(schemaVersionKey)}}, Exact: qdrant.PtrOf(true)})`.
   - `Total` may be a whole-collection exact Count, or derived as `sum(present buckets) + absent`; if derived, do so with a comment noting the invariant is test-asserted against `sum(buckets) + absent`. Keep it server-side; never accept a CLI-supplied count.
3. Edge behavior: an empty collection returns zero buckets, Absent 0, Total 0. An all-migrated (all-v1) collection returns a bucket v1:N and Absent 0 — the histogram still represents the (single-version) distribution, not a scalar. A mixed collection returns multiple buckets plus the Absent count.

   - WHOLE-RANGE PREFLIGHT (D-13) — MUST run before ANY write: select the chain from every target version down to `to`. Since 2026-08-12.01 ships a single registered step (v0→v1, irreversible), the preflight walks `migrate.Registry` (or the provided steps for tests) and for each step whose `To` is above `to` (i.e. in the requested revert range) reads `step.Reversibility()`; if `IrreversibleReason(rev)` returns a non-empty reason, refuse the ENTIRE revert: return an error formatted as `fmt.Errorf("field=steps hint=irreversible: revert cannot reach v%d: step (From=%d To=%d) is irreversible: %s; recovery is a collection snapshot", to, from, to, reason)`. Name EVERY irreversible step in the range and its stated reason (D-14). Zero records touched.
   - If the range is fully reversible, select a stepped reverse path. A utility that selects the steps whose To is strictly greater than `to` in descending To order (reverse application) is acceptable; reuse `migrate.StepsFrom`/`Validate` where they apply, but keep the reverse ordering explicit (inverses run in reverse order).
   - REVERSE WALK: same re-derive-per-pass loop shape as `Store.Migrate` — per pass a fresh exact Count of records at a version above `to`, then a fresh Scroll (Offset nil). For each record, apply each selected step's declared `Inverse()` in reverse order via per-point `DeletePayload` (for inverse-removed keys) and `SetPayload` (for inverse-modified values). Use the `int(target)` cast at every Qdrant value boundary (tdt50852ww), and set `schemaVersionKey` back to the target version on the write. No collection lock; resume = call `Revert` again.
