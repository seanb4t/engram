<objective>
Give the chat/summarize lane its own provider credential, all the way from the operator's env var to
the outbound `Authorization` header, and make it reachable for Helm users in the same phase.

The base-URL half of this split already shipped: `ENGRAM_OPENAI_CHAT_BASE_URL` is resolved by
`cmp.Or` at `summarizerFromConfig` and rendered from `memory.summarize.chatBaseURL`. This plan is
that pattern's exact sibling — registry entry, struct field, one `cmp.Or` line, one chart value, one
checksum re-pin (D-01, D-02, D-04, D-04a, D-04b). Nothing here is new design; the highest-value
behavior is literal pattern-matching against the shipped `chat_base_url` work.

**D-04's literal path was falsified by research and is superseded by D-04a.** D-04 named
`memory.openai.chatApiKeySecret`. The chart does not group by config-key namespace — it groups by
lane. `memory.openai.*` is the *embedder's* namespace, and this key's actual sibling `chatBaseURL`
already lives at `memory.summarize.chatBaseURL`. The value ships at
**`memory.summarize.chatApiKeySecret`**, mirroring where its sibling landed rather than where the
embedder's key landed. If this plan's diff touches `memory.openai.*` in `values.yaml`, that is the
warning sign that the falsified premise crept back in.

D-05 is a deliberate non-action: no `loadAndValidate` branch, because an API key has no verifiable
shape and empty is meaningful (inherit).

Purpose: close #350 — an operator splitting embedder and chat gateways can finally give each its own
credential.
Output: the config key, the construction-site fallback, the end-to-end test, the Helm value, and the
re-pinned drift checksum.
</objective>
