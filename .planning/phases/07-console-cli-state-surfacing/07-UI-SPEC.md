# Phase 7 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** this is a pure UX-layer extension of an established design system
(`ui/src/app.css`, `ui/src/lib/components/ui/*`, `ui/components.json`), same as Phase 19. Phase 7
adds **read/observability surfaces only** — a State section, list-row markers, sidebar include
toggles, and a silent-at-zero migration banner in the console; a STATE column, `engram get`, a
migration-status verb, and an advisory footer in the CLI. Nothing below invents a new visual
language: it reuses Phase 19's spacing/typography/color scales and the `--destructive` token verbatim,
and resolves the phase's one genuinely open question — precedence for compound record state — against
the codebase's own conventions plus one external grounding pass (Carbon Design System's
highest-attention-wins consolidation rule), not by pre-guessing.

`2026-08-12.01 Phase 5` and `2026-08-12.01 Phase 6` are the direct dependencies; this document treats
their CONTEXT.md decisions as load-bearing (`optional` presence asymmetry, `renderOperatorView`'s
shape, `--output text` non-stability).

## Color

Existing 60/30/10 split, unchanged — **no new color token required**, `--destructive` already exists
(added by Phase 19, aliased to `--cat-gotcha`):

| Role | Value (light / dark) | This phase's usage |
|------|-------|-------------------|
| Dominant (60%) | `--background` | Page background, list/detail panels |
| Secondary (30%) | `--card` / `--secondary` / `--muted` | Migration banner background (`bg-muted`), sidebar |
| Accent (10%) | `--primary` `#6E56CF` / `#8B7BE8` | **Not used by this phase.** State markers and the migration banner are explicitly excluded from accent — accent stays reserved for primary CTAs, active nav, `✦ auto`, and focus rings (Phase 19's reservation list, unchanged and re-confirmed here). |
| Destructive | `--destructive` (= `--cat-gotcha`) | The **ahead-version** migration banner only (`bg-destructive/10 text-destructive border-destructive/30`) — this is the one condition in this phase serious enough to earn the app's single existing "something is wrong" color, because it means the running binary cannot fully read its own collection. |

**Explicit rule — state markers are achromatic.** `archived` / `superseded` / `scheduled` badges use
`Badge variant="outline"` with **no per-state hue**. All three render in the same neutral
border/`text-foreground` treatment. Two reasons, both load-bearing:

1. This app's only existing hue-coding system is the **category** color set
   (`--cat-convention`/`--cat-gotcha`/`--cat-decision`/`--cat-preference`), and every row/detail view
   already shows the category badge adjacent to where a state badge would sit. Giving state badges
   their own hue set would either collide with category colors or force a second, unrelated hue
   vocabulary onto the same visual field — exactly the ambiguity Phase 19's accent-reservation table
   exists to prevent.
2. Per the accessibility contract below, color is never the state signal — text is. Achromatic badges
   make that true by construction rather than by discipline.

**Behind-version migration banner is deliberately neutral, not destructive.** "Pending migrations
exist; run `engram migrate`" is routine maintenance advisory, not an error — using `--destructive`
here would train operators to ignore it (alert fatigue) and would make the ahead-version warning less
distinguishable. It renders `bg-muted text-foreground border-border`, the same neutral surface tone
already used for the sidebar and row hover states.

## State Vocabulary and Compound-State Precedence

**The wire is the vocabulary (D-13, locked).** Both surfaces derive a record's state purely from
proto field presence — never an invented word with no field behind it:

```
archived_at present         → archived
superseded_by present       → superseded
not_after in the past       → expired
not_before in the future    → scheduled
```

**`expired` and `scheduled` are mutually exclusive** — `not_before must be strictly before
not_after` is enforced at write time on both lanes (`internal/surfaces/rules.go:222`, `HintOrdering`),
so no record can carry both. At most three of the four words ever compose.

**`expired` was added 2026-08-20 (Sean) resolving this document's flagged open gap.** It is not a
violation of "the wire is the vocabulary" — `not_after` is a wire field, and this rule has the
identical shape to the other three (field presence/relation → one lowercase word). D-13's original
three-rule derivation simply did not cover the `not_after`-in-the-past case that `include_scheduled`
also reveals, because `activeWindowConditions` (`store.go:1013/1017`) gates on **both** halves of the
window. The locked three-bool API (`include_archived`/`include_superseded`/`include_scheduled`) is
**unchanged** — only the derivation gains a rule, so nothing about the Connect or CLI surface widens.

**Canonical order (used everywhere a compound state is listed or composed):** `archived, superseded,
expired, scheduled` — this fixed order is used for the STATE column's composed value, the console badge
left-to-right order, and `engram get`'s headline parenthetical. Rationale for this exact order,
grounded rather than arbitrary: it reflects descending **operator-action finality** —

- `archived` is a deliberate, terminal operator action removing a record from active management.
- `superseded` is a correction with a live successor to follow — less final, structurally recoverable
  via the link.
- `expired` is a lapsed validity window — the record is past, not corrected and not deliberately
  removed, and `engram prune-expired` is what eventually reclaims it. Less final than a deliberate
  archive, more final than a correction that left a live successor behind.
- `scheduled` (not-yet-active) is the least "severe": the record isn't hidden because something is
  wrong with it, only because its `not_before` window hasn't opened yet.

`expired` slots between `superseded` and `scheduled` because it is the boundary of the finality
scale's past half: everything above it is history, `scheduled` alone is future.

This ordering is the same property Carbon Design System's status-indicator pattern calls
"consolidate to the highest-attention state" — applied here as a fixed rendering order rather than a
single collapsed color, since D-15 requires the marker to stay composable (all present states are
shown, never collapsed to one).

### Compound-state precedence rule (the phase's flagged open question, resolved)

**Dimming is binary, never stacked, and is driven by finality — not by state count:**

| Condition | Dimmed? |
|---|---|
| `archived` only | Yes |
| `superseded` only | Yes |
| `archived` + `superseded` | Yes — **same single dimmed treatment as either alone, never extra-dimmed.** There is no "more dimmed" tier. |
| `expired` only | Yes — an expired record *is* history: its window closed and `prune-expired` reclaims it. Same single dimmed treatment, no extra tier. |
| `scheduled` only | **No.** A not-yet-active record is not history — it is the live record, early. Dimming it as if it were archived/superseded would misrepresent a record that will become perfectly normal the moment its window opens. |
| `scheduled` + (`archived`, `superseded`, or `expired`) | Yes — driven by the archived/superseded/expired component; `scheduled` alone never adds or removes dimming. |

**The rule in one sentence:** dim iff the record is **past** (`archived`, `superseded`, or
`expired`); `scheduled` describes a record's *future*, so it never dims and never suppresses a dim
contributed by another state.

This resolves the "biggest open visual question" the phase brief names: precedence is not needed for
*which* state wins visually, because the marker is composable and shows every present state as its
own word — precedence is needed (and now fixed) only for the single yes/no **dimming** decision, and
the rule above answers it without inventing a graduated opacity scale.

**Accessibility carve-out (hard rule, not a style preference):** the state marker badge(s) render at
**full opacity even inside a dimmed row** — only the row's summary text, category label, timestamp,
and tags dim. Applying the row's dimming opacity to the badge text as well would risk pushing an
already-small 9.5–10px label below WCAG AA contrast on the exact element the marker-plus-dimming
pattern (D-15) designates as the non-decorative, load-bearing signal.

### Resolved — `expired` (was this document's flagged open gap)

`include_scheduled` relaxes `activeWindowConditions`, which gates on **both** `not_before` and
`not_after` (07-CONTEXT.md canonical refs, `store.go:1013/1017`). D-13's three-rule derivation named
only `not_before` in the future → `scheduled`, so a record whose `not_after` had already passed — an
**expired**, not merely not-yet-active, record — would have been revealed by `include_scheduled` while
rendering with **no marker at all**, visually indistinguishable from a live record. That directly
contradicts this phase's own success criterion that the console renders a record's state.

**Resolution (Sean, 2026-08-20): add the fourth wire-derived word `expired`** (see the derivation
table above). Two alternatives were considered and rejected:

- *Split `include_scheduled` into two bools* (`include_scheduled` for `not_before`, a new
  `include_expired` for `not_after`) so the flags are strictly one-to-one with the two gate
  conditions. Rejected as reopening a locked decision and widening the Connect + CLI surface for a
  problem that is purely about *rendering* a revealed record, not about *which* records are revealed.
- *Accept no marker.* Rejected: it leaves an operator who opts into `include_scheduled` unable to tell
  a lapsed record from a live one, which is the exact legibility failure this phase exists to fix.

## Component Specs

### Console — `MemoryRow.svelte` (D-15)

- State badges render in the meta line, **after** the category label and relative time, **before**
  scope chip and tags (state is more central to "what is this record" than scope/tags in this
  context). Each present state renders as its own `Badge variant="outline"` at the uppercase
  micro-label size, canonical order, achromatic (see Color).
- An optional decorative icon prefix per badge is **allowed but not required**; if used it MUST carry
  `aria-hidden="true"` and never replace the visible text — the text is the accessible carrier, not
  the icon.
- Row dimming: apply `opacity-60` (or the project's nearest existing dim utility) to the row's
  `<button>` content **excluding** the state badge wrapper, per the compound-state precedence table
  above. Live rows (no state) are unaffected — zero visual change for the common case.
- **Overflow — the meta line wraps to a second row** (Sean, 2026-08-20). When state badges plus
  category/time/scope/tags exceed the panel width, the meta line wraps rather than truncating or
  hiding anything: add `flex-wrap` with a small `gap-y` to the existing meta-line row. Nothing is
  ever elided, so no element needs a priority order and no state can be pushed out of view — which
  matters because the badge is the load-bearing, non-decorative signal (D-15) and must not be the
  thing that overflow removes. **Consequence to plan for:** list row height becomes variable, so any
  fixed-row-height or virtualization assumption in the list must be checked; a row with all four
  states present is the worst case to test against.
- No new component: this is an addition to the existing `flex items-center gap-2 text-[11px]
  text-muted-foreground` meta-line row, alongside the existing category/time/scope/tags spans.

### Console — `MemoryDetail.svelte` (D-14)

- **`schema_version` is always present**, rendered in the existing meta chip row (`by` / `src` /
  `vis`) as a fourth chip: `<span class="border border-border rounded px-1.5 py-0.5"><span
  class="text-muted-foreground">schema</span> v{N}</span>` — same visual family as the existing
  by/src/vis chips, so it reads as one row of facts, not a bolted-on addition. This chip appears for
  every record, live or otherwise, in the **Meta** tab (not a new tab).
- **State section** renders **only when the record carries non-default state**, as a new block
  directly below the by/src/vis/schema chip row inside the existing Meta tab (extends the tab rather
  than adding a fourth `Tabs.Trigger` — the existing three-tab structure, Summary/Content/Meta, is
  unchanged). Section header: `text-[9.5px] uppercase tracking-wide text-muted-foreground
  font-semibold` — same caption treatment as the Summary tab's "Summary" label.
- Inside the section, one line per present state:
  - `archived` → `archived {fullTimestamp(archived_at)}` (reuse the already-imported `fullTimestamp`
    helper — no new date formatting).
  - `superseded` → `superseded by` followed by a **link** (a `<button>` styled as a link, reusing
    the existing `text-primary underline` link treatment already used for markdown links in
    `MemoryDetail`'s `.markdown-body :global(a)` style) that selects the target record by id/short_id
    — i.e. the same `onselect`-style navigation `MemoryRow` already uses, not a page navigation.
  - `supersedes` (when present, plural) → `supersedes` followed by one link per predecessor, same
    treatment, stacked or comma-joined (executor's choice — not visually load-bearing).
  - `expired` → `expired {fullTimestamp(not_after)}` (same `fullTimestamp` helper; parallel in shape
    to the `archived {date}` line, because both state a moment in the past at which the record left
    active use).
  - `scheduled` → `not yet active — opens {fullTimestamp(not_before)}` (and, if `not_after` is also
    set and in the future, a second line `closes {fullTimestamp(not_after)}` — this is presentation of
    an already-fetched field, not a new derived state per the vocabulary lock above).
- A live record's detail pane is **unchanged** — no empty "State" heading renders when there is
  nothing to say, mirroring the banner's own silent-at-zero rule at the component level.

### Console — `AppShell.svelte` (D-07)

- Migration banner(s) render as a **slim strip directly below the header, above the `flex flex-1
  min-h-0` route content row** — every route, since `AppShell` wraps all of them.
- Two independent strips, each `px-3 py-2 text-[13px] flex items-center gap-2 border-b border-border`:
  1. **Behind-version** (`bg-muted text-foreground`), renders first (top) when `pending > 0`.
  2. **Ahead-version** (`bg-destructive/10 text-destructive`), renders second (below the first, or
     alone if behind-version is silent) when `future_total > 0`.
  Stacking order (behind above ahead) matches how an operator reads top-to-bottom: the routine
  advisory first, the more serious warning second — reading order ends on the more severe fact,
  which is the one that should be freshest in the operator's mind before they act.
- Each strip pairs a small Lucide icon (decorative, `aria-hidden="true"`) with the copy string from
  the Copywriting Contract — never color or icon alone. A reasonable icon choice: `ArrowUpCircle` (or
  similar "pending update") for behind-version, `TriangleAlert` (already imported by the existing
  `sonner.svelte` toast, so it's an already-used icon in this codebase, not a new import decision) for
  ahead-version — icon choice itself is not load-bearing, the visible text is.
- Data source: fetched once via the new Connect RPC on `AppShell` mount (session-scoped, not
  per-route or polling — the migration backlog is not a fast-changing number, and polling every route
  transition would add RPC volume for a diagnostic that changes on operator-run `engram migrate`
  timescales, not request timescales). A failed fetch renders no banner (see Copywriting Contract).

### CLI — `renderMemoryTable` (D-12)

- **Column order:** `SHORT_ID  SCOPE  CATEGORY  STATE  SCORE  SUMMARY` (search) / `SHORT_ID  SCOPE
  CATEGORY  STATE  SUMMARY` (list) — STATE inserted immediately after CATEGORY, before the
  variable-width SCORE/SUMMARY columns, so identity-ish columns (id/scope/category/state) stay grouped
  left, and the widest/most-variable column (SUMMARY) stays last, matching the table's existing
  left-to-right narrow-to-wide convention.
- **Cell value:** blank for a live record (D-12, locked). For a non-default record, the canonical-order
  state words joined with a comma and **no space** (`archived,superseded`; worst case
  `archived,superseded,expired` — at most three words ever compose, because `expired` and `scheduled`
  are **mutually exclusive by a write-time invariant**: `not_before must be strictly before
  not_after` is enforced on both write lanes (`internal/surfaces/rules.go:222`, `HintOrdering`), so
  an inverted window is unrepresentable and a record cannot simultaneously have a future
  `not_before` and a past `not_after`) — compact, single-cell,
  greppable, and avoids ambiguity with tabwriter's tab-delimited column model (an embedded space
  inside a cell is harmless there, but comma-no-space reads as one token to `cut`/`awk`-style
  downstream processing an operator might pipe this through, even though `--output text` carries no
  stability promise — free correctness is still free).
- **No Unicode glyphs, no ANSI dimming, in this column or anywhere in the text lane.** Two independent
  reasons, both binding:
  1. **Wide/combining-character safety.** The scope note names this constraint directly: this
     codebase already rejected `text/tabwriter` for the *operator view* renderer in favor of manual
     `utf8.RuneCountInString` padding, documenting wide/combining-character misalignment as an
     accepted limitation there. `renderMemoryTable` itself still uses `text/tabwriter`
     (`client_common.go:397`) — a different renderer with a different, real, and separate hazard: an
     embedded ANSI escape sequence is counted as visible-width runes by `tabwriter`'s own column-width
     calculation, so wrapping a cell's content in color codes would inflate that row's column width
     and misalign every other row sharing the column. This is a genuine `text/tabwriter` limitation
     with no clean fix inside the "zero new Go dependencies" constraint this milestone has held for
     three consecutive phases (a third-party ANSI-aware tabwriter replacement would break that).
  2. **Determinism.** Skipping ANSI entirely means the text lane renders byte-identically whether or
     not stdout is a TTY, NO_COLOR is set, or output is piped — there is no TTY-conditional branch to
     get wrong, test, or drift. This is a stronger property than "correctly gate ANSI by TTY
     detection," not a weaker one, and it matches Phase 6 D-03's framing of the text lane as an
     unstable *view* rather than a format worth hardening a second, conditional code path for.
  This resolves the scope note's "dimming via ANSI where a TTY is present... and what happens when it
  is not a TTY" question: there is no ANSI branch, on either path, anywhere in the text lane. The plain
  comma-joined word list is the CLI's entire state signal — which is sufficient, because the console's
  own dimming is explicitly decorative-only (D-15) and never the sole carrier there either.

### CLI — `engram get` / `renderOperatorView` (D-09, D-10, D-11)

- Renders the full record via the existing `renderOperatorView` over a `json.RawMessage`-wrapped
  protojson payload (D-10's one-line adapter) — every proto field (`archived_at`, `superseded_by`,
  `supersedes`, `not_before`, `not_after`, `schema_version`) appears as its own labeled line via the
  existing `humanizeKey` machinery. **No new field-rendering code is introduced for state** — the
  vocabulary lock (D-13) is satisfied by the raw fields already being present and readable, not by a
  synthesized "State:" line duplicating them.
- **Headline** (the one addition, D-11's fix applied): `record {short_id}` plain, or `record
  {short_id} ({archived, superseded, ...})` when non-default, using the exact canonical-order word
  list — see Copywriting Contract. This is the single place this phase adds new headline text, and per
  D-11 it MUST route through `sanitizeViewValue` before being written — `short_id` is server-minted so
  it is inherently safe, but the parenthetical is built entirely from this document's own fixed
  vocabulary strings (never record-derived free text), so the headline as specified here carries no
  new injection surface even before sanitization; sanitize it anyway, structurally, per D-11's intent
  that the property hold by construction rather than by this call site happening to be safe today.

### CLI — migration status verb + advisory footer (D-05, D-08)

- Verb output: `renderOperatorView` over the `MigrateStatusResult` fields, headline `migration
  status` (see Copywriting Contract) — no bespoke table needed, the existing field-table mechanism
  already handles the buckets/absent/future/future_total/total shape via `viewFields`'s array-of-object
  handling (`Buckets`/`Future` render as indented rows, same as any other repeated-message field).
- Footer on `search`/`list`: `renderCoverageFooter`-shaped line appended after the table (or after the
  JSON document is written, when `--output json` — the footer is a text-lane-only addition; the JSON
  response shape is untouched per D-08's explicit rejection of piggybacking the count onto the hot
  response messages).

## Accessibility Contract

Because dimming is decorative-only by decision (D-15) and the ahead/behind banner distinction must
survive the removal of color, every state on every surface must be conveyable **without** color and
**without** opacity:

| Surface | Mechanism that survives color/opacity removal | What is explicitly NOT relied on |
|---|---|---|
| Console list row (`MemoryRow`) | Visible lowercase text badge(s) — `archived` / `superseded` / `expired` / `scheduled` — always rendered at full opacity, never color-coded | Row dimming (decorative only, exempts the badge); any per-state hue |
| Console detail pane (`MemoryDetail`) | Named State section with explicit labeled lines (`archived {date}`, `superseded by {link}`, `expired {date}`, `not yet active — opens {date}`) | Badge color; section placement alone (screen reader gets the text content, not spatial layout) |
| Console migration banner | Full sentence copy naming the condition explicitly ("pending migration" vs "newer schema version... may not render correctly"), paired with (never replaced by) an `aria-hidden` icon | Strip background color (`bg-muted` vs `bg-destructive/10`) as the sole distinguisher between the two conditions — a screen reader or forced-colors/high-contrast mode user reads two different sentences regardless |
| Console sidebar toggles | Standard `Checkbox` + text label pair (existing pattern, inherently accessible — checked state exposed via `aria-checked`, not color) | N/A — no new risk introduced |
| CLI STATE column | Plain lowercase ASCII words, no glyphs, no ANSI — see Component Specs rationale | Any escape-sequence-based emphasis; any TTY-conditional rendering |
| CLI `engram get` headline/state | Same plain-word vocabulary, sanitized text | N/A |
| CLI advisory footer | `key: value` plain text lines | N/A |

Forced-colors mode and `NO_COLOR` are trivially satisfied by construction on the CLI (no color-bearing
codes exist in the text lane at all, per the Component Specs decision above) and are satisfied on the
console because every state-bearing element already carries a required text label independent of the
`Badge`/strip background color — removing `--destructive`/`--cat-*`/`opacity-60` from the stylesheet
entirely (a forced-colors browser mode does effectively this) leaves every sentence and label still
readable and still distinguishing the two banner conditions and four record states.
