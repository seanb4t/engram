<objective>
Make the publishing pipeline correct by construction: prove the cross-repo credential before any
release depends on it, and make a `workflow_dispatch` backfill structurally unable to regress the tap.

Implements D-12 (the existing release-please GitHub App is the tap-writing identity — no new secret,
no expiry to rotate), D-13 (a read-only `workflow_dispatch` credential probe asserting
`.permissions.push` is true, run once before the first cask release and re-runnable after any
re-scope), and D-14 (a per-cask `skip_upload` driven by a newest-tag comparison computed before the
GoReleaser step — there is no `--skip=homebrew` CLI value; the unified `--skip` flag accepts only
`before`, `validate`, and `publish`).

Under D-15, ROADMAP success criteria 3 and 5 are satisfied **by construction**, not by rehearsal.
No staged `brew install` failure and no backfill rehearsal will be performed: criterion 3 rests on
D-09's reviewed post-install hook plus D-11's ownership boundary, and criterion 5 on this plan's
`skip_upload` guard plus its credential probe. A verifier must not fail those two criteria on their
literal rehearsal wording.

**Recorded decision — the credential probe lives in its own workflow file, not in `release.yaml`.**
01-PATTERNS.md placed it alongside the release job, but `release.yaml`'s `workflow_dispatch` trigger
declares `tag` as `required: true`, and its `target` resolver step treats any supplied tag as a
re-ship instruction. Dispatching that workflow to run a read-only probe would therefore also re-ship
release artifacts and — with the newest tag supplied — rewrite the tap's cask. A probe that cannot be
run without performing a release is not a probe. `.github/workflows/verify-tap-credential.yaml`
carries `on: workflow_dispatch` with no inputs, so it is dispatchable at any time with no side
effects. This satisfies D-13 exactly as written (a `workflow_dispatch`-only, read-only job); only the
file placement differs from the pattern map, which is advisory rather than a locked decision.

**Recorded decision — the App-token mint names BOTH repositories.** `actions/create-github-app-token`'s
`repositories:` input is a closed allowlist, not an addition to the default: unset means "the current
repository only", and setting it replaces that default outright. Scoping it to `homebrew-tap` alone
would break the release-please step running earlier in the *same job*, which writes release PRs, tags,
and Releases to `engram` — a different and worse failure than the one this phase prevents. The input
is therefore `repositories: engram,homebrew-tap` in both workflows, and the probe uses the identical
value so it verifies the exact scope the release job will hold rather than an approximation of it.

Purpose: the v0.11.0 release failed at the Go proxy/sumdb wait and shipped zero artifacts, which is
why the `workflow_dispatch` re-ship path exists. That same path already dragged `docker pull …:latest`
backwards once. The cask is version-pinned in a way `latest` is not, so the identical regression here
would leave every `brew install` serving an older build until someone noticed.

Output: a guard step and an explicitly scoped token mint in `release.yaml`, a templated `skip_upload`
on the cask, a standalone read-only credential-probe workflow, and one blocking human step to grant
the App access to the tap.
</objective>

**Workflow step.** Insert a step named `Resolve Homebrew upload guard` immediately before the
`goreleaser/goreleaser-action` step, gated on the same `if: ${{ steps.target.outputs.ship == 'true' }}`
condition every shipping step already carries. It must sit after the `actions/checkout` step, because
`git tag -l` needs the tags that `fetch-depth: 0` fetched. Pass the shipped tag in through an `env:`
block as `SHIPPED_TAG: ${{ steps.target.outputs.tag }}`, following the file's established
`env:`-block-then-`run:`-script shape rather than interpolating the expression into the shell body.

The script runs under `set -euo pipefail` and reuses the exact newest-tag computation already present
in the "Reconcile :latest after a re-ship" step: `git tag -l 'v*' --sort=-v:refname | head -1`. One
computation, one place — do not write a second, parallel implementation inside the GoReleaser template.
Echo both values so a run's log records the comparison. If no `v*` tag is found, emit a
`::error::`-annotated message and exit 1 rather than guessing a default; an empty result here means the
checkout is wrong, and silently choosing either branch would be worse than failing. Otherwise write
`SKIP_HOMEBREW_UPLOAD=false` to `$GITHUB_ENV` when the newest tag equals `SHIPPED_TAG`, and
`SKIP_HOMEBREW_UPLOAD=true` when it does not.

Note the boundary explicitly in a comment: equal to the newest tag means upload, anything older means
skip. The push path always ships the newest tag and so always uploads; only a `workflow_dispatch`
backfill of an older tag lands on the skip branch. Run the step unconditionally on both entry paths
rather than gating it on `github.event_name == 'workflow_dispatch'` the way the `:latest` reconciliation
does — the env var must always be defined by the time GoReleaser runs, and a push of the newest tag
correctly evaluates to `false` on its own.

**Cask field.** Add `skip_upload` to the single `homebrew_casks:` entry in `.goreleaser.yaml`, as a
quoted Go template using GoReleaser's documented optional-env idiom: an `if index .Env "SKIP_HOMEBREW_UPLOAD"`
guard that emits the variable's value when it is present and the literal `false` otherwise. A bare
`{{ .Env.SKIP_HOMEBREW_UPLOAD }}` would hard-fail template evaluation whenever the variable is unset,
which would break `task release:snapshot` for anyone running it locally. The guarded form keeps local
snapshot renders working while CI always supplies the real value.

Do not use `skip_upload: auto`. `auto` skips uploads for tags carrying a prerelease indicator, which is
a different rule from the newest-tag rule D-14 specifies, and layering it on top would make the
effective condition harder to reason about than either rule alone. Document that choice in a comment
above the field, along with the reason the value is computed in the workflow rather than in the
template: GoReleaser's template functions cannot run `git tag -l`.

Add a comment on the field naming the regression class it prevents — this repo already lost `latest`
to a v0.11.0 backfill after v0.11.1 had shipped, and a version-pinned cask would fail the same way with
no floating tag to notice it by.
