<objective>
Replace the bare `dev` sentinel with a real, SemVer-ordered version for every build that GoReleaser
did not stamp: a `go build` inside the working tree, and `go install …/cmd/engram@vX.Y.Z`.

Implements D-04 (derive from `runtime/debug.ReadBuildInfo()`, no Taskfile/Makefile/CI change),
D-05 (the patch-bump base is a release-please-managed Go const, registered as a fourth `extra-files`
entry with the `generic` updater), D-07 (both lanes render the same resolved value, so the invariant
plan 01-01 pinned keeps holding), and D-08 (no `v` prefix on any reported version).

**Recorded decision — the `.N` in `0.14.1-dev.N+g<hash>` is the fixed literal `0`.** RESEARCH.md's
Open Question 1 established that `debug.BuildInfo.Settings` has no commit-distance field at all
(only `vcs`, `vcs.revision`, `vcs.time`, `vcs.modified`), so a real "commits since last tag" count
would need either a `git rev-list --count` shell-out at build time via ldflags — reopening exactly
the no-Taskfile-change premise D-04 exists to preserve — or `git` present at runtime on the end
user's machine. D-04's only ordering requirement is `lastRelease < dev-string < nextRelease`, and a
fixed `0` satisfies it completely: `0.14.0 < 0.14.1-dev.0+g800a98f1 < 0.15.0` under SemVer
precedence, because build metadata after `+` is ignored for ordering and `-dev.0` is a prerelease of
`0.14.1`. Per-build uniqueness is already carried by `vcs.revision` and the `.dirty` marker, which
are the parts that actually identify a build. This decision is stated in `buildversion.go`'s own
source comment so a later reader finds the reasoning rather than an unexplained zero.

**Do not "fix" the patch arithmetic.** With `bump-minor-pre-major: true`, the real next release after
`0.14.0` is usually `0.15.0`, not `0.14.1`. The patch bump is a correctly-ordering lower bound, never
a prediction of the next version number.

Purpose: `main.version` has two consumers — the cask's install-time gate (which only ever sees an
ldflags-stamped release build, and is unaffected) and OpenTelemetry's `service.version`
(`internal/telemetry/config.go:31`), which today reports the useless string `dev` for every
non-release deployment.

Output: a `cmd/engram/buildversion.go` unit with three pure, directly-testable functions plus a thin
`debug.ReadBuildInfo()` wrapper; a test file covering all of them and pinning the const against the
release-please manifest; and the fourth `extra-files` entry that keeps the const current.
</objective>
