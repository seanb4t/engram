Write the guide. Mirror `guides/reindex.md`'s section rhythm closely enough that an operator who has
read one can navigate the other without re-orienting; the exact headings are your call.

Frontmatter is a `---` block on line 1 with `title` and `description`, nothing else required. Give the
description enough specificity to be useful in a search result: name the three verbs and the
schema-version mechanism, and make clear it is not about embedder reindexing or owner remapping.

Cover, at minimum:

**What the mechanism is.** Every record carries a server-stamped `schema_version`. A record written
before the key existed reads as version 0 by absence — no backfill was ever needed. The registry in
`internal/migrate` holds an ordered chain of steps; today that chain is a single v0-to-v1 step that
mints a short id for any record lacking one. Steps are additive-only and must declare reversibility;
both are registration invariants, so a step that is silent about reversibility is not a representable
state.

**How the sweep converges, stated as precisely as the code does.** The write path stamps the current
version before the sweep runs, so ordinary writes arrive already-current and never create new
below-target work, and successful migration writes reduce the backlog. Do NOT write that the backlog
is finite and strictly shrinking. `internal/store/migrate.go:498-528` carries a PA-3
non-shrinking-backlog termination guard whose existence is the design's own admission that the state
is reachable, and its error text distinguishes two causes: writes not landing (a `failed` count), and
a concurrent writer replenishing the backlog at the sweep's own drain rate. Say what the guard does —
the sweep stops and reports rather than looping forever — and say which of the two an operator is
looking at, because the message tells them. Also note that in manifest-limited apply, `backlog`
truthfully includes `appeared` records this run intentionally did not touch, so a non-zero `backlog`
there is not a failure signal.

**What is and is not automatic.** No migration ever APPLIES automatically — not on startup, not on
failure, and a failed `--apply` is never auto-reverted (auto-revert would turn one partial write into
two). What IS automatic is a read-only status probe at startup: `warnPendingMigrations` runs a single
`MigrateStatus` with a 10-second budget, logs a warning when pending work exists and a second,
separate warning when future-version records exist, and never gates startup. Its doc comment states
it MUST NOT invoke `Store.Migrate` under any circumstance. State both halves. Say explicitly that
never-applying-automatically diverges from what a reader may expect from a single-binary server, so
nobody waits for a sweep that will never come — and say that the warning they may already have seen
in their logs is that probe, not a migration.

**The preview-and-apply contract, stated before the first copyable command.** Both mutating verbs
route through the shared destructive registration, so they PREVIEW by default and mutate only under
`--apply`. Note that this differs from the `--dry-run` idiom the *non-destructive* operator sweeps
use, and link to the CLI guide's own operator-tier classification
(`/guides/cli/`) for why the two idioms coexist rather than re-arguing it. **Make that contrast
without naming any specific non-version-driven command** — the scope-boundary gate below requires
zero occurrences of those command names on this page, and the classification the reader needs is the
tier, not the roster. Every example that shows `--apply` carries the sentence saying what it does; do
not show a copyable `--apply` invocation before the contract has been stated.

**What `--apply` acts on.** It re-derives eligibility inside its own run and migrates only the
intersection of what the preview showed and what is still eligible. A record that became ineligible
since the preview is `spared`; one that became newly eligible is reported as `appeared` but not
migrated, and picking it up means re-running. Explain that re-running is the normal recovery path:
the sweep is idempotent and safe to re-run against a freshly re-derived backlog. **Do not call it
resumable.** `REQ-migration-resumability` is a deferred v2 requirement, and
`internal/store/migrate.go`'s D-07 comment records that there is no persisted cursor — every pass
re-derives from scratch with a nil offset. Say that plainly: there is no checkpoint file, no
`--resume` flag, and nothing to reconcile after an interruption; you re-run the same command.

**`migrate status`.** It reports a version DISTRIBUTION across the collection, not a scalar. Say why:
a mixed-version collection is legitimate mid-rollout, and a scalar would misreport it. Explain each
field of its report, including the future-version buckets and what it means to see them.

**`migration-status`.** The Connect-lane sibling reaching the same histogram over the wire, for an
operator with a server URL and a token but no direct Qdrant access. It takes no arguments.

**`migrate revert --to <v>`.** Reverse-walks records above the target version back down, previewing
by default like the forward sweep. Document the refusal contract in BOTH of its reachable forms,
because they have different consequences:

1. **Preflight refusal (the normal case).** A whole-range, zero-write preflight runs before anything
   is touched — twice, in fact: once in the command and again inside `Store.Revert`. If the range
   contains ANY irreversible step or unsupported stored version, the WHOLE operation refuses, naming
   every offending step and version, and nothing was written.
2. **Race-discovered refusal (the case a guide is tempted to omit).** A concurrent
   `engram migrate --apply` can land an above-target record in the window between a preflight and
   the write loop's own re-scroll. The loop then refuses on that single record — with the same typed
   refusal, from a synthetic one-record plan — after earlier records in the pass were already
   reverted. The report's `reverted` count is real; the operation is not atomic in this case. Tell
   the operator to re-run `migrate status` and take a fresh preview to reconcile, and tell them the
   way to avoid the window is not to run a forward sweep concurrently with a revert.

State plainly that the recovery path for an irreversible step is a collection snapshot. Do not
describe revert as a general undo.

**Flags.** A table per verb in `reindex.md`'s format, covering `--apply`, `--output`, `--timeout`,
and `--to`. For `--timeout`, link to the CLI guide's budgeting guidance rather than restating it —
note that `revert --apply` budgets TWO full read-only whole-range scans plus the write loop under one
timeout, which `migrate --help` states and which materially changes the number an operator picks.

**Output.** Show and explain both lanes. Every json key of the three CLI report structs must appear
as a backticked field name and be explained; derive the key list from the structs themselves rather
than from memory. Then cover the two ways the Connect lane's document differs: it carries a `pending`
field the CLI structs do not (`MigrateStatusResponse` field 7 — the same `status.Pending()` value the
startup warning and the console banner use), and protojson renders `uint64` fields as JSON *strings*,
so a script parsing both lanes cannot use one numeric parser for both.

**See also.** Link to `guides/cli.md` for the shared operator-tier contracts (blast radius, exit
codes, `--output`, timeout budgeting), to `reference/memory-record.md` for the `schema_version` field
contract, and to `guides/upgrade.md`'s schema-version release note for the release-specific context.

**Scope discipline.** Do not document the owner-remap, async summary-fill, or embedder-reindex sweeps
as part of this mechanism, and do not name them at all. None is version-driven. If you need to
distinguish this guide from `reindex.md`, do it in one sentence that says reindexing is not a
migration and links out — `reindex` is the one such name the boundary gate permits, and if you use
it, quote the sentence in the summary.

`backfill-short-ids` is a legitimate subject here — it is the registered v0-to-v1 step and its
standalone command is now a thin delegating alias — but describe it as the mechanism's first customer,
not as a separate procedure.
