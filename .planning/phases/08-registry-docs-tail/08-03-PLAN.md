  <action>
Write the guide. Mirror `guides/reindex.md`'s section rhythm closely enough that an operator who has
read one can navigate the other without re-orienting; the exact headings are your call.

Frontmatter is a `---` block with `title` and `description`, nothing else required. Give the
description enough specificity to be useful in a search result: name the three verbs and the
schema-version mechanism, and make clear it is not about embedder reindexing or owner remapping.

Cover, at minimum:

**What the mechanism is.** Every record carries a server-stamped `schema_version`. A record written
before the key existed reads as version 0 by absence — no backfill was ever needed. The registry in
`internal/migrate` holds an ordered chain of steps; today that chain is a single v0-to-v1 step that
mints a short id for any record lacking one. Steps are additive-only and must declare reversibility;
both are registration invariants, so a step that is silent about reversibility is not a representable
state.

**Why the sweep converges without a collection lock.** The write path stamps the current version
before the sweep runs, so new writes arrive already-current and never create new work. The backlog is
finite and strictly shrinking. This is a stated dependency of the design, not a happy accident, and
an operator who understands it will not go looking for a maintenance window.

**Nothing runs automatically.** No migration runs on startup. At most, startup emits a non-blocking
warning that pending migrations exist. Say explicitly that this diverges from what a reader may
expect from a single-binary server, so nobody waits for an automatic sweep that will never come.

**The preview-and-apply contract, stated before the first copyable command.** Both mutating verbs
route through the shared destructive registration, so they PREVIEW by default and mutate only under
`--apply`. Note that this differs from the `--dry-run` idiom `reindex` and `summarize-missing` use,
and link to the CLI guide's own explanation of why the two idioms coexist rather than re-arguing it.
Every example that shows `--apply` carries the sentence saying what it does; do not show a copyable
`--apply` invocation before the contract has been stated.

**What `--apply` acts on.** It re-derives eligibility inside its own run and migrates only the
intersection of what the preview showed and what is still eligible. A record that became ineligible
since the preview is spared; one that became newly eligible is reported as appeared but not migrated,
and picking it up means re-running. Explain that a re-run is the normal recovery path — the sweep is
idempotent and resumable, and a failed apply is never auto-reverted, because auto-revert would turn
one partial write into two.

**`migrate status`.** It reports a version DISTRIBUTION across the collection, not a scalar. Say why:
a mixed-version collection is legitimate mid-rollout, and a scalar would misreport it. Explain each
field of its report, including the future-version buckets and what it means to see them.

**`migration-status`.** The Connect-lane sibling reaching the same histogram over the wire, for an
operator with a server URL and a token but no direct Qdrant access. It takes no arguments.

**`migrate revert --to <v>`.** Reverse-walks records above the target version back down, previewing
by default like the forward sweep. It refuses a range containing ANY irreversible step WHOLE rather
than reverting partially and leaving the collection between versions, and the refusal message says
so. State plainly that the recovery path for an irreversible step is a collection snapshot. Do not
describe revert as a general undo.

**Flags.** A table per verb in `reindex.md`'s format, covering `--apply`, `--output`, `--timeout`,
and `--to`. For `--timeout`, link to the CLI guide's budgeting guidance rather than restating it —
the forward sweep and the revert have different cost profiles and that guidance already exists.

**Output.** Show and explain both lanes. Every json key of the three report structs must appear and
be explained; derive the key list from the structs themselves rather than from memory.

**See also.** Link to `guides/cli.md` for the shared operator-tier contracts (blast radius, exit
codes, `--output`, timeout budgeting), to `reference/memory-record.md` for the `schema_version` field
contract, and to `guides/upgrade.md`'s schema-version release note for the release-specific context.

**Scope discipline.** Do not document `migrate-remap-owner`, `summarize-missing`, or `reindex` as part
of this mechanism, and do not mention them in a way that implies `migrate status` accounts for them.
None is version-driven. If you need to distinguish this guide from `reindex.md`, do it in one sentence
that says reindexing is not a migration, and link out.

`backfill-short-ids` is a legitimate subject here — it is the registered v0-to-v1 step and its
standalone command is now a thin delegating alias — but describe it as the mechanism's first customer,
not as a separate procedure.

No SPDX header: `docs-site/**` is excluded in `.licenserc.yaml`, and a header would sit above the
frontmatter, which must start on line 1. No sidebar config edit: the Guides section autogenerates.
