**The field-reference table.** Add rows for `not_before`, `not_after`, and `schema_version`, matching
the existing row shape exactly (Field, JSON key, Type, Set by, Description, with an in-page link where
a section elaborates). `not_before` and `not_after` are client-set RFC3339 strings on the wire, stored
as epoch-second integers, exactly like `archived_at` — the existing `archived_at` row and the
paragraph at the end of `### Archiving` already establish that convention, so match it rather than
inventing a second description of the same storage detail. `schema_version` is server-set and never
client-supplied.

**A validity-window section.** Add a section covering the window fields and the two words derived from
them. Derive every claim from `activeWindowConditions`, not from the neighbouring prose and not from
the two existing implementations — those agree with the gate, but a docs page that copies a
derivation instead of the source is a third place for the same error to propagate. State explicitly:

- `not_before` is compared with an INCLUSIVE lower bound, so a record whose `not_before` equals the
  current instant is already active and carries no `scheduled` word. The moment of the boundary
  belongs to the active side.
- `not_after` is compared with an EXCLUSIVE upper bound, so a record whose `not_after` equals the
  current instant is already expired. The moment of the boundary belongs to the expired side.
- The two boundaries are therefore ASYMMETRIC, and that asymmetry is deliberate. Say so, because the
  reader's default assumption is that a window's two ends behave the same way.
- `expired` and `scheduled` are mutually exclusive: `expired` is evaluated first and suppresses
  `scheduled`. Note that this precedence lives in the derivation rather than in write-time validation,
  because `not_before` and `not_after` are independent wire fields and an inverted window can arrive
  from a legacy or future path even though writing one is rejected.
- The canonical order in which state words are emitted is `archived, superseded, expired, scheduled`,
  descending by finality.
- A record with no window is unaffected: absence matches, which is why the feature needed no backfill.

**A schema-version section.** State that every write stamps the current version, that a record written
before the key existed reads as version 0 by absence and needs no backfill, that the value is
wire-visible on both the MCP and Connect lanes rather than an internal audit stamp, and that it never
appears in a recall or authorization filter. State the forward-compatibility property in both
directions: a binary reading a record stamped NEWER than its own constant still reads it and never
rejects, hides, or downgrades it. Link to the operator guide `/guides/migrate/` for the procedure that
advances a record's version; do not restate the procedure here.

state fields are visible on BOTH lanes, and describe the cited issue as closed by that work rather
than as a pending gap. Do not carry any of the old paragraph's negative phrasing forward into the
replacement; write the positive contract from the proto file you read. Keep the surrounding true
content (the epoch-second storage detail, the RFC3339 round-trip, the deliberate lack of a payload
index) intact.

Keep the page's existing voice and density. This is a reference page, not a changelog: state the
current contract, do not narrate what changed or in which release. No SPDX header —
