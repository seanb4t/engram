## The completeness redesign this revision makes (review findings H3 + H4)

Cross-AI review (`02-REVIEWS.md`) landed two HIGH findings on this plan's previous design. Both are
correct and both are about the same thing: **what the completeness claim is derived from.**

**H4 — scanning `&qdrant.Filter{` literals is not a derivation of transmitted recall filters.** It is
the same defect plan 02-02 carried at a different syntax layer. A future recall path can obtain its
filter from a helper, a parameter or a constructor and add no `&qdrant.Filter{` literal to the
entry-point function; the enumeration assertion stays green while an unwalked filter reaches Qdrant.

**H3 — the recall/operator binary partition is not exhaustive, and calling it one is false.** The
package contains filter-building functions that are genuinely neither. Verified by scan at revision
time: `ResolvePointID`'s `short_id` lookup (`store.go:1631`), `MintShortID`'s collision probe
(`store.go:2638`), `ownerlessFilter` (`store.go:2567`), `missingShortIDFilter` (`store.go:2661`).
Calling these "operator" is semantically false; calling them recall-walked is false because no task
exercises them.

**The corrected derivation is reachability from the caller-facing recall entry points, over the
emission boundary.** Concretely: scan for the call sites that actually *transmit* a filter (`Query`,
`QueryBatch`, `Scroll`, `ScrollAndOffset`, `Count`), build a same-package call graph by callee name,
take the transitive closure from the six caller-facing recall entry points, and assert the reachable
emission set equals the enumerated recall-transmitter classification. This answers both findings at
once:

- It is anchored on transmission, not on where a `Filter` value happened to be typed (H4).
- It makes "which functions are out of scope" a *derived* fact rather than a forced bucket: a helper
  that no recall entry point can reach is out of scope by construction, and the leftover emission
  sites get a genuine three-way classification with per-item justification (H3).

### Known limits of the reachability derivation, stated at their real strength

Two distinct limits, and cycle-2 review was right that the previous revision conflated them into one
over-generous "backstop" claim.

**Limit 1 — the call graph does not follow function values, interface dispatch or reflection.** For
the recall paths as they exist today there is no such indirection: `Search` → `ownerScopeFilter` →
`ownerOrSharedCondition` are all direct method calls. For this limit the classification genuinely
*is* a backstop, and for a good structural reason: the emission-site **scan** is
reachability-independent, so a site that reachability cannot reach still surfaces in the derived set
and must be written into one of the three lists by hand, with a justification. The failure mode is an
active, reviewable misclassification rather than silence.

**Limit 2 — the method vocabulary is a maintained list, and the classification CANNOT backstop it.**
This is the correction. An emission behind a method name the scan does not enumerate produces **no
subject at all**: it reaches none of the three lists, causes no set difference, and the suite stays
green with nothing to review. `ScrollAndOffset` was exactly that case until this revision — which is
the proof that this limit is live rather than theoretical, not merely a hypothetical. Widening the
vocabulary narrows the gap; it does not close it. **Do not write "an unreachable emission always
surfaces for justification" into the test file** — that sentence is only true within the scanned
vocabulary, and stating it unconditionally is the overclaim this phase exists to avoid.

**Limit 3 — no type identity.** `go/ast` without `go/packages`/`go/types` cannot establish that a
matched `Scroll` belongs to `*qdrant.Client`, and the name-only call graph cannot distinguish
`s.Search`, another receiver's `Search`, and a package function named `Search`. See § "Name-collision
behaviour and its bias" below.

Write all three limits into the test file's doc comment, each named separately, together with the
statement that **the runtime interception in Task 3 — not this AST derivation — is the authoritative
proof that today's recall paths transmit no `schema_version` condition.** The AST derivation's job is
to catch tomorrow's recall path, and it does that for every shape inside the scanned vocabulary and
the direct-selector-call topology. A future maintainer who deletes the classification as "redundant
with reachability" would remove the Limit-1 backstop.

### Name-collision behaviour and its bias (cycle-2 actionable #7)

Without `go/types`, three things are indistinguishable: a method call `s.Search(...)`, the same
method name on a different receiver type, and a package-level function named `Search`. State the
behaviour and the bias explicitly in `buildSamePackageCallGraph`'s doc comment:

- **On the emission scan the bias is over-approximation.** A same-named method on an unrelated type
  becomes a spurious emission subject that someone must classify — one line of cost, no hole.
- **On the call graph the bias is also over-approximation.** A collision *invents* an edge (two
  different `Search`es collapse into one node), which enlarges the reachable set, which pushes more
  sites into `recallTransmitters`, which is the stricter side: those sites then have to be justified
  or walked. A collision cannot *erase* an edge, because resolution never narrows a callee — an
  unresolvable receiver resolves to the enclosing declaration's receiver type rather than to nothing.
- **Where it cannot over-approximate it under-approximates silently**, and that is Limit 1: a callee
  that is not a plain identifier or a receiver selector (a function value, an interface method)
  produces no edge at all.

Over-approximation is the correct bias for a gate: a false positive costs a line of classification, a
false negative is the hole. Say that, and say which of the three surfaces above is which.

## Why this walker is new code

RESEARCH.md and PATTERNS.md both confirm by grep that **no filter-condition walker exists anywhere
in this repository**. Every existing filter-related test in `internal/store` asserts on query
*results* — does `Search` return record X — never on the shape of the `*qdrant.Filter` object
itself. A result-shaped assertion is exactly what D-13 rejects: a filter could reference
`schema_version` and still pass if the test data happens to satisfy the condition. Build the walker
from scratch. The only thing to reuse from `collectionprefix_conformance_test.go` is its *discipline*
— derive the set, assert completeness, guard against scanning nothing — not its traversal, whose
target is source AST rather than a runtime proto struct graph.
