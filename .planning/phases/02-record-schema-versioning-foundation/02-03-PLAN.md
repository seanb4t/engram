## The completeness redesign this revision makes (review findings H3 + H4)

Cross-AI review (`02-REVIEWS.md`) landed two HIGH findings on this plan's previous design. Both are
correct and both are about the same thing: **what the completeness claim is derived from.**

**H4 — scanning `&qdrant.Filter{` literals is not a derivation of transmitted recall filters.** It is
the same defect plan 02-02 carried at a different syntax layer. A future recall path can obtain its
filter from a helper, a parameter or a constructor and add no `&qdrant.Filter{` literal to the
entry-point function; the enumeration assertion stays green while an unwalked filter reaches Qdrant.

**H3 — the recall/operator binary partition is not exhaustive, and calling it one is false.** The
package contains filter-building functions that are genuinely neither. Verified by scan at revision
time: `ResolvePointID`'s `short_id` lookup (`store.go:1631`), `MintShortID`'s collision probe
(`store.go:2638`), `ownerlessFilter` (`store.go:2567`), `missingShortIDFilter` (`store.go:2661`).
Calling these "operator" is semantically false; calling them recall-walked is false because no task
exercises them.

**The corrected derivation is reachability from the caller-facing recall entry points, over the
emission boundary.** Concretely: scan for the call sites that actually *transmit* a filter (`Query`,
`QueryBatch`, `Scroll`, `Count`), build a same-package call graph by callee name, take the transitive
closure from the six caller-facing recall entry points, and assert the reachable emission set equals
the enumerated recall-transmitter classification. This answers both findings at once:

- It is anchored on transmission, not on where a `Filter` value happened to be typed (H4).
- It makes "which functions are out of scope" a *derived* fact rather than a forced bucket: a helper
  that no recall entry point can reach is out of scope by construction, and the leftover emission
  sites get a genuine three-way classification with per-item justification (H3).

### Known limit of the reachability derivation, stated rather than hidden

A same-package call graph built from callee names does not follow function values, interface dispatch
or reflection. For the recall paths as they exist today there is no such indirection — `Search` →
`ownerScopeFilter` → `ownerOrSharedCondition` are all direct method calls — but the limit is real for
future code. That is precisely why the leftover emission sites still get an explicit three-way
classification rather than being dropped: the classification is the backstop for reachability's blind
spot, and a newcomer must be classified either way before the suite goes green. Write this reasoning
into the test file's doc comment; a future maintainer who deletes the classification as "redundant
with reachability" would remove the backstop.

## Why this walker is new code

RESEARCH.md and PATTERNS.md both confirm by grep that **no filter-condition walker exists anywhere
in this repository**. Every existing filter-related test in `internal/store` asserts on query
*results* — does `Search` return record X — never on the shape of the `*qdrant.Filter` object
itself. A result-shaped assertion is exactly what D-13 rejects: a filter could reference
`schema_version` and still pass if the test data happens to satisfy the condition. Build the walker
from scratch. The only thing to reuse from `collectionprefix_conformance_test.go` is its *discipline*
— derive the set, assert completeness, guard against scanning nothing — not its traversal, whose
target is source AST rather than a runtime proto struct graph.
