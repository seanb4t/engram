<objective>
Ship `engram spine-review purge`: preview-by-default deletion, gated on rule `7smp8vy9hr`'s
extract-before-delete ordering, deleting only the intersection of what the operator saw and what is
still eligible at apply time, carried between two process invocations by a manifest whose
provenance cannot be forged.

Purpose: this is the phase's sharpest edge. Every other leaf reports; this one destroys. The
intersection guarantee, the unforgeable manifest and the extraction gate exist so an operator never
loses something they did not see, and never loses something whose content was not preserved first.

Output: `PurgeManifest` with a compiler-enforced provenance marker, `PreviewPurge` / `ApplyPurge`,
the eligibility classes and filter path, the leaf command, and a registered scope rule for the
filter path.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Choose the preview-to-apply manifest transport</name>
  <decision>
D-11 requires `--apply` to delete the intersection of the PREVIEW set and a fresh re-derivation.
Preview and apply are two separate process invocations, so the preview's result must cross a process
boundary. RESEARCH.md flags this as the phase's primary research item and explicitly recommends an
operator decision here rather than a silent planner choice, because the three options are materially
different implementations, not variations of one.
  </decision>
  <context>
Memory `55zra87def` and RESEARCH.md Pitfall 1 both settle one half already: the in-memory type MUST
carry an unexported provenance marker (mirroring `internal/surfaces.ConditionalRule.declared` /
`IsDeclared()`), so a `store.PurgeManifest{...}` literal built anywhere outside `internal/store`
always carries the zero value and is rejected. That is compiler-enforced and is not in question.

What IS in question is what crosses between the two invocations, because the Go-type guarantee is
lost the moment the manifest is serialised.

Bounding the blast radius of a forged transport: `ApplyPurge` ALWAYS re-derives eligibility fresh and
intersects. A forged token can therefore never cause the deletion of a record that is not, at that
moment, both eligible under the selected class and past the extract-before-delete gate. It can only
cause the deletion of an eligible record the operator never previewed — which is precisely the
guarantee D-11 exists to provide, but it is not unbounded destruction.

**Two sub-decisions this checkpoint also records** (both Claude's Discretion in CONTEXT.md; stated
here so an objection is cheap now rather than mid-build):

- **How a milestone-summary record is identified for D-09's batch floor:** a `tags` convention — a
  record carrying a reserved tag, in the same scope as the candidates, whose `created_at` is strictly
  after the newest candidate's. Chosen because `tags` is already an AND-filterable mechanism with
  zero schema change (RESEARCH.md assumption A4). The per-record extraction link uses the same
  mechanism: a tag naming the short id of the record that preserved the content.
- **The retention window default for D-10's archived class:** 90 days, overridable with
  `--older-than`, stated in the flag's help text and in the CLI guide. The class only fires when the
  operator explicitly selects it, and it still passes through the extract gate and `--apply`.
  </context>
  <options>
    <option id="option-a">
      <name>HMAC-signed opaque token with a durably-stored key</name>
      <pros>Tamper-evident across processes and across restarts: a hand-edited id list fails the integrity check before any re-derivation runs. Supports a genuine preview-today-apply-tomorrow workflow. Stdlib `crypto/hmac` + `crypto/sha256`, zero new dependencies.</pros>
      <cons>Needs a durable home for the key, which no operator command has today — every other operator command is stateless across invocations. That key becomes a new operational artifact to manage, back up and rotate. ASVS V6 becomes applicable to this phase where it currently is not.</cons>
    </option>
    <option id="option-b">
      <name>Unsigned opaque token, unforgeable in-process type, fresh re-derivation at apply</name>
      <pros>No key, no new operational artifact, no cryptography. The in-process forgery hole memory `55zra87def` names is closed at compile time. A tampered token's blast radius is bounded to records that are eligible right now and already past the extract gate. Matches how every other operator command behaves — stateless between invocations.</pros>
      <cons>A hand-edited token can add an id the operator never previewed, provided that id independently passes eligibility and the extract gate. The token is integrity-checked only for corruption, not for authorship.</cons>
    </option>
    <option id="option-c">
      <name>Qdrant-payload tombstone: preview marks candidates, apply deletes marked-and-still-eligible</name>
      <pros>Survives restart with no key and no token to copy between terminals. The marker is auditable in the store itself.</pros>
      <cons>Preview becomes a MUTATION, which contradicts the whole preview-is-safe premise this phase is built on, and the marker then needs its own soft-hide, TTL and cleanup story — a materially larger implementation, plus a fifth record state one phase after adding a fourth.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c. Also confirm or amend the two sub-decisions (milestone-summary tag convention; 90-day archived retention default).</resume-signal>

Implement D-09's two-path gate as `checkExtractGate(candidates []purgeCandidate, batch []Memory) error`.
Per-record path: a candidate passes individually when it carries the extraction-link tag naming an
existing record whose `created_at` is strictly after the candidate's. Batch floor: absent per-record
links, the whole batch requires a record carrying the milestone-summary tag, in the same scope as the
candidates, whose `created_at` is strictly after the NEWEST candidate's. Failing the gate returns an
error naming which candidates lacked a link and what the batch floor required — never a partial
delete. Use the tag conventions Task 1's checkpoint confirmed.

`PreviewPurge(ctx, opts) (PurgeManifest, error)` runs the derivation, runs the gate, and returns the
verified manifest. It performs NO write of any kind unless Task 1 selected option-c.

`ApplyPurge(ctx, manifest, opts) (PurgeResult, error)` rejects an unverified manifest first, with an
invalid-argument-class error, before touching Qdrant. It then re-runs `derivePurgeEligible`, re-runs
the gate, computes `intersection = manifest ids ∩ fresh ids` and `appeared = fresh ids \ manifest ids`,
and issues ONE `client.Delete` whose selector is a filter built from `qdrant.NewHasID` over the
intersection — not a re-evaluated structural predicate, which could delete a record that newly
qualified under a DIFFERENT class between preview and apply. A single RPC also means partial failure
means "the whole apply failed, retry with a fresh preview", not "N of M were deleted and which N is
unclear". `PurgeResult` reports the deleted ids, the spared ids and the appeared ids as three
separate fields.

validate the token's integrity to whatever degree the selected option provides before doing so.
