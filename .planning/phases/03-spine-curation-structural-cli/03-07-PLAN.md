<objective>
Ship `engram spine-review purge`: preview-by-default deletion, gated on rule `7smp8vy9hr`'s
extract-before-delete ordering, deleting only the intersection of what the operator saw and what is
still eligible at apply time, carried between preview and apply by an IN-PROCESS manifest whose
provenance cannot be forged because it never crosses a process boundary at all.

Purpose: this is the phase's sharpest edge. Every other leaf reports; this one destroys. The
intersection guarantee, the unforgeable manifest and the extraction gate exist so an operator never
loses something they did not see, and never loses something whose content was not preserved first.

Output: `PurgeManifest` with a compiler-enforced provenance marker and NO serialization surface,
`PreviewPurge` / `ApplyPurge`, the eligibility classes and filter path, the leaf command, a
registered scope rule for the filter path, and the phase's end-to-end acceptance run.
</objective>

## The purge manifest transport is settled: IN-PROCESS ONLY

**Decided by Sean on 2026-08-06, during Phase 3 plan convergence cycle 2. This is not open, and
nothing below re-litigates it.** It falls squarely inside the discretion `03-CONTEXT.md` already
grants (Claude's Discretion, item 3: whether the D-11 manifest is persisted, held as a tombstone
marker, or expressed as an opaque token — "Research item"). It does NOT contradict D-11, whose
requirement is that `--apply` acts on the intersection, not that the manifest be portable. No
`/gsd-phase` roadmap edit is needed.

**What this means concretely.** `purge` previews and applies within ONE invocation. The command
prints the preview; `--apply` re-derives eligibility fresh at that moment and deletes only the
intersection of the preview set and the fresh re-derivation. The `PurgeManifest` type stays, but as
an in-process value only: its unexported `verified` marker, set solely inside `internal/store` and
read back through `IsVerified()` at the `ApplyPurge` entry, now actually holds — because nothing
anywhere reconstructs a manifest from bytes. This is memory `55zra87def`'s pattern working as
intended rather than being defeated by a parse path.

**Removed from scope entirely — do not implement, plan for, or leave a hook toward any of these:**
`ParsePurgeToken` / `ParsePurgeManifest` / any `Parse*` or `Decode*` constructor over
operator-controlled bytes; `Encode` / `Token()`; the `--token` flag; the `--manifest <path>` flag;
HMAC signing and verification; the signing key, its `internal/config` registry entry, its startup
validation, its file-permission and rotation policy; and all `charts/` / Helm secret wiring. ASVS V6
does not become applicable to this phase. No file under `internal/config/` or `charts/` is touched by
this plan, and none appears in `files_modified` — correctly, not by omission.

**Rationale, recorded so a later reader finds a decision rather than a gap.** Unforgeability and
serializability are in direct tension. The moment a token crosses a process boundary the guarantee
must come from a signature rather than from Go's visibility rules, and the key management that
implies — generation, config loading, startup validation, filesystem permissions, rotation, a Helm
secret — is a whole workstream this phase does not want. In-process keeps D-11's intersection
guarantee genuinely unforgeable, at the cost of exactly one capability.

**Residual limitation, stated plainly here, in the CLI `--help`, and in the CLI guide.** An operator
cannot preview in one invocation and apply in a later one. The confirmation is same-run: the apply
invocation renders the set it is about to delete before deleting it. If cross-invocation preview is
wanted later it is an ADDITIVE change that must introduce a signature — that is the forward path, and
it should be recorded as such rather than as a defect. Do not describe the current shape as
"temporary" or "v1" anywhere; it is the shipped contract.
