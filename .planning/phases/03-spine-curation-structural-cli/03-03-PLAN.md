<objective>
Make the destructive operator tier uniformly preview-by-default under an explicit `--apply`
(D-02), with membership DERIVED from Phase 2's blast-radius table rather than declared per command
(D-03), and flip `prune-expired` to the new contract with an upgrade note (D-04).

Purpose: this is the payoff of Phase 2's D-11. The blast-radius table stops being documentation and
becomes load-bearing for runtime safety — a future destructive command inherits `--apply`
automatically instead of by someone remembering.

Output: a derived gate, a registered conditional rule bound on every advertising surface, the
`prune-expired` hard flip, and a migration note.
</objective>

  <context>
**D-02 (one-way):** `--apply` becomes the advertised safety contract for every destructive
operator command, replacing `--dry-run` as the idiom on that tier. Reverting later re-arms the
dangerous default on tooling operators will by then have scripted against.

**D-04 (one-way):** `prune-expired` stops deleting without `--apply` immediately — no deprecation
window — documented in the upgrade guide. Reverting is a second breaking change and a second
migration note.

**The unanticipated consequence.** D-03 says membership is derived: a command is
preview-by-default **iff** the blast-radius table classifies it destructive. Reading
`internal/surfaces/toolclass.go` verbatim, the CLI rows classified `Destructive: true` today are
`migrate-remap-owner` AND `prune-expired`. (`migrate-set-owner` is `Destructive: false` — its own
row explains it only fills an EMPTY owner. The MCP-only destructive rows — `update_memory`,
`delete_memory`, `delete_all` — carry an empty `CLICommand` and are therefore outside the CLI gate.)

So D-03 forces `--apply` onto `migrate-remap-owner` too, which today uses `--dry-run`. RESEARCH.md
§ State of the Art asserts `--dry-run` "remains on migrate-remap-owner ... none of which are
classified destructive" — that sentence is wrong against the live table, and this plan follows the
table, not the prose.

Re-classifying `migrate-remap-owner` as non-destructive to avoid the flip is NOT on the table: it
overwrites an existing owner value in place with no history retained, and shortening the boundary to
silence a gate is exactly what D-03's derive-don't-declare property exists to prevent.
  </context>
