<objective>
Make archive a first-class record state (D-12): a new orthogonal `archived_at` payload key,
soft-hidden at exactly the same recall call sites `superseded_by` already is, exposed through
`get_memory`, surfaced as an `archived` bucket in `scan`, and driven by `archive` / `restore` verbs.

Purpose: REQ-archive-tier demands a state distinct from BOTH supersession's soft-hide and expiry.
Overloading `not_after` would make a naturally-expired record indistinguishable from an archived one
at three independent read sites — the failure D-12 rejected that option to avoid.

Output: the `archived_at` key with its round-trip and soft-hide wiring, two Subject-less store
methods, two leaf commands, and the published field contract.
</objective>

  <context>
**D-12 (one-way).** Once `archived_at` appears on a record returned by `get_memory`, it is part of
the published memory contract: agents read it, skills branch on it, and removing it later is a
breaking change to the MCP surface, not just to the CLI.

RESEARCH.md verified the two candidate mechanisms concretely:

- **A new orthogonal `archived_at` payload key**, soft-hidden by appending
  `NewIsEmpty("archived_at")` at the same four recall call sites `superseded_by` already occupies.
  Archived and expired stay independently readable predicates.
- **Reusing `not_after` plus a second marker** — the option D-12 already rejected. RESEARCH.md
  Pitfall 3 confirms why by reading the code: `activeWindowConditions` and `PruneExpired`
  independently match on `not_after`, so three call sites would each need to also consult the marker,
  and one future read path that forgets misreads an archived record as naturally expired.

Two shape questions this checkpoint settles:

1. **Value type.** An epoch-second integer (matching `not_before` / `not_after`'s stored form) versus
   an RFC3339 string (matching `created_at` / `last_accessed_at`'s stored form). The recall filter
   needs `IsEmpty` only, so either works for hiding; the integer form matches the other two window
   keys and makes a future retention-window range filter (plan 03-07's third structural purge class)
   a direct `Range` query rather than a parse-and-compare.
2. **Whether `archive` / `restore` accept ids only, or also a filter.** CONTEXT.md leaves this to
   discretion. Ids only keeps the blast radius of a mutating verb explicitly enumerated; a filter form
   would need its own scope gate, mirroring plan 03-07's purge filter path.
  </context>
  <options>
    <option id="option-a">
      <name>Orthogonal `archived_at` as an epoch-second integer; `archive` / `restore` take explicit ids only</name>
      <pros>Matches `not_before` / `not_after`'s stored form, so a retention-window range filter needs no parsing. Ids-only keeps a mutating verb's blast radius explicitly enumerated by the operator. Smallest new surface.</pros>
      <cons>Archiving a large set means many invocations or a shell loop. Epoch seconds are less legible than RFC3339 when read raw out of `get_memory`.</cons>
    </option>
    <option id="option-b">
      <name>Orthogonal `archived_at` as an RFC3339 string; `archive` / `restore` take explicit ids only</name>
      <pros>Legible in `get_memory` output without conversion; matches `created_at` / `last_accessed_at`.</pros>
      <cons>A retention-window filter (plan 03-07's archived-past-retention purge class) must then parse strings client-side or store a second numeric key — reintroducing the two-fields-for-one-fact shape D-12 rejected.</cons>
    </option>
    <option id="option-c">
      <name>Orthogonal `archived_at`; `archive` / `restore` accept ids OR a scope-gated filter</name>
      <pros>Bulk archiving in one invocation, which is the realistic milestone-close workflow. Reuses the explicit-scope gate plan 03-07 builds for purge.</pros>
      <cons>Adds a second conditional rule and a second filter path in the same phase as purge's. Widens a mutating verb's blast radius before anyone has asked for it.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c.</resume-signal>
</task>
