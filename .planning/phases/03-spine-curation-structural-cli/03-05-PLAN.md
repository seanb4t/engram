<objective>
Ship `engram spine-review consolidate`: a whole-spine, deterministic near-duplicate sweep that
reports ranked `(A, B, score)` pairs using records' already-stored vectors, and never merges or
mutates anything.

Purpose: consolidation is a judgment about identity. This phase supplies only what is derivable
structurally — the ranking — so Phase 4's semantic skill has something to judge without this command
having pre-decided anything.

Output: a Subject-less batched vector-neighbour query and the leaf that renders its ranked report in
text and JSON.
</objective>

The assumption: "near-duplicate" is defined here purely as *vector proximity under the collection's
existing embedding*, with no notion of a correct answer. There is consequently no boundary value
this plan can defend as the point where a pair stops being a candidate — which is exactly why D-15
ships no default threshold. If a future reviewer expects `consolidate` to have a defensible
"how close is close enough" edge, that expectation is not satisfied by this phase and is not a
regression; it is Phase 4's judgment call.

The operator-supplied `--min-score` filter exists to bound REPORT SIZE, not to encode a correctness
boundary, and its default must therefore be "no filter", not a tuned number.
</planner_assumptions>

  <behavior>
    - A scope with zero records returns an empty, non-nil slice and a nil error.
    - A scope with one record returns an empty slice — a single record has no partner.
    - A scope with two near-identical records returns exactly one pair, not two, and its score is the cosine similarity Qdrant reports.
    - A record is never paired with itself.
    - Every record in the scope is queried: with N records the implementation issues exactly one query per record, batched.
    - Records outside the requested scope never appear in a pair.
    - The returned slice is sorted by score descending, with a deterministic tiebreak on the pair's ids so two runs over the same data produce identical ordering.

  <action>
Add `NearDuplicates(ctx context.Context, opts NearDuplicateOptions) ([]DuplicatePair, error)` to
`internal/store/spine.go`, with `NearDuplicateOptions{Scope string; TopK uint64; MinScore float32}`
and `DuplicatePair{A, B string; AShortID, BShortID string; Score float32}`.

Implement the exhaustive path RESEARCH.md verified, not the Search Matrix shortcut. First enumerate
every point id in the requested scope with `client.Scroll`, requesting neither payload nor vectors, so
the id set is cheap and complete — this enumeration is what lets the report claim whole-spine
coverage. Then chunk the ids and issue `client.QueryBatch` with one `QueryPoints` per id, each using
`qdrant.NewQueryID` so Qdrant resolves the query vector server-side from the point's own stored
vector: no text is re-embedded and no vector is transmitted from engram. Each `QueryPoints` carries a
`Must` scope match and a `MustNot` `NewHasID` on the querying id so a record never matches itself.

Do NOT use `SearchMatrixPairs` or `SearchMatrixOffsets`. Their `sample` parameter carries no
documented guarantee of exhaustive or deterministic coverage (RESEARCH.md Pitfall 4), and this
command's whole claim is that every record was checked.

Collapse the two-sided results: the sweep naturally produces both (A,B) and (B,A), so key the
accumulator on the ordered-by-id pair and keep one row. Apply `MinScore` as a filter after collapsing
and `TopK` as the per-query neighbour limit. Sort by score descending with a deterministic tiebreak on
(A, B) so the output is stable across runs.

Follow `ScanSpine`'s span and telemetry boilerplate with op name `NearDuplicates`, take no `Subject`
parameter, and add no owner or shared condition.

Extend `internal/store/spine_test.go` with integration coverage for every behavior-list row. Include
an explicit assertion that no write RPC is issued: capture the collection's point count and payload
digest before and after the call and assert both are unchanged.
