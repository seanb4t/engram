<objective>
Give `internal/setup` a plugin-delivery lane parallel to registration: a `PluginRuntime` optional
interface that claude-code and codex implement in their own files (probe argv, JSON parse, coarse
marketplace parse, authored write argv), a shared content-blind executor in `plugin.go` that runs ONE
`plugin list --json` read probe for capability AND state (D-10), the `marketplace list` read probe
(D-11), classifies absent / outdated / current with a stdlib SemVer-core comparator (D-01, D-03),
authors exactly the argv preview needs (D-02, D-04, D-05, D-06), and under apply runs the decided
actions through the same `runSeam` bound as every registration exec. A probe failure is
`unavailable` with a reason — never a failed outcome (D-12).

Purpose: REQ-plugin-capability-detection needs capability distinct from binary-on-PATH;
REQ-plugin-three-way-state needs a content-aware comparison the registration executor's blind
byte-compare cannot express (03-RESEARCH.md Summary); REQ-plugin-install-or-update needs exact
argv beforehand and zero writes when current. Plan 03-03 composes this lane into the report row and
the skills routing; plan 03-04 renders the claude-code argv into `/engram-setup`.

Decision applied (orchestrator, Open Question 1): plugin actions are authored per runtime in the
runtime's own file and carried on the plan-lane vocabulary (`PluginRuntime.PluginActions`), NOT
interleaved into `Plan.Actions` — one `execute()` sequence cannot report a `wrote` registration
beside a `failed` plugin install (REQ-plugin-facet-reported), so the plugin lane executes its own
authored actions through the same `runSeam` and reports its own outcome. `execute()` is untouched.

Output: `PluginState`, `PluginRuntime`, `PluginResult`, `PluginPreview`, `PluginApply`,
`classifyPluginVersion`, the claude-code and codex implementations, and four tests. One new
production file, one new test file, zero new dependencies.
</objective>
