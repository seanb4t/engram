<objective>
Make the shared verifier real at the process level and give an operator an explicit, default-off
switch to mount Connect on a headless deployment.

Three things ship together here because they are one wiring decision: the chain is built **once**
and injected into both mount sites so drift is impossible by construction (D-06); `connect.headless`
becomes a first-class `ENGRAM_` registry key (D-10); and the mount decision is composed from two
independent booleans upstream of `mountConnect`, whose capability gate is never touched (D-12),
with a startup refusal when headless is set and no auth lane exists (D-11).

Purpose: closes RESEARCH.md Pitfall 4 (two independently-constructed chains drift) and Pitfall 5
(a headless mount silently flips a deployment's exposure on upgrade).
Output: the `connect.headless` config key, `buildAuthChain`, `connectHeadlessGuard`,
`connectResolverFor`, and the refactored `withAuth`.
</objective>

## Flagged Assumptions

1. **Probe edge `REQ-connect-headless-mount` / `ordering` — unresolved, judged inapplicable.** The
   probe asks "when elements compare equal, is output order specified and stable?" A single boolean
   mount decision produces no multi-element output whose tie-break order could vary. The one
   ordering-shaped question that *is* real for this requirement — what happens when `ui.enabled` and
   `connect.headless` are both set — is the `adjacency` probe, resolved above as the
   `TestConnectResolverForBothLanes` criterion. Surfaced rather than dropped; a reviewer who
   disagrees should read the adjacency criterion as its answer.
2. **No Helm chart value is added for `connect.headless` in this phase.** `charts/engram/values.yaml`
   enumerates operator-facing env vars (e.g. `ui.enabled` at `:141`), so a chart entry is the natural
   follow-on, but no source artifact for this phase asks for one: CONTEXT.md's deferred section
   scopes Phase 1's documentation obligation to `docs-site` `guides/configure.md` only, and STATE.md
   records that `task chart:validate` is a required CI check no phase gate runs. Filed as a
   follow-up issue in Plan 04 rather than planned here.
3. **`buildAuthChain` returning `(nil, nil)` is not an error case.** Two callers read that nil
   differently — `withAuth` treats it as "MCP validation disabled, log loudly" (unchanged behavior)
   while `connectHeadlessGuard` treats it as fatal when the headless flag is set. The nil is the
   shared signal; if a future lane needs to distinguish "no lane configured" from "construction
   failed", the second return value already carries that.
