<objective>
Wire one path end-to-end: a headless caller presents a bearer credential to the ConnectRPC
lane, the server verifies it through an injected expiry-enforcing verifier, records **which
lane** authenticated the request as a typed value, and the CSRF interceptor decides its
exemption from that record alone.

This is the phase's tracer slice and its security core. The lane-provenance stamp and the
CSRF exemption that reads it are **one atomic unit** (ROADMAP "why these four ship
together"): shipping the stamp without its reader would land a value nothing consumes.

Purpose: closes two defect classes that are invisible to a green test suite — `Expiration`
written by the verifier chain and read by nothing on this lane, and a CSRF exemption that
could be inferred from attacker-controlled request content.
Output: `internal/auth`'s transport-agnostic bearer policy, the Connect adapter and composed
resolver, the typed lane context key, and the lane-gated CSRF exemption.
</objective>

<assumption_delta_decision>
The detector fired `pluralization` on this phase scope, and the substantive delta is real: the
Connect lane has had exactly **one** identity mechanism (the session cookie) since it was
introduced, and this phase adds a second (bearer). The question the checkpoint asks — does the
current identity model still name the right noun? — has a concrete answer here.

- **Primary noun (generalized):** `auth.Lane` — *which credential family verified this request*.
- **Decision: `promote`.** The lane is promoted to an explicit, typed, compiler-enforced third
  return value on the resolver contract, and "cookie" is demoted to one variant of it
  (`auth.LaneCookie`). Every downstream cookie-lane side effect is re-keyed off the generalized
  noun rather than off "is there a cookie": the CSRF exemption (D-08) and session re-sealing
  (D-09) both branch on `auth.Lane` and on nothing request-derived. `auth.LaneUnknown` is the
  zero value and is invalid, so a future third lane cannot be added without declaring itself —
  the generalization cannot silently regress to the singular assumption.
- **Not `add-alongside`.** The rejected shape was carrying the lane as a key inside
  `mcpauth.TokenInfo.Extra` beside the existing owner claim, which would have left the old
  cookie-shaped assumption primary and the lane an optional detail a resolver could forget.
  CONTEXT.md D-07 rejected it for exactly that reason.
- **Invariant test encoding the generalized intent:** `TestCSRFLaneUnstampedFailsClosed` (Task 2)
  goes red the instant any future resolver returns an undeclared lane, and
  `TestResealGatesOnCookieLane` (Plan 02) goes red if a cookie-lane side effect is re-keyed off
  cookie presence again.
</assumption_delta_decision>
