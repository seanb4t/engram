Add a `### Headless Connect lane` subsection to `guides/configure.md`, placed after the
`### Service principals (machine-to-machine)` subsection and before `## Logging`, matching the
surrounding four-column table format (`Environment variable | Flag | Default | Description`) used by

The table row documents `ENGRAM_CONNECT_HEADLESS`, flag `--connect-headless`, default `false`, and a
description stating it mounts the ConnectRPC lane on a deployment with the web UI disabled.

The accompanying prose must state four things an operator needs and cannot infer:

  - The flag defaults **off** and is independent of every `ENGRAM_UI_*` and `ENGRAM_SERVICE_AUTH_*`
    variable. A deployment that has no Connect surface today gains none on upgrade, including one
    that already has service-auth configured — configuring an auth lane never mounts Connect by
    itself.
  - Connect is mounted when the web UI is enabled **or** this flag is set. With both, one lane
    serves both credential types: a well-formed `Authorization: Bearer` credential authenticates
    against the same verifier chain the MCP lane uses, and everything else falls through to the
    session-cookie lane.
  - Setting it with no auth lane configured (no `ENGRAM_OIDC_ISSUER` and no `ENGRAM_SERVICE_AUTH_*`)
    **refuses to start**, because mounting would expose every write RPC unauthenticated into the
    anonymous empty-owner bucket. Name the two ways to configure a lane.
  - A bearer-authenticated Connect caller is exempt from the `X-CSRF-Token` double-submit check that
    cookie-authenticated browser callers must satisfy; the exemption is decided by which lane
    verified the request, never by which headers the caller sent.

Close the subsection with a `Source:` line in the file's existing style naming
`internal/config` (the `connect.headless` registry row), `cmd/engram/serve.go`
(`connectHeadlessGuard`, `connectResolverFor`), and `internal/server/connectbearer.go`.

Correct the two now-stale `Source:` attributions in the sections above: the `## OIDC / Auth` line and
the `### Service principals (machine-to-machine)` line both credit `withAuth` with chain
construction, which moved to `buildAuthChain` in Plan 03. Update both to name `buildAuthChain`, and
note in the `## OIDC / Auth` line that token expiry is now enforced by `auth.EnforceExpiry` on the
composed chain rather than only inside the MCP bearer wrapper.

Do not document the CLI client, its flags, or its exit codes — that surface is v0.12.x Phase 2 and
does not exist yet. Do not add a Helm values entry; that is Task 2's follow-up issue.
