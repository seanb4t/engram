<objective>
Collapse the CI `test` job's four concurrent Qdrant testcontainers into one shared instance, and make
a container death produce evidence instead of a connection-refused cascade.

Purpose: `go test ./...` runs packages concurrently, so a 2-vCPU runner can be hosting four
`qdrant/qdrant:v1.18.2` instances at once. `internal/store` dies while its siblings pass, and the
resulting cascade buries whatever really failed. Removing the resource pressure at its source is the
fix; capturing the exit reason is what makes a recurrence diagnosable rather than inferred.
Output: a `services:` Qdrant on the `test` job, the shared-address env var, the store/server
collection-name collision resolved, a one-container assertion, and an on-failure diagnostics step.
</objective>

a `docker inspect` of the image's healthcheck config and record the answer in the SUMMARY.

blocks steps until the declared health check passes and tears the container down automatically; a

leaves this choice to planning discretion and this is the resolution.

Add two steps to the `test` job.

**The one-container assertion (D-20).** A step that runs before `go test` and fails the job unless
exactly one container from the pinned Qdrant image is running. Count with a Docker filter on the
image ancestor, emitting one id per line, and compare the count to 1. This is the mechanism
assertion: the fix's claim is "one container instead of four", and this makes that claim a gate
rather than a description. Echo the resolved `ENGRAM_QDRANT_TEST_ADDR` in the same step so the job
log records which address the suite will use — that is the second of D-20's three checkable claims.
Do not use `2>/dev/null || echo 0` style fallbacks in the count: a suppressed failure that defaults
to a passing comparison is a gate that certifies while measuring nothing.

**The diagnostics post-step (D-19).** A step guarded by `if: failure()`, placed after the test step,
that dumps: the Qdrant container's state and exit code from a Docker inspect scoped to the pinned
image; the tail of that container's logs, bounded to a fixed number of lines; and kernel OOM evidence
filtered out of `dmesg`. This runs on the runner rather than inside the Go process on purpose — when
the container dies mid-run, the Go side often cannot reach it either, so in-process capture yields
nothing in exactly the case that matters most. Directly answering "was it OOM-killed" is the point:
that hypothesis is the one the existing diagnosis leaves open.

Bound and scope the dump. Emit only the Qdrant service container's own inspect output and log tail —
never a full `docker ps -a` dump of every container on the runner, never the job environment, never
`printenv`. CI job logs are readable by anyone who can see the PR. Pass any workflow expression value
through `env:` rather than interpolating it into the shell body, mirroring the `ui-drift` job's
existing convention and the comment there that names the hazard. Every command in the step tolerates
its own absence (a missing container, an unreadable `dmesg`) without failing the step — a diagnostics
step that fails masks the real failure it was added to explain.

Add a short comment block above both steps explaining what they assert and why the assertion is the
mechanism rather than a run count, so a future reader does not "simplify" them away.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → the Qdrant service container | Job steps reach a network service the workflow declares; the runner's Docker daemon controls its lifecycle. |
| Qdrant container logs and kernel `dmesg` → the CI job log | On failure, container-produced text is emitted into a log readable by anyone who can see the pull request. |
| four concurrently-running test packages → one shared Qdrant | Package isolation that used to be enforced by separate containers is now enforced only by collection naming. |
