## Decisions this plan settles (RESEARCH.md's two open questions, plus proseTargets)

### Open Question 1 — the reactive trigger is prose-only, not a hook. DECIDED.

Not a preference; the hook mechanism cannot express the decision.

- D-03 fires the reactive path **only** when staleness is visible from what the agent already has
  open — "the recalled record cites a file or commit the agent already has open or just read, and
  plainly contradicts it." That is a judgment over the agent's own live context.
- A `PostToolUse` hook is an external process. It has no access to the agent's open context, so it
  cannot evaluate that condition. The most it can do is inject a blanket nudge after **every**
  matching tool call — which is precisely the nag D-03 exists to prevent and the failure mode
  CONTEXT.md spends a paragraph guarding against.
- Supporting evidence, not the reason: `skill/engram/hooks/hooks.json`'s only `PostToolUse` matcher
  is `Edit|Write|NotebookEdit`, so the existing capture-nudge precedent does not even fire on recall
  tools. A recall-matching hook would be new surface, not a reuse.
- Consequence: no file is added under `skill/engram/hooks/`, `hooks.json` is unchanged, and no new
  pytest file appears in `skill/engram/hooks/tests/`. RESEARCH.md's Wave 0 item for this resolves to
  "no new test surface needed."
- Reversibility: `reversible`. A hook can be added later; nothing published depends on its absence.

### Open Question 2 — `distinct` is recorded as an `update_memory` tag. DECIDED, with a stated limit.

- CONTEXT.md deferred this only "if it needs a store change." It does not: `update_memory` already
  accepts `tags`, so the convention is achievable in pure prose with zero server change.
- **The `rule-declined` precedent is not directly reusable here.** `curating-memory` records a
  decline by storing a *new* `category: decision` memory — which requires `store_memory`, a tool
  outside the six this phase is allowed to call. So the analogous shape is a tag on an existing
  record, not a new record.
- Convention: tag the record whose `short_id` sorts lexicographically first with
  `spine-distinct-<other short_id>`. One tag write per `distinct` verdict, deterministic, and it
  names the specific counterpart so it cannot over-suppress unrelated future pairs. The character
  class matches the existing `rule-declined` convention (lowercase, hyphens) plus a Crockford base32
  short id — no tag grammar is invented.

#### The exact MCP call shape — corrected after review, re-verified against source

Cross-AI review found the originally-planned call **invalid on the MCP lane**. The premise was
re-checked directly this session and holds. Read `internal/server/tools.go:823-841` and
`internal/server/summary.go:23-37` before writing this prose:

- `validateUpdateArgs` rejects `a.Content == nil` with
  `argErrf(classMalformed, HintRequired, "content", "content is required")` — i.e.
  `field=content hint=required`. Its doc comment states it is called **ONLY** from the
  `update_memory` MCP closure, never from `deps.updateMemory`, because the Connect protoconv
  field-mask lane legitimately updates with a nil content. **A tag-only update is legal on Connect
  and illegal on MCP**, and the skill uses the MCP lane. That asymmetry is why this slipped through.
- `deps.updateMemory` computes `contentChanged := a.Content != nil && *a.Content != cur.Content`.
  Resending content **byte-identical** therefore leaves `contentChanged` false. That matters:
  `resolveSummaryUpdate` refuses an update that changes content while stranding a
  `summary_source=client` summary (`errStaleSummary`, a failed-precondition). Byte-identical content
  keeps a caller-authored summary preserved silently and keeps the call legal without sending a
  `summary` at all.

So the required sequence, which the skill prose must state as five ordered steps:

1. `mcp__engram__get_memory` on the chosen record (already mandated for judging the pair).
2. Take its `content` **exactly** as returned. Do not reflow, re-wrap, trim, or "tidy" it — an
   altered byte makes `contentChanged` true and can turn a metadata write into a rejected one.
3. Take its current `tags` and compute the union with the new marker.
4. Call `mcp__engram__update_memory` with **both** the unchanged `content` and the full replacement
   tag set.
5. Send no `summary`. Content is unchanged, so a caller-authored summary is preserved untouched;
   sending one would be an unrequested second mutation riding on a consented first.

- **Second correction: this is not pure metadata bookkeeping.** A tags-only change still re-embeds,
  because tags are part of the embedded document — `internal/server/tools.go:1682-1703` routes any
  content-or-tags change through `d.em.Embed(ctx, store.EmbedText(contentToStore, tags))` and its
  comment says so explicitly ("This re-embeds even on a tags-only change"). Consequence the prose
  must carry: writing the marker shifts the record's vector slightly and can change which pairs
  `consolidate` ranks highest on a future sweep. That is acceptable — the marker is a real semantic
  fact about the record — but the user is entitled to know the write is not free before saying yes.
- Consent: the tag write is a mutation, so it is a batch item like any other, with its own yes. One
  `distinct` judgment about one pair produces exactly one write, so this is not the batch-approve
  shortcut D-10 forbids.
- **The pre-proposal check reads BOTH records, and it reads them from `get_memory`.** The
  consolidate row carries no tags at all — `consolidatePairDoc` is exactly `a`, `b`, `a_short_id`,
  `b_short_id`, `a_scope`, `b_scope`, `score` (`cmd/engram/spine_review_consolidate.go:139-147`,
  verified). Checking only the lexicographically-first record is also insufficient: if that record
  is later superseded the marker travels with it, so the counterpart is the only place the pair's
  history may still be visible. Check either record for a tag naming the other.
- **Stated limit, not papered over:** a *declined* proposal has no durable record here, because that
  would need `store_memory`. Within a session, step 3's "ask once, then stop" covers it; across
  sessions it does not persist. The skill must say so plainly. This is the residual part of
  CONTEXT.md's deferred "recording a `distinct` judgment durably" item and stays deferred.
