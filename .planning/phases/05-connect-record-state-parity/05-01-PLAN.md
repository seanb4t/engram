<commit_range_protocol>
Three acceptance criteria below assert something about THE CHANGE THIS TASK MADE. They must not be
spelled over the bare working tree.

Why: `execute-plan.md:194` commits the task as part of completing it, and only THEN does the HARD
GATE at `:197-203` run the acceptance loop; the SUMMARY self-check at `:158-159` re-runs ALL
acceptance criteria later still. At both evaluation points the working tree is CLEAN, so a bare
`git diff <path>` is EMPTY and every negative gate over it passes unconditionally: `rg` matches
nothing in empty input, exits 1, criterion "satisfied", regardless of what the change did.

Protocol, performed by you at the START of every task below, BEFORE your first edit:

1. Run `git rev-parse HEAD` and record the 40-character SHA. Call it TASK_BASE.
2. Shell variables do NOT persist between tool calls in this runtime (verified). Do not write
   `$TASK_BASE` and expect it to be set — substitute the LITERAL SHA into every command below.
3. Quote the recorded TASK_BASE SHA in the SUMMARY so the criteria you ran are reproducible.

Spelling: `git diff <TASK_BASE> -- <paths>` — base against the WORKING TREE, with NO `..HEAD`. This
sees committed AND uncommitted changes, so ONE command serves both the post-commit acceptance gate
and the working-tree GATE-RED PROOF. See `<review_cycle_3_incorporation>` for why `..HEAD` was
rejected.

NON-EMPTY IS MANDATORY: each such criterion FIRST asserts the range diff is non-empty (`[ -s ... ]`).
An assertion whose input can legitimately be empty must state that emptiness is a FAILURE, or it
degrades straight back into the vacuous gate this protocol exists to remove.

Plan-level `<verification>` uses PLAN_BASE — the same SHA as task 1's TASK_BASE, since nothing
commits between plan start and task 1.
