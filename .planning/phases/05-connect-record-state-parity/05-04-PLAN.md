## G-05-9 (severity: minor) — from 05-UAT.md test 9

**Truth that failed:** "The embedded operator-console bundle is internally consistent: every asset
`index.html` references under `_app/immutable/**` exists in the embedded FS and is actually served,
so a `task ui:build` regeneration cannot ship a stale chunk reference."

**Reason:** Phase 05 commit `33a6a8c5` ("rebuild embedded web UI for regenerated Connect TS types")
was a plan-mandated drift commit that rewrote `internal/webauth/static/index.html` and every hashed
`_app/immutable/**` chunk filename. Nothing observes that rewrite. The user reported: *"we should
have an e2e test for this."*

**Why all three existing test layers miss it — the crux of this plan:**

| Layer | Why it cannot see the gap |
|-------|---------------------------|
| `go test ./...` | Never renders anything. The bundle is a static asset; a dangling chunk reference stays green forever. |
| `ui/`'s Vitest browser tests (~10 `*.browser.test.ts` driving real headless Chromium) | Mount components in isolation FROM SOURCE, served by **Vite**. They never load `index.html`, never request `_app/immutable/**`, and never go through the Go server. They pass on a build whose `index.html` points at a chunk absent from `embed.FS`. |
| `internal/e2e` | Boots the real binary but speaks HTTP/MCP only — no DOM. |

The gap is precisely the seam none of them cross: **the real Go server serving the real embedded
bundle to a real browser.**

**Prior art — this class is not hypothetical.** GH #106: a bare `//go:embed static` excluded `_app/`
(go:embed skips names beginning with `_` or `.`) and left the SPA unable to mount. The `all:` prefix
at `internal/webauth/static.go:18` is the fix for that incident, and nothing guards it.

**The UAT's own `missing:` item** (satisfied here as a supplementary assertion inside the rendering
test, per G9-D3): "A test that parses index.html … extracts every `_app/immutable/**` reference,
asserts the extracted set is NON-EMPTY … and requests each one … asserting 200 and a non-empty body."
</gap>

<verified_facts>
Everything below was read out of this tree or resolved against upstream during planning. Treat it as

**1. The console is behind a real OIDC issuer at BOOT, not just at login.**
`cmd/engram/serve.go:184-218`: when `uiCfg.Enabled`, startup calls
`webauth.NewAuthenticator(oidcCtx, uiCfg.Issuer, …)` with a 15-second timeout, and that calls
`oidc.NewProvider` → an HTTP GET of `{issuer}/.well-known/openid-configuration`. **The UI cannot be
enabled against an unreachable issuer.** So a discovery stub is REQUIRED — the cheap-path hope of
"just skip OIDC entirely" does not survive contact with startup. The stub only needs the discovery
document; no JWKS fetch, no token exchange, because the test never performs a login.

`go-oidc v3.20.0` (`oidc/oidc.go:167-175, 301, 321-336`) reads exactly
`issuer`, `authorization_endpoint`, `token_endpoint`, `device_authorization_endpoint`, `jwks_uri`,
`userinfo_endpoint`, `id_token_signing_alg_values_supported`, and hard-fails unless the document's
`issuer` string EQUALS the configured issuer byte-for-byte. `httptest.NewServer` yields
`http://127.0.0.1:PORT` with no trailing slash — echo `srv.URL` back as `issuer`.

**2. Activation requires four creds plus an issuer** (`cmd/engram/uiconfig.go:42-84`):
`ENGRAM_OIDC_CLIENT_ID`, `ENGRAM_OIDC_CLIENT_SECRET`, `ENGRAM_UI_REDIRECT_URL`,
`ENGRAM_UI_COOKIE_KEY` must all be non-empty; the issuer comes from `ENGRAM_UI_ISSUER` falling back
to `ENGRAM_OIDC_ISSUER`. **Set `ENGRAM_UI_ISSUER` and leave `ENGRAM_OIDC_ISSUER` unset** so the MCP
bearer lane stays anonymous and no second stub is needed. `ownerClaimGuard`
(`cmd/engram/serve.go:348-362`) is satisfied by the registry default owner-claim (`email`).
`ENGRAM_UI_REDIRECT_URL` is never dereferenced on this path — a static
`http://127.0.0.1/auth/callback` is sufficient, which sidesteps the chicken-and-egg of needing the
server's port before `startServer` picks it.

**3. `ENGRAM_UI_COOKIE_KEY` decoding** (`cmd/engram/uiconfig.go:92-106`) tries hex FIRST. Generate 32
random bytes, hand the server `hex.EncodeToString(key)` (64 chars), and keep the raw 32 bytes in the
test for `webauth.NewSessionCodec`.

**4. The session cookie is mintable from `internal/e2e`.** `webauth.NewSessionCodec([]byte)` and
`(*SessionCodec).Seal(Session)` are EXPORTED (`internal/webauth/session.go:48-80`), and `Seal`
overwrites `Session.V` with the current payload version itself, so the test never stamps a version.
`Session{Owner, Expiry}` is all that is needed. The cookie NAME is `sessionCookieName =
"engram_session"` and is UNEXPORTED (`internal/webauth/handlers.go:17`) — the test restates the
literal in a named constant with a comment pinning it to that line, and a key link binds the two.
The alternative (a full stub OIDC login dance) is NOT needed and must not be built.

**5. `Resolver.Resolve` rejects an empty owner** (`internal/webauth/resolver.go:64-66`). A cookie
session therefore ALWAYS has a non-empty owner, which is why the fixture record must be written by
that same identity rather than through the anonymous MCP lane — an MCP-written record lands in the
`owner==""` bucket and would be invisible to the console. Writing over Connect with the cookie is
what makes writer and reader one identity.

**6. The Connect write lane needs the CSRF double-submit** (`internal/server/connectcsrf.go:100-109`):
the `engram_csrf` COOKIE and the `X-CSRF-Token` HEADER must both be present, be equal, and verify
against the owner. Both are derivable in-test: `webauth.DeriveCSRFKey(key)` →
`webauth.NewCSRFSigner(k)` → `.Token(owner)`. Names come from the exported
`webauth.CSRFCookieName` / `webauth.CSRFHeaderName` (`internal/webauth/csrf.go:21-24`). READ RPCs are
never CSRF-gated (`connectcsrf.go:62-64`), so the browser needs only the session cookie — but inject
both anyway, for production fidelity.

**7. Connect client precedent already exists in-repo:**
`internal/server/connectapi_cookie_test.go:65-72` —
`engramv1connect.NewEngramServiceClient(http.DefaultClient, baseURL)` then
`connect.NewRequest(&engramv1.ListMemoriesRequest{…})` with `req.Header().Set(…)`. Copy that shape.
`StoreMemoryRequest` (`proto/engram/v1/engram.proto:160-171`) is
`{content, scope, source, category, tags, repo, workspace, worktree, base_dir, summary}`; `category`
is constrained to `decision|preference|convention|gotcha`; the response carries `id` and `short_id`.
`ListMemoriesRequest.scope` has NO `min_len`, which is why the console's `scope: ''` call works.
An existing e2e scope literal shape is `repo:e2e-roundtrip` (`internal/e2e/boot_test.go:191`).

**8. What the console actually renders.** `ui/src/routes/+page.svelte` issues `listScopes({})` and
`listMemories({scope:'', limit, offset, categories:[], visibility:''})`, then renders
`<h1>engram — operator console</h1>` and a `MemoryList`. `MemoryRow.svelte` prints
`stripCategoryPrefix(memory.summary, memory.category)` as the row's primary text. **`h1` exists only
after hydration — the shipped `index.html` contains that same string only inside `<title>`, never as
an `h1`.** There is NO `data-testid` on a memory row; there is one on the loading skeleton
(`data-testid="list-loading"`). This plan does NOT add a testid, because the record's unique summary
marker is a strictly stronger hook: it cannot exist in the shell, cannot exist in the JS bundle, and
appears only after bundle + hydration + auth + a live ListMemories round trip all succeed. Leaving
`ui/` untouched also keeps the vendored bundle out of this plan's diff.

**9. Static serving.** `internal/webauth/static.go:25-51` (`StaticHandler`) is mounted at
`mux.Handle("/ui/", http.StripPrefix("/ui/", …))` (`cmd/engram/serve.go:253`). A GET of `/ui/`
strips to `""` → `index.html`. The shipped `index.html` declares nine `modulepreload` links plus one
stylesheet, all under `/ui/_app/immutable/`, and bootstraps via a dynamic `import()` of
`entry/start.*.js` and `entry/app.*.js`.

**10. chromedp API, verified against `v0.16.0` this session (`go doc`, real module):**
- `chromedp.NewExecAllocator(parent, opts...) (context.Context, context.CancelFunc)`;
  `chromedp.NoSandbox` is an `ExecAllocatorOption`. `DefaultExecAllocatorOptions` ALREADY includes
  `Headless` and `disable-dev-shm-usage`, and auto-adds `--no-sandbox` ONLY when running as uid 0 —
  GitHub runners run as a non-root user, so `NoSandbox` must be passed explicitly (Ubuntu 24.04
  restricts unprivileged user namespaces, which is what breaks the Chrome sandbox on that image).
- `network.SetCookie(name, value) *SetCookieParams` with `.WithDomain/.WithPath/.WithSecure/
  .WithHTTPOnly/.WithSameSite`, and `Do(ctx) error` — a SINGLE return value in this version. Run it
  inside a `chromedp.ActionFunc`.
- `chromedp.Poll(expr string, res *bool, opts...)` with `chromedp.WithPollingTimeout` /
  `WithPollingInterval` — returns an error on timeout (fail-closed).
- `chromedp.ListenTarget(ctx, func(ev any))` — the callback runs SYNCHRONOUSLY on the event
  goroutine, so shared state it writes MUST be mutex-guarded and it must never block.
- chromedp enables `runtime`, `log`, `network`, `page`, `dom`, `css` by default
  (`chromedp.go:445-465`), so `network.EventRequestWillBeSent`, `network.EventResponseReceived`,
  `network.EventLoadingFailed` and `runtime.EventExceptionThrown` all arrive with no extra setup.
  `EventLoadingFailed` carries only a `RequestID` — correlate it to a URL by recording
  `EventRequestWillBeSent.Request.URL` per `RequestID`.
