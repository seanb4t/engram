## Ruling

### PD-07 — maximum target count — **DROPPED**

**Chosen: `no-cap`.** There is no maximum target count. The input stays unbounded exactly as it is
today.

Binding consequences for implementing plans, stated so no executor has to infer them:

- **Plan 03 (03.1-03)** MUST NOT introduce a `maxSupersedeTargets` constant, and MUST NOT include a
  set-length branch in validation class 1. Class 1 checks set shape only: empty array and blank
  entry. It names the argument, never a value, and never a length.
- **The generated MCP JSON schema** for `supersedes` gains `minItems: 1` **only**. No `maxItems`
  constraint is emitted, and no test may assert one.
- **Plan 05 (03.1-05)** MUST NOT publish a maximum target count in `reference/tools.md` or any other
  surface. There is no number to document.
- No new externally-visible rejection is added to previously-unbounded input. Every call that
  succeeds today on set shape continues to succeed on set shape.

Rationale as ruled: a cap is not a correctness control. CONTEXT.md D-15 already declined the hard
cap at 32 and chose the reconciliation pass as the single mechanism covering both the within-chunk
and cross-chunk partial-failure classes; any cap above 32 closes nothing. This ruling keeps
reconciliation as that single mechanism.

**Accepted residual risk (T-03.1-05, Denial of Service, medium):** a single authenticated caller can
still drive an arbitrarily large resolve/lock amplification — two sequential Qdrant round trips
(`ResolvePointID` at `store.go:1530`, then `FetchForUpdate`) plus one held in-process lock per
target, for the whole operation. This is accepted knowingly rather than mitigated by a bound. It is
not a silent gap: it was quantified in the plan and transferred to the developer, who declined the
bound.

### PD-06 — rejection class order and ambiguous short ids — **ADOPTED**

**Chosen: `collapse-ambiguous`.** Four classes, and no class before the ownership stage may say
anything about a specific record:

1. **Set shape** — empty array, blank entry. Names the argument, never a value. Runs before any
   store call. (No length branch — see PD-07.)
2. **Addressability and access** — resolution-not-found, resolution-ambiguous, fetch-not-found and
   not-owned ALL collapse into one class, reported as the existing not-found sentinel, naming every
   offending input as the caller spelled it.
3. **Rule immutability** — evaluated only over records the caller provably owns.
4. **Already superseded** — same.

Accepted cost, as ruled: a caller whose short id collides globally now receives "not found" rather
than "ambiguous", and must name that target by its full UUID. Short ids are minted with
collision-retry, so a collision means another owner holds the twin — precisely the case where the
detailed answer would be an existence oracle (T-03.1-01, Information Disclosure, high — mitigated by
this ruling).

`owner-filtered-resolution` and `report-ambiguous-early` were both considered and are NOT adopted.
No owner-filtered resolve method is added to the store in this phase.

### PD-01 — duplicates inside one target set — **ADOPTED**

**Chosen: `dedupe-silently`.** `[A, A]` and `[short_id_of_A, uuid_of_A]` both mean `[A]`. A repeated
target is not an argument error.

The dedupe pass runs over **resolved UUIDs**, not over the caller's spellings — this is mandatory,
not stylistic: the in-process locker is a non-reentrant `sync.Mutex`, so locking one target twice on
one goroutine deadlocks with no panic and no race-detector hit.

### PD-02 — heterogeneous merges — **ADOPTED**

**Chosen: `allow-heterogeneous`.** One merge may span scopes, categories and visibilities. There is
no homogeneity requirement and no rejection class for it. Every target remains independently
owner-gated, and `rule` stays excluded as a target for every target in the set.
