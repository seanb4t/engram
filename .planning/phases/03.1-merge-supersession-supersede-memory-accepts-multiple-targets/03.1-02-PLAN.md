<objective>
Close the failure class this phase creates: a multi-ID `SetPayload` that errors has, at the pinned
Qdrant version, already stamped every target it found. Detect that, compensate the survivor, and
reconcile the targets — then prove it against a real Qdrant with a forced mid-sequence failure.

The single multi-ID back-stamp call stays exactly as plan 03.1-01 wired it, per D-06 as revised: it is
retained as the fast, common path for its batching and its smaller race window, NOT as an atomicity
guarantee. This plan adds only what that revision obligates.

Purpose: without the reconciliation pass, a *failed* merge permanently soft-hides live records.
Targets stamped before the error keep a `superseded_by` pointing at an id the compensating delete
just removed; that value is non-empty, so all four `IsEmpty("superseded_by")` recall gates drop
those records from `search_memory`, `list_memory`, `search_discovery`, and `list_scheduled` forever.
This failure class did not exist at N=1 and is the correctness core of the phase, not hardening.

Output: a declared mutation fault seam, a classified reconciliation pass inside `Store.Supersede`'s
lock scope, an internal point-removal primitive for the survivor, a documented chunk-size constant,
and `TestSupersedeMultiTOCTOU` asserting both that the error surfaces and that no target is left
dangling.
</objective>

<claim_scope>
**The exact claim this plan proves, and the one it does not.**

Provable: *once a merge attempt has returned and its reconciliation succeeded, no partial merge state
remains* — the survivor is gone and no target carries a `superseded_by` pointing at it. When
reconciliation cannot complete, the original error is returned and every unresolved id is logged.

NOT provable, and therefore never to be written into a comment, a test name, a `must_have`, or a
published sentence: that a partially-applied merge is *never observable*. `TargetLocker` serializes
WRITERS only. Its two call sites are `Update` (`store.go:1749`) and `Supersede` (`store.go:2012`);
`Store.Get` (`store.go:1500`) and every recall query hit Qdrant without taking any lock. A concurrent
reader therefore CAN observe a predecessor soft-hidden in the window between Qdrant's partial write
and the reconciliation pass.

This narrowing came from cycle-1 cross-AI review and was verified directly against the working tree
before being accepted. ROADMAP SC3 and REQ-merge-atomicity were both rewritten to match on
2026-08-10. If a stronger claim is ever wanted, compensation is the wrong mechanism for it — that
would need a visibility or commit marker the four recall filters understand, which is a different
design and not this phase.
</claim_scope>

This task has three parts: declare the seam, route the write path through it, and replace plan 01's
minimal inline compensation with the classified reconciliation pass.

DECLARE THE MUTATION SEAM (internal/store/store.go).
Cross-AI review established that the failure branches this plan claims are not reachable from a test
without one. `Store.Supersede` takes its locks and `defer unlock()`s through the `SetPayload`, so
nothing a test does between entry and the back-stamp can create the window; and deleting a target
before the call is rejected by the method's own under-lock `getWritable`. Guessing at a trigger is
how a plan ends up with a green test that never exercised the branch it names.

The seam is NOT a new invention. This file already carries four function-var fields for exactly this
purpose, and `deletePayloadKeys`'s own doc comment states the rationale: `*qdrant.Client` is a
concrete type with no interface seam, so a function-var field is how a partial-failure path is
injected.

**One of the two seams already exists when this plan runs.** Plan 03.1-01 declares
`setPayloadKeys func(ctx context.Context, ids []string, kv map[string]any) error` with its
production default `defaultSetPayloadKeys`, and routes `Store.Supersede`'s back-stamp through it —
it had to, because its own compensation test has no reachable trigger otherwise. Verify that field
and its default are present and unchanged, and do NOT redeclare either. This plan adds exactly one
new field, in the same block and the same style:

- `deletePoint func(ctx context.Context, id string) error`, with a production default method named
  `defaultDeletePoint` issuing the raw `client.Delete` for one point id with `Wait` true.

Document it: it is the internal, UNGATED point-removal primitive used only for the survivor this
same call just created, and it exists for a second, independent reason — `Store.Delete` re-runs
`getWritable` with `authz.ActionDelete` (`store.go:2095`), which is a SECOND authorization decision
taken during rollback. A policy that permits create and write but denies delete would block
compensation and strand the orphan. Rollback correctness must not depend on a policy file. State
explicitly that this primitive MUST NOT be used for any caller-supplied id — the only legitimate
argument is `newMem.ID`, a record minted inside this call, never linked, never recallable by another
caller.

HOW A FUNCTION-VAR SEAM IS INVOKED — the one correct form, and the form that panics.
Cycle-2 review found the previous version of this plan mandating receiver-qualified calls on
nil-defaulted fields, and pinning those exact literals in `key_links`, which made the verification
gate and a safe implementation mutually exclusive. Both are corrected here.

There is no accessor method in this repo and you must not add one. `New` (`store.go:383-393`)
populates no function field, so on a production `Store` every one of them is nil and a
receiver-qualified invocation panics. The in-repo idiom — read it verbatim at `store.go:1912-1916`
and again at `internal/store/spine.go:812` — resolves the field into a LOCAL VARIABLE immediately
before the call: assign the field to a local, test that local against nil, assign the named
`default…` method to it in the nil branch, then invoke the local. Copy that shape, changing only
the names.

Local names, fixed so the gates can pin them: `setKeys` for `setPayloadKeys` (already established
by plan 01 — leave it), `delPoint` for `deletePoint`, and `clearKeys` for `deletePayloadKeys`.

REPLACE THE MINIMAL COMPENSATION WITH THE CLASSIFIED PASS.
Plan 01 landed an inline compensation block so no wave-2 commit could leave a dangling link. Lift it
into a named function with a classified result — do not leave two compensation paths.

Declare
`type supersedeReconcileResult struct { RemoveErr error; ReadFailures []string; ClearFailures []string; Dangling []string }`
and
`func (s *Store) reconcileSupersedeFailure(ctx context.Context, survivorID string, targets []string) supersedeReconcileResult`.

**Single ownership — the function performs BOTH halves and populates all four fields.** Cycle-2
review found the previous version splitting this: the caller removed the survivor and was told to
record the outcome "in the result's `RemoveErr`" before the value that carries `RemoveErr` existed.
A returned value cannot hold an error produced before the call that returns it. So:
`reconcileSupersedeFailure` removes the survivor FIRST — invoking the `delPoint` local, resolved by
the nil fallback, with `survivorID` — and stores whatever that returns in `RemoveErr`. It then
reconciles the targets, populating `ReadFailures`, `ClearFailures` and `Dangling`. The caller calls
it once and reads the result; the caller performs no removal of its own. Removal failure does NOT
abort reconciliation — an orphaned survivor and a dangling link are independent problems and the
operator needs both reported.

Resolve the `clearKeys` local ONCE, before the classification loop, not once per iteration. Then,
for each id in the FULL requested target set — not one chunk, not only the ids the failed call is
believed to have reached — read the record with `s.Get` and classify:
- read succeeded, `SupersededBy` is nil, empty, or points somewhere else → nothing to do;
- read succeeded and `SupersededBy` equals `survivorID` → clear the key by invoking `clearKeys`
  with the id and a one-element key slice holding `superseded_by`. On error, append the id to BOTH
  `ClearFailures` and `Dangling`;
- read failed with `ErrNotFound` → RESOLVED, not dangling. The target is gone, so nothing points
  anywhere. Do not report it;
- read failed with any other error → append to BOTH `ReadFailures` and `Dangling`. A transport
  failure means the state is unknown, and unknown must be reported as possibly-dangling rather than
  assumed clean. This classification is the difference between an operator who knows what to fix and
  one who does not, and it has its own test.

Clear by DELETING the key, never by writing an empty string: an empty value is still a value and the
recall gates test for key emptiness, so writing one leaves the record hidden. `Store.Restore`'s
`archived_at` removal is the in-repo precedent; confirm the mechanism against it.

In `Store.Supersede`, on a non-nil back-stamp error, capture it as the error to return, then, still
holding every lock:
1. call `reconcileSupersedeFailure` ONCE with the survivor id and the full deduped target set, and
   keep the single result value it returns. It owns both the survivor removal and the target
   reconciliation; delete plan 01's inline removal rather than keeping a second copy of it here;
2. if the result's `RemoveErr` is non-nil or its `Dangling` is non-empty, emit ONE
   `slog.ErrorContext` carrying the survivor id, the dangling ids, and the read/clear split as
   structured fields — never in the returned error;
3. return the ORIGINAL back-stamp error unchanged, preserving the existing single-fault envelope.

Carry plan 01's D-09 comment forward to the survivor-removal call site inside
`reconcileSupersedeFailure`, in these terms: "no
`delete_memory` in the merge path" means predecessor history is never destroyed; the compensated
survivor was never linked to anything, was never recallable by another caller, and carries no
lineage, so removing it destroys zero history. Without this comment a future reader will see a point
removal inside `Supersede` and "fix" it.

Add `const qdrantPayloadOpBatchSize = 32` near the top of the file with a doc comment stating: this
mirrors the pinned Qdrant server's own payload-operation batch size; the server chunks a multi-ID
payload write by this size and a later chunk can error after an earlier chunk has fully committed;
the target set is deliberately NOT capped at this value (D-15), so the reconciliation pass — which
re-reads the whole requested set — is the single mechanism covering both the within-chunk and the
cross-chunk partial-application classes; a Qdrant image bump must re-verify this number against the
new version's source. The constant exists to make the number visible; it is not a limit.

Update `Store.Supersede`'s doc comment. Two things go in and one comes out. Out: any language
promising that a failed merge wrote nothing. In: (a) compensation and reconciliation are best-effort
— they talk to the same Qdrant that just failed and degrade in exactly the outage that triggers them
— so a no-op is the usual outcome, not a guarantee; and (b) the scope of the guarantee is the
TERMINAL state after this method returns. Say plainly that the locks serialize writers only, that
`Get` and every recall query are lock-free, and that a concurrent reader can therefore observe a
soft-hidden predecessor inside the window between Qdrant's partial write and the reconciliation pass.
A future reader who believes the window is closed will build on a guarantee that is not there.
