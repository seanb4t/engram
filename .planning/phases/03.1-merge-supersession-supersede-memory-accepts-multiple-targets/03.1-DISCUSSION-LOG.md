## Atomicity boundary & the orphan survivor

| Option | Description | Selected |
|--------|-------------|----------|
| Targets only — leave the orphan, return the error | REQ satisfied literally; never deletes; store accretes junk on repeated failure | |
| Compensating delete of the orphan on stamp failure | Failed merge is a true no-op; puts a delete in the merge path | ✓ |
| Widen the boundary — preflight before Upsert | Shrinks the window to pure infrastructure failure | ✓ |

**User's choice:** *"2 seems to be the most _correct_ to me, and 'user perceived idempotent' because they can .. just do it again? What am I missing?"* — then, on the follow-up, combined 2 + 3.
**Notes:** Two genuine gaps were surfaced in response: (a) the compensating delete fails in exactly the outage that triggers it, so it is best-effort rather than contract; (b) the sharp case is retry-after-*unobserved*-success, not retry-after-failure — and preflight is what makes it fail clean with nothing created. Also established that "no `delete_memory` in the merge path" is about predecessor history, not about the `Delete` primitive.

## idempotency_key on this verb

| Option | Description | Selected |
|--------|-------------|----------|
| Keep unsupported; make the error self-explaining | Derived from existing state, no new machinery | |
| Support `idempotency_key` now | Replay returns the original survivor id | ✓ |
| Keep unsupported, error unchanged | Smallest surface | |

**User's choice:** *"why woudl we not want an idempotency key? what decision is being unwound if we went with 2?"* — then, once answered: support it, fingerprint over content + target set.
**Notes:** The question prompted a history dig. Finding: **nothing principled is being unwound.** WR-03/WR-04 were review findings that the code *claimed* to exclude the key but did not (the `json:"-"` shadow removes it from the advertised schema only, not the wire decode); the fix made the absence honest and tested. The real deferral was `plan T-25-10 deferred scope`. Also surfaced: Phase 25's own deferred list defers multi-parent supersession "revisit only if a real need appears" — Phase 03.1 is that revisit, and `idempotency_key` was cut in the same phase for the same reason. Costs named: a target-set-aware fingerprint (new logic, not reuse) and replay-check-before-preflight ordering.

An intermediate option was offered and not taken: when every target already points at one common successor, say so and name it — deriving "you already did this" from existing state with no machinery.
