<objective>
Support `idempotency_key` on `supersede_memory`, with the replay fingerprint keyed on content AND
the target set, and the replay check ordered before the already-superseded stage.

Purpose: a multi-target merge is exactly when an ambiguous failure is expensive. The retry that
matters is the one the caller did not see fail — the server succeeded and the response was lost. With
the replay check after the already-superseded stage, every such retry is rejected with a conflict the
caller cannot act on, and the key is never consulted. Ordered correctly, the retry returns the answer
it lost.

Output: `mergeFingerprint`, `checkIdempotentMergeReplay`, the unwinding of Phase 25's deliberate
absence, and three inverted tests that used to pin that absence.
</objective>

<decision_history>
This plan reverses no design principle. `plan T-25-10` deferred `idempotency_key` on this verb **for
scope**, not on principle. Phase 25's review findings WR-03/WR-04 established that the code *claimed*
to exclude the key but did not: the `json:"-"` shadow field removes `idempotency_key` from the
advertised schema only, never from the wire decode, because a field with no JSON name never enters
`encoding/json`'s same-name shadowing contest. The promoted field on the embedded struct stayed the
sole decode target, and it was the defensive clear at the top of the handler — not the shadow — that
actually made the field inert. The Phase 25 fix made the absence honest and tested; it never argued
the feature should not exist. D-12 closes the deferred scope.

Three existing tests exist solely to pin that absence and are inverted here, not deleted:
`TestSupersedeMemorySchemaExcludesIdempotencyKey`, `TestSupersedeArgsDecodePopulatesPromotedIdempotencyKey`,
and `TestSupersedeMemoryIgnoresIdempotencyKey`.
</decision_history>

<planner_decisions>
- **PD-09 — the fingerprint keys on RESOLVED target UUIDs, and the replay check sits after existence
  and ownership.** Resolved ids are the identity of the records, so a target named by short_id in the
  first call and by UUID in the retry is the same operation; this pairs with the dedupe decision
  (PD-01) so `[A, A]` and `[A]` also fingerprint identically. The cost is that resolution must happen
  first, which places the replay check after the addressability-and-access stage rather than at the
  very top of the handler. D-14's requirement is satisfied in full — the check precedes the
  already-superseded stage, which is the case D-14 names — and the motivating scenario is unaffected,
  because supersession never deletes a target, so a retry after an unobserved success always finds
  its targets.

  **The residual narrowing, stated as a contract rather than a footnote (review, MEDIUM).** A retry
  whose targets were deleted in the meantime, or whose ownership changed, does NOT replay: it is
  rejected as not found. That is weaker than ordinary idempotent-replay semantics, where the key
  alone determines the answer. It is a deliberate trade — replaying without re-checking ownership
  would let a key minted while the caller owned a record still act after they no longer do — and
  because it is deliberate it belongs in the published contract. Plan 05 carries the sentence into
  `reference/tools.md`; this plan carries it into `checkIdempotentMergeReplay`'s doc comment and
  pins it with `TestSupersedeMemoryReplayAfterTargetDeletedRejects`.

  Reversibility: reversible — the ordering is one statement's position between two existing calls,
  and the fingerprint input is one function's argument.
</planner_decisions>

THE LOSING RACER — the path that post-write re-read cannot cover.

1. Both callers clear `checkIdempotentMergeReplay` — neither sees a survivor yet.
2. Both clear plan 03's state validation.
3. Winner takes the target locks, `Upsert`s the survivor, back-stamps, returns.
4. Loser takes the locks afterward and is rejected by the under-lock already-superseded check at

The loser therefore never reaches `Upsert`, never reaches the post-write re-read, and gets
`ErrAlreadySuperseded`. The existing precedent at `tools.go:1036-1054` reconciles two writes that
both landed; it cannot turn a store-tier rejection into an answer. Something has to.

Add
`func (d *deps) resolveLostMergeRace(ctx context.Context, a supersedeArgs, targets []string, pointID string, supersedeErr error) (id, shortID string, err error)`
to `internal/server/tools.go`, beside `checkIdempotentMergeReplay`, and call it in exactly one place:
the error branch of the `Supersede` call. Its contract, in this order:

- `pointID` empty (unkeyed call) → return `supersedeErr` unchanged. The unkeyed path has no
  deterministic id to look up and this recovery must never fire there.
- `supersedeErr` does not satisfy `errors.Is(…, store.ErrAlreadySuperseded)` → return it unchanged.
  This recovery is scoped to exactly one rejection; every other store error propagates untouched.
- Otherwise `Get` the deterministic `pointID`:
  - **not found** → return `supersedeErr` unchanged. There is no winner to defer to, so the
    rejection stands. This is the case where the targets were superseded by some OTHER call.
  - **read error** → return that read error. Do not mask a transport failure as a conflict or as a
    success.
  - **fingerprint equals `mergeFingerprint(a.storeArgs, targets)`** → REPLAY. Return the persisted
    record's id and short id, nil error. A record already sits at the caller's own deterministic id
    carrying the caller's own fingerprint; the operation the caller asked for has happened, and
    returning the winner's persisted answer is the correct idempotent result.
  - **fingerprint differs** → this is a genuine conflict, not a lost race, and D-13 governs it
    here exactly as it governs the ordinary replay check: a mismatch is always a rejection, never a
    success. The same key is being
    reused for a different operation and the targets happen to be superseded already. Return the
