# Phase 03.1 Plan 02: Classified Reconciliation for Failed Multi-Target Supersede Summary

**`Store.Supersede`'s back-stamp-failure path is now a classified reconciliation pass — a `deletePoint` fault seam plus `reconcileSupersedeFailure` that removes the survivor through an internal ungated primitive, re-reads the FULL requested target set across every Qdrant payload-op chunk, clears dangling `superseded_by` links, and logs whatever it could not resolve — proved against a real pinned Qdrant (`v1.18.2`) with a forced mid-sequence partial-application failure.**

## Performance

- **Duration:** ~55 min (not precisely instrumented at start; includes three throwaway probe-program verifications against a live Qdrant before writing tests against real, not assumed, server behavior)
- **Tasks:** 3/3 completed
- **Files modified:** 2

## Accomplishments

- `deletePoint func(ctx, id) error` + `defaultDeletePoint` (raw, ungated `client.Delete`) declared on `Store`, following the exact `setPayloadKeys`/`deletePayloadKeys`/`mintCandidate` local-nil-fallback idiom (`delPoint := s.deletePoint; if delPoint == nil { delPoint = s.defaultDeletePoint }`) — never a receiver-qualified call, verified by a zero-count grep gate.
- `type supersedeReconcileResult{RemoveErr, ReadFailures, ClearFailures, Dangling}` and `func (s *Store) reconcileSupersedeFailure` replace plan 01's inline compensation block: single ownership of both survivor removal (`RemoveErr`) and target reconciliation, called exactly once from `Store.Supersede`'s back-stamp-error branch, holding every per-target lock the whole time.
- Classification is four-way per target: clearable (read succeeded, points at the survivor) → clear the key by deletion, never an empty-string write; not-found → RESOLVED, not reported; points elsewhere or never stamped → nothing to do; any other read error (a real transport/protocol failure) → possibly-dangling, reported in both `ReadFailures` and `Dangling`.
- `const qdrantPayloadOpBatchSize = 32` documents the pinned server's payload-op chunk size and is kept genuinely live via a `engram.supersede.multi_chunk` OTel span attribute, not merely referenced in comments.
- `Store.Supersede`'s doc comment rewritten to the narrowed, cross-AI-reviewed claim: compensation/reconciliation are best-effort (a no-op is the usual outcome, never a guarantee), and the provable scope is the TERMINAL state after the call returns — `Get` and every recall query are lock-free, so a concurrent reader can observe a soft-hidden predecessor mid-window. No sentence anywhere claims a partial merge is never observable.
- `TestSupersedeMultiTOCTOU` generalizes the single-target TOCTOU test to N=3 against the real pinned server: falsifies (Part 1) that a multi-ID `SetPayload` naming one missing id among three still mutates the existing points before erroring, then (Part 2) drives `Store.Supersede` end to end through the `setPayloadKeys` seam — forwarding a real subset through the production default and triggering the actual missing-id error via a second raw write, never an injected sentinel.
- REQ-merge-supersession store-tier N=3 coverage: `TestSupersedeMultiAlreadySuperseded` (single- and two-offender rejection via the typed `*MultiTargetError`, no survivor written), `TestSupersedeMultiRecallGate` (three-target merge soft-hides all three from List/Search, every one still fetchable with content intact), `TestSupersedeMultiChainKeepsSingleHead` (a merge does not resurrect a non-head record; the live head remains superseded).
