# Cross-AI Plan Review — Phase 03.1

Single-reviewer cycle (`--codex`). Codex received the full source-grounding prompt plus an
explicit correction brief: D-06 was falsified mid-flight, D-15's reconciliation pass is the
correctness core, and SC3/REQ-merge-atomicity now read "not observable" rather than

## Codex Review

## Summary

The five-plan decomposition is strong: tracer-first pluralization, failure reconciliation, authorization/error semantics, idempotency, then published-contract drift gates. It correctly abandons the falsified “multi-ID `SetPayload` is atomic” premise and recognizes that dangling `superseded_by` values are especially damaging because four recall paths filter on key presence.

However, the plans are not execution-ready. Plan 01 omits required interface/fake migrations. Plan 02 lacks a workable seam for forcing the actual mid-operation failure or compensation failure it claims to prove, and compensation cannot make partial state literally unobservable to lock-free readers. Plan 03’s proposed resolution algorithm contains an impossible step and retains an owner-agnostic ambiguous-short-ID disclosure. Plan 04 leaves its most load-bearing staging refactor undecided during execution. The invented 256-target cap is implemented three waves before human approval.

Overall risk: **HIGH** until these blockers are corrected.

## Strengths

- The revised atomicity analysis matches the real damage mechanism. `Search`, `SearchDiscovery`, `List`, and `ListScheduled` all suppress any record carrying the key, regardless of whether its successor exists: [store.go:954](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:954), [store.go:1054](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:1054), [store.go:1191](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:1191), and [store.go:1426](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:1426). Plan 02 is right that merely deleting the survivor would permanently hide stamped predecessors.

- Plan 01 correctly treats pluralization as a full persistence seam. The current type, writer, and decoder are all scalar at [store.go:177](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:177), [store.go:498](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:498), and [store.go:592](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:592). A tolerant decoder is necessary because the current unconditional `GetStringValue` path would silently lose list data.

- Sorted, deduplicated lock acquisition is the right local concurrency strategy. The current operation holds one keyed lock through its check/write sequence at [store.go:2009](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:2009), while the locker is a keyed, non-reentrant mutex abstraction. Preserving that interface while acquiring canonical IDs in sorted order avoids overlapping-set deadlocks.

- The plans preserve the store-tier authorization recheck rather than trusting handler preflight. The actual write gate is `getWritable`, which deliberately collapses nonexistent and unauthorized records to `ErrNotFound`: [store.go:1621](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:1621). The current handler also gates before embedding at [tools.go:1746](/Volumes/Code/github.com/seanb4t/engram/internal/server/tools.go:1746), so retaining both layers is correct.

- Plan 04 correctly preserves `idempotencyPointID`. The existing point ID is derived from owner, scope, and key at [tools.go:977](/Volumes/Code/github.com/seanb4t/engram/internal/server/tools.go:977), while request differences are detected through the stored fingerprint at [tools.go:985](/Volumes/Code/github.com/seanb4t/engram/internal/server/tools.go:985). Target-set identity belongs in the fingerprint, not in a changed lookup ID.

- The documentation plan explicitly recognizes that `docs-site/**` is excluded from markdown lint and adds a semantic drift test instead. That is substantially stronger than relying on `task lint:markdown`.

- No `must_haves.pattern` entry contains a backslash escape. The patterns consistently use character classes such as `[(]` and `[.]`, so they avoid the known parser hazard.

## Concerns

### Plan 03.1-01

- **HIGH — Plan 01 omits required production and test-interface files.** Task 1 changes `Store.Supersede` from a scalar target to a slice, but `files_modified` omits both `internal/server/store_iface.go` and `internal/server/fakestore_test.go`. The production interface still declares the scalar signature at [store_iface.go:39](/Volumes/Code/github.com/seanb4t/engram/internal/server/store_iface.go:39), and the compile-time assertion at [store_iface.go:47](/Volumes/Code/github.com/seanb4t/engram/internal/server/store_iface.go:47) will immediately fail. The spy implementation also has the scalar signature at [fakestore_test.go:214](/Volumes/Code/github.com/seanb4t/engram/internal/server/fakestore_test.go:214). “Call-site sweep (both test files)” is therefore incomplete.

- **HIGH — The spy’s behavior must be pluralized, not merely its signature.** The spy currently checks and stamps one target at [fakestore_test.go:219](/Volumes/Code/github.com/seanb4t/engram/internal/server/fakestore_test.go:219). Handler tests using it cannot prove multi-target authorization, all-target preflight, or multi-target stamping unless its implementation is updated consistently.

- **MEDIUM — Plan 01 knowingly lands an unsafe intermediate implementation.** It changes production to multi-ID `SetPayload` while deferring reconciliation to Plan 02. The current method simply returns the stamp error at [store.go:2037](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:2037). After Plan 01, the branch can leave dangling predecessor links—the exact correctness failure this phase exists to prevent. If each plan is committed independently, Wave 1 produces a knowingly unsafe repository state.

- **LOW — The proposed grep backstop is brittle.** “Every non-test Go read routes through the decoder” is worthwhile, but exact hit counts will drift with comments and documentation. An AST-level or focused codec test is more durable than a global textual count.

### Plan 03.1-02

- **HIGH — The proposed TOCTOU trigger does not exercise the claimed window.** Task 2 suggests deleting the target “as a side effect of releasing the last acquired lock.” But `Store.Supersede` defers unlock until the method returns; release occurs after `SetPayload`, too late to create the target race. The alternative—deleting between an explicit `getWritable` and a subsequent `Supersede` call—also fails, because `Supersede` performs its own under-lock `getWritable` at [store.go:2018](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:2018) and will reject before `Upsert`. The existing test’s “end-to-end” case has this same limitation: it deletes before entry and only proves the initial gate at [store_test.go:3581](/Volumes/Code/github.com/seanb4t/engram/internal/store/store_test.go:3581).

- **HIGH — A deliberate production seam is required.** To prove failure after preflight and after survivor creation, the plan needs a hook between `Upsert` and the multi-ID `SetPayload`, or an injectable points client whose `SetPayload` can execute a partial mutation then return an error. The current plan explicitly claims “no new fault-injection seam needed,” but the source contradicts that.

- **HIGH — Compensation failure logging is not testable with the current design.** The plan requires tests for survivor-delete failure and reconciliation failure while preserving the original stamp error. The current store owns its Qdrant client directly and exposes no described mutation fault script. A naturally missing target can trigger stamp failure, but Qdrant will normally be healthy enough for compensation to succeed. An outage severe enough to break cleanup also prevents deterministic setup and observation.

- **HIGH — “Not observable” is stronger than the proposed mechanism.** Store locks serialize writers, not readers. `Get` directly calls Qdrant without acquiring a target lock at [store.go:1501](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:1501), and all recall queries are likewise lock-free. After Qdrant partially applies `SetPayload` and before reconciliation deletes the keys, a concurrent reader can observe hidden predecessors. The proposed tests check terminal state only. The plan can prove “no partial state remains after the call returns when compensation succeeds,” not literal non-observability.

- **MEDIUM — `reconcileSupersedeFailure`’s return shape is underspecified.** Returning only `dangling []string` must distinguish not-found from read failure and clear failure. The plan says not-found is harmless, but transport errors must cause the target to be reported as potentially dangling. That exact classification should be specified and tested.

- **MEDIUM — `Store.Delete` adds another authorization decision during rollback.** `Delete` re-runs `getWritable` using `ActionDelete` at [store.go:2095](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:2095). A policy that permits creation/write but denies delete could prevent compensation. A private internal raw-delete primitive scoped to the freshly-created survivor may be more correct, or the plan must explicitly accept and test this policy interaction.

- **MEDIUM — Vacuous test gates remain.** Plan 02 accepts `go test ./internal/store/... -count=1` by exit status alone. Because Go returns success when a `-run` pattern matches nothing, every named-test gate should count `--- PASS`; the broad suite command can remain a supplemental gate, not evidence that a specific proof ran.

### Plan 03.1-03

- **HIGH — Class C contains an impossible operation.** The plan says inputs whose `ResolvePointID` returned not-found should “carry forward” and then be passed to `FetchForUpdate`. But no canonical ID exists for those inputs. Source confirms missing short IDs return `ErrNotFound` without an ID at [store.go:1564](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:1564). The algorithm must instead collect resolution-not-found inputs directly into the same Class C bucket while calling `FetchForUpdate` only for successfully resolved IDs.

- **HIGH — Ambiguous short IDs remain an unauthenticated existence signal.** `ResolvePointID` is explicitly owner-agnostic at [store.go:1530](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:1530), scrolls the global collection by short ID at [store.go:1555](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:1555), and returns `ErrAmbiguousShortID` when at least two records match at [store.go:1569](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:1569). Reporting Class B before ownership therefore reveals that a guessed handle has multiple global matches. The plan preserves full indistinguishability only for Class C, not across the entire target resolution process.

- **HIGH — PD-07 is implemented before approval.** The 256-target cap is a new externally-visible rejection for calls that are currently unbounded. Plan 03 is autonomous in Wave 2; human review occurs only in Plan 05 after implementation and documentation. That checkpoint is too late for a costly published contract decision.

- **MEDIUM — The cap is not tied to generated schema constraints.** Runtime validation and documentation are specified, but the JSON schema is not required to advertise `maxItems: 256` or `minItems: 1`. Agents relying on the advertised MCP schema will not learn the restriction until runtime.

- **MEDIUM — The cap does not address the Qdrant risk used to motivate it.** It still permits eight server chunks at the documented size of 32. Its only defensible purpose is request-amplification control, but 256 sequential resolve/fetch operations plus 256 held locks may itself be excessive. The plan should justify the number with a latency or resource budget.

- **MEDIUM — Store-tier offender remapping is fragile.** Plan 03 asks the handler to parse store error contents containing resolved IDs and map them back to inputs. Sentinel errors are not structured offender lists today; the existing store returns formatted prose at [store.go:2026](/Volumes/Code/github.com/seanb4t/engram/internal/store/store.go:2026). Parsing or substring matching would be brittle. Introduce a typed multi-target error carrying canonical IDs internally.

- **LOW — One acceptance gate relies on bare suite exit status.** `go test ./internal/server/... -count=1 exits 0` is useful as a broad regression check but not as evidence that the named rejection tests ran.

### Plan 03.1-04

- **HIGH — The load-bearing staging API is left undecided during execution.** Task 2 says to either add a hook to `resolveSupersedeTargets` or split it into two functions. This determines whether replay truly runs between ownership and already-superseded validation and should be fixed in the plan, not delegated to implementation judgment.

- **MEDIUM — PD-09 satisfies D-14 narrowly, but the contract needs explicit wording.** Resolving and ownership-gating before replay does not violate “before already-superseded,” and a normal retry after success still works because supersession does not delete its targets. However, a retry after targets are later deleted or ownership changes will not replay. That is a deliberate weakening of ordinary idempotent replay semantics and must be surfaced in the public contract, not only in a test.

- **MEDIUM — The proposed fingerprint duplicates the full content encoding.** `contentFingerprint` already owns the canonical field list at [idempotency.go:64](/Volumes/Code/github.com/seanb4t/engram/internal/server/idempotency.go:64). Copying its “exact field list and order” into `mergeFingerprint` creates two implementations that can drift. Prefer composing the existing content fingerprint with a length-prefixed canonical target encoding.

- **MEDIUM — Concurrent identical keyed merges are insufficiently specified.** Existing store-memory idempotency relies on deterministic IDs and post-write rereads, but multi-target calls also race on target locks and already-superseded state. The plan tests sequential replay, not two simultaneous identical keyed calls. One caller could pass the initial replay lookup, wait on locks, then hit already-superseded. A concurrency test should require both callers to return the same persisted result.

- **LOW — Two acceptance gates rely on broad bare exit status.** The package-wide `go test ... -count=1` checks are fine as supplemental regression gates, but named tests should remain the proof.

### Plan 03.1-05

- **HIGH — Documentation overstates terminal compensation if Plan 02 remains best-effort.** Saying a failed merge is “usually observably a no-op” is acceptable only if the immediately following sentence explains that cleanup failure can leave a survivor, dangling links, or both. The source has no durable retry/recovery queue, so operator logging is the only remediation.

- **MEDIUM — `task lint:markdown` is not evidence for docs-site correctness.** The plan acknowledges this at Plan 05 Task 1, but still includes `task lint:markdown` as a docs acceptance criterion. Keep it as a general repository gate, while making the semantic drift test and explicit content assertions the only evidence for `docs-site/**`.

- **MEDIUM — The drift test risks duplicating rather than invoking rendering logic.** “Calling the same wrapping the handler uses” is underspecified because current handler errors are assembled inline with `fmt.Errorf`, for example at [tools.go:1755](/Volumes/Code/github.com/seanb4t/engram/internal/server/tools.go:1755). A test that repeats the same `fmt.Errorf` expression can drift in parallel. Extract production rendering helpers and call those from both handler and test.

- **MEDIUM — Human approval arrives after all three disputed choices have shipped in code.** The checkpoint should precede Plan 03, especially for the cap and error class order. Plan 05 should verify approved decisions, not request first approval after implementation.

- **LOW — The stale-claim sweep is phrase-specific.** Testing only historical fragments can miss semantically equivalent stale wording. Retain it, but also positively assert the current key-support statement in every relevant document.

## Suggestions

1. **Amend Plan 01 file ownership and tasks.**
   - Add `internal/server/store_iface.go` and `internal/server/fakestore_test.go` to `files_modified`.
   - Explicitly pluralize `memStore.Supersede` and update the spy to preflight and stamp every target.
   - Add compile-time and spy multi-target tests.
   - Prefer landing Plan 01 and Plan 02 in the same atomic commit, or include minimal reconciliation in Plan 01 so no committed state introduces dangling-link behavior.

2. **Add a deterministic mutation fault seam in Plan 02.**
   - Introduce a narrowly-scoped injectable points-mutation wrapper or a test hook immediately after survivor `Upsert` and before back-stamp.
   - Script: partially stamp A/B, report C missing, optionally fail survivor delete, optionally fail selected `DeletePayload` calls.
   - Use it to prove original-error preservation and logging.
   - Keep the real-Qdrant test to prove Qdrant’s partial mutation semantics, but use the injected seam for complete production-flow coverage.

3. **Correct the atomicity claim.**
   - Replace “partially-applied merge is not observable” with:
     “After `Supersede` returns, successful reconciliation leaves no partial merge state; concurrent readers may observe the transient Qdrant state, and failed reconciliation is logged.”
   - If literal non-observability is mandatory, compensation is insufficient; the design needs a visibility/commit marker or staging protocol that recall filters understand.

4. **Specify reconciliation outcomes structurally.**
   - Return something like `{deleteErr error, readFailures []string, clearFailures []string, dangling []string}` internally.
   - Log all unresolved targets.
   - Treat `ErrNotFound` as resolved, transport errors as “possibly dangling.”
   - Consider an internal raw delete for the freshly-created survivor so rollback is not blocked by a second authorization decision.

5. **Rewrite Plan 03’s stage algorithm.**
   - Resolution stage should yield three buckets: resolved pairs, resolution-not-found inputs, and ambiguous inputs.
   - Class C begins with resolution-not-found inputs and appends resolved inputs whose `FetchForUpdate` returns not-found.
   - Never call `FetchForUpdate` without a canonical ID.

6. **Resolve ambiguous short-ID disclosure.**
   - Either perform owner-filtered resolution for this write path, or collapse ambiguous and not-found into the same caller-visible class.
   - Add a cross-owner collision test proving no global handle-count disclosure.

7. **Move the cap decision before Wave 2.**
   - Add a blocking checkpoint before Plan 03.
   - If approved, add `minItems: 1` and `maxItems: 256` to the generated MCP schema and test them.
   - Justify 256 with an explicit request-cost budget; otherwise omit the cap.

8. **Use typed internal multi-target errors.**
   - Have the store return a typed error carrying canonical offender IDs.
   - Map those IDs to original caller inputs in the handler without parsing prose.
   - Keep caller-facing sentinel identity unchanged.

9. **Fix Plan 04’s staging decision now.**
   - Split preflight into explicit functions:
     `resolveAndAuthorizeSupersedeTargets` → replay check → `validateSupersedeTargetState`.
   - This makes D-14 obvious and testable.
   - Add a concurrent identical-key merge test requiring both callers to return the same survivor.

10. **Compose fingerprints rather than duplicate field lists.**
    - Hash a length-prefixed `contentFingerprint(a)` plus a canonical target-set encoding.
    - Preserve `idempotencyPointID` and its namespace byte-for-byte.

11. **Strengthen Plan 05’s drift gate.**
    - Extract production rejection-rendering helpers and invoke them from both the handler and documentation test.
    - Treat `task lint:markdown` only as a general gate.
    - Positively assert current key-support language in addition to rejecting historical phrases.

12. **Replace remaining vacuous named-test risks.**
    - Every specific behavior gate should use a named `-run` expression and count `^--- PASS`.
    - Keep bare full-package exit status only as a supplemental regression gate.

## Risk Assessment

**Overall risk: HIGH.**

The architecture is directionally sound and the revised Qdrant analysis is correctly incorporated. The main problem is proof quality: Plan 02’s proposed test cannot reach the failure window it claims to test, compensation is transiently observable to readers, and cleanup-failure behavior lacks an injectable seam. Separately, Plan 01 will not compile as scoped because it misses the store interface and spy implementation, while Plan 03 contains an impossible resolution step and introduces a public cap before approval. These are execution blockers, not polish issues. Once the fault seam, interface migration, staging algorithm, ambiguity handling, and early cap decision are fixed, the plan set should fall to medium risk.
