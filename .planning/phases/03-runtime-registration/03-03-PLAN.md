<objective>
Convert opencode to the `Args`/`Probe` model and, in the same edit, fix a confirmed live bug the
phase inherits: `internal/setup/opencode.go` authors its bearer header in HTTP-header-string form
(name, colon, space, value), but opencode's `--header` flag requires the `KEY=VALUE` form. Fed the
shipped form, the real CLI fails immediately —
`Invalid HTTP header: ... Expected KEY=VALUE` — so opencode's bearer path has never worked.
This is not new scope: it is a defect in code this phase already rewrites for D-01, and
`03-RESEARCH.md` Pitfall 2 reproduced it live against opencode 1.18.20.

The second task pins the two third-party constraints opencode imposes on this design — no
per-server read verb, and a documented upstream `{env:...}` substitution reliability issue — so
neither is rediscovered as a surprise or "fixed" by adding the output parsing D-08 rejects.

Purpose: make opencode's registration actually run, across every auth mode it supports, and make
its two real limitations legible rather than latent.

Output: a corrected `opencode.go` and its own test file.
</objective>

Make opencode's two real limitations legible, and pin the convergence behavior they produce.

**Document, in `opencode.go`'s own doc comment**, mirroring how `02-SECURITY.md`'s T-02-13
documents `sanitizeViewValue`'s narrower-than-it-sounds scope:

1. **The probe asymmetry.** `opencode mcp list` is the only read verb available. It has no `--json`
   flag; it renders a human-formatted table with box-drawing and status glyphs; it lists EVERY
   registered MCP server, not just engram's; and it dials the network for each of them on every
   invocation (live-observed at roughly 1.2–1.7 seconds per call). The consequence for D-08's
   byte-compare is that an unrelated server's transient connection-status flip between read #1 and
   read #2 makes the two captures differ. State plainly that this degrades in the SAFE direction
   only — D-08's invariant resolves ambiguity to `wrote` and never to `already-correct` — and that
   the correct response is never to parse or filter the output to isolate engram's row, which D-08
   already rejected for buying a third-party output-format dependency.
2. **The `{env:...}` substitution reliability caveat.** opencode's own issue tracker documents
   inconsistent `{env:VAR}` resolution for specific MCP servers, with no confirmed fix as of the
   probed 1.18.20. Engram cannot detect this: it never observes the resolved header value, by
   design (D-05). Record the failure signature an operator would see — a registration engram
   reports as succeeded whose MCP connection then fails auth — and name the upstream issue so they
   have a lead rather than a mystery. This is REQ-register-auth-modes' "states plainly which are
   unsupported for that runtime" clause extended to cover "supported, with a known upstream
   reliability caveat". Do NOT write a test asserting opencode's substitution behavior: repo rule
   `m45p2b4bp7` forbids red-gating third-party behavior engram does not own.

All three drive the fake; none invokes a real `opencode` binary.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| engram → opencode CLI | engram starts `opencode` as a child process with an authored argument list |
| opencode CLI → engram | `opencode mcp list`'s output — box-drawing glyphs, status markers, and every OTHER registered server's identity — becomes report content and convergence input |
| opencode → the operator's credential store | opencode resolves the `{env:...}` reference itself at connect time; engram never observes the resolved value |
