**Two things need your approval before the implementing task runs.**

### 1. A locked CONTEXT.md premise is factually wrong

`03-CONTEXT.md`'s **D-08** states as an accepted consequence: *"the write always runs (already
sanctioned — D-13 of Phase 2 classifies `setup` `Destructive: true` precisely because `mcp add`
overwrites an existing entry)"*. `internal/surfaces/toolclass.go`'s `setup` row comment states the
same thing as fact for all three CLIs.

Live re-probing (claude 2.1.265, this machine, 2026-09-08, reproduced twice) found:

| Runtime | `mcp add` on an existing name | Verified how |
|---|---|---|
| codex | silently overwrites | `config.toml` diff after a changed `--url` |
| opencode | silently overwrites | `opencode.json` diff after a changed `--url` |
| **claude-code** | **refuses, exit 1, `"already exists"`** | reproduced at `--scope project` AND `--scope user`, including with an unchanged URL; no `--force`/`--overwrite`/`--replace` flag exists on `claude mcp add` or `claude mcp add-json` |

**Consequence if implemented as literally specified:** `OutcomeAlreadyCorrect` is unreachable for
claude-code. Every second `engram setup --apply` would report `failed` for a registration that is
already perfectly correct — which is precisely what REQ-setup-idempotent and success criterion 5
forbid.

**Proposed correction:** claude-code's `Plan()` authors two write actions — a tolerant
`claude mcp remove engram --scope user` that clears the slot regardless of prior state, then a
fatal `claude mcp add ...`. This reproduces the overwrite semantics codex and opencode get for
free. D-08's read → write → read byte-compare is untouched; only the "write" step becomes two
actions instead of one.

### 2. The correction opens a destructive window — this is the part that is not reversible

`claude mcp remove` succeeding followed by `claude mcp add` failing (or the process being
interrupted between them) leaves the operator with **no claude-code registration where they
previously had a working one**. Engram cannot restore it: it never read the prior entry, and
reading a runtime's config file is forbidden by this phase's central constraint.

The mitigations proposed:
- the failure `reason` explicitly states that the prior registration was removed and that re-running
  `--apply` is the recovery;
- the tolerant action's own exit code and stderr are recorded on `notes=` so a genuinely broken
  `remove` is visible in `--output json` even though it does not fail the row;
- `toolclass.go`'s `Destructive: true` classification is unchanged — remove-then-add is strictly
  more destructive than an overwrite, so the existing conservative value still holds.

There is no non-destructive alternative available: without a force flag, and with config-file
reading forbidden, there is no way to make `claude mcp add` idempotent.

### 3. A mechanism choice `03-RESEARCH.md` explicitly hands to the planner

Its Assumptions Log A4 requires an explicit pick between:

- **Option 1 (research's recommendation):** the shared executor's rule is "only the LAST action's
  exit determines `OutcomeFailed`" — tolerance is implicit in position.
- **Option 2 (what plan 03-01 built):** an authored `Action.Tolerant bool`, per action.

**Option 2 was chosen**, diverging from the research recommendation, because `plan.go`'s own doc
comment records that `Plan.Actions` is a slice specifically so a later phase (skills distribution,
Phase 4) can grow it. A position-derived rule would silently make every non-final skills action
tolerant — a latent defect that ships green. `Tolerant` is authored in `Plan()`, in the runtime's
own file, which is also where every other runtime-specific fact in this package already lives.

The `assumption-delta scan` detector fired (`detected: true`, kind `pluralization`). Two
assumptions genuinely lost their monopoly in this phase; both are resolved by **promote**, not by
add-alongside.

**1. Primary noun: the ACTION SEQUENCE, not the single action.**
`plan.go`'s shipped doc comment reads *"Phase 2 ships exactly one Action per Plan"*. That singular
assumption is dead: claude-code's plan carries two, and Phase 4's skills distribution will carry
more. Decision: **promote** — `Plan.Actions` is genuinely plural, and every executor rule is
per-action-DECLARED (`Action.Tolerant`), never derived from position or count. Adding a positional
rule alongside the declared one was explicitly rejected: it is the add-alongside shape, and it
silently contradicts the generalized intent the moment a later variant does not fit the old
primary.

**2. Primary noun: RUNTIME as "a target engram can register with", not "a binary on PATH".**
Every registered runtime has so far been a real binary, and `Detect` has been synonymous with
`exec.LookPath`. Plan 03-04's `generic` pseudo-runtime breaks that. Decision: **promote** —
default-set membership moves out of the implicit "every registered runtime is a real binary"
assumption and into an explicit structural predicate on the runtime itself. That work belongs to
plan 03-04 and is recorded there.

**Companion invariant test (accepted):** `TestActionToleranceIsAuthoredNotPositional` (Task 3)
encodes the generalized intent for (1) and goes red the instant the singular/positional assumption
is reintroduced.
