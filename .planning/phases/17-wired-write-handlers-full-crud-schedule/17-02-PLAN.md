**Round-7 review (this revision):** REVERT the round-6 whole-payload overwrite back to the
round-5 TARGETED two-op design. (HIGH, Codex — orchestrator-CONFIRMED) The round-6 change
persisted the payload-only update as a single whole-payload `OverwritePayload(payload(cur))` to
close the round-5 partial-write window — but that INTRODUCED a worse hazard. `payload(cur)`
writes the ENTIRE payload including `"content"` and `"tags"` (store.go:304-305) from a STALE
`FetchForUpdate` snapshot, and the write is NOT a compare-and-swap. Under ordinary concurrent
writes: (1) a visibility-only request fetches `oldCur`; (2) a concurrent content update writes
new content + a new re-embedded vector via `store.Update`→`Upsert` (store.go:1367,:1406); (3) the
visibility request runs `OverwritePayload(payload(oldCur))` → restores OLD content/tags, but a
payload-only op does NOT touch the vector, so the NEW vector survives with OLD content → durable
content/vector desync → corrupted recall, violating engram's core recall-precision value. It also
deletes unknown/forward-schema payload keys (store.go:2035 acknowledges `Memory` round-trips lose
keys). Decisive corroboration: the codebase's own `SetVisibility` (store.go:1417) deliberately
uses a TARGETED `SetPayload` writing only the mutated keys and never rewrites the whole payload
from a stale snapshot — round-6 diverged from that established pattern. Task 1 therefore reverts to
the round-5 TARGETED two-op design: a `SetPayload` writing ONLY the mutated keys
(visibility/summary/summary_source/access_count/last_accessed_at) PLUS a targeted `DeletePayload`
for `summary_model`/`summary_egress_at` when provenance must be cleared (matching `SetVisibility`).
Its ONLY downside is an ACCEPTED, minor, recoverable non-atomicity: if the `DeletePayload` fails
after the `SetPayload` succeeds, the record is left with stale provenance METADATA only (mislabels
a summary's source) — it never corrupts content or the vector, and a later write reconciles it. Do
NOT reintroduce `OverwritePayload` unless a real optimistic-concurrency/version (CAS) mechanism is
added first. The round-6 `WithVectors(true)` vector-preservation assertion, the raw-payload
key-absence assertions (proving `summary_model`/`summary_egress_at` are gone after the targeted
`DeletePayload`), the usage-bump semantics (`access_count`/`last_accessed_at`) matching
`store.Update` (store.go:1379), and the round-6 gen-ts LOW fix are all KEPT. No round-1/2/3/4/5
fix is regressed.
