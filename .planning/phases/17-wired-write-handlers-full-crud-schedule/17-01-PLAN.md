<objective>
Evolve the shared `auth.ClaimIdentity` owner resolver from a single claim to an
ordered claim list so authenticated service/machine tokens without an `email`
claim resolve to a stable, namespaced owner instead of failing closed — while
keeping every existing single-value `email` deployment byte-for-byte unchanged.

This is an authorization-key change (owner is the authz key, compared directly in
the store's authz filters). Per the cross-AI review, the original `<claim>:<value>`
D-06 encoding is NOT collision-free and is HARDENED here to a provably injective
length-prefixed scheme, with a guard so a crafted email value cannot occupy the
reserved (non-email) namespace. Three invariants are load-bearing: the
`email_verified` gate (D-05), namespace injectivity/disjointness (D-06 hardened),
and fail-closed empty resolution (D-04).

Purpose: closes the "service token has no email → fails closed" gap and lays the
collision-safe owner-space foundation the six write RPCs (later plans) attribute
records under.
Output: an ordered-list `ClaimIdentity` with an injective encoder, list-valued
config plumbing with parse/default separation, dedicated D-05/D-06 security
unit tests (including the two adversarial colliding pairs from the review), AND
the rollout-migration guardrails the round-2 review escalated to HIGH.

**Round-2 review — the owner-encoding change is a MIGRATION, not just a refactor
(finding 3, HIGH, security-critical).** Existing non-email deployments store the
bare claim value; the new encoding changes the authz key, so pre-encoding records
go invisible and — worse — a LIVE session cookie carries the old bare owner and
`Resolver.Resolve` forwards it unchanged (resolver.go:54). After the change, new
logins get encoded owners while old cookies keep bare owners: one principal SPLIT
across two owner buckets AND the D-06 collision PRESERVED for the cookie's
lifetime. This plan closes the rollout with three mitigations: (a) the
reserved-namespace email guard (already present, T-17-08); (b) a VERSIONED session
payload that rejects any legacy (unversioned / bare-owner) cookie and forces
re-login, so no bare owner survives into the encoded space (lower-friction than
mandating a `ui.cookie_key` rotation — the re-auth is automatic); (c) the existing
`engram migrate-remap-owner` operator runbook, documented for remapping existing
non-email records. Session versioning is additive and forward-compatible with the
Phase-18 sliding-reseal (D-08) — Phase-18 re-seals simply carry the current
version.

Addresses review concerns: D-06 hardening (Codex HIGH, round 1); parse/default
separation (Codex MEDIUM); malformed-entry validation (Codex MEDIUM); **round-2:
owner-encoding rollout migration + session versioning (Codex HIGH, finding 3);
empty-owner-claim acceptance criterion retargeted to `--owner-claim=""` (Codex
MEDIUM, finding 9)**.

**Round-3 review (this revision):** the malformed-present-email fallthrough is closed
(HIGH-1 — email presence is checked separately from string conversion; a present
non-string/`null` email REJECTS instead of falling through to `sub` and selecting a
different authz bucket); the owner-claim parser converges on ONE deterministic strict
contract (LOW-7 — reject duplicate/interior-empty entries and `:`/`,`/leading-digit
claim names, fail-fast at startup, no silent normalization); `SessionCodec.Seal`
auto-injects the payload version so every mint site is version-consistent by default
(LOW-9); and the migrate-remap-owner runbook shows worked encoded-target examples for
`sub`/`client_id` (LOW-10). Out-of-scope deferral pointer (recorded, no work here):
syncing the companion CSRF-cookie MaxAge to the slid session TTL belongs to the
Phase-18 sliding re-seal (D-08), not Phase 17.
</objective>
