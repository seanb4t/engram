ROADMAP criterion 1 is already CLOSED in writing (`03-AUTHZ-GATE.md`). Criterion 2 is the durable

evidence about authorization. So this test does not go through `Store.Search` at all — it builds the
exact `*qdrant.Filter` the post-D-05 cross-spine path will produce and runs it directly.

<assumption_delta_decision>
**Signal:** `pluralization` on ROADMAP success criterion 3 ("returns hits from multiple scopes").
**Primary noun:** `scope` — remains primary and **singular**.
**Decision:** `add-alongside`. NOT `promote`.

**Rationale.** Cross-spine is an opt-in *read-time widening*, not a change to the identity model. A
memory belongs to exactly one scope: every write path (`store_memory`, `schedule_memory`,
`store_rule`, `store_discovery`) and `delete_all` take one required scope, `scope` is a single
payload key under the one-collection invariant `DEC-2bv`, and `store.Memory.Scope` is a `string`.
Promoting `scope` to a scope-*set* primary would imply a record can live in several scopes at once,
which contradicts both `DEC-2bv` and the two-tier spine/overlay model. What this phase adds
alongside the singular primary is a query-time *span* (`searched_scopes`) — a property of the
request, not of the record.

**What would force a later promote:** (a) a record needing simultaneous membership in multiple
scopes, or (b) the deferred `REQ-cross-spine-scope-prefix` landing with prefix semantics that make a
scope-set the natural query unit.

**Optional invariant test — declined, with reasoning.** A test asserting "a record's `scope` payload
is exactly one value" would be asserting that a Go `string` field holds one string; it cannot fail.
The load-bearing half — *every read path attributes a hit to that single value, and a cross-spine
read spans more than one distinct value* — is exactly what `TestCrossSpineResultScope` (plan 03-03,
task 3) asserts. It does not earn a second test.
</assumption_delta_decision>
