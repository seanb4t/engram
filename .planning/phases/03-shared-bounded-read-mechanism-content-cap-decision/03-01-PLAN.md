<objective>
Decide and enforce decision A on the create-style memory write paths: memory `content` gets an
always-enforced byte cap, and memory `tags` get an always-enforced count cap and per-tag byte cap,
declared once in the `internal/config` registry and enforced once in `validateStoreArgs`, which
`store_memory`, `schedule_memory` and `supersede_memory` share on both the MCP and Connect lanes.

Decisions implemented: D-01 (a registry-declared `ENGRAM_MEMORY_MAX_CONTENT_BYTES`, default 65536,
rejected with the EXISTING `field=content hint=too_long` envelope — no new hint code), D-09 (always
enforced: validation rejects `0` and non-positive values, a documented divergence from
`ENGRAM_MEMORY_MAX_SUMMARY_BYTES`'s `0 disables`), D-10 (`ENGRAM_MEMORY_MAX_TAGS` default 128 and
`ENGRAM_MEMORY_MAX_TAG_BYTES` default 128, rejected with the existing `field=tags hint=too_many` /
`too_long`). Framing (D-00): the existing registry → `Config.Validate` → `deps` → validator pattern
that `ENGRAM_MEMORY_MAX_SUMMARY_BYTES` already uses; no new mechanism.

Scope of this plan: the three create paths. `update_memory` (whose Connect lane bypasses
`validateUpdateArgs`), the legacy over-cap record contract, the store-side record ceiling wiring,
the CLI end-to-end proof and all documentation land in plans 03-03 and 03-05. The CLI needs no code
here: `engram store` is a Connect client of `StoreMemory`, so this plan's server-side check is what
it hits (proven end to end by plan 03-05).

Purpose: REQ-content-cap-decided (write half); the caps are also the inputs plan 03-02 derives the
per-record read ceiling from.

Output: three registry rows and validated `MemoryConfig` fields, `memoryWriteCaps` on `deps`, two
shared rejection helpers, and hermetic MCP + Connect tests (spy store, no Qdrant).
</objective>
