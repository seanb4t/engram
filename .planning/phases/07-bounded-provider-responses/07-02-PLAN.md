<objective>
Make the six new provider bounds real, operator-facing configuration: registry entries, struct
fields, and validation that refuses a value which would quietly mean "no bound".

This plan is deliberately parallel with plan 07-01. It shares no file with any other plan in this
wave, and it delivers its own observable behavior rather than laying foundation: after it, a
mistyped or unbounded provider-tuning value fails startup with the variable named, whether or not
any client is reading the value yet.

Decisions covered: D-04 (the four drain knobs, per-client, mirroring the existing timeout pairing),
D-05 (zero is valid on a drain bound, negative is not, and nothing means unbounded), D-07 and D-13
(the two `Timeout` doc comments are corrected), D-08 (the two ceiling knobs, non-positive rejected).

Purpose: an operator can see, set and mis-set these bounds, and a mis-set one is caught at boot
rather than at 3 a.m.

Output: six registry rows, six struct fields, six validation blocks, and a test file that pins all
three layers against each other.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| environment → process configuration | Every `ENGRAM_` value is operator-supplied text that must be parsed and range-checked before anything depends on it. |
| configuration → runtime bound | A value that parses but is silently replaced by a default produces a validated-versus-enforced divergence: the operator believes one bound is in force while another is. |
| documentation → operator expectation | A doc comment promising "zero disables the timeout" is a contract; leaving it in place after the behavior changes misleads the reader who most needs it. |
