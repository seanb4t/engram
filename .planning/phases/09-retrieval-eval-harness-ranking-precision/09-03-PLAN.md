<objective>
Close REQ-ranking-precision using the eval as the decision mechanism (D-05).
The #261 failure is phrasing-sensitive: near-verbatim restatements (Query A/B) of
Record T fail to surface T within default `k` because sticky topical neighbors
crowd it out. Because near-verbatim restatements have high lexical overlap with
their target, the light lever most likely to fix this — and the one D-06 mandates
trying first — is an in-process, dependency-free heuristic rerank (lexical-overlap
boost / MMR / score-gap), optionally with a higher default `k`.

This plan (1) implements the D-06 heuristic reranker wired into both the real
search path and the eval, (2) upgrades the #261 fixture to a hard acceptance bar
and runs the eval to get real numbers, and (3) makes the eval-gated accept/escalate
decision. Hybrid dense+lexical fusion (D-07) and a cross-encoder reranker (D-08)
are IN SCOPE only if the eval shows D-06 is insufficient — they are represented
here as conditional escalations with their RESEARCH mechanics, not as committed
work (D-05: nothing added speculatively).

Purpose: eliminate phrasing-sensitive misses so search-before-store stops
producing duplicates (the #261 goal), proven by the eval not intuition.
Output: the D-06 reranker + the eval-selected ranking decision.
</objective>

**D-07 — Hybrid dense+lexical (BM25) fusion** (RESEARCH Pattern 3/4, Pitfall 2):
- Qdrant server-side `qdrant/bm25` `Document` inference is Cloud-Inference-only and
  unavailable on self-hosted/OSS Qdrant (the Helm-deployed backend) — do NOT use it.
- Instead: generate sparse vectors client-side in Go (deterministic tokenize →
  hash terms to indices → term-frequency values, SAME tokenizer document- and
  query-side) and let Qdrant's `Modifier_Idf` on `SparseVectorParams` compute IDF
  server-side. Query via `QueryPoints.Prefetch` (dense + sparse) fused by
  `qdrant.NewQueryFusion(qdrant.Fusion_RRF)`.
- Converting the current single UNNAMED dense vector to a named-vector map
  (`"dense"` + `"sparse"`) is a breaking, immutable schema change → requires the
  existing `engram reindex --target <new-collection>` flow (re-embed AND
  re-tokenize every record, `--dry-run`, cut over `ENGRAM_QDRANT_COLLECTION`), NOT
  an in-place mutation. Model operator ergonomics on `cmd/engram/reindex.go`.

**D-08 — Cross-encoder reranker** (RESEARCH Pattern 5):
- Opt-in only; off the default hot path unless the eval justifies default-on.
- A second-stage HTTP call to a Cohere/Jina-compatible `/v1/rerank` endpoint
  (vLLM-hosted cross-encoder), mirroring `internal/embed`'s `net/http` client — NO
  new Go dependency; plain stdlib.
- New opt-in `ENGRAM_RERANK_*` koanf fields in `internal/config/registry.go` (no
  Default = disabled when empty; no Legacy). Any proposed rerank client LIBRARY
  (instead of hand-rolled `net/http`) MUST pass the Package Legitimacy Gate + a
  blocking human checkpoint before adoption — none is pre-approved.
- Data-flow note: rerank sends the FULL candidate record content (not just the
  query) to the external gateway — same trust boundary as existing embed/summarize
  calls, but a broader payload; document this for operators choosing D-08.
