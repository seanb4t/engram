## Gap — the CLI never reaches cross-spine

**Phase 3 shipped `cross_spine` on the Connect API. Phase 2's CLI never wires it.**

Verified independently by the orchestrator: `rg -i 'cross.spine|CrossSpine|searched_scopes' cmd/engram/`
returns zero hits, while `gen/go/engram/v1` carries `CrossSpine` on both `SearchMemoriesRequest`
(field 9) and `ListMemoriesRequest` (field 12).

- `cmd/engram/client_search.go:72-79` — flag set has no `--cross-spine`; the request literal never
  sets the field.
- `cmd/engram/client_list.go:84-94` — same.
- Neither command reads `searched_scopes` / `scopes_truncated` from the response, so even the
  provenance half of Phase 3 is invisible to CLI callers.

Per `internal/server/connectapi.go`'s deliberate, documented asymmetry (D-04), an empty `Scope` does
**not** imply cross-spine on these two RPCs — unlike `SearchDiscoveries`. So this is not a case
where the default happens to work; the capability is genuinely unreachable from the shipped CLI.

### No requirement is violated

- `REQ-cross-spine-search` promised *"MCP↔Connect parity via an additive proto field"* — satisfied.
  It does not mention the CLI.
- `REQ-cli-client-commands` promised `search` / `store` / `list` over the generated Connect stubs —
  satisfied. It does not mention cross-spine.

### What *is* violated is the milestone goal

*"Make engram usable by agents that are not a top-level MCP client."* The headless CLI agent is
precisely the caller cross-spine recall was built for, and is the only caller that cannot reach it.
The capability is available over raw Connect RPC, which means an agent must bypass the shipped CLI —
the exact thing Phase 2 exists to prevent.

### Why nothing caught it earlier

Ordering. Phase 2 (CLI) shipped 2026-07-31; Phase 3 (cross-spine) shipped 2026-08-01. Phase 3's
plans covered MCP and Connect because those were its named surfaces. Nothing sent anyone back to the
CLI, and the roadmap's execution-order note explicitly allowed 3 to run independently of the 1→2
spine. Each phase verified against its own scope and passed honestly. Seams between phases belong to
no phase.

**This is a structural lesson, not a blame:** a phase that adds an argument to a shared API needs an
explicit consumer-inventory step, or the newest consumer silently misses it. The repo already has a
convention pointing this way — `yaj7dqz9qq`, *"a new tool argument with no guidance is an incomplete
feature"* — which Phase 3 honored for documentation surfaces but not for the CLI.

## Confirmed integrated (no defect)

1. **Auth chain still single.** `buildAuthChain` (`cmd/engram/serve.go:386`) remains the only
   production call site of `auth.New` / `auth.NewService` / `auth.NewStaticTokenVerifier`. The one
   other reference is a parity test deliberately constructing its own verifier. Phase 1's structural
   guarantee survived four subsequent phases.
2. **Error envelope ordering intact.** `internal/server/connecterror.go:59-68` still has the
   `*argError` arm first, guarded by its anti-regression comment. Phase 5's `fmt.Errorf` calls are
   in operator-facing reindex paths that never route through `connectError` — correctly out of
   scope, not a bypass.
3. **Cross-spine authz composition untouched by Phase 5.** `ownerScopeFilter`
   (`internal/store/store.go:792-799`) still appends `ownerOrSharedCondition` unconditionally,
   outside the `scope != ""` conditional. Phase 5's reindex edits are in a disjoint region and
   `Store.Reindex` never calls it.
4. **CLI exit-code table covers Phase 4's widened codes.** `client_common_test.go:29-53` enumerates
   all 16 `connect.Code` values with a count assertion that fails if one is dropped.
   `CodeOutOfRange` and `CodeFailedPrecondition` both map to `exitUsage`.
5. **Docs coherent.** Four phases appended to `CLAUDE.md`'s Memory contract and the docs-site
   reference; additions are additive and non-contradictory, each concept stated once.

## Recommendation

The gap is small and well-understood: add `--cross-spine` to `search` and `list`, thread it into
both request structs, and surface `searched_scopes` / `scopes_truncated` in the JSON output when
present. It is a CLI-only change against an already-shipped, already-tested server capability.

Routing is the user's call — accept and file, or close it before the milestone completes.
