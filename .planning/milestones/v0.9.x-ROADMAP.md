## Overview

Make recall **measurably trustworthy** as the store grows, so `search-before-store`
stops producing duplicates (the GitHub #261 failure). Four phases delivered a labeled
retrieval-quality eval harness with per-result similarity scores and a
dependency-free reranker that kills phrasing-sensitivity; reconciled the already-shipped
asymmetric query/document embedding capability; moved summary generation off the
synchronous write path via a bounded async worker pool; and added per-record usage
signals as curation metadata that **never** affects ranking.

All 6 requirements satisfied (3-source cross-referenced), all 4 phases verified passed,
cross-phase integration fully WIRED (11/11 links), all E2E flows COMPLETE, security clean
(0 open threats at ASVS-L1), Nyquist compliant.

## Phases

### Phase 9: Retrieval Eval Harness & Ranking Precision

**Goal**: A near-verbatim restatement of a record reliably surfaces that record within
default `k`, and recall changes are measurable — so `search-before-store` stops producing
duplicates (the #261 failure).
**Depends on**: Phase 2 (recall semantics), Phase 6 (telemetry — eval reuses OTLP seams)
**Requirements**: REQ-retrieval-eval, REQ-search-similarity-scores, REQ-ranking-precision
**Plans**: 3 plans (2 waves)

Plans:

- [x] 09-01: Retrieval eval harness — `internal/retrievaleval` + `task eval:retrieval`, env-gated Go test, #261 regression fixture (Record T + 15 sticky distractors), recall@k/MRR
- [x] 09-02: Document the always-on `search_memory` similarity score (tools.go Description, CLAUDE.md, docs-site); record D-04 supersession
- [x] 09-03: Eval-gated ranking precision — dependency-free lexical-overlap reranker behind shared `store.SearchReranked` on both MCP + Connect paths

**Details:**
A reproducible retrieval eval (`task eval:retrieval`) seeds the permanent #261 regression
fixture through the exact prod doc-embed sequence into a Qdrant testcontainer and reports
recall@k/MRR plus the #261 baseline rank and score gap. `search_memory` carries an always-on
per-result similarity score (raw Qdrant cosine). The D-06 reranker (pure lexical-overlap,
stdlib-only, tie-broken by raw Score then ID) is shared via `Store.SearchReranked` and proven
by a live eval surfacing the #261 target at rank 1/8 for both near-verbatim queries
(recall@8=1.00, MRR=1.000) — closed on the lightest lever: no schema change, no reindex, no
new dependency.

### Phase 11: Async-on-Write Summaries

**Goal**: New summary-less records gain summaries automatically, without an operator sweep
and without risking the write path.
**Depends on**: Phase 2 (auto-summary / `FillSummary` seam)
**Requirements**: REQ-async-summaries
**Plans**: 3 plans (3 sequential waves)

Plans:

- [x] 11-01: Foundation — `ENGRAM_SUMMARY_ON_WRITE`/`_WORKERS`/`_QUEUE_SIZE` config knobs + `Validate()`, `cenkalti/backoff/v5` promoted to direct, `telemetry.SummaryQueueMetrics` instruments
- [x] 11-02: Queue core — `internal/server/summaryqueue.go` bounded non-blocking worker pool (drop-and-count, bounded backoff retry with per-attempt timeout, best-effort drain) + `store.LogSummaryEgress` audit helper + deterministic Qdrant-free tests
- [x] 11-03: Wiring + lifecycle + docs — enqueue in `store_memory`/`schedule_memory` behind the D-01 AND-gate, `Register` returns a drain closure invoked after `httpSrv.Shutdown`, depth gauge on OTLP, docs

**Details:**
After a successful `store_memory` upsert the record id is enqueued and an in-process worker
pool drains it via the idempotent, vector-preserving `Store.FillSummary`. The summarizer is
never on the synchronous write path — a gateway/embedder outage degrades to "no summary yet"
and never fails `store_memory`. The queue is bounded and observable (depth gauge + fill-latency
on OTLP). Two durable Go concurrency kernels emerged from code review: (CR-01) an RWMutex+closed
guard so `tryEnqueue`/`close` are mutually exclusive — `net/http.Server.Shutdown` does not
force-terminate active handlers, so drain-after-shutdown is necessary-but-insufficient without
the guard; (WR-02) derive `WithMaxElapsedTime` from the per-attempt timeout so a short elapsed
cap can never silently collapse the retry count. Residuals tracked in GitHub #335.

### Phase 12: Per-Memory Usage Signals

**Goal**: Track strong per-record usage to inform curation, as operational metadata that
never silently changes what recall returns.
**Depends on**: Phase 6 (OTLP → ClickStack), Phase 3 (by-id tools)
**Requirements**: REQ-usage-signals
**Plans**: 6 plans (3 waves)

Plans:

- [x] 12-01: Store foundation — `Memory.AccessCount`/`LastAccessedAt` + payload round-trip, `IncrementAccess` (SetPayload, no re-auth), free `Update` bump, D-08 rerank invariance test
- [x] 12-02: Config gate `ENGRAM_USAGE_SIGNALS` (default on) + `telemetry.UsageQueueMetrics` (enqueued/dropped/failed, no retry)
- [x] 12-03: Proto `Memory` fields 19/20 (`access_count`/`last_accessed_at`) + `task proto:gen` + commit `gen/` (isolated, blocking)
- [x] 12-04: D-06 recall-id analytics — bounded `engram.recall.ids`/`engram.recall.count` on `store.Search`/`List`/`Get` spans + span-recorder tests
- [x] 12-05: D-10 async get-path incrementer `usagequeue.go` — CR-01 shutdown-safety kernel minus retry, drop-on-full, Qdrant-free tests
- [x] 12-06: Wiring + lifecycle + exposure — config-gated `buildUsageQueue`, get/Connect-GetMemory `tryEnqueue` (D-01, call-and-ignore, success-only), D-07 `recallView`/`memoryToProto`, D-02 negative-space e2e, `task` green

**Details:**
Counters increment only on `get_memory` fetch-by-id and `update_memory` — never on
search/list result-set membership (D-02, negative-space test). Storage is hybrid: recall ids
ride OTLP spans → ClickStack for analytics (zero storage change), and a payload `access_count`
+ `last_accessed_at` are maintained for MCP-visible curation and exposed read-only on the
compact recall view + Connect wire (proto fields 19/20). A hard D-08 invariant keeps usage
signals out of ranking (`SearchReranked`/`rerank.go` must not read them; `TestRerankHitsIgnoresAccessCount`).
The async get-path incrementer reuses the Phase 11 CR-01 shutdown kernel with no retry budget
(D-10). Durable Go convention (WR-02): optional timestamps use `*time.Time` (nil = never), not
`time.Time`+`omitempty` (a no-op on struct values that emits bogus year-1 timestamps).

## Milestone Summary

**Key Decisions:**

- D-04 supersession (Phase 9): ROADMAP Phase-9 SC2 "similarity score (opt-in)" wording superseded by the shipped always-on `search_memory` score (accepted as better DX).
- D-06 reranker (Phase 9): pure lexical-overlap term-set-intersection boost, stdlib-only, shared via `Store.SearchReranked` (candidateK bounded), called by MCP, Connect, and the eval — chosen because the live eval numbers cleared the #261 bar without needing D-07 hybrid fusion or D-08 cross-encoder.
- Phase 10 already-shipped reconciliation: `REQ-embedder-native-params` verified complete under Phase 4; no plans built; #305 closed.
- D-01 AND-gate (Phase 11): async summary worker runs only when `ENGRAM_SUMMARY_ON_WRITE=true` **and** `ENGRAM_SUMMARY_MODEL` set — breaks the presence-enables coupling; unparseable = disabled.
- D-08 shutdown ordering (Phase 11): drain the pool strictly after `httpSrv.Shutdown()` returns, guarded by the CR-01 RWMutex+closed kernel — send-on-closed-channel otherwise.
- D-08 ranking isolation (Phase 12): usage counters never affect ranking — hard invariant with a negative-space test; usage-weighted recall is an explicit out-of-scope future decision.
- D-09 (Phase 12): `ENGRAM_USAGE_SIGNALS` defaults **on** (unlike `summarize.on_write`) — usage signals are local, non-egressing curation metadata.
