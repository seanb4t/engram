<objective>
Add the D-06 analytics half of the hybrid design: attach the returned record ids
(bounded) and count as attributes on the existing `store.Search` / `store.List` /
`store.Get` spans, so ClickStack can answer "which ids appeared in which result
sets" without any storage change and without ever touching the payload counter.

Purpose: This is the "zero storage change" analytics leg. It lives at the store
layer — the single seam shared by both the MCP and Connect call paths — not in the
MCP-only `instrumentTools` middleware (which lacks typed result ids).
Output: a bounded `recallIDs` helper + `engram.recall.ids`/`engram.recall.count`
on Search/List/Get spans, with span-recorder tests.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-11 | Denial of Service | engram.recall.ids attribute cardinality | high | mitigate | `recallIDs` caps the slice at a bounded const; an attacker issuing huge-k recalls cannot blow up span attribute size unboundedly. |
| T-12-12 | Information Disclosure | recall ids on spans | low | accept | Ids are the same opaque UUIDs the caller already received in the result set; the span is emitted only for the caller's own gated recall (owner/scope filter runs before Search/List). No cross-actor leak — the result slice is already owner-filtered. |
| T-12-05 | Tampering (integrity) | recall-span path vs ranking/counter | high | mitigate | This path is analytics-only: it reads result ids but never writes access_count and never feeds rerank — verified by keeping the edit inside the span defer with no store mutation (D-02/D-06/D-08 boundary). |
| T-12-SC | Tampering | package installs | low | accept | No new external packages (otel already vendored). |
</threat_model>
