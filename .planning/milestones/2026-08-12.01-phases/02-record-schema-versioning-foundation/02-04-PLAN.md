## The older-than direction at `CurrentVersion = 0`

Plan 02-01 resolves `migrate.CurrentVersion = 0`. `CurrentVersion - 1` is therefore not a
representable record state, and inventing a negative version to satisfy the letter of D-08 would be
a fabricated test subject.

The genuine older-than-binary state at `CurrentVersion = 0` is **the key-absent legacy record** — a
record written before the field existed, which is exactly the population criterion 2 is about and
exactly what a rolled-back binary encounters. That is the mirror case, and it is real.

**Do not paper over this with a silent `t.Skip`.** A row that quietly disables itself is the vacuous
shape this project has already shipped once. Instead the row set is *derived* from the constant:

- `CurrentVersion == 0` → two rows: `absent` (older-than) and `newer` (`CurrentVersion + 1`).
- `CurrentVersion > 0` → three rows: `absent`, `older-explicit` (`CurrentVersion - 1`), and `newer`.

The test asserts its executed row count equals the derived expected count. When Phase 3 or 4 raises
the constant, the third row activates on its own and the count assertion is what forces it to
actually run.

## Two records per row, and why one cannot work (review finding H5)

The previous revision of this plan asked each row to "seed the row's record so those paths
legitimately apply" for `ListScheduled` and `SearchDiscovery`. **That is unsatisfiable for a single
record**, and Codex is right to have flagged it HIGH. Verified against source:

- Normal `List` appends `activeWindowConditions(s.now())` to its filter (`store.go:1260`), so it
  returns only records whose temporal window is currently valid.
- `ListScheduled` selects on `scheduledStateCondition` — pending (`now < not_before`) or expired
  (`now >= not_after`) — and its own type comment says so explicitly: *"Active (currently-valid)
  windowed records are never returned here — they surface through normal Search/List"*
  (`store.go:1417`, `store.go:1459`).

The two populations are disjoint by construction. No seeding trick makes one record a member of both.

**The five recall paths also do not share recall semantics**, and the plan must stop implying they
do. `SearchDiscovery` applies **no temporal gate at all** — verified by reading `store.go:1118-1135`,
its `must` slice carries category, scope, kind, authz, `superseded_by` and `archived_at`, and no
window conditions. So a *pending* discovery record is visible through `SearchDiscovery` while hidden
from normal `Search`/`List`. Treating the five as interchangeable would produce assertions that are
either wrong or accidentally true.

**The fix: each version row seeds TWO raw-injected records with identical version and unknown-key
shapes.**

| Record | Temporal shape | Category | Asserted through |
|---|---|---|---|
| `active` | no window, or a currently-valid one | `discovery` | `Search`, `SearchReranked`, `SearchDiscovery`, `List`, `Store.Get` |
| `windowed` | pending (`not_before` in the future) | `discovery` | `ListScheduled`, `SearchDiscovery`, `Store.Get` |

The `windowed` record appearing in BOTH `ListScheduled` and `SearchDiscovery` is not a contradiction
— it is the direct consequence of `SearchDiscovery` having no temporal gate, and asserting it there
is what pins that fact rather than leaving it as an accident. Comment it as such.

**Express this as an explicit per-path applicability matrix in the test**, one entry per (record,
recall path) pair with a boolean expectation and a one-line reason. That replaces the previous
plan's "every recall path" language, which the review correctly called a success criterion weakened
into prose: a path is either asserted-present, asserted-absent, or carries a written reason it does
not apply — never silently omitted, and never claimed by a blanket phrase the fixtures cannot honour.

## The previously-flagged probe item: RESOLVED

An earlier revision of this plan carried one probe item as an unresolved flagged assumption — the
probe could not classify which edge category applies to "a binary reading a record whose
`schema_version` is newer than its own constant," so the plan asked a reviewer to confirm the two
assumed edges.

**Both reviewers rejected carrying it, and they are right.** Codex: testing `CurrentVersion + 1` is
sufficient for decoder tolerance because the decoder does not dispatch on the numeric value —
`fromPayload` reads the integer into a field and never branches on it, so a version newer by one and
a version newer by ten exercise the same code. Kimi, more bluntly: it is process theater, because
CONTEXT.md D-08 already defines exactly those edges in writing.

**Resolution: covered by D-08.** The operative edges are *decode tolerance* (an unrecognized payload
key is ignored rather than fataled) and *monotonic non-downgrade on rewrite*, and D-08 names both.
No reviewer action is outstanding and no flagged-assumption block is carried forward. A farther-future
row becomes worth adding only if a later phase introduces numeric bounds or version dispatch — at
which point the decoder WOULD branch on the value and the extra row would test something new.
`REQ-version-dispatch-codec` is deliberately deferred to v2, so that is not this phase.

**Probe accounting, restated so the arithmetic does not dangle** (this matters because removing the
one unresolved item changes the totals): **9 probe items → 9 authored into `must_haves` → 0 flagged
assumptions.** The item formerly carried as unresolved is now authored as the `newer`-row truths
covering decode tolerance and monotonic non-downgrade. If a reader counts 8 or finds a flagged block
below, this plan was edited out of sync with this paragraph and the discrepancy is the bug.
