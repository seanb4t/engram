<objective>
Prove ROADMAP success criterion 4: `Store.Migrate`'s sweep survives a forced mid-sequence partial
`SetPayload` failure against a real pinned Qdrant, and a subsequent resume converges the backlog to
zero — reconciling by re-derivation, never by trusting the write call's own success/failure signal.

Purpose: Qdrant chunks a multi-ID payload write internally and mutates every point it finds before
raising an error for one it does not (qdrant/qdrant#9371, already documented in this repo at
`store.go:127-140` and `:2213-2223`). The consequence is that a `SetPayload` error means
*possibly-partial*, never reliably *nothing landed*. The sweep's entire recovery design rests on
refusing to read that signal. This plan makes that refusal observable by injecting a failure whose
error value is deliberately a LIE — the write commits and the call still errors — and showing the
sweep converges anyway.

**What this proves about #9371, stated precisely** (review cycle 1: the earlier framing overclaimed).
The sweep writes ONE point per `SetPayload` (PA-2), which removes the WITHIN-CALL multi-ID partiality
class BY CONSTRUCTION — there is no second id in the call for a later internal chunk to miss. That is
a design improvement, not a test result, and this plan does not reproduce that class. What remains,
and what these scenarios actually exercise, are the two classes per-point writing does NOT remove:
CROSS-CALL partial progress (some points of a pass landed, some did not, and the next pass must
re-derive rather than replay) and UNRELIABLE ERROR SIGNALS (a call that committed and still returned an
error, which is #9371's actual operational hazard). SC4's evidence must be worded that way in the
SUMMARY — "eliminated by construction" for the first, "proven by test" for the other two — rather than
claiming a reproduction of batch non-atomicity the implementation deliberately made unreachable.

Output: a gRPC fault-injecting client seam extending the one plan 02-03 already built, a three-scenario
integration test against the pinned `qdrant/qdrant:v1.18.2` testcontainer, and two committed RED
patches — one that re-introduces a persisted cursor, one that makes the sweep trust the error it must
not trust.
</objective>

**PA-3 (carried forward from 03-01).** The sweep terminates on a **non-shrinking freshly-counted

**PA-7 (two injection modes, and why both).** The injector supports failing *before* invoking (the
write never reaches the server) and failing *after* invoking (the write commits, then the call returns
an error). Only the second reproduces qdrant/qdrant#9371's actual hazard — an error that does not
describe what landed. A plan that injected only the first would prove the sweep retries, not that it
disbelieves the signal, and D-09 is specifically about the second.

**Say what the fail-after mode is and is not** (review cycle 1). It is a SEMANTIC simulation: the RPC
succeeds at the server and the interceptor substitutes a `status.Error` on the way back, so what
`Store.Migrate` observes is an ordinary gRPC status error returned from its own call, carrying exactly
the information a server-generated one would — which is to say, nothing about what landed. It is NOT a
literal server-generated transport failure, and no comment, doc comment or SUMMARY line may call the
induced error "indistinguishable from a real failure at the wire". D-10's locked choice of the
interceptor mechanism is unchanged; only this plan's characterisation of the fail-after mode is
tightened. What matters for D-09 is the sweep's epistemic position — an error value that does not
describe the collection — and the simulation reproduces that exactly.

interceptor is the deliberately different choice here, and the reason is that the hook partly tests the
hook rather than the sweep.

**PA-16 (the resume must be OBSERVED, not assumed — review cycle 1's confirmed HIGH finding).** The
previous shape of scenario 2 asserted something about "the ids the injector recorded for the resume's
writes" while the injector was wired ONLY to the first client. The resume ran through a second, plain
client the injector never saw, so its recorded set for the resume was empty and the exclusion
assertion was trivially true whether the resume re-derived or replayed. That is precisely the
observes-nothing failure mode this phase exists to eliminate (durable record `x6v6qxqd6f`).

The resolution keeps D-07's point — the resume is a different `*Store` on a different client, sharing
no in-process state — and adds a SECOND, INDEPENDENT recording interceptor on that resume client. A
`setPayloadFaultInjector` left DISARMED is exactly a recorder: it counts writes and records their
selected ids without altering behavior. The resume store is therefore built with
`dialFaultInjectingTestClient(t, resumeInj)` where `resumeInj` is a fresh, never-armed instance. It is
a test observer, not shared sweep state: it holds no cursor, no failed-id set, and nothing
`Store.Migrate` reads. Two assertions then carry the scenario, and neither is satisfiable by an
interceptor that saw nothing:
- `resumeInj.seen() > 0` — the resume's writes were observed at all;
- `resumeInj`'s recorded id set is SET-EQUAL to the ids that had NOT been written before the resume,
  with both difference directions printed. A replay of the already-migrated record shows up as an
  extra id and fails; an unobserved resume shows up as an empty set and fails.
