<objective>
Close the one non-obvious write path and wire the caps into the production store. Connect's
`UpdateMemory` calls `deps.updateMemory` directly and never runs `validateUpdateArgs`, so a content
or tags cap placed only in a validator would never fire for it (the #360-shaped trap RESEARCH names).
This plan puts both checks inside `deps.updateMemory`, gated on what actually changes, proves that a
legacy over-cap record stays readable and editable, and passes the configured caps to the store so
plan 03-02's read-side ceiling is derived from exactly what the write side enforces.

Decisions implemented: D-01 (every memory write path, `update_memory` when it changes content,
existing `field=content hint=too_long` envelope), D-09 (the content check lives where every lane
reaches it — inside `deps.updateMemory`, gated on `contentChanged`), D-10 (tags caps on update, with
the existing `too_many` / `too_long` hints), D-07 ("existing oversized records stay readable": served
by `get_memory`, and an owner can trim one via `update_memory`), and D-02/D-09's read-side link
(`store.WithRecordCaps` from the same parsed config). Framing (D-00): one shared enforcement point,
the existing `Option` pattern, no new mechanism.

Gating choice for tags (planner's discretion, following D-09's `contentChanged` precedent): the tags
check runs when the supplied set differs from the stored set (`slices.Equal`, order-sensitive), so
resending a legacy record's own tags is not a rejection. `update_memory` applies the memory caps to
whatever record it edits, discovery and rule records included; `store_discovery`'s and
`store_rule`'s own create-time bounds are unchanged.

Purpose: REQ-content-cap-decided (the update lane and the legacy-readable half); the production
wiring REQ-byte-budget-pages' ceiling depends on.

Output: two guarded checks in `deps.updateMemory`, `recordCapsFromConfig` and its use in
`storeFromConfig`, and hermetic update/legacy tests plus one Qdrant-backed wiring test.
</objective>
