<objective>
Introduce the phase's one new architectural piece — a shared, byte-and-time bounded response-body
drain — and land it end to end on the embed lane: helper, client options, both call sites, and the
regressions that prove a provider can no longer stall a goroutine through either axis.

This plan also closes the embed half of the request-timeout hole: `WithTimeout(0)` stops meaning
"forever" and resolves to a configurable ceiling instead (D-07/D-09), and the already-shipped
bounded error read gains the truncation assertion it never had (D-10).

Why the tracer covers only the code spine and not the configuration lane: the novel, failure-prone
part of this phase is the helper's mechanism and the deliberate defaults divergence (D-01, D-05,
D-06). The `internal/config` registry lane that plan 07-02 adds is a twenty-precedent pattern with
no architectural unknown — a tracer through it would add no information, so it runs in parallel
instead.

Decisions covered: D-00 (choose by idiom and long-term maintenance, never by effort — which is why
the mechanism goes in one shared package rather than a private copy per lane), D-01
(timer-closes-the-body mechanism), D-02 (one shared helper in a new
package), D-03 (both embed sites, success path included), D-05 (zero skips the drain), D-06
(defaults before options), D-07 and D-09 (the ceiling, applied in `New` after options), D-10 (the
truncation assertion — embed half), D-11 (both regression shapes — embed half).

Purpose: after this plan, no embed response body — however large, however slow — can hold a
goroutine past a bound the operator can see.

Output: a new `internal/httpdrain` package, a shared bounded trickle handler in `internal/testhttp`,
and an embed client whose every post-response read is bounded on both axes.
</objective>

**The helper this plan creates** (`internal/httpdrain/httpdrain.go`). CONTEXT.md D-01 pins the
mechanism; the API shape below is this plan's choice and every later plan depends on it verbatim:

```go
// Drain abandons the rest of body, bounded by bytes and by time.
func Drain(body io.ReadCloser, maxBytes int64, maxTime time.Duration)
```

Both bounds are honored: the copy runs through `io.LimitReader(body, maxBytes)`, and a
`time.AfterFunc(maxTime, …)` closes the body so a blocked read is released; `defer t.Stop()` means
no timer and no goroutine outlives the call. A non-positive value for EITHER bound closes the body
and returns without reading anything (D-05). Errors are discarded: the unblocked read returns
`errReadOnClosedResBody`, which needs no special case.

**Existing embed shapes this plan changes** (`internal/embed/embed.go`):

- `Client` struct (`:46-71`) — gains `drainBytes int64`, `drainTimeout time.Duration`,
  `maxTimeout time.Duration`.
- `New` (`:133-148`) — today the struct literal is
  `&Client{baseURL: …, http: &http.Client{Timeout: defaultEmbedTimeout}}`, options run, then two
  post-loop fallbacks fire (`embeddingsURL`, `maxResponseBytes`).
- `WithMaxResponseBytes` (`:120-131`) — the sibling convention: `if n > 0 { … }`, so a non-positive
  value is silently ignored and the default survives. The drain options must NOT copy this.
- `WithTimeout` (`:103-110`) — one line, `c.http.Timeout = d`, with a doc comment that currently
  promises `d <= 0` disables the timeout. Both the comment and the resulting behavior change here.
- `maxErrorBodyBytes = 4096` (`:37`), `defaultMaxResponseBytes = 1 << 20` (`:44`),
  `defaultEmbedTimeout = 30 * time.Second` (`:31`) — all unchanged.
- The two drain sites, `:295` (after the bounded error read) and `:309` (after the bounded decode).
  Both are a single line copying `resp.Body` into the discard writer with no bound at all, with a

- The caller's `defer func() { _ = resp.Body.Close() }()` (`:281`) stays exactly as is. After the
  drain closes the body, that deferred call is a harmless second Close — `net/http` returns nil.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| provider response → engram goroutine | A response body is attacker-shaped as far as engram is concerned: size and arrival RATE are both under the provider's control, and both were previously unbounded after the useful read finished. |
| provider error body → operator log | A non-2xx body is surfaced in an error that `connectError`'s default arm logs server-side, so an oversized or reflecting body reaches an operator log. |
| operator configuration → client bounds | An operator-supplied bound decides how long a goroutine may be held; a value that silently resolves to "no bound" defeats the control. |
| test harness → CI wall clock | A deliberately slow test server holds a CI worker for as long as it chooses to keep writing. |
