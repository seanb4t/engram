<task type="checkpoint:decision" gate="blocking">
  <decision>D-08: `--page-token` supplied together with `--offset` becomes a hard error (exit 2) instead of being silently ignored.</decision>
  <context>
This is a one-way door. Today `client_list.go`'s help text promises `--page-token` "ignores
`--offset`", so a caller passing both gets a successful, differently-paged response. After this
change the same invocation fails with exit 2 before any dial. Any script relying on the ignore
breaks, and undoing it later means re-publishing a contract callers will have already adapted to
(a `guides/upgrade.md` entry names it in plan 01-09).

Note the blast radius is wider than the literal `--page-token`+`--offset` pair: cobra's flag groups
count a *supplied* flag, not its value, so `engram list --offset 0 --page-token ''` — both at their
zero values — is also rejected. CONTEXT.md records the human choosing this option; this checkpoint
confirms the door with that widened radius made explicit.
  </context>
  <options>
    <option id="reject-both">
      <name>Reject any two of the paging trio, regardless of value (the D-08 decision)</name>
      <pros>The paging model becomes correct-by-reading; a caller-supplied flag is never silently discarded; one `MarkFlagsMutuallyExclusive` call closes both the unenforced trio and D-08.</pros>
      <cons>Breaks callers that pass both today; also rejects zero-valued combinations that were previously harmless.</cons>
    </option>
    <option id="reject-nonzero-only">
      <name>Keep a hand-rolled guard that only rejects when both flags carry non-zero values</name>
      <pros>Narrower blast radius; zero-valued combinations keep working.</pros>
      <cons>Re-introduces exactly the fourth hand-rolled guard SC1 exists to eliminate, and leaves the constraint declared in help text but enforced somewhere else.</cons>
    </option>
  </options>
  <resume-signal>Select: reject-both, reject-nonzero-only, or describe an alternative</resume-signal>

Wire ONE path end-to-end. Three edits and one test, no other call sites.

1. `cmd/engram/client_list.go` — inside the existing `init()`, immediately before
   `rootCmd.AddCommand(listCmd)`, add
   `listCmd.MarkFlagsMutuallyExclusive("offset", "cursor-mode", "page-token")`.
   Also correct the three flags' `Usage` strings so the interface teaches the real rule: `--offset`,
   `--cursor-mode`, and `--page-token` each name the other two as mutually exclusive. Remove the
   `--page-token` usage text's promise that it ignores `--offset`; that promise is what D-08
   retracts.

2. `cmd/engram/root.go` — change `rootCmd.PersistentPreRunE`'s signature from `func(_ *cobra.Command,
   _ []string) error` to `func(cmd *cobra.Command, _ []string) error` and add, after the existing
   `config.CheckLegacy` call, a call to `cmd.ValidateFlagGroups()` whose non-nil result is returned
   wrapped by `usageErrorf`. Leave `config.CheckLegacy`'s own error untouched in this task — Task 2
   owns it.

   Why this is the mechanism and not `SetFlagErrorFunc`: cobra 1.10.2 calls `c.ValidateFlagGroups()`
   inline inside `Command.execute()` with no hook of its own, immediately after `PersistentPreRunE`
   and immediately before `RunE`. Because `EnableTraverseRunHooks` is false, cobra invokes the first
   `PersistentPreRunE` found walking child to parent — root's, the only one in this binary — and it
   passes the *leaf* command as the callback's first argument. So `cmd.ValidateFlagGroups()` inside
   root's hook validates the running subcommand's groups and short-circuits `execute()` before
   cobra's own redundant call is reached. One edit types every flag-group site in the binary.
   Cobra's later call still runs when the hook returns nil; it re-validates unchanged flag state and
   can only agree.

3. Add a `<verify>`-bearing end-to-end test in a new `cmd/engram/flaggroup_test.go` (Apache-2.0 SPDX
   header, `package main`): `TestFlagGroupPagingTrioRejectedBeforeDial`. It must
   (a) start a `net.Listener` on `127.0.0.1:0` whose accept loop increments a counter and closes,
   (b) run `runClient(t, "list", "--server", "http://"+ln.Addr().String(), "--scope", "s",
   "--offset", "1", "--page-token", "X")`,
   (c) assert `exitCodeFromError(err)` is `exitUsage`, and
   (d) assert the accept counter is 0.
   The zero-accept assertion is the load-bearing half — it is what proves "rejected before any
   network dial" rather than merely "rejected". Call `resetClientFlags(t)` and
   `resetCommandFlagState(t, rootCmd)` first.

4. In the same file add `TestFlagGroupRejectionPerformsNoIO`, which carries edge item **E-04** (see
   the edge ledger in plan 01-01). Reuse the single accept-counting listener from step 3 and drive a
   small table of rejected paging-trio invocations from several goroutines against it, joined with a
   `sync.WaitGroup`. Assert three things after the join: every invocation's `exitCodeFromError(err)`
   is `exitUsage`; the listener's total accept count — read through a mutex or `atomic.Int64`, since
   the accept loop and the assertions are on different goroutines — is exactly 0; and no invocation
   produced a result payload on stdout (`runClient`'s captured stdout is empty for each).

   This is a deliberate exception to "do not mark subtests parallel": these rows share no cobra flag
   state because each supplies the identical argv, so there is nothing for a `Changed` latch to leak
   between them. Serialize the argv construction, not the runs. If the harness turns out not to be
   safe to call from multiple goroutines, keep the assertions and run the table sequentially against
   the one shared counter — the load-bearing claim is the shared total of 0, not the parallelism.

Do not touch `client_search.go`, `migrate.go`, `client_common.go`'s guard, or any operator command
in this task; those are the expansion in plan 01-04.
