<task type="checkpoint:decision" gate="blocking">
  <name>Checkpoint: which `serve` failures join the taxonomy, and which stays on exit 1</name>
  <decision>Does `serve`'s `ListenAndServe` failure (for example, "address already in use") get a taxonomy mapping, or stay on the exit-1 backstop?</decision>
  <context>
D-03 says the six operator commands get "full classification", and `serve` is one of them — but
D-03 does not reach inside `serve` to say how deep. RESEARCH.md raised this as a genuinely
undecided question rather than guessing, and it is a one-way call on the same published contract
D-03 changes: once `serve` starts reporting a specific code for a failed bind, withdrawing it
breaks whoever began branching on it.

`serve`'s pre-flight failures are unambiguous — an empty listen address, a malformed cookie key,
an invalid OIDC or UI configuration, an owner-claim parse failure, headless without a configured
auth lane — all are the operator supplying a value the process cannot use, and D-03's "bad flag
value -> 2" covers them. The genuinely open case is the listener itself failing to bind. That is a
*local OS resource* failure. Exit 5 has meant "the remote server or Qdrant is unreachable" at every
other site in this taxonomy, so mapping a local bind failure onto it would make 5 ambiguous for any
caller that scripts both `serve` and a client verb.
  </context>
  <options>
    <option id="backstop-1">
      <name>Pre-flight config failures exit 2; `ListenAndServe`'s own failure stays on exit 1, documented</name>
      <pros>Keeps 5 unambiguous for every caller already branching on it; matches D-02's framing of 1 as the backstop where a genuinely unclassified failure degrades loudly rather than being misfiled; the exception is named in the source, `guides/cli.md`, and `guides/upgrade.md` so it reads as deliberate.</pros>
      <cons>`serve` retains one exit-1 path, so "no path falls through to a bare exit 1" is true only for classifiable paths — the success criterion must be read that way.</cons>
    </option>
    <option id="map-to-5">
      <name>Map `ListenAndServe`'s failure to exit 5 as well</name>
      <pros>`serve` has no exit-1 path at all; the success criterion reads literally.</pros>
      <cons>Overloads 5 with two unrelated conditions — a remote backend that cannot be reached, and a local port that is taken — so a supervisor branching on 5 can no longer tell which remedy applies.</cons>
    </option>
    <option id="new-code">
      <name>Introduce a further exit code for a local resource failure</name>
      <pros>Unambiguous for both conditions.</pros>
      <cons>A second published-contract addition in the same phase, beyond what any decision authorized, with its own catalog entry, upgrade note, and consumer audit.</cons>
    </option>
  </options>
  <resume-signal>Select: backstop-1, map-to-5, new-code, or describe an alternative</resume-signal>
</task>
