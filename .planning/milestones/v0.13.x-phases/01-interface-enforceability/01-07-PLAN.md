<task type="checkpoint:decision" gate="blocking">
  <decision>D-01: `exitAuth = 3` survives the unification rather than being collapsed into the 0/2/4/5 set named by the success criterion.</decision>
  <context>
This is a one-way door on a published contract. `engram catalog` advertises the exit-code set, and
removing a code breaks any consumer branching on it — a removal would need its own upgrade note and
could not be quietly reversed.

The case for keeping it: SC2 names "0 (success), 2 (usage/validation), 4 (not found), 5
(unavailable)" as the codes the unification moves things *into*, not as an exhaustive taxonomy.
`exitAuth` is already distinct, already pinned by `TestClientSearchExitCodeAuth`, already
advertised, and reachable only through the Connect mapper. Collapsing it would lose a distinction
callers act on — re-authenticate, versus fix your flags, versus retry later — and would itself be a
gratuitous breaking change inside a phase whose whole purpose is to make breaking changes
deliberate.
  </context>
  <options>
    <option id="keep-3">
      <name>Keep `exitAuth = 3` (the D-01 decision)</name>
      <pros>Preserves a distinction callers act on; avoids a second, unrequested breaking change; the code is already advertised and tested.</pros>
      <cons>The advertised set is larger than SC2's literal enumeration, so the success criterion must be read as non-exhaustive.</cons>
    </option>
    <option id="collapse-3">
      <name>Collapse authentication failures into exit 2</name>
      <pros>The advertised set matches SC2's literal wording exactly.</pros>
      <cons>Removes a published code; a script cannot distinguish "your token expired" from "your flags are wrong"; requires its own upgrade note and consumer audit.</cons>
    </option>
  </options>
  <resume-signal>Select: keep-3, collapse-3, or describe an alternative</resume-signal>

<task type="checkpoint:decision" gate="blocking">
  <decision>D-06: a client-side timeout reports a new dedicated exit code 6 rather than reusing 5.</decision>
  <context>
This is a one-way door for the same reason as D-01: adding a code to a published contract cannot be
withdrawn without breaking whoever started branching on it.

The case for a new code: "the server never answered in time" and "I could not connect at all" call
for different operator responses — raise the timeout versus check the server is up. Today
`connect.CodeDeadlineExceeded` is folded into `exitUnavailable` alongside `CodeUnavailable` and
`CodeCanceled`, so the two are indistinguishable.

Consequences to accept: a new constant, a new catalog entry, a `guides/upgrade.md` line, and a
consumer audit that covers the new code as well as the changed ones.
`TestCatalogExitCodesMatchMapper` re-derives its expected set from the mapper and needs no edit, but
`TestCatalogListsEveryExitCode` hard-codes a count of 6 and a 0-5 range and will fail red in the
same commit unless updated.
  </context>
  <options>
    <option id="new-code-6">
      <name>Add `exitTimeout = 6` (the D-06 decision)</name>
      <pros>A caller can distinguish a slow server from an absent one; the timeout capability is discoverable through the catalog.</pros>
      <cons>Widens the published code set; every consumer audit must cover a code that did not exist before.</cons>
    </option>
    <option id="reuse-5">
      <name>Report a timeout as `exitUnavailable` (5), as today</name>
      <pros>No change to the advertised code set; no catalog or consumer-audit work for a new code.</pros>
      <cons>Conflates two conditions with different remedies; a caller that raises `--timeout` in response to a 5 may be chasing a server that is simply down.</cons>
    </option>
  </options>
  <resume-signal>Select: new-code-6, reuse-5, or describe an alternative</resume-signal>
</task>
