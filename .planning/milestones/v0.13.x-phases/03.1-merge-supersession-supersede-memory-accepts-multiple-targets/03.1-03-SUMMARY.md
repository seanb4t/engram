# Phase 03.1 Plan 03: Staged Multi-Fault Rejection Preflight Summary

**`supersede_memory`'s preflight split into `resolveAndAuthorizeSupersedeTargets` (set-shape + addressability/access, collapsed into one not-found class) and `validateSupersedeTargetState` (rule immutability + already-superseded), proven by two whole-rejection indistinguishability tests, a mixed-pass caller-order test, and four observed-red regression checks.**

## Performance

- **Duration:** ~40 min (not precisely instrumented at start; bounded by container/session timestamps)
- **Tasks:** 3/3 completed
- **Files modified:** 2

## Accomplishments

- `resolveAndAuthorizeSupersedeTargets` (Classes 1-2): Class 1 checks set shape only (empty array, blank entry) — no length branch, per PD-07's cap-dropped ruling. Class 2 resolves every input, sorts results into a `resolved` bucket and an `unaddressable` bucket over THREE causes (resolution-not-found, resolution-ambiguous, fetch-not-found/not-owned), all reported through the existing `store.ErrNotFound` sentinel. The unaddressable bucket carries each entry's ORIGINAL input index and is stable-sorted by it before rendering, so a mixed-pass rejection (`[nonOwned, missing]`) still names offenders in the caller's order.
- `validateSupersedeTargetState` (Classes 3-4): rule immutability and already-superseded, evaluated only over the already-resolved, already-owned pairs Class 2 returned — nothing here can be reached by a non-owned or nonexistent target.
- `renderTargetRejection(sentinel, inputs) error` is the one production helper every rejection in this verb goes through (`fmt.Errorf("%w: %s", sentinel, strings.Join(inputs, ", "))`), including both store-tier re-wraps in the rewired handler.
- `resolvedSupersedeTarget{Input, ID, Rec}` carries the caller's original string alongside the resolved id and fetched record; every rejection message is built from `Input`, never `ID`.
- `deps.supersedeMemory` rewired onto the two staged calls as separate statements with a marker comment naming plan 04's idempotency-replay insertion point between them; store-tier `ErrNotFound` (the race window) and `ErrAlreadySuperseded` (via `errors.As` against `*store.MultiTargetError`, PD-10) are both re-wrapped through `renderTargetRejection` with the caller's original inputs, never a resolved UUID, and never by parsing an error message.
- `supersedeMemoryInputSchema()` builds the advertised MCP schema and sets `minItems: 1` on `supersedes` directly on the generated `*jsonschema.Schema` — the "jsonschema" struct tag can only supply a description, not a numeric constraint (confirmed against jsonschema-go v0.4.3's `infer.go`, which sets `MinItems`/`MaxItems` only for fixed-size Go arrays, never slices). `Register()`'s `supersede_memory` `mcp.AddTool` call and `TestSupersedeMemorySchemaAdvertisesTargetBounds` both call this exact function, so the advertised schema and the asserted bound can never drift apart. No `maxItems` is set or asserted, per PD-07.
- `supersede_memory`'s tool Description restated for the multi-target, collapsed-class contract (not-owned/nonexistent/ambiguous are all the same answer; an ambiguous short id must be replaced with the full UUID).
- Eight new handler-level tests plus two function-level table tests prove the class order, the two security-relevant indistinguishability invariants, caller-order preservation across mixed passes, and the schema bound (see Task Commits below).
- Four regression checks were run manually (not committed): first-offender-only collection, resolved-id echo, ambiguity-reported-as-its-own-class, and the index-stable sort removed. All four produced the exact predicted failures and were reverted before committing (see "Regression checks" below).

## Decisions Made

- **PD-07 cap-dropped ruling implemented exactly as recorded in `03.1-00-SUMMARY.md`:** no `maxSupersedeTargets` constant exists anywhere in `internal/server/tools.go` (`rg -o 'maxSupersedeTargets' internal/server/tools.go | wc -l` = 0), Class 1 has no length branch, and the advertised schema carries `minItems: 1` with no `maxItems`. `TestSupersedeMemoryTooManyTargetsRejected` from the plan's artifact list does not exist — there is no oversized-set behavior to cover.
- **`supersedeMemoryInputSchema()` extracted as a named function rather than an inline schema literal in `Register()`:** the plan requires the SAME schema-building path to back both the production registration and the bounds test, so the advertised schema and the test's assertion can never independently drift. This also means `registerTools` now has a genuine (if practically unreachable) failure mode — its doc comment was updated to say so rather than left stating "always returns nil today," which would have become an inaccurate claim.
- **Class 2's two-pass bucket collection requires an explicit per-entry index and a stable sort**, not just appending in whatever order each pass runs — cycle-3 review's MEDIUM finding. Verified load-bearing via the regression check below (removing the sort breaks exactly the mixed-pass ordering test and nothing else).
- **`errors.As` against `*store.MultiTargetError` maps offending canonical ids back to caller inputs via a `map[string]string` built from the resolved pairs, with a whole-input-set fallback if the mapping ever comes back empty** — conservative by construction, and never parses the error's message text (a parsing bug here would be a disclosure bug, not just a cosmetic one).

## Deviations from Plan

### Process Deviation

**1. Tasks 1 and 2 landed in one commit instead of two**
- **Rationale:** Task 1 (the staged preflight functions) and Task 2 (rewiring `deps.supersedeMemory` onto them) both modify the exact same function body — the whole point of Task 2 is replacing Task 1's own target, the pre-existing inline resolve/gate sequence, with calls to what Task 1 just added. Splitting them into two commits after the fact would have required hand-reconstructing an intermediate state (new staged functions coexisting with the OLD, still-inline `supersedeMemory` body) that the available editing tools cannot cleanly extract from a single completed edit without redoing the work twice. Plan `03.1-01` (wave 2, same phase) hit and documented the identical constraint for its own three tasks.
- **Impact:** Both tasks' acceptance criteria were independently verified — `rg` structural counts, the two dedicated unit tests (`TestResolveAndAuthorizeSupersedeTargets`, `TestValidateSupersedeTargetState`), the full pre-existing `TestSupersedeMemory*` suite, and `golangci-lint run ./internal/server/...` — before the single commit landed. No verification was skipped or merged across task boundaries; see the acceptance-criteria checks recorded during execution.

No auto-fixed issues (Rules 1-3): the plan's action text was specific enough that no bug, missing-functionality gap, or blocking issue required an unplanned fix.

## Regression checks (observed red, then reverted — not committed)

- **First-offender-only collection** (would break D1): changed Class 2's resolution loop to `return nil, renderTargetRejection(store.ErrNotFound, []string{in})` on the first unaddressable input instead of collecting all. `TestSupersedeMemoryMultiNamesAllNotFoundTargets` failed: `tools_test.go:3370: err not found: notfound001 does not name both missing targets "notfound001", "notfound002"`. Reverted via `git checkout -- internal/server/tools.go`; suite green again.
- **Resolved-id echo instead of caller input** (would break D5): changed the fetch-pass unaddressable append to carry `r.ID` instead of `r.Input`. `TestSupersedeMemoryMultiEchoesOriginalInput` failed on both assertions: `tools_test.go:3470: err not found: d0000000-...-000000000001 does not echo the caller's original short_id input "abtarget99"` and `tools_test.go:3473: ... leaks the resolved UUID ... (404-indistinguishability violation)`. Reverted; suite green again.
- **Ambiguity reported as its own class ahead of ownership** (would break D3, the T-03.1-23 mitigation): split `store.ErrAmbiguousShortID` out of the collapsed bucket to `return nil, err` immediately. `TestSupersedeMemoryAmbiguousShortIDIndistinguishable` failed: `tools_test.go:3621: errAmbig=ambiguous short id: abcdefghjk errNoSuch=not found: nosuchid01, want both store.ErrNotFound`. Reverted; suite green again.
- **Index-stable sort removed** (would break D6, cycle-3 review's MEDIUM): removed the `slices.SortStableFunc` call over the unaddressable bucket. `TestSupersedeMemoryMultiOffenderOrderIsCallerOrder` failed on EXACTLY the predicted subtest — `nonOwned_then_missing_(pass-two_offender_first)`: `tools_test.go:3571: err "not found: zzzznotfnd, e0000000-...-000000000001": offender order is wrong`. The mirrored subtest (`missing_then_nonOwned_(pass-one_offender_first)`) still PASSED, because in that ordering pass order and caller order coincide by construction — the exact contrast the acceptance criteria describes as proof the sort is load-bearing rather than cosmetic. Running the full `TestSupersedeMemory*` suite with this regression applied confirmed every OTHER test still passed (only the offender-order test failed). Reverted; full suite green again.
