# Phase 03.1: Merge Supersession - Context

**Gathered:** 2026-08-10
**Status:** Ready for planning

<domain>
## Phase Boundary

`supersede_memory` accepts a **set** of `supersedes` targets. One call stores one new correcting
record and back-stamps `superseded_by` on every target, so a duplicate set collapses to a single
surviving record with history preserved for all predecessors — and with **no `delete_memory` in the
merge path**.

Not in scope: producing the candidate pairs (Phase 3's `spine-review consolidate` owns that), the
semantic judgment of whether two records are the same fact (Phase 4's skill owns that), and a
versioned payload-migration mechanism (deferred — see below).

</domain>

<decisions>
## Implementation Decisions

### Link shape — the singular→plural seam

- **D-01:** `supersedes` is **promoted to a list**. The single-target call becomes the 1-element
  case of the general form; there is no second way to express the same fact. Rejected:
  keep-scalar-plus-a-new-plural-key (two keys encoding overlapping truth, every future reader must
  know which wins) and drop-the-outbound-pointer (breaks existing single-target behavior and turns
  "what did this replace?" into a scan).
  — **Reversibility:** costly — the key is persisted in Qdrant payloads, read by the store decoder,
  rendered by the MCP response builders and the CLI, and described in `docs-site`. Reverting means
  touching all of those together plus every record already written in the plural form.

- **D-02:** `superseded_by` **stays scalar** and is untouched. Each predecessor has exactly one
  successor, and the recall soft-hide gate filters on `IsEmpty("superseded_by")` at four call sites
  (`store.go:954`, `1054`, `1191`, `1426`). The pluralization is strictly one-directional.

- **D-03:** The wire shape is **always an array**, even for one predecessor — `supersedes: ["<id>"]`.
  One shape for every reader; no polymorphic string-or-array field for agents to type-switch on.
  Accepted cost: this is an observable output change for anything already parsing the scalar, and
  `supersede_memory` is MCP-only, so "anything" means agents reading the JSON.
  — **Reversibility:** costly — it is a published output shape consumed by agents; changing it back
  would break any client written against the array form.

- **D-04:** **Tolerant decoder, no backfill command.** The decoder accepts string *or* array; a
  legacy scalar record surfaces as a 1-element list. No operator verb ships for this.
  Rationale: unlike `backfill-short-ids` — where a missing `short_id` meant a *missing capability*,
  a record unaddressable by handle — a scalar `supersedes` loses nothing functionally under a
  tolerant read. A backfill would be purely cosmetic payload convergence.
  **Planning obligation:** the tolerance MUST be pinned by a test. Today's decoder calls
  `v.GetStringValue()` (`store.go:592-594`), and protobuf's oneof accessor returns `""` for a list
  value rather than erroring — so a reader that loses the tolerance fails *silently*, which is the
  false-green class this repo has repeatedly been bitten by.

### Atomicity and the orphan survivor

- **D-05:** Operation order is **preflight → Upsert → stamp → compensate**. Ownership, rule-immutability,
  and not-already-superseded are checked for **every** target, under lock, *before* the survivor is
  written. Today's order (Upsert first, `store.go:2029-2032`) is inverted for the checks only.
  Rationale: the sharp failure case is not retry-after-failure — it is retry-after-*unobserved*-success
  (server succeeded, response lost). With preflight, that retry fails clean with nothing created.
  Without it, every such retry mints and then deletes a survivor.

- **D-06 (REVISED 2026-08-10 — original premise falsified by research):** All N targets are still
  stamped in **one `SetPayload` call** (`PointsSelectorIDs` accepts a slice, `store.go:2040`), but
  **not** because partial stamping is unrepresentable — it is not. The escape clause in the original
  decision fired.

  **What research established (verified against the pinned server's Rust source, not inferred):** at
  `qdrant/qdrant:v1.18.2` (`store_test.go:32`) / `go-client v1.18.3` (`go.mod:19`), shard-level
  `set_payload` (`lib/shard/src/update.rs`) chunks point IDs by `PAYLOAD_OP_BATCH_SIZE = 32` and,
  within a chunk, runs `apply_points_with_conditional_move(...)` — mutating every point that exists —
  **before** `check_unprocessed_points(chunk, &updated_points)?` raises `PointIdError` for a missing
  one. An error return therefore means **possibly-partial**, never "nothing was written".

  **Revised framing:** partial stamping is **detected and compensated**, not unrepresentable. The
  single-call design is retained as the fast/common path for its batching and its smaller race
  window — not for an atomicity guarantee it does not provide. See D-15 for the reconciliation this
  obligates. Durable record: engram `mc1d0jmh69`.

- **D-07:** On stamp failure the survivor is **compensating-deleted**, so a failed merge is
  observably a no-op. This does **not** violate the phase's no-delete intent: see D-09.
  **Amended by D-15:** deleting the survivor is necessary but no longer *sufficient* — on its own it
  now creates the dangling-predecessor state D-15 exists to clear.

- **D-08:** The compensating delete is **best-effort, not contract**. If `SetPayload` failed because
  Qdrant is unreachable, the cleanup call hits the same unreachable Qdrant and fails too — it
  degrades in exactly the outage that triggers it. When cleanup fails: **return the original stamp
  error** (preserving the single-fault `field=<name> hint=<code>` envelope) and log the orphaned
  survivor id via structured logging for the operator. Do not surface the orphan id to the caller.
  Documentation MUST NOT advertise "a failed merge is a no-op" as a guarantee — only as the usual
  outcome.

- **D-09:** **"No `delete_memory` in the merge path" means: do not destroy predecessor history.**
  It does not mean the `Delete` primitive may never appear. The compensated survivor was never
  linked to anything, never recallable by another caller, and carries no lineage — deleting it
  destroys zero history. This reading MUST be written into the code comment at the call site, or a
  future reader will see a delete inside `Supersede` and "fix" it.

- **D-15 (NEW 2026-08-10 — consequence of D-06's revision):** A failed multi-target stamp requires a
  **post-failure reconciliation pass**, not just the survivor's compensating delete. Treat any error
  from the multi-ID `SetPayload` as *possibly-partial* and, still inside the same lock scope:
  1. compensating-delete the survivor (D-07/D-08, unchanged); then
  2. re-read the **full requested target set** and clear `superseded_by` on every target whose value
     equals the just-deleted survivor's id.

  **Why step 2 is mandatory, not hardening.** Without it, targets stamped before the error keep
  pointing at an id the compensating delete just removed. That dangling `superseded_by` is non-empty,
  so all four `IsEmpty("superseded_by")` recall gates (D-02) **soft-hide those records permanently** —
  a *failed* merge silently disappears live memories. This failure class did not exist before this
  phase: at N=1 there is no "some existing, some missing" state to reach, which is why the current
  single-target `Store.Supersede` never met it.

  **Inherits D-08's honesty constraint.** Reconciliation is best-effort for the same reason the
  compensating delete is — it talks to the same Qdrant that just failed. When it cannot complete:
  return the original stamp error, and log the survivor id **and** the still-dangling target ids via
  structured logging. Documentation MUST NOT advertise "a failed merge is a no-op" as a guarantee.

  **Known limitation, deliberately accepted (not closed by construction).** The target set is **not**
  capped at 32, so a set larger than one `PAYLOAD_OP_BATCH_SIZE` chunk carries a *second, independent*
  partial-failure class: an early chunk can commit fully before a later chunk errors. The
  reconciliation pass above covers this too (it re-reads the full requested set, not one chunk), but
  the cross-chunk window is wider. Capping the set was considered and declined — the reconciliation
  pass is the single mechanism for both classes. The planner MUST make this limitation visible rather
  than let 32 stay an invisible constant.

- **D-10:** **Sorted-order acquisition** over all targets — sort the resolved UUIDs, take every lock
  in that order, release in reverse. The classic deadlock-free discipline: two concurrent merges
  with overlapping sets can never hold each other's next lock. Preserves today's exact guarantee
  (different targets never contend) and requires **no change to the `TargetLocker` interface**, so
  the documented future distributed locker (`locker.go:19-20`, `WithTargetLocker`) still drops in.
  Rejected: a single hashed set-key (two merges over *different but overlapping* sets get different
  keys and never contend — silently weaker than today, and precisely the race the lock exists to
  prevent); try-lock-and-fail-fast (a new error class and a retry contract for a rare race).

- **D-11:** An invalid set rejects the **whole call** (atomicity requires it) and the error **names
  every offending target at once**, so a caller fixing a bad 5-target set learns the full picture in
  one round trip. The error envelope widens to carry a list; `docs-site/src/content/docs/reference/
  errors.md` must document the multi-fault shape.
  — **Resolved 2026-08-10 (mixed failure classes):** research found no existing precedent for
  reporting *heterogeneous* per-target failures — `ErrNotFound`, `ErrAlreadySuperseded`, and
  `errRuleImmutable` are three separate non-`argError` sentinels mapped to different Connect codes.
  Resolution: **staged-by-class preflight**. Check every target for class 1 and, if any fail, return
  naming *all* class-1 offenders; only when that class is clean proceed to class 2, and so on. One
  error code per response, every offending target of that class named. This keeps the existing
  sentinel→code mapping and 404-indistinguishability intact and avoids inventing a per-target
  multi-code envelope. Rejected: a single merged envelope carrying per-target reason codes — more
  informative, but it needs a new error shape *and* an arbitrary choice of which Connect code
  represents the whole call.
  — **Reversibility:** costly — `reference/errors.md` publishes the envelope as a machine-stable
  contract; narrowing it later breaks callers parsing the list.

### Idempotency

- **D-12:** **`idempotency_key` is supported on this verb**, closing what `plan T-25-10` deferred for
  scope in Phase 25. Investigated during discussion: WR-03/WR-04 were review findings that the code
  *claimed* to exclude the key but did not (the `json:"-"` shadow removes it from the advertised
  schema only, never from the wire decode) — the fix made the absence honest and tested; it never
  argued the feature should not exist. **No design principle is reversed.** Supporting it deletes
  the shadow field and the defensive clear, and inverts `TestSupersedeMemorySchemaExcludesIdempotencyKey`,
  `TestSupersedeArgsDecodePopulatesPromotedIdempotencyKey`, and `TestSupersedeMemoryIgnoresIdempotencyKey`
  — all of which exist to pin an absence.
  Motivation: v0.12.x REQUIREMENTS names the anti-pattern directly — *"A CLI that retries mutating
  calls on ambiguous failure without an idempotency key… reintroduces the hazard it closed"* — and a
  multi-target merge is exactly when an ambiguous failure is expensive.

- **D-13:** The replay fingerprint keys on **content + the target set**. Same content against a
  different set is a different operation. This is new logic, not reuse of `store_memory`'s
  content-only fingerprint.

- **D-14:** The **replay check runs before the already-superseded preflight**. Ordered the other way,
  preflight rejects the retry with `ErrAlreadySuperseded` and the key is never consulted — the
  failure mode is easy to introduce and invisible in a happy-path test.

### Invariants that constrain planning (not choices)

- **INV-01: 404-indistinguishability applies to D-11.** The multi-fault error MUST echo the caller's
  **original** input strings (short_id as supplied), never resolved UUIDs, and MUST NOT distinguish
  "not yours" from "does not exist" — both collapse to the same not-found class. Echoing a resolved
  UUID leaks another owner's real id (`tools.go:1780-1785`).

- **INV-02: Rules are immutable to this verb.** `errRuleImmutable` (`tools.go:1764-1766`) must gate
  **every** target in the set, not just the first — a merge must not become a back door to
  superseding a rule.

- **INV-03: `Update` still refuses to set the link.** `store.go:1755` restores `Supersedes`,
  `SupersededBy`, and `ArchivedAt` from a fresh read under lock. That forgery defense stays; this
  phase adds no second path to creating a supersession link.

- **INV-04: Supersession stays never-automatic.** No similarity trigger, no write-through path. The
  verb is invoked explicitly, by a caller acting on user-blessed judgment.

### Claude's Discretion

- Whether duplicate ids within a single `supersedes` set are deduplicated or rejected.
- Whether a merge may span scopes, categories, or visibilities, or must be homogeneous.
- How the async summary queue behaves for a survivor with N predecessors
  (`tools.go:1789 tryEnqueue`) — currently fired once per successful write; nothing about the
  multi-target case obviously changes it, but planning should confirm rather than assume.
- Whether `Store.Supersede` keeps its single-target signature with a slice-taking sibling, or the
  signature itself pluralizes and callers pass a 1-element slice. D-01's promote logic argues for
  the latter, but the store API is internal and this is a code-shape call, not a contract call.

## Existing Code Insights

### Reusable Assets

- **`SetVisibility`'s payload-stamp shape** — `getWritable(id, subj, action)` → single-key
  vector-preserving `SetPayload`. `Supersede` was built from it and the multi-target form keeps it,
  changing only the selector from one id to a slice.
- **The `TargetLocker` interface** — already abstracted for a future distributed locker. D-10
  deliberately generalizes *usage* (sorted acquisition at the call site) rather than the interface,
  so that substitution stays available.
- **`checkIdempotentReplay` / `IdempotencyFingerprint`** (from Phase 24) — the mechanism D-12
  adopts. Reused as machinery; the fingerprint *input* is new (D-13).
- **The testcontainers Qdrant harness** — real-Qdrant integration tests already exist in this
  package and skip cleanly when Docker is unavailable.

### Established Patterns

- **Unrepresentable over tested** — recorded in Phase 3's decisions and applied here as D-06: prefer
  a design where the bad state cannot be expressed to one where a test asserts it does not occur.
- **Fail-closed on TOCTOU** — a mutated/deleted point between gate and write surfaces as an error,
  never as a silent success. D-08's cleanup path must not violate this by swallowing the original error.
- **404-indistinguishability** — non-owned and non-existent are the same answer. INV-01.
- **Absence must not be indistinguishable from success** — the repeated false-green failure mode in
  this repo (`gfh6q1ack4`, `an0zmqwxvp`). D-04's silent-empty-string decoder risk is the same class
  and is why the tolerance needs a pinning test.
- **Error envelopes stay narrow** — `field=<name> hint=<code>` is deliberately single-fault. D-11
  widens it knowingly, which is why it carries a documentation obligation.

### Integration Points

- **Phase 4's `curating-spine` skill** — the sole consumer of the plural form. Its `same-fact` and
  `overlapping` verdicts both compile to one `supersede_memory(content, supersedes=[A,B])` call.
- **`spine-review consolidate --output json`** — produces the candidate pairs upstream of that call.
- **`docs-site` reference and guides** — the memory contract, the error envelope, and the tool
  reference all describe this verb's current single-target shape.

<specifics>
## Specific Ideas

- **The roadmap's proto constraint is inapplicable — success criterion 1 needs correcting.** It
  requires *"no breaking proto change (a `deprecated` field still occupies its number)"*, but
  `proto/engram/v1/engram.proto` declares **11 RPCs and no `Supersede`**: supersession is MCP-only,
  defined as a Go struct with `jsonschema` tags (`internal/server/tools.go:614-622`). There is no
  field number to preserve. The real compatibility surface is the advertised JSON schema, and D-03
  changes it deliberately. A planner that takes SC1 literally will look for a proto field that does
  not exist.

- **Follow the mechanics, don't assert them.** Carried from Phase 4's context and reconfirmed twice
  in this discussion: the proto misconception above, and the `idempotency_key` "deliberate design"
  that turned out to be deferred scope, were both found by reading the code and the review history
  rather than trusting a summary. Downstream agents should do the same with this document.

- **The retry that matters is the one you did not see fail.** The user's framing drove D-05: a
  caller who *observes* an error and retries is easy to serve; a caller whose success was lost in
  transit is the case that determines the operation order.

</specifics>

<deferred>
## Deferred Ideas

- **A versioned payload-migration mechanism.** There is no stored schema/payload version anywhere in
  `internal/store/` or `cmd/engram/` — every payload evolution so far shipped as its own one-shot
  operator command (`backfill-short-ids`, `migrate-set-owner`, `migrate-remap-owner`,
  `summarize-missing`), and CLAUDE.md states the stance explicitly: *"Not used here: database
  migrations."* Wrapping evolutions into a single versioned `engram migrate` would mean a version
  key, an ordered migration registry, idempotency, and a current-version report — a new capability
  and a reversal of a stated project decision. Captured as a backlog item for research; **not this
  phase.**

- **`spine-review consolidate --apply`** — a CLI-side merge inheriting this verb. Carried forward
  from Phase 4's deferred list; unchanged.

- **Un-supersede / restore** — deferred by Phase 25 and still deferred. A merge makes the reversal
  question larger (unstamping N targets), but does not change its status.

</deferred>
