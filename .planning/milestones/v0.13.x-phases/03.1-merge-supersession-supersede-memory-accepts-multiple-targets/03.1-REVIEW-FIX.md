## Fixed Issues

### CR-01: Idempotency-keyed multi-target merges with disjoint target sets can silently corrupt the supersession graph

**Files modified:** `internal/store/store.go`, `internal/store/store_test.go`
**Commit:** `9ef8148f`
**Applied fix:** `Store.Supersede`'s per-target lock (`lockTargets`) previously
locked only the caller's `targets` slice, never `newMem.ID` — the survivor's
own deterministic id for a keyed call. Two concurrent keyed calls sharing an
`idempotency_key` but naming disjoint target sets therefore contended on no
lock at all, and the second call's whole-payload `Upsert` could silently
replace the first's survivor record with no error and no log, orphaning the
first call's already-back-stamped target.

Fixed by locking the **union** of `targets` and `newMem.ID` (when keyed) —
`lockTargets` dedupes+sorts whatever it is given, so a coincidental
target/survivor-id collision is never locked twice (which would self-deadlock
the non-reentrant per-id mutex). The back-stamp/`getWritable` "stamp set"
(`sorted`) is deliberately computed **independently** of the lock set, from
`targets` alone — `newMem.ID` must never join it, or the survivor would
back-stamp itself as one of its own targets. Once the extended lock is held,
a new race-free re-check (step "0.5") re-decides the same
same-key-different-operation question `checkIdempotentMergeReplay` already
asks at the server layer, but now atomically: a fingerprint match is a true
replay (no-op success); a mismatch is rejected as `store.ErrIdempotencyConflict`
before ever reaching `Upsert`.

Added `TestSupersedeConcurrentKeyedDisjointTargetsCannotBothLand`
(`internal/store/store_test.go`, run with `-race`) — asserts on resulting
graph state (exactly one success + one conflict; the persisted survivor's
`Supersedes` equals only the winner's target set; the losing target's
`superseded_by` stays nil) rather than merely a returned error. Confirmed RED
against pre-fix code (both calls silently succeeded, 2 successes / 0
conflicts) before the fix landed, then confirmed the fix restores it to
green.

### WR-01: `supersedes` entries have no length bound, and are echoed verbatim in rejections — contradicting errors.md's own "no value echo" invariant

**Files modified:** `internal/server/tools.go`, `internal/server/tools_test.go`, `docs-site/src/content/docs/reference/errors.md`, `docs-site/src/content/docs/reference/tools.md`
**Commit:** `b18c11b6`
**Applied fix:** Added `maxSupersedeTargetBytes = 256` and a per-entry length
check in `resolveAndAuthorizeSupersedeTargets`'s Class 1 (set-shape) stage,
mirroring the `maxIdempotencyKeyBytes`/`HintTooLong` pattern already used for
every other client-supplied string in this file's blast radius. This is a
per-**entry** length bound only — PD-07's decline of a target-**count** cap
is untouched (no `maxItems`, no branch on `len(inputs)` beyond the existing
empty-array check). Added `TestSupersedeMemoryOversizedTargetRejected`
(mirrors `TestSupersedeMemoryOversizedKeyRejected`'s shape), confirmed it
fails to compile without the new constant (the fix is required for the test
to exist).

Also resolved `errors.md`'s direct self-contradiction: the "No value echo"
section claimed a rejection "never echoes the value you sent," while the same
document's "Multi-target rejections" section states plainly that "Each
target is echoed exactly as you wrote it." Per orchestrator guidance, resolved
in favor of what the code actually does (echoing is deliberate and safe here)
by scoping "No value echo" to name its one bounded exception, with a
cross-reference to the per-entry length bound. Added a corresponding sentence
to `reference/tools.md` documenting the 256-byte per-entry bound.
`TestSupersedeDocsMatchShippedContract` (the existing drift gate) still
passes unmodified.
