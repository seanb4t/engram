**Decision 1 — PD-07: is there a maximum target count, and what is it?**

What is NOT true about a cap: it is not a correctness control. CONTEXT.md D-15 offered a hard cap
at 32 precisely to eliminate the cross-chunk partial-failure class, and it was **declined** — the
reconciliation pass was chosen as the single mechanism covering both the within-chunk and the
cross-chunk classes. Any cap above 32 therefore closes nothing: 256 still permits eight full
32-point server chunks.

What a cap can honestly be: a request-cost bound. The measured budget, from the shipped code path,
is **two sequential Qdrant round trips per target before any write** — one `ResolvePointID`
(`store.go:1530`) and one `FetchForUpdate` — plus one held in-process lock per target for the whole
operation. At 256 targets that is ~512 sequential round trips and 256 simultaneously held mutexes
per call, from a single authenticated caller.

Today the input is unbounded. Adding a bound is an externally-visible rejection on calls that
currently succeed, which is why it needs your ruling rather than the planner's judgment.

  - **cap-256-advertised** — `maxSupersedeTargets = 256`, rejected in the first validation class
    before any id is resolved, AND advertised in the generated MCP JSON schema as `minItems: 1` /
    `maxItems: 256` with a test asserting both constraints appear, AND published in
    `reference/tools.md`. An agent learns the bound from the schema, not from a runtime failure.
  - **cap-N-advertised** — the same, at a number you name. If the budget above suggests a different
    figure to you, name it and plan 03 uses it verbatim.
  - **no-cap** — delete the constant and its check. The input stays unbounded exactly as it is
    today; the reconciliation pass remains the only mechanism, as D-15 chose. Nothing else in the
    phase depends on the cap: plan 03 simply omits validation class 1's length branch, plan 05 omits
    the published maximum, and the schema gains only `minItems: 1`.

**Decision 2 — PD-06: the rejection class order, and what happens to an ambiguous short id.**

An invalid set rejects the whole call and the rejection names every offender of ONE failure class
(D-11). The class order is what makes that deterministic. Review found the originally-planned order
leaked: `ResolvePointID` is owner-agnostic, scrolls the whole collection, and returns
`ErrAmbiguousShortID` when two or more records anywhere match the handle (`store.go:1530`, `:1555`,
`:1569`). Reporting that class BEFORE the ownership stage tells an unauthenticated guesser that a
handle they invented matches multiple records they cannot read.

  - **collapse-ambiguous** (planner recommendation) — four classes, and no class before the
    ownership stage can say anything about a specific record:
      1. set shape — empty array, blank entry, and (if adopted) oversized. Names the argument, never
         a value. Runs before any store call.
      2. addressability and access — resolution-not-found, resolution-ambiguous, fetch-not-found and
         not-owned ALL collapse into one class, reported as the existing not-found sentinel, naming
         every offending input as the caller spelled it. This is the stage that makes "not yours"
         and "does not exist" one answer, and it now absorbs ambiguity too.
      3. rule immutability — evaluated only over records the caller provably owns.
      4. already superseded — same.
    Cost, stated plainly: a caller whose short id collides globally now gets "not found" instead of
    "ambiguous", and must name that target by its full UUID. Short ids are minted with
    collision-retry, so a collision means someone *else* holds the twin — exactly the case where the
    detailed answer is the leak.
  - **owner-filtered-resolution** — keep a distinct ambiguous class, but add an owner-filtered
    resolve used only by this write path so ambiguity is reported only among records the caller can
    read. More faithful, but it is a new store method with its own authz surface, and it must be
    kept in step with `ResolvePointID` forever.
  - **report-ambiguous-early** — the originally-planned order. Listed so you can see it was
    considered: it is the shape review flagged as an existence oracle. Choosing it means accepting
    that disclosure knowingly.

**Decision 3 — PD-01: duplicates inside one target set.**

  - **dedupe-silently** (planner recommendation) — `[A, A]` and `[short_id_of_A, uuid_of_A]` both
    mean `[A]`. The wire form accepts either spelling of the same record, so a duplicate is usually
    two spellings rather than caller error. Note the dedupe pass over *resolved* UUIDs is mandatory
    either way: the in-process locker is a non-reentrant `sync.Mutex`, so locking one target twice
    on one goroutine hangs forever with no panic and no race-detector hit.
  - **reject-duplicates** — a repeated target is an argument error. Honest, but it forces the caller
    to resolve short ids to UUIDs itself before it can know whether two entries are the same record.

**Decision 4 — PD-02: may one merge span scopes, categories and visibilities?**

  - **allow-heterogeneous** (planner recommendation) — no homogeneity requirement. Every target is
    independently owner-gated, `rule` stays excluded for every target, and a legitimate cross-scope
    de-duplication stays possible.
  - **require-homogeneous** — all targets must share a scope. Adds a rejection class with no
    security value, since ownership is already checked per target.
