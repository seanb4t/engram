<objective>
Make an invalid target set reject the whole call once, naming every offending target of one failure
class, without ever letting a caller learn that a record they cannot read exists.

Purpose: D-11 requires that a caller fixing a bad five-target set learns the full picture in one round
trip. INV-01 requires that the widened message echo the caller's own input strings and collapse
"not yours" into "does not exist". Those two requirements pull in opposite directions unless the
preflight is staged by class — and getting that wrong is how a merge becomes an existence oracle for
another actor's records.

Output: `resolveAndAuthorizeSupersedeTargets` and `validateSupersedeTargetState` — a staged-by-class
preflight split at exactly the seam plan 04 needs — one production rendering helper, set-shape
validation, a handler that gates every target before the embed, and per-class rejection tests
including two whole-rejection indistinguishability proofs.

Two things changed after cycle-1 review and are not negotiable at execution time: the class order now
puts EVERY record-specific class behind the ownership stage (an ambiguous short id is no longer its
own answer), and the preflight is split rather than hooked.
</objective>

<planner_decisions>
Three contract-shaped decisions CONTEXT.md left open. RESEARCH.md Open Question 1 flagged the first as
a genuine fork and recommended, but did not lock, the staged option.

**All three are now ruled on by plan `03.1-00`, a blocking decision gate in wave 1.** Read
`03.1-00-SUMMARY.md` before implementing anything below and follow the recorded ruling; the text here
is the recommendation that was put to the developer. Where the ruling amended a recommendation, the
ruling wins.

- **PD-05 — staged-by-class preflight, existing sentinels, no new error type.** Each rejection keeps
  its current sentinel (`store.ErrInvalidArgument` via `argError`, `store.ErrAmbiguousShortID`,
  `store.ErrNotFound`, `errRuleImmutable`, `store.ErrAlreadySuperseded`) and widens only its *message*
  to name every offending target of that class, comma-joined, in the caller's input order. Rejected:
  a heterogeneous per-target `{target, reason}` envelope — a Connect response carries exactly one
  status code, so a mixed envelope forces an arbitrary choice of which code represents the whole call,
  and it would need a new wire shape. Rejected: reusing `argError.Fields` to carry target ids —
  `Fields` means *argument names* on every other rejection in the tree, and overloading it would make
  `field=` ambiguous for every existing parser. The `connecterror.go` sentinel-to-code switch is
  therefore UNCHANGED. Reversibility: costly — `docs-site/.../errors.md` publishes this as a
  machine-stable contract and narrowing it later breaks callers parsing the list.

- **PD-06 (REVISED after review) — the class order is fixed, documented, and ordered so that nothing
  reportable about a specific record precedes the ownership stage.** The original order put ambiguous
  short ids ahead of ownership. Review verified that `ResolvePointID` is owner-agnostic
  (`store.go:1530`), scrolls the whole collection (`:1555`), and reports `ErrAmbiguousShortID` on two
  or more global matches (`:1569`) — so answering "ambiguous" told an unauthenticated guesser that a
  handle they invented matches several records they cannot read. 404-indistinguishability held for
  not-found and not-owned but not across the whole resolution process, which is the same leak wearing
  a different label.

  Revised order, four classes:
  1. **set shape** — empty array, blank/whitespace entry, and (only if plan 00 adopted a cap) an
     oversized array. Names the `supersedes` argument and the bound; never echoes a value. Runs
     before any store call, so it discloses nothing about any record.
  2. **addressability and access** — resolution-not-found, resolution-ambiguous, fetch-not-found and
     not-owned all collapse into ONE class reported with the existing not-found sentinel, naming
     every offending input in the caller's order. This is the stage that makes "not yours" and "does
     not exist" one answer, and it now absorbs ambiguity too.
  3. **rule immutability** — evaluated only over records the caller provably owns.
  4. **already superseded** — same.

  One class per response; a later class is evaluated only once the current one is clean. A fixed
  order is what makes the rejection deterministic across concurrent runs; picking whichever class is
  encountered first per target is not.

  Rejected alternative: **owner-filtered resolution** — a new store method that resolves a short id
  only among records the caller can read, preserving a distinct ambiguous class. More faithful, but
  it adds a second resolution path with its own authz surface that must be kept in step with
  `ResolvePointID` forever, and the case it serves — a caller who owns one of two records sharing a
  handle — is already reachable by naming the target with its full UUID. Surfaced in plan 00 so the
  developer could take it; implement it only if the ruling says so.

- **PD-07 — a maximum target count. RULED ON IN PLAN 00, NOT HERE.** No CONTEXT.md decision addresses
  a cap, and D-15 explicitly declined capping the set *at 32* to eliminate the cross-chunk
  partial-application class — choosing reconciliation as the single mechanism for both failure
  classes. Any cap above 32 therefore closes nothing (256 still permits eight full chunks) and can
  only be a resource bound. Review found the original plan shipping it autonomously in wave 2 with
  approval in wave 4, on an input that is unbounded today.

  Implement exactly what `03.1-00-SUMMARY.md` records:
  - **if a cap was adopted** — declare `maxSupersedeTargets` at the ruled value, reject in class 1
    with the existing `too_many` hint before any id is resolved, AND advertise it in the generated
    MCP JSON schema as `maxItems` alongside `minItems: 1`, with a test asserting both constraints
    appear in the generated schema. A runtime-only bound that the advertised schema does not mention
    is a rejection an agent can only discover by failing.
  - **if the cap was dropped** — omit the constant and the class-1 length branch entirely, keep
    `minItems: 1` in the schema for the empty-array case, and omit the published maximum from plan
    05's documentation. Nothing else in the phase depends on it.

  Reversibility: costly — a cap becomes a published input contract.
</planner_decisions>

THE ONE RENDERING HELPER.
Declare `func renderTargetRejection(sentinel error, inputs []string) error`, returning
`fmt.Errorf("%w: %s", sentinel, strings.Join(inputs, ", "))`. Every rejection in this verb — every
class below, and the handler's store-error re-wraps in Task 2 — goes through it, and nothing
hand-assembles an equivalent `fmt.Errorf`. This is not tidiness: plan 05 builds a documentation drift

STAGE ONE — `func (d *deps) resolveAndAuthorizeSupersedeTargets(ctx context.Context, c caller, inputs []string) ([]resolvedSupersedeTarget, error)`.

Class 1 — set shape. Reject an empty slice with the existing required-hint argument error on the
`supersedes` field. Reject any entry that is empty or whitespace-only with the malformed-shape
argument error. If a cap was adopted, reject a slice longer than the bound with an out-of-range
argument error using the existing `too_many` hint, naming the bound and the received count but never
echoing the values. All of these run before any store call, so this class discloses nothing about any
record — which is precisely why it is allowed to run first.

Class 2 — addressability and access, as ONE stage over THREE buckets. Call `ResolvePointID` for every
input and sort each result into:
  - **resolved** — `(Input, ID, Index)` triples, where `Index` is the input's ORIGINAL position in the
    caller's slice;
  - **unaddressable** — `(Input, Index)` pairs for inputs whose resolution returned not-found OR the
    ambiguous-short-id sentinel, carrying the same original index;
  - and nothing else; any other resolution error is a transport failure and propagates immediately.

Then call `FetchForUpdate(ctx, pair.ID, c.Subj)` for the RESOLVED pairs ONLY, and append the input of
any pair that returns not-found to the unaddressable bucket, carrying its original index with it.
Never call `FetchForUpdate` without a canonical id: a resolution not-found produces no id at all
(`store.go:1564` returns the sentinel with no id), so "carrying it forward into the fetch" is not an
operation that exists.

If the unaddressable bucket is non-empty, STABLE-SORT it by that original index and pass the inputs to
`renderTargetRejection(store.ErrNotFound, …)` in that order.

The index and the sort are load-bearing, not tidiness — cycle-3 review, MEDIUM. The bucket is filled
in TWO passes: resolution failures in the first pass over `ResolvePointID`, fetch/ownership failures
in the second pass over the resolved pairs. Without an index-stable sort the bucket comes out in
pass order rather than caller order, so an input of `[nonOwnedA, missingB]` renders as `B, A` — which
contradicts the caller-order guarantee stated immediately below, the identical-offender-count property
Class 2 exists to provide, and the contract plan 05 publishes in `reference/tools.md` ("in the order
the caller supplied them"). Put a comment at the sort saying exactly that, because on the
single-class inputs most of the tests use the sort is a visible no-op and a later reader will
otherwise delete it.

Two comments are mandatory here, because both properties are invisible from the code alone:
  - This single class is what makes "not yours" and "does not exist" one answer: a non-owned record
    fails the same fetch, joins the same bucket, and produces the same sentinel and the same offender
    count as a nonexistent id.
  - Ambiguity joins that bucket for the same reason and not by accident. `ResolvePointID` is
    owner-agnostic and scrolls the whole collection, so reporting "ambiguous" as its own class would
    tell an unauthenticated guesser that an invented handle matches several records they cannot read.
    A caller who legitimately owns one of two records sharing a handle addresses it by full UUID; say
    so in the comment so the trade is visible to whoever reads this next.

On success return the pairs deduped by resolved `ID`, preserving the first occurrence's `Input` and
the caller's input order, so a duplicate never produces two entries in a later rejection message.

STAGE TWO — `func (d *deps) validateSupersedeTargetState(ctx context.Context, c caller, targets []resolvedSupersedeTarget) error`.

Class 3 — rule immutability. For every target whose category is the rule category, collect the
`Input`. If any, return the rule-immutable sentinel through the rendering helper, keeping the existing
guidance text about deleting the rule instead.

Class 4 — already superseded. For every target whose `SupersededBy` is non-nil and non-empty, collect
the `Input` and return the already-superseded sentinel through the helper. Comment that this stage is
a preflight, not the authority: the store re-checks under lock because a concurrent caller can
supersede a target between this read and the write, and the store's re-check is what closes that
race.

Both classes need the fetched records. Carry them: have stage one return the fetched `store.Memory`
alongside `Input` and `ID` on each pair (extend `resolvedSupersedeTarget` with a `Rec store.Memory`
field) rather than re-fetching in stage two, which would double the round trips and open a second
TOCTOU window.

WHY TWO FUNCTIONS AND NOT ONE WITH A HOOK.
Review found the original plan deferring this choice to plan 04's executor ("either add a hook to
`resolveSupersedeTargets` or split it"). It is decided here, in the plan that writes the code: the
split is the API. Plan 04's idempotency replay check runs BETWEEN the two calls, which is what makes
D-14's ordering — replay before the already-superseded check — a structural property of the call
sequence rather than a statement's position inside a function that a later edit can quietly move. A
callback parameter would put the same ordering behind an argument nobody has to pass. Do not add one.

Add a package-level doc comment above stage one recording the class order and why one class per
response is the shape: a Connect response carries exactly one status code, so a homogeneous rejection
is what keeps the existing sentinel-to-code mapping intact. Do not modify `connecterror.go`.
