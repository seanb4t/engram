# Phase 03.1: Code Review Report

**Reviewed:** 2026-08-11T00:00:00Z
**Depth:** standard
**Files Reviewed:** 16
**Status:** issues_found

## Summary

This phase promotes `supersede_memory` from a single target to a target set and
adds `idempotency_key` support to the verb. The multi-target write path in
`internal/store/store.go` (`Supersede`, `lockTargets`, `reconcileSupersedeFailure`)
is unusually well-engineered: sorted/deduped per-target locking avoids the
non-reentrant-mutex self-deadlock and the cross-caller deadlock the review brief
flagged as a risk, the partial-back-stamp compensation path is documented and
tested against both within-chunk and cross-chunk Qdrant failure classes, and the
404-indistinguishability discipline (collapsed rejection classes, no resolved-UUID
echo) is enforced by tests that compare whole rejection strings, not just error
classes. `mergeFingerprint`/`contentFingerprint` use an injective length-prefixed
encoding verified by dedicated boundary-shift tests. The documentation drift gate
(`supersededocs_test.go`) binds published examples to `renderTargetRejection`'s
actual output rather than a re-typed copy, so it is not vacuous.

Against that backdrop, one finding rises to Critical: the new interaction between
multi-target supersession and the newly-added `idempotency_key` support opens a
data-integrity gap that is outside anything `03.1-00-SUMMARY.md` rules on. The
per-target lock this phase relies on for concurrency safety only locks the
*targets* being superseded — never the survivor's own (deterministic, keyed) id —
so two concurrent keyed merges sharing a key but naming disjoint target sets can
silently corrupt the supersession graph with no error and no log. Two further
warnings cover an unbounded-length gap on individual `supersedes` entries and a
direct contradiction between two sections of `errors.md`.

## Critical Issues

### CR-01: Idempotency-keyed multi-target merges with disjoint target sets can silently corrupt the supersession graph

**File:** `internal/server/tools.go:1011-1030` (`checkIdempotentMergeReplay`), `internal/store/store.go:2085-2262` (`lockTargets`/`Supersede`)
**Issue:**

`lockTargets` (store.go:2085-2106) locks only the ids in the caller's `targets`
slice. It never locks `newMem.ID` — the *survivor's* id — even though for a
keyed call that id is deterministic (`idempotencyPointID(owner, scope, key)`,
computed once per `(owner, scope, key)` tuple, independent of the target set).

Two concurrent `supersede_memory` calls that share an owner, scope, and
`idempotency_key` but name **disjoint** target sets therefore never contend for
any lock at all:

1. Caller sends call 1: `idempotency_key=K`, `supersedes=[A]`, content "fix A".
2. Caller (or a legitimate retry with an adjusted target list) sends call 2
   concurrently: `idempotency_key=K`, `supersedes=[B]`, content "fix B" — `A`
   and `B` are different records.
3. Both calls' `checkIdempotentMergeReplay` (tools.go:1011-1030) call
   `d.st.Get(ctx, pointID)` before either has written. Both observe
   `store.ErrNotFound` (classic TOCTOU) and proceed.
4. `Store.Supersede` acquires locks for `{A}` and `{B}` respectively — disjoint
   sets, so both proceed fully in parallel; neither blocks on the other.
5. Both pass their own preflight (`getWritable`/already-superseded) checks,
   since `A` and `B` are each independently valid, unsuperseded, owned targets.
6. Call 1 `Upsert`s the survivor at `pointID` with `Supersedes=[A]`, then
   back-stamps `A.superseded_by = pointID`.
7. Call 2 `Upsert`s the survivor at the **same** `pointID` (whole-payload
   replace) with `Supersedes=[B]`, then back-stamps `B.superseded_by = pointID`.
8. Final state: `A.superseded_by == pointID` (set in step 6, never revisited),
   but the record actually persisted at `pointID` carries `Supersedes=[B]` —
   nothing in the store ever again shows that `A` was corrected by `pointID`,
   or what "fix A" said. `A` is now permanently soft-hidden from
   `search_memory`/`list_memory` with a dangling forward link to a record that
   does not acknowledge superseding it, and call 1's correcting content is
   gone — overwritten before anything ever observed it.
9. **Neither call returns an error.** `reconcileSupersedeFailure` only runs on
   a `SetPayload` *error* (store.go:2235-2260); here both `Upsert`s and both
   back-stamps succeed individually, so no compensation, no operator log entry,
   and no test in this phase catches it.

This is a genuinely new exposure introduced by this phase, not a restatement of
the already-accepted "last-write-wins on a keyed point" tradeoff
`persistAndEnqueue` documents for plain `store_memory` (tools.go:1136-1150).
That existing tradeoff is *contained*: the losing racer's content is discarded,
but no *other* record is mutated, so there is no dangling link. Supersession
breaks that containment by design — the whole point of the verb is to reach out
and mutate other records' `superseded_by` — and the keyed-write race was
extended to it (`mergeFingerprint`, D-12/D-13) without re-examining that the
per-target lock no longer covers the hazard the survivor's own id now carries.

The team has already noticed and partially mitigated the surface symptom: see
`TestSupersedeMemoryKeyedPostWriteReReadPrefersPersisted`
(`internal/server/tools_test.go:4633-4670`) and its `raceWriteStore` helper
(tools_test.go:4604-4631), whose doc comment explicitly names "a genuinely
concurrent DIFFERENT keyed merge (same owner+scope+key, a non-overlapping
target set, so no shared target lock blocks it)". That test proves the
**returned short_id** is corrected via a post-write re-read
(tools.go:2145-2149) — but nothing corrects the **graph**: no test asserts that
target `A` in the scenario above still has a discoverable, consistent link to
whatever superseded it, and nothing does.

**Fix:** Extend the lock scope in `lockTargets`/`Supersede` to also cover
`newMem.ID` for keyed calls (or unconditionally), and re-check for an existing
record at that id under the lock before the `Upsert` — treating a keyed
survivor-id collision the same way an already-superseded target is treated
today (reject via `checkIdempotentMergeReplay`'s fingerprint comparison, now
made race-free by the lock, rather than a blind whole-payload overwrite). At
minimum, until that lands, `reconcileSupersedeFailure`-style detection should
be extended to notice a target whose `superseded_by` does not appear in the
survivor's own `Supersedes` list, so the corruption is at least observable
rather than silent.

## Warnings

### WR-01: `supersedes` entries have no length bound, and are echoed verbatim in rejections — contradicting errors.md's own "no value echo" invariant

**File:** `internal/server/tools.go:1851-1865` (`resolveAndAuthorizeSupersedeTargets`, Class 1); `docs-site/src/content/docs/reference/errors.md:161-167` vs. `:47-92`
**Issue:**

Every other client-supplied string this phase's blast radius touches carries an
explicit byte bound: `idempotency_key` (`maxIdempotencyKeyBytes = 512`,
tools.go:734), `summary` (`ENGRAM_MEMORY_MAX_SUMMARY_BYTES`), citation `excerpt`
(`maxCitationExcerptBytes`), discovery `content`
(`maxDiscoveryContentBytes`). The Class-1 shape check on `supersedes`
(tools.go:1857-1864) checks only that the array is non-empty and that no entry
is blank after `strings.TrimSpace` — there is no maximum length per entry.

`03.1-00-SUMMARY.md`'s PD-07 ruling deliberately declines a cap on the
**number** of targets in the set; it says nothing about the **length** of an
individual target string. An unresolvable entry (one that fails both
`uuid.Parse` and the `short_id` lookup) is added to `unaddressable` and echoed
back verbatim, comma-joined with every other offender, via
`renderTargetRejection` (tools.go:1829-1831, 1939-1943) — the caller's entire
oversized string becomes part of the rejection text, which
`docs-site/.../errors.md:37-40` documents as **the entire MCP wire payload**
for a tool-call error.

Combined with the accepted no-count-cap ruling, this means a caller can submit
an array of many very long strings as `supersedes` and have all of them
reflected back in a single response — bounded in practice only by the
transport's own message-size ceiling (e.g. gRPC's default 4 MiB), not by any
engram-level validation. This is a genuine gap in the size-bound discipline
this same file otherwise applies uniformly to client-supplied strings, and it
directly contradicts `errors.md`'s own "What is NOT in an error" section:

> **No value echo.** An engram rejection ... never echoes the value you sent.
> ... This means an engram rejection is safe to log verbatim: it cannot carry
> a secret or an oversized blob back out through your own logs.

— which is flatly inconsistent with the same document's "Multi-target
rejections" section, stating plainly that "Each target is echoed exactly as
you wrote it" (errors.md:69-70). The multi-target section is accurate; the
"No value echo" claim is not, for this verb, once an unbounded-length entry is
in play.

**Fix:** Add a per-entry maximum length check in Class 1 of
`resolveAndAuthorizeSupersedeTargets` (mirroring `maxIdempotencyKeyBytes`'s
`argErrf(classOutOfRange, HintTooLong, ...)` pattern — a real UUID or short_id
never exceeds a small, fixed length, so a generous bound like 256 bytes costs
nothing legitimate). Then either scope the "No value echo" claim in
`errors.md` to exclude the multi-target rejection class it already documents
as an exception, or fold that exception's existence into the "No value echo"
section itself so the two sections stop contradicting each other.

### WR-02: `contentFingerprint`'s field-sensitivity test omits `Citations`

**File:** `internal/server/idempotency_test.go:80-125` (`TestContentFingerprintFieldSensitivity`)
**Issue:** `contentFingerprint` (idempotency.go:64-102) folds `Citations` into
the hash (citesEnc, lines 85-90, 96) and the doc comment explicitly calls out
that Phase 26 previously shipped a real gap here (26-REVIEW CR-01: a forgotten
field silently discards a caller's changed value on replay). Despite that
history, `TestContentFingerprintFieldSensitivity` — the one test whose stated
purpose is to prove every client-authored field changes the fingerprint —
enumerates content/category/tags/source/repo/workspace/worktree/base_dir/summary
but has no `"citations"` case. A regression that stopped `citesEnc` from being
folded into the hash (e.g., an accidental refactor that computes it but never
appends it to `b`) would not be caught by this test, only by the narrower
`TestMergeFingerprintTargetBoundaryInjectivity`-style tests, none of which
target `Citations` either.
**Fix:** Add a `"citations"` case to `TestContentFingerprintFieldSensitivity`
alongside the other storeArgs fields, given the field's own history of being
the exact class of gap this test exists to catch.
