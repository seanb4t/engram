## User Constraints (from CONTEXT.md)

### Locked Decisions

**Link shape — the singular→plural seam**

- **D-01:** `supersedes` is promoted to a list. The single-target call becomes the 1-element case of
  the general form; there is no second way to express the same fact.
  — Reversibility: costly (persisted Qdrant payload key, read by the store decoder, rendered by MCP
  response builders and the CLI, described in docs-site).
- **D-02:** `superseded_by` stays scalar and is untouched. Each predecessor has exactly one
  successor; the recall soft-hide gate filters on `IsEmpty("superseded_by")` at four call sites
  (`store.go:954`, `1054`, `1191`, `1426`). Strictly one-directional pluralization.
- **D-03:** The wire shape is always an array, even for one predecessor — `supersedes: ["<id>"]`.
  Observable output change for anything already parsing the scalar; `supersede_memory` is MCP-only.
  — Reversibility: costly (published output shape consumed by agents).
- **D-04:** Tolerant decoder, no backfill command. The decoder accepts string *or* array; a legacy
  scalar record surfaces as a 1-element list. No operator verb ships for this. **Planning
  obligation: the tolerance MUST be pinned by a test** — today's decoder calls `v.GetStringValue()`
  (`store.go:592-594`) and protobuf's oneof accessor returns `""` for a list value rather than
  erroring, so a reader that loses the tolerance fails silently.

**Atomicity and the orphan survivor**

- **D-05:** Operation order is preflight → Upsert → stamp → compensate. Ownership,
  rule-immutability, and not-already-superseded are checked for every target, under lock, before the
  survivor is written. Today's order (Upsert first, `store.go:2029-2032`) is inverted for the checks
  only.
- **D-06:** All N targets are stamped in one `SetPayload` call. `PointsSelectorIDs` already accepts a
  slice (`store.go:2040`), so partial stamping becomes unrepresentable rather than merely
  tested-against. **Research must verify** that a multi-ID `SetPayload` is all-or-nothing in the
  pinned Qdrant version. **If it is not all-or-nothing, that finding changes this decision and must
  be surfaced, not worked around silently.**
- **D-07:** On stamp failure the survivor is compensating-deleted, so a failed merge is observably a
  no-op. Does not violate the no-delete intent (see D-09).
- **D-08:** The compensating delete is best-effort, not contract. On cleanup failure: return the
  original stamp error (preserving the single-fault `field=<name> hint=<code>` envelope) and log the
  orphaned survivor id via structured logging. Do not surface the orphan id to the caller.
  Documentation MUST NOT advertise "a failed merge is a no-op" as a guarantee — only as the usual
  outcome.
- **D-09:** "No `delete_memory` in the merge path" means: do not destroy predecessor history. It does
  not mean the `Delete` primitive may never appear. The compensated survivor was never linked, never
  recallable, carries no lineage — deleting it destroys zero history. This reading MUST be written
  into the code comment at the call site.

**Locking across a target set**

- **D-10:** Sorted-order acquisition over all targets — sort the resolved UUIDs, take every lock in
  that order, release in reverse. Requires no change to the `TargetLocker` interface, so
  `WithTargetLocker` (future distributed locker) still drops in. Rejected: single hashed set-key
  (silently weaker than today for overlapping-but-different sets); try-lock-and-fail-fast (new error
  class + retry contract).
- **D-11:** An invalid set rejects the whole call and the error names every offending target at once.
  The error envelope widens to carry a list; `docs-site/.../errors.md` must document the multi-fault
  shape.
  — Reversibility: costly (published machine-stable contract).

**Idempotency**

- **D-12:** `idempotency_key` is supported on this verb, closing what `plan T-25-10` deferred for
  scope in Phase 25. WR-03/WR-04 were review findings that the code claimed to exclude the key but
  did not — the fix made the absence honest and tested; it never argued the feature should not exist.
  Supporting it deletes the shadow field and the defensive clear, and inverts
  `TestSupersedeMemorySchemaExcludesIdempotencyKey`, `TestSupersedeArgsDecodePopulatesPromotedIdempotencyKey`,
  and `TestSupersedeMemoryIgnoresIdempotencyKey`.
- **D-13:** The replay fingerprint keys on content + the target set. Same content against a different
  set is a different operation. New logic, not reuse of `store_memory`'s content-only fingerprint.
- **D-14:** The replay check runs before the already-superseded preflight. Ordered the other way,
  preflight rejects the retry with `ErrAlreadySuperseded` and the key is never consulted.

**Invariants that constrain planning (not choices)**

- **INV-01:** 404-indistinguishability applies to D-11. The multi-fault error MUST echo the caller's
  original input strings (short_id as supplied), never resolved UUIDs, and MUST NOT distinguish "not
  yours" from "does not exist."
- **INV-02:** Rules are immutable to this verb. `errRuleImmutable` (`tools.go:1764-1766`) must gate
  every target in the set, not just the first.
- **INV-03:** `Update` still refuses to set the link. `store.go:1755` restores `Supersedes`,
  `SupersededBy`, `ArchivedAt` from a fresh read under lock. Stays; no second path to a supersession
  link.
- **INV-04:** Supersession stays never-automatic. No similarity trigger, no write-through path.

## Summary

This phase generalizes `Store.Supersede` from one target to a set, and the central open question —
whether Qdrant's `SetPayload` is all-or-nothing across multiple point IDs — has a definitive,
source-verified answer: **it is not.** At the pinned server version (`qdrant/qdrant:v1.18.2`, the
testcontainers image; `v1.18.3` in the Helm chart and the vendored `go-client`), the shard-level
`set_payload` function (`lib/shard/src/update.rs`) chunks the requested point IDs into batches of 32
(`PAYLOAD_OP_BATCH_SIZE`), and within each chunk it **mutates every point that exists, unconditionally
and immediately**, before checking whether any requested ID went unprocessed. Only after all existing
points in the chunk are already stamped does `check_unprocessed_points` look for a missing one and
return `PointIdError` for the *first* one found. A caller who requested `SetPayload` on `{A, B, C}`
where `C` was deleted between preflight and this call gets back an error — but `A` and `B` are already
stamped by the time that error returns. D-06's "unrepresentable, not merely tested" premise is false as
stated; the correct framing for planning is "detected and must be compensated," and the compensation
surface is larger than D-07/D-08 anticipated: it is not just the new survivor record that can be
orphaned, but now also the already-stamped predecessor targets, which are left pointing (via
`superseded_by`) at a survivor id the compensating delete then removes.

The remaining research areas resolve cleanly against existing, deliberately-reusable machinery: sorted
target-id lock acquisition needs no `TargetLocker` interface change but MUST dedupe the resolved ID set
before locking (the in-process locker's `sync.Mutex` is not reentrant — a duplicate id in the set
self-deadlocks); the idempotency extension reuses `idempotencyPointID`/`checkIdempotentReplay` verbatim
and only needs a new fingerprint function that folds in a canonical (sorted) target-id list; and the
scalar-to-list payload seam has one single, precisely characterized failure mode (`Value.GetStringValue()`
returns `""`, not an error, when the underlying oneof holds `ListValue`) with a small, enumerable set of
read sites.

**Primary recommendation:** Treat D-06 as "requires revision" per its own escape clause. Design the
multi-target `SetPayload` call as the fast/common path, but add an explicit post-failure reconciliation
step that (a) compensating-deletes the survivor per D-07/D-08, AND (b) re-reads the requested target set
and clears `superseded_by` on any target whose `superseded_by` now equals the deleted survivor's id —
closing the newly-discovered orphan-predecessor class, not just the orphan-survivor class D-07/D-08
already covers. Prove this with a generalized `TestSupersedeTOCTOU`: delete one of N≥3 targets between
preflight and the multi-ID `SetPayload` call, and assert both that the error surfaces AND that no
surviving target is left pointing at a since-deleted id.

### Pattern 1: Preflight-then-single-batch-mutate-with-compensation (extends D-05/D-06/D-07/D-08)

**What:** Validate everything cheaply before any write; issue one Qdrant mutation call for the whole
set; on any failure from that call, run a bounded, best-effort compensation pass that undoes exactly
what the failed call may have partially done.

**When to use:** Any Qdrant multi-point mutation where "all requested points exist" was true at
preflight time but is not re-verified transactionally at mutate time (true of every operation the
Qdrant source shows using the `chunks(...).map(apply_points_with_conditional_move).check_unprocessed_points`
pattern — not just `set_payload`, also `update_vectors`, `delete_payload`, `overwrite_payload`,
per the Qdrant source read this session).

**Example — the existing single-target compensation-free version (to generalize):**
```go
// Source: internal/store/store.go:1996-2043 (Store.Supersede, current single-target form)
func (s *Store) Supersede(ctx context.Context, newMem Memory, vec []float32, target string, subj Subject) (err error) {
	unlock, err := s.locker.Lock(ctx, target)
	if err != nil {
		return err
	}
	defer unlock()

	targetRec, err := s.getWritable(ctx, target, subj, authz.ActionWrite)
	if err != nil {
		return err
	}
	if targetRec.SupersededBy != nil && *targetRec.SupersededBy != "" {
		return fmt.Errorf("%w: %s", ErrAlreadySuperseded, target)
	}
	if err := s.Upsert(ctx, newMem, vec); err != nil {
		return err
	}
	_, err = s.client.SetPayload(ctx, &qdrant.SetPayloadPoints{
		CollectionName: s.collection, Wait: qdrant.PtrOf(true),
		Payload:        qdrant.NewValueMap(map[string]any{"superseded_by": newMem.ID}),
		PointsSelector: qdrant.NewPointsSelectorIDs([]*qdrant.PointId{qdrant.NewID(target)}),
	})
	return err
}
```
For N=1 this is trivially all-or-nothing (either the one point exists and is stamped, or it doesn't
and the error surfaces with nothing stamped) — which is exactly why the single-target TOCTOU test
(`TestSupersedeTOCTOU`) never needed a compensation step for the *target*. The multi-target form loses
that trivial property and needs an explicit reconciliation branch (see Common Pitfalls #1 for why, and
Code Examples for the shape).

### Pattern 2: Sorted-order lock acquisition over a slice (D-10)

**What:** Take every target's per-id lock in a globally consistent order (sorted UUID string
comparison), release in reverse.

**When to use:** Any operation that must hold ≥2 keyed locks from the same lock domain
(`inProcessTargetLocker`'s `sync.Map`-backed per-key mutex) simultaneously, where two different
callers might request overlapping-but-different sets.

```go
// Illustrative shape — not existing code. Extends internal/store/locker.go's
// existing TargetLocker interface with no interface change (D-10).
targets := slices.Clone(resolvedTargetIDs)
targets = slices.Compact(slices.Sorted(slices.Values(targets))) // dedupe (Pitfall #3) + sort in one pass
unlocks := make([]func(), 0, len(targets))
for _, t := range targets {
	unlock, err := s.locker.Lock(ctx, t)
	if err != nil {
		for i := len(unlocks) - 1; i >= 0; i-- {
			unlocks[i]() // release what was already acquired before erroring out
		}
		return err
	}
	unlocks = append(unlocks, unlock)
}
defer func() {
	for i := len(unlocks) - 1; i >= 0; i-- {
		unlocks[i]()
	}
}()
```
`[ASSUMED]` — this is a design sketch derived from `internal/store/locker.go`'s actual `Lock`
signature (`Lock(ctx, key) (unlock func(), err error)`, verified this session) plus the classic
sorted-lock-ordering discipline D-10 names explicitly; it is not existing code and the exact shape is
planning's to finalize.

**Critical ordering note (D-14), verified against the existing single-target flow:**
`checkIdempotentReplay` in `deps.storeMemory`/`deps.scheduleMemory` runs at `tools.go:999`/`1089`,
*before* any store-level precondition (`store.go:2018-2028`'s ownership/already-superseded checks,
which live inside `Store.Supersede`, called much later in the handler). The merge handler must
replicate this exact ordering: call the replay check immediately after `validateStoreArgs`, before
resolving/fetching any target for the already-superseded preflight — otherwise a retry after an
unobserved success hits `ErrAlreadySuperseded` from the (now-already-stamped) targets before the
replay lookup ever runs, exactly the failure mode D-14 names.

### Anti-Patterns to Avoid

- **Treating a Qdrant multi-ID mutation as transactional without verifying the specific operation's
  server-side implementation.** `SetPayload`, `UpdateVectors`, `OverwritePayload`, and `DeletePayload`
  all share the same `chunks(...).apply_points_with_conditional_move(...).check_unprocessed_points(...)`
  pattern in the pinned Qdrant version — "atomic" language in Qdrant's own marketing/docs pages refers
  to *not interleaving with other concurrent operations at the same point-version level* (an MVCC/WAL
  ordering guarantee), not to "all points in one request succeed or none do." These are different
  claims and conflating them is exactly the trap D-06 was written to avoid, and (per the source read
  this session) still fell into.
- **Locking a duplicate id twice in the same call.** `inProcessTargetLocker`'s `Lock` wraps a plain
  `sync.Mutex`, which is not reentrant in Go — the same goroutine calling `Lock` twice on the same key
  deadlocks permanently, with no timeout (`Lock` only checks `ctx.Err()` up front, then blocks on
  `mu.Lock()` unconditionally — verified `locker.go:50-58`). Any target-set dedup MUST happen before
  the lock-acquisition loop, not as an afterthought.
- **Assuming `docs-site/reference/errors.md`'s `field=/hint=` grammar directly extends to
  heterogeneous multi-target failures.** Today `ErrNotFound`, `ErrAlreadySuperseded`, and
  `errRuleImmutable` are three *different* Connect-code-mapped sentinels (`connecterror.go:69-91`),
  none of which currently render through the `argError`/`field=/hint=` envelope at all — they are
  plain `fmt.Errorf("%w: %s", sentinel, id)` strings. D-11's "the error envelope widens to carry a
  list" is straightforward if every offending target fails the *same* class of check (e.g., all
  not-found) but has no existing precedent for a mixed-class failure (target A not-found, target B
  already-superseded) in one response — a Connect/gRPC response carries exactly one status code. See
  Open Questions.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Multi-ID atomic payload write | A custom per-point transaction/rollback protocol against Qdrant | `qdrant.NewPointsSelectorIDs([]*qdrant.PointId{...})` in one `SetPayload` call, PLUS the reconciliation pass this research specifies | Qdrant has no client-facing multi-point transaction primitive to build on; the reconciliation pass documented in Pattern 1 is the minimum necessary correctness layer, not a place to over-engineer a general transaction manager. |
| Deterministic idempotency point IDs | A new hashing scheme for the merge verb | `idempotencyPointID(owner, scope, key)`, unchanged | Already exists, already handles the owner/anonymous-bucket edge case (IN-02 in `idempotency.go`'s doc comment), already has a UUIDv5 namespace constant marked LOAD-BEARING/never-change. |
| Lock-ordering deadlock avoidance | A lock-manager / wound-wait scheme | Plain sorted-key acquisition over the existing `TargetLocker` | The classic sorted-order discipline is sufficient for this access pattern (bounded, short-lived locks, no cross-lock-domain waiting) — D-10 already selected this over a hashed-set-key or try-lock alternative. |

**Key insight:** every "don't hand-roll" item in this phase already has an existing, working
single-target instance in this codebase (`Store.Supersede`, `idempotencyPointID`,
`inProcessTargetLocker`) — the work is disciplined generalization, not new-primitive construction. The
one place actual new engineering judgment is required is the reconciliation pass in Pattern 1, because
that gap did not exist in the single-target world (N=1 is trivially all-or-nothing).

## Common Pitfalls

### Pitfall 1 (THE central finding): `SetPayload` over multiple point IDs is not all-or-nothing — D-06's premise is false

**What goes wrong:** A caller assumes (as D-06 hoped) that if `SetPayload` returns an error, no target
in the request was mutated. This is false. Existing/found targets in the request ARE stamped,
unconditionally and before the error is even computed.

**Why it happens — verified against the actual pinned-version Qdrant source**
(`https://github.com/qdrant/qdrant/blob/v1.18.2/lib/shard/src/update.rs`, fetched and read in full
this session):

```rust
// lib/shard/src/update.rs:714-741 (v1.18.2)
const PAYLOAD_OP_BATCH_SIZE: usize = 32;

pub fn set_payload(
    segments: &SegmentHolder,
    op_num: SeqNumberType,
    payload: &Payload,
    points: &[PointIdType],
    key: &Option<JsonPath>,
    hw_counter: &HardwareCounterCell,
) -> OperationResult<usize> {
    let mut total_updated_points = 0;

    for chunk in points.chunks(PAYLOAD_OP_BATCH_SIZE) {
        let updated_points = segments.apply_points_with_conditional_move(
            op_num,
            chunk,
            |id, write_segment| write_segment.set_payload(op_num, id, payload, key, hw_counter),
            |_, _, old_payload| match key {
                Some(key) => old_payload.merge_by_key(payload, key),
                None => old_payload.merge(payload),
            },
            hw_counter,
        )?;

        check_unprocessed_points(chunk, &updated_points)?;
        total_updated_points += updated_points.len();
    }

    Ok(total_updated_points)
}
```
and the check that runs *after* mutation:
```rust
// lib/shard/src/update.rs:1046-1055 (v1.18.2)
fn check_unprocessed_points(
    points: &[PointIdType],
    processed: &AHashSet<PointIdType>,
) -> OperationResult<usize> {
    let first_missed_point = points.iter().copied().find(|p| !processed.contains(p));

    match first_missed_point {
        None => Ok(processed.len()),
        Some(missed_point_id) => Err(OperationError::PointIdError { missed_point_id }),
    }
}
```
and the underlying per-point apply, confirming missing points are silently excluded from
processing rather than erroring the whole batch
(`lib/shard/src/segment_holder/mod.rs:362-420` `find_points_to_update_and_delete`, and
`mod.rs:503-530` `apply_points`, both read in full this session): a point ID absent from every
segment simply never enters the `to_update` map — no error is raised for it at this level, and every
point that IS found is mutated in a plain `for` loop with no per-point rollback:
```rust
// lib/shard/src/segment_holder/mod.rs:518-527 (v1.18.2), inside apply_points
for (segment_id, points) in to_update {
    let segment = self.get(segment_id).unwrap();
    let segment_arc = segment.get();
    let mut write_segment = segment_arc.write();

    for point_id in points {
        let is_applied = point_operation(point_id, segment_id, &mut write_segment)?;
        applied_points += usize::from(is_applied);
    }
}
```

**The concrete consequence for this phase:** call `SetPayload` with `{A, B, C}` where `C` was deleted
between preflight and this call (the exact TOCTOU window `TestSupersedeTOCTOU` already probes for
N=1). Qdrant stamps `A` and `B` with `superseded_by = newSurvivorID`, THEN returns
`PointIdError{missed_point_id: C}`. `Store.Supersede` sees an error and (per D-07/D-08)
compensating-deletes the new survivor. Result: `A` and `B` now carry `superseded_by` pointing at an id
that **no longer exists** — a dangling reference, and both `A` and `B` are permanently soft-hidden from
recall (the `IsEmpty("superseded_by")` gate at the four call sites D-02 names) even though the merge
"failed." This is a *worse* outcome than the single-target case ever produced, because it did not
exist before this phase: N=1 has no "some existing, some missing" state to reach.

**How to avoid:** Treat any error from the multi-ID `SetPayload` call as "possibly-partial," not
"definitely none." After the compensating delete of the survivor (D-07/D-08 unchanged), re-read the
full requested target set and clear `superseded_by` on any target whose current `superseded_by` equals
the just-deleted survivor's id (a second, small `SetPayload` — or a per-target check + clear). This is
new scope beyond what D-07/D-08 describe and should be called out explicitly to the planner as a
required addition, not an optional hardening.

**Warning signs a plan is under-specifying this:** a plan that treats "the survivor's compensating
delete" as sufficient cleanup after a `SetPayload` failure; a plan whose TOCTOU test only checks "the
error surfaces" without also asserting no *other* target in the set carries a dangling
`superseded_by`; a plan that keeps `PAYLOAD_OP_BATCH_SIZE`'s 32-item chunking invisible — for target
sets that could exceed 32 (unlikely from `spine-review consolidate`'s typical output, but not
categorically bounded by this phase's contract), cross-chunk partial application is a second,
independent failure mode layered on top of the within-chunk one documented above.

**Secondary observation on `wait`:** the existing back-stamp call already sets `Wait:
qdrant.PtrOf(true)` (`store.go:2038`). `wait` controls whether the RPC blocks until the operation is
applied (and, in a replicated deployment, acknowledged per the collection's write-consistency
settings) before responding — it does not change the intra-request atomicity semantics documented
above, which are a property of the segment/shard update path itself, not of response timing.
`[CITED: api.qdrant.tech/api-reference/points/set-payload — WriteOrdering description]`.

### Pitfall 2: In-process lock is not reentrant — duplicate target ids self-deadlock

**What goes wrong:** A caller supplies `supersedes: [A, A, B]` (same target twice, e.g. one as a UUID
and once as its own `short_id` resolving to the same UUID). If the merge handler sorts and locks each
entry in the raw list without deduping first, the second `Lock(ctx, A)` call blocks forever on the
same goroutine's own held mutex.

**Why it happens:** `inProcessTargetLocker.Lock` (`locker.go:50-58`, read in full this session) is a
thin wrapper over `sync.Map`-stored `*sync.Mutex` — plain `mu.Lock()`, which is not reentrant in Go and
has no built-in deadlock detection for same-goroutine re-entry (Go's race detector and deadlock
detector catch cross-goroutine deadlocks, not a single goroutine blocking on its own held lock inside
the same call stack — this manifests as an unrecovered permanent hang, not a panic).

**How to avoid:** Deduplicate the *resolved* target-UUID set (not the raw caller input strings — two
different short_ids or a short_id and its full UUID can resolve to the same target) before the
lock-acquisition loop. This must happen regardless of which way "Claude's Discretion" (dedupe vs.
reject duplicates) is resolved for the *observable* behavior — even a "reject duplicates" design still
needs the duplicate-detection pass to happen before any lock is taken, not as a post-hoc check.

**Warning signs:** a test suite that never sends the same target twice; a plan that describes
deduplication as purely a UX/API-shape decision without connecting it to the locking mechanism.

### Pitfall 3: The `field=/hint=` envelope has no existing precedent for heterogeneous multi-target failures

**What goes wrong:** A plan assumes D-11's "the error names every offending target at once" extends
mechanically from the existing `argError.Fields []string` (comma-joined field names, ONE shared
`Hint`) to a target list where different targets fail for genuinely different reasons (not-found vs.
already-superseded vs. rule-immutable) — but the existing `Fields`/`Hint` shape has exactly one hint
per response, and today's single-target rejections for these three cases are not even `argError`
instances (they are bare-wrapped sentinels: `store.ErrNotFound`, `store.ErrAlreadySuperseded`,
`errRuleImmutable`, each mapped to a *different* Connect code by `connecterror.go:69-91`).

**Why it happens:** Connect/gRPC responses carry exactly one status code. A response naming targets
A (not-found) and B (already-superseded) together cannot cleanly map to both `CodeNotFound` and
`CodeFailedPrecondition` simultaneously. `supersede_memory` has no Connect RPC today (confirmed:
`proto/engram/v1/engram.proto` declares 11 RPCs, none named Supersede — the `connecterror.go` arms for
`ErrAlreadySuperseded`/`ErrIdempotencyConflict` are explicitly commented "pre-positioning only ...
Connect RPC exposes it yet"), so this is not blocking today, but the *error text itself* (the entire
MCP wire payload per `argError`'s own doc comment) still needs one coherent shape.

**How to avoid:** The natural resolution, consistent with D-05's already-mandated ordering
("preflight... checked for every target... before the survivor is written"), is staged-by-class
preflight: check existence+ownership across ALL targets first and fail with every such-failing target
named together if any fail; only if all pass, check already-superseded across all and fail with every
such-failing target together; only if all pass that, check rule-immutability the same way. This keeps
every actual rejection response homogeneous (one failure class, N targets), matching the
`Fields`/single-`Hint` shape with no wire-contract redesign — but this is a design choice research
surfaces, not one CONTEXT.md resolves; flag it for the planner explicitly (see Open Questions).

**Warning signs:** a plan that tries to build a heterogeneous "list of {target, reason}" error shape
without first checking whether staged-by-class preflight makes that unnecessary; a plan that silently
picks whichever failure class it encounters first per-target (non-deterministic across concurrent runs
if evaluation order isn't fixed) instead of a defined check order.

### Pitfall 4: Tolerant-decode silent-empty-string is real and already pinned as a codebase-wide failure class

**What goes wrong:** A decoder that calls `v.GetStringValue()` on a payload value that Qdrant is now
storing as a `ListValue` (post-D-01) silently reads `""` instead of erroring, and every other read site
built on that same helper repeats the mistake independently.

**Why it happens — verified against the vendored client source**
(`/Users/sean/go/pkg/mod/github.com/qdrant/go-client@v1.18.3/qdrant/json_with_int.pb.go:214-240`, read
in full this session):
```go
func (x *Value) GetStringValue() string {
	if x, ok := x.GetKind().(*Value_StringValue); ok {
		return x.StringValue
	}
	return ""
}

func (x *Value) GetListValue() *ListValue {
	if x, ok := x.GetKind().(*Value_ListValue); ok {
		return x.ListValue
	}
	return nil
}
```
`Kind` is a Go interface-typed protobuf oneof (`isValue_Kind`); when the stored value is a list,
`GetStringValue()`'s type assertion fails silently (`ok == false`) and returns the zero value `""` —
there is no error return, no panic, nothing to catch in a normal control-flow review. This is exactly
the "absence must not be indistinguishable from success" failure class STATE.md already names as
repeated in this repo (`gfh6q1ack4`, `an0zmqwxvp`).

**How to avoid:** The tolerant decoder for `supersedes` must branch on `Kind` explicitly — check
`GetListValue()` first (or check the oneof type), and only fall back to the scalar `GetStringValue()`
path when the kind is actually `Value_StringValue`. Every read site touching `p["supersedes"]` needs
this same branch: confirmed sites this session are `internal/store/store.go:592-595` (`fromPayload`,
the sole decode site) and every consumer of `Memory.Supersedes` downstream of it — `get_memory`
(`tools.go:1607`, returns `store.Memory` directly, no intermediate DTO) and `list_memory --full`. No
CLI (`cmd/engram`) rendering site exists for `supersedes` today (grep across `cmd/` and non-test
`internal/server/*.go` returned zero hits outside `supersedeArgs`/`supersedeMemory` themselves,
consistent with "supersede_memory is MCP-only" — but `get_memory`/`list_memory` ARE reachable from the
CLI's Connect lane, so the CLI DOES render this field once fetched, indirectly, through whatever
generic JSON-output path the CLI already uses for `store.Memory`).

**Warning signs:** a test that only exercises the write-then-read-back path for a *freshly written*
list value (which round-trips fine through `SetVisibility`-style helpers that don't touch
`GetStringValue`) without a companion test that decodes a *legacy scalar-shaped* record with the new
tolerant decoder AND a test that decodes a *new list-shaped* record with the old naive decoder (to
prove the silent-`""` regression the tolerance is meant to close is actually closed, not merely
untested).

## Open Questions

1. **How does the multi-target rejection error handle heterogeneous failure classes across targets?**
   - What we know: D-11 locks "the error names every offending target at once" and the existing
     `argError.Fields []string` already supports multiple names under ONE `Hint`. Today's three
     per-target failure sentinels (`ErrNotFound`, `ErrAlreadySuperseded`, `errRuleImmutable`) are
     distinct, non-`argError` types mapped to different Connect codes.
   - What's unclear: whether a single call where different targets fail for different reasons should
     (a) collapse to one class via staged-by-class preflight (this research's recommendation, Pitfall
     3), (b) invent a genuinely heterogeneous multi-hint error shape, or (c) simply pick the
     first-encountered class and defer the rest to a subsequent retry.
   - Recommendation: staged-by-class preflight (option a) — it requires no wire-contract redesign
     beyond D-11's already-accepted list-widening, and is directly consistent with D-05's mandated
     "checked for every target before the survivor is written" ordering. Planning should confirm this
     explicitly rather than let it fall out implicitly from whatever check-loop order is easiest to
     write.

2. **Does the target set have any upper bound, and does it matter given `PAYLOAD_OP_BATCH_SIZE = 32`?**
   - What we know: `spine-review consolidate`'s typical output (Phase 3, upstream of this phase) is
     near-duplicate CANDIDATE pairs/small clusters — realistically single-digit N. Qdrant chunks
     `SetPayload` point-ID lists into batches of 32; cross-chunk calls are NOT atomic with each other
     (each chunk's own `?` on `apply_points_with_conditional_move`/`check_unprocessed_points` can fail
     independently, and a later chunk's failure does not roll back an earlier chunk's success).
   - What's unclear: whether this phase's contract should impose an explicit N-target cap (matching or
     under 32) to keep the reconciliation logic in Pattern 1 tractable, or leave it uncapped and accept
     that N>32 merges have a second, independent partial-failure class layered on top of the
     within-chunk one.
   - Recommendation: given no CONTEXT.md decision addresses this and the practical N from Phase 3's
     output is expected to be small, planning should either impose an explicit cap (simplest,
     eliminates the cross-chunk class entirely) or explicitly document that the cross-chunk case is
     accepted-and-unmitigated, mirroring D-08's "best-effort, not contract" framing for the
     within-chunk case. Silence on this is not an option — the reconciliation code in Pattern 1
     implicitly assumes single-chunk behavior unless stated otherwise.

3. **Does `spine-review consolidate`'s candidate output ever cross scope/category/visibility
   boundaries, and if so does that interact with the per-target rule-immutability/ownership gates in a
   way that needs explicit handling?**
   - What we know: CONTEXT.md marks "whether a merge may span scopes, categories, or visibilities" as
     Claude's Discretion. `errRuleImmutable`/ownership gates already apply per-record regardless of
     scope.
   - What's unclear: whether Phase 3's `consolidate` report ever surfaces cross-scope candidates in
     practice (this research did not re-read Phase 3's implementation to confirm), which would make
     this discretion item load-bearing rather than theoretical.
   - Recommendation: planning should either confirm via Phase 3's actual `consolidate` output shape
     (out of this research's scope — Phase 3 is already complete and out of this phase's boundary) or
     make the homogeneity decision independent of that and document the choice explicitly, since
     CONTEXT.md leaves it open either way.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|-----------------------|
| TOCTOU between preflight ownership/existence check and the actual mutating call (the central finding of this document) | Tampering / Elevation of Privilege (a target deleted or reassigned mid-window could otherwise be stamped incorrectly) | Fail-closed on TOCTOU (established repo pattern) — extended per Pitfall 1's reconciliation pass, not merely re-checking under lock (the lock only guarantees single-instance atomicity, per `TargetLocker`'s own doc comment — it does not make Qdrant's own multi-ID mutation atomic). |
| Same-goroutine lock re-entry causing a permanent hang (Pitfall 2) | Denial of Service (a malformed/duplicate target set could hang the handling goroutine indefinitely, and repeated such requests could exhaust worker capacity) | Deduplicate resolved target IDs before any lock acquisition; no timeout exists on `sync.Mutex.Lock()` today (`locker.go:50-58`), so prevention (dedup) is the only mitigation — there is no recovery once the deadlock occurs. |
| ID/ownership leak via error message (404-indistinguishability, INV-01) | Information Disclosure | Unchanged existing pattern — echo caller-original input strings, never resolved UUIDs, across every target in the multi-fault list, not just the first. |
| Idempotency key reused across a different target set silently overwriting/misapplying a prior merge | Tampering | D-13's fingerprint-on-content+target-set closes this by design — a mismatch returns `ErrIdempotencyConflict`, never a silent different-operation success (mirrors `contentFingerprint`'s existing same-key/different-content detection). |
