# Phase 03.1 Plan 04: Merge Idempotency Summary

**`supersede_memory` now accepts `idempotency_key` with a target-set-keyed replay fingerprint (`mergeFingerprint`, composing the existing `contentFingerprint`) checked BEFORE the already-superseded stage — a same-key/different-target retry conflicts, a reordered/duplicated set replays (PD-01), and a losing simultaneous keyed merge recovers its answer from `resolveLostMergeRace` rather than surfacing the store's under-lock rejection.**

## Performance

- **Duration:** ~55 min (not precisely instrumented at start; bounded by container/session timestamps)
- **Tasks:** 3/3 completed
- **Files modified:** 5

## Accomplishments

- `mergeFingerprint(a storeArgs, targets []string) string` (`internal/server/idempotency.go`): composes `contentFingerprint(a)` — called, never re-listed — with a sorted, deduped, per-element length-prefixed target-set encoding, hashed with the same sha256 construction. `idempotencyPointID`'s derivation and UUIDv5 namespace are untouched (diff-verified).
- `checkIdempotentMergeReplay` and `resolveLostMergeRace` (`internal/server/tools.go`), beside `checkIdempotentReplay`: the former copies `checkIdempotentReplay`'s control flow against `mergeFingerprint`; the latter recovers a losing racer's answer from the store's `ErrAlreadySuperseded` rejection, but ONLY on a fingerprint match against the caller's own deterministic point — a mismatch stays a genuine conflict, never a success.
- `deps.supersedeMemory` rewired: the replay check now sits between `resolveAndAuthorizeSupersedeTargets` and `validateSupersedeTargetState` as two separate statements — D-14's ordering is a property of the call sequence. On a keyed non-replay write, the survivor's id is set to the deterministic point, `mergeFingerprint` is stamped, and (mirroring `persistAndEnqueue`'s tail) the point is re-read after `Upsert` to prefer the actually-persisted short_id.
- `supersedeArgs`'s depth-zero `IdempotencyKey json:"-"` shadow field and the handler's defensive clear are both gone: the promoted `storeArgs.IdempotencyKey` is now the sole schema and decode target, so `idempotency_key` is advertised, decoded, AND read.
- The three Phase 25 absence-pinning tests are inverted in place (renamed, assertions flipped): `TestSupersedeMemorySchemaIncludesIdempotencyKey`, `TestSupersedeArgsDecodePopulatesIdempotencyKey`, `TestSupersedeMemoryHonorsIdempotencyKey`. No reference to any of their old names survives (`rg` count: 0 across the package).
- Eleven new tests cover the replay contract end to end: replay, different-target-set conflict, reordered+duplicated-set replay (PD-01), the D-14 ordering proof, unkeyed-unchanged, oversized-key, concurrent-identical-key race (same persisted survivor), lost-race fingerprint-mismatch (scripted store, call-sequence assertions), `resolveLostMergeRace`'s six branches (table-driven, direct calls), replay-after-target-deleted (PD-09's published narrowing), and cannot-self-link.
- A twelfth test, `TestSupersedeMemoryKeyedPostWriteReReadPrefersPersisted`, was added during the acceptance-criteria regression pass — see Deviations below for why the plan's own tests did not cover this probe.

## Decisions Made

- **PD-01 (dedupe-silently) implemented exactly as ruled in `03.1-00-SUMMARY.md`:** `TestSupersedeMemoryIdempotencyReorderedSetReplays` covers a duplicated entry in the same test case as the reordering. `TestSupersedeMemoryDuplicateTargetRejectedBeforeFingerprint` was never written — it belongs to the `reject-duplicates` branch, which is dead under this ruling.
- **`mergeFingerprint` composes, never copies** `contentFingerprint`'s field list — the exact anti-drift discipline the repo's carry-forward gotcha already names for `contentFingerprint` itself. Verified structurally (the canonical field list appears exactly once in `idempotency.go`) and behaviorally (four unconditional pure-function tests).
- **Two separate concurrency-recovery mechanisms, not one:** the winner's own post-write short-id re-read only ever answers for the winner (it re-reads AFTER its own successful `Upsert`); the loser of an identical-key race never reaches `Upsert` at all (the store's already-superseded check runs BEFORE `Upsert`, under the target lock), so `resolveLostMergeRace` is a structurally separate recovery path, not a variant of the same one.
- **Tasks 2 and 3 landed in one commit** — see the Deviations section immediately below.

- **Rationale:** Task 2's code changes (removing `supersedeArgs`'s outer `IdempotencyKey` shadow field, wiring `checkIdempotentMergeReplay`) make the three pre-existing Phase 25 absence-pinning tests (`TestSupersedeMemorySchemaExcludesIdempotencyKey`, `TestSupersedeArgsDecodePopulatesPromotedIdempotencyKey`, `TestSupersedeMemoryIgnoresIdempotencyKey`) fail by construction — they exist specifically to pin the OPPOSITE behavior Task 2 introduces. The package only compiles and passes as a whole once Task 3's renames/inversions land in the same change. This mirrors the identical constraint plans `03.1-01` and `03.1-03` (same phase, earlier waves) both hit and documented for the same reason.
- **Impact:** Both tasks' acceptance criteria were independently verified (structural `rg` counts, full `TestSupersedeMemory*`/`TestSupersedeArgs*`/`TestResolveLostMergeRace*` suite, `-race` run, `task` lint+test) before the single commit landed. ### Regression-Check Findings (observed red, then reverted — not committed)

Per the plan's acceptance criteria, three DELIBERATE regression checks were run manually and reverted before committing. All three are recorded here as required; two produced a BROADER result than the plan's own prediction, which is stronger evidence, not a defect — and is flagged here per the instruction to surface uncertainty rather than bury it.

1. **Replay moved to AFTER `validateSupersedeTargetState`.** The plan predicted `TestSupersedeMemoryReplayPrecedesAlreadySupersededPreflight` would fail "while every other test in the file still passes." Observed: **four** tests failed, not one — `TestSupersedeMemoryIdempotencyReplay`, `TestSupersedeMemoryIdempotencyDifferentTargetSetConflicts`, `TestSupersedeMemoryIdempotencyReorderedSetReplays`, and `TestSupersedeMemoryReplayPrecedesAlreadySupersededPreflight`, each with `target is already superseded: ...` where a replay/conflict was expected. This makes sense in hindsight: every test whose SECOND call is a retry against an already-superseded target (not just the one explicitly named "PrecedesAlreadySupersededPreflight") independently exercises the same D-14 ordering property. Reverted; full suite green again.
2. **`resolveLostMergeRace` neutered to always return its incoming error unchanged.** The plan predicted `TestSupersedeMemoryConcurrentIdenticalKeyReturnsSameSurvivor`, `TestSupersedeMemoryLostRaceFingerprintMismatchConflicts`, and `TestResolveLostMergeRaceBranches`' match/mismatch subtests would fail. Observed: all three named tests failed as predicted, PLUS `TestResolveLostMergeRaceBranches/point_read_transport_error_returns_that_error` also failed (since the neutered helper no longer surfaces the transport-read error either). Reverted; full suite green again.
3. **Keyed-path post-write short-id re-read removed.** Running the plan's own acceptance-listed tests first (`TestSupersedeMemory|TestSupersedeArgs|TestResolveLostMergeRace`) found **zero** failures — confirming the plan's own caveat verbatim: "this re-read covers the WINNER's short id only — the loser's answer comes from `resolveLostMergeRace` — so the concurrency test is not the right probe for it." None of the plan's specified tests exercise a scenario where the SAME deterministic point id is written by TWO DIFFERENT keyed calls concurrently (Store.Supersede's per-target locks only serialize calls sharing at least one TARGET, not calls merely sharing a deterministic point id with disjoint target sets) — so a genuinely different-target-set race on the same point id was structurally untested. A new deterministic test, `TestSupersedeMemoryKeyedPostWriteReReadPrefersPersisted` (backed by a new `raceWriteStore` scripted-store helper, mirroring `lostRaceStore`'s pattern), was added to close this gap: it FAILED with the re-read removed (`sid = "eemhx3vtwd", want "RACERWON01"`) and PASSED with it restored. This is a genuine addition beyond the plan's named artifact list, made because the plan's own acceptance criterion ("at least one keyed test must FAIL") could not otherwise be satisfied honestly.
