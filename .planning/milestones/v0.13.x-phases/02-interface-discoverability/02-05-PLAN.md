<objective>
Extend the blast-radius taxonomy to the CLI lane, then pin both teaching surfaces — every command's
`--help` output and the bare `engram` catalog JSON — behind golden files regenerated by the same
`task surfaces:gen` target and gated by the same CI drift job.

Purpose: D-11 closes the gap that v0.12.x's headless CLI lane opened — agents can drive engram
without MCP but currently have no way to classify a command before running it. Landing it now means
Phase 3's `spine-review purge` is born classified rather than retrofitted. D-12/D-13/D-14 then make
the CLI's primary teaching surface un-driftable: one golden generated by walking the live tree so
completeness is automatic, plus the rendered catalog JSON so exit codes, blast radius, and field names
are pinned too.

Output: the catalog blast-radius field, both goldens, the `-update` regeneration path wired into
`task surfaces:gen`, the extended CI drift paths, and D-14's interpretation recorded in a durable doc.

  <name>Checkpoint: choose the published `blast_radius` JSON shape on `engram catalog`</name>
  <decision>The JSON shape of the new blast-radius classification on `engram catalog`</decision>
  <context>
`engram catalog` is a published contract. Adding a field is additive and safe, but agents will begin
branching on whatever shape ships, so the shape itself is a one-way door: changing it later breaks
every agent that learned to read it. CONTEXT.md D-11 locks the decision to ADD per-command blast
radius derived from the same table — that is settled and is not being re-asked. What is not locked is
the field's rendered JSON shape, which is Claude's discretion in CONTEXT.md and is the part agents
will depend on.

The classification data is fixed either way: four booleans per command (read-only, destructive,
idempotent, open-world), matching the MCP lane exactly.
  </context>
  <options>
    <option id="option-a">
      <name>Nested object mirroring MCP: `"blast_radius": {"read_only": bool, "destructive": bool, "idempotent": bool, "open_world": bool}`</name>
      <pros>Lossless — every hint an MCP agent reads is available to a CLI agent in the same shape. One taxonomy really is one taxonomy across both lanes, so an agent written against MCP transfers its logic unchanged. Adding a fifth hint later is additive inside the object.</pros>
      <cons>Four booleans is more for a caller to branch on than a single token. Snake_case JSON keys differ from the MCP wire's camelCase `readOnlyHint`, so the shapes rhyme without being identical.</cons>
    </option>
    <option id="option-b">
      <name>Single string enum: `"blast_radius": "read-only" | "additive" | "destructive"`</name>
      <pros>One token for an agent to branch on; the simplest possible gate before running a command. Reads well in `--help`-adjacent documentation.</pros>
      <cons>Lossy — it collapses four independent booleans into three buckets, so `idempotent` and `open_world` become unreadable on the CLI lane. Recovering them later means either a second field or a breaking change to this one. The two lanes stop being one taxonomy in what they actually publish.</cons>
    </option>
    <option id="option-c">
      <name>Both: the nested object plus a derived `"blast_radius_summary"` string</name>
      <pros>Serves the one-token consumer and the full-fidelity consumer at once.</pros>
      <cons>Two published fields that can be read inconsistently, and the derived summary is a second representation of the same fact — the exact duplication this phase exists to eliminate. Doubles the surface an agent may come to depend on.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>
</task>
