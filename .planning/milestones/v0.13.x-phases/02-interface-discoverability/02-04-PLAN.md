Populate one row per MCP tool, applying D-09's conservative stance — a hint is true only if it holds
under EVERY valid invocation. `openWorldHint` is false on every row: engram is a closed memory domain
and an omitted hint reads as "nobody decided", which is the ambiguity this phase exists to remove.

not from the tool's name. The stance resolves the three worked examples CONTEXT.md names explicitly:
`store_memory` and `schedule_memory` are NOT idempotent because `idempotency_key` is optional and an
unkeyed repeat duplicates; `update_memory` IS destructive because it replaces content in place;
`supersede_memory` is NOT destructive because it is additive under all inputs — history is preserved
and the target is soft-hidden, never deleted or overwritten. Resolve the remaining twelve tools by the
same rule and record any row whose reasoning is not obvious from its Description in a one-line comment
on that row.

The read verbs (`search_memory`, `list_memory`, `list_scheduled`, `get_memory`, `search_discovery`,
`list_rules`) are read-only; note that per the MCP spec `destructiveHint` is meaningful only when
`readOnlyHint` is false, so set it to false on those rows rather than leaving it to interpretation.

`buildCatalog` emits. Set their `MCPTool` to the empty string and classify them by the same
conservative stance — `prune-expired` and `migrate-remap-owner` are destructive, `reindex` and
`summarize-missing` and `backfill-short-ids` mutate but additively, `version` and the bare

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| engram MCP server → connected agent | `ToolAnnotations` are advertised to every connected agent and shape what an agent believes it is safe to call |
| shared taxonomy table → two consuming lanes | one table feeds both `mcp.ToolAnnotations` and (in plan 02-05) the published `engram catalog` JSON |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-13 | Spoofing | an annotation advertising a tool as safer than it is | high | mitigate | D-09's conservative stance is the mitigation: a hint is true only if it holds under EVERY valid invocation, so `store_memory`/`schedule_memory` are non-idempotent (the key is optional) and `update_memory` is destructive. An agent reading a hint gets a guarantee, not an aspiration. Values are spot-asserted against the three worked examples and reviewed as one table. |
| T-02-14 | Tampering | a tool silently registered with no classification | high | mitigate | The both-directions gate fails when a registered tool has no table entry AND when a table entry names no registered tool, and it additionally rejects a nil `Annotations` or a nil `*bool` hint, so a zero-valued `&mcp.ToolAnnotations{}` cannot pass as annotated. Proven fail-first in all three directions with the observed reds recorded in the SUMMARY. |
| T-02-15 | Information Disclosure | `openWorldHint` omitted, defaulting to true | medium | mitigate | The go-sdk models `OpenWorldHint` as `*bool` where nil means the spec default `true`; every row sets it explicitly to false via `boolPtr`, and a test asserts no row leaves it unset. |
| T-02-16 | Tampering | shared mutable hint pointer | low | mitigate | `boolPtr` allocates a fresh `bool` per call rather than handing out the address of a package-level variable, so no caller can mutate one tool's hint through another's pointer. Asserted by a source check that no package-level false-valued variable is address-taken. |
| T-02-SC | Tampering | npm/pip/cargo/go installs | low | accept | Zero new packages. `mcp.ToolAnnotations` is already available on the vendored go-sdk v1.7.0; RESEARCH.md's Package Legitimacy Audit records no new external packages for this phase. No install task, so no legitimacy checkpoint applies. |

Note the go-sdk carries the MCP spec's own caveat, which this phase does not contradict: annotations
are hints, and clients should never make tool-use decisions based on annotations received from
untrusted servers. They are a discoverability aid, never an authorization mechanism.
</threat_model>
