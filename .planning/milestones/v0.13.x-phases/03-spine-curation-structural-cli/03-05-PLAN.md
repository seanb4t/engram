<objective>
Ship `engram spine-review consolidate`: a whole-spine, deterministic near-duplicate sweep that
reports ranked `(A, B, score)` pairs using records' already-stored vectors, and never merges or
mutates anything.

Purpose: consolidation is a judgment about identity. This phase supplies only what is derivable
structurally — the ranking — so Phase 4's semantic skill has something to judge without this command
having pre-decided anything.

Output: a Subject-less batched vector-neighbour query and the leaf that renders its ranked report in
text and JSON.
</objective>

**Model all-scopes explicitly.** `AllScopes bool` is a separate field, NOT an empty `Scope` string.
Every `QueryPoints` carries a `Must` scope match ONLY when `AllScopes` is false; in all-scopes mode
the scope condition is omitted entirely. The previous revision encoded all-scopes as an empty scope
while requiring the `Must` match unconditionally, which matches only records whose scope is literally

**All-scopes pair semantics, settled here rather than left undefined:** cross-scope pairs ARE
reported. Two scopes holding the same fact is precisely the duplication an operator wants to see, and
partitioning by scope would hide it. Each row therefore names `AScope` and `BScope`, and the
formatter renders both. Record this in the CLI guide in Task 2.

**Represent "no minimum score" in the type.** `MinScore` is a `*float32`: nil means no filter. Cosine
similarity is negative-capable, so a `float32` zero value applied as `score >= MinScore` silently
imposes a threshold — exactly what D-15 and this plan's `<planner_assumptions>` forbid, and a default
the old type could not even express.

Implement the exhaustive path RESEARCH.md verified, not the Search Matrix shortcut. First enumerate
every point id in scope through plan 03-01's shared `scrollAllPoints` iterator, requesting neither
payload nor vectors, so the id set is cheap and complete — this enumeration is what lets the report
claim whole-spine coverage. Do NOT call `s.client.Scroll` and do NOT write a second `ScrollAndOffset`
loop; `Client.Scroll` issues one RPC and discards `NextPageOffset`
(`qdrant/go-client@v1.18.3 points.go:70-76`), so on any spine larger than one page the "every record
was checked" claim would be false with nothing to detect it. `internal/store/spine.go` must still hold
exactly ONE scroll call site after this task.

Then chunk the ids and issue `client.QueryBatch` with one `QueryPoints` per id, each using
`qdrant.NewQueryID` so Qdrant resolves the query vector server-side from the point's own stored
vector: no text is re-embedded and no vector is transmitted from engram. Each `QueryPoints` carries a
`MustNot` `NewHasID` on the querying id so a record never matches itself.

**Fetch only what the report renders.** Use a payload INCLUDE selector naming `short_id` and `scope`
rather than `WithPayload: true`. The report carries ids, short ids, scopes and scores; requesting the
whole payload ships full `content` for up to N×TopK points across the wire for data that is then
discarded — and this is the operator tier, so that content belongs to every actor.

Do NOT use `SearchMatrixPairs` or `SearchMatrixOffsets`. Their `sample` parameter carries no
documented guarantee of exhaustive or deterministic coverage (RESEARCH.md Pitfall 4), and this
command's whole claim is that every record was checked.

Collapse the two-sided results: the sweep naturally produces both (A,B) and (B,A), so key the
accumulator on the ordered-by-id pair and keep one row. Apply `MinScore` as a filter after collapsing
(skipping the filter entirely when nil) and `TopK` as the per-query neighbour limit. Sort by score
descending with a deterministic tiebreak on (A, B) so the output is stable across runs.

Call `Progress` (when non-nil) after each batch with the running scanned/queried counts, so the leaf
can report progress to stderr on a long sweep. **A maximum-records cap is DEFERRED with rationale:**
this command's only claim is exhaustiveness, and a silent cap would make the claim false in exactly
the case that matters (a large spine). The operator-visible scanned/queried counts and `--scope`
give bounded runs without a cap that lies. Record this in the SUMMARY and file a follow-up issue if a
cost ceiling turns out to be needed.

Follow `ScanSpine`'s span and telemetry boilerplate with op name `NearDuplicates`, take no `Subject`
parameter, and add no owner or shared condition.

Extend `internal/store/spine_test.go` with integration coverage for every behavior-list row. Include

digest before and after the call and assert both are unchanged.
