Create `cmd/engram/destructive.go` with the gate as a STRUCTURAL choke point, not a per-command
convention. The previous revision derived only that an `--apply` flag EXISTS; nothing stopped a
future `RunE` from ignoring it, so D-03's "a future destructive command inherits the guard
automatically" was not delivered. The fix is to take the `RunE` away from the leaf:

`destructiveByClassification(cmd *cobra.Command) bool` looks up
`surfaces.ClassForCommand(commandKey(cmd))` and returns the row's `Destructive` value, treating a
missing row as a programming error routed through the same panic discipline `buildCatalog` uses —
never as a silent false.

`addApplyFlag(cmd *cobra.Command, target *bool)` registers an `--apply` bool flag defaulting to false
whose Usage string is built from `surfaces.RuleByID(surfaces.RuleDestructiveRequiresApply)`'s
Sentence — composed from the registry, never re-typed.

`applyRequested(applied bool) bool` is a one-line pure predicate returning the flag's VALUE. Read the
value, never `pflag.Flag.Changed`: cobra flag groups trip on a flag being SUPPLIED rather than on its
value (memory `k66tenzbhy`), and an explicit `--apply=false` must behave exactly like an omitted flag.

`registerDestructive(cmd *cobra.Command, target *bool, preview func(*cobra.Command, context.Context) error, apply func(*cobra.Command, context.Context) error)` is the choke point. It calls `addApplyFlag`, then ASSIGNS `cmd.RunE` itself to a closure that: panics if `destructiveByClassification(cmd)` is false (a non-destructive command must not register here); builds the context exactly as `prune.go`'s skeleton does; resolves the mode via `applyRequested(*target)`; and invokes `preview` or `apply` accordingly. The `apply` closure is unreachable in preview mode by construction — there is no code path from the preview branch to it. A destructive leaf therefore supplies two closures and never writes `RunE`, so it CANNOT skip the gate by forgetting to consult a flag.

**Mark `registerDestructive` with a `//go:noinline` pragma directly above its declaration**, and say
in the adjacent doc comment that the pragma exists to keep the installed closure attributable at
runtime — `TestDestructiveCommandsRouteThroughGate` resolves the closure's symbol name through
`runtime.FuncForPC`, and an inlined enclosing function can leave that name unrecognisable. This is a
testability pragma, not a performance one; `registerDestructive` runs once per command at `init()`
time, so the cost is nil.

`mutationMode` is the small named type the closure resolves to (`modePreview` / `modeApply`), exposed to the leaf's closures so wording can differ without re-deriving the decision.

`cliNow` is a package-level `var cliNow = func() time.Time { return time.Now().UTC() }` — the clock seam the preview cutoff reads. `prune.go:36` currently calls `time.Now().UTC()` inline with no injection point, which makes the byte-identical-re-run must-have unsatisfiable across a second boundary. Every destructive command's cutoff derivation reads `cliNow()`, and tests override it with a `t.Cleanup` restore.

Add no bypass of any kind — not a flag, not an environment variable, not a config key. This plan's first prohibition states the reason in full, and this is the file where such a thing would otherwise be added. The gate is a flag-set equality per destructive command, so any bypass flag fails the build regardless of what it is named.
