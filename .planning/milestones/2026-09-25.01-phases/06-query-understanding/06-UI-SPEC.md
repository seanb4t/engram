## Scope & Canonical Sources

In scope this phase: the **"Suggested" row** of dashed-outline, unapplied filter chips rendered
directly under `FacetStrip` on `/search`, sourced from the new `UnderstandQuery` Connect RPC.
Accept-by-click/Enter, dismiss-by-`×`/Delete/Backspace, a roving-tabindex toolbar keyboard model.
Absent whenever there is nothing useful to show (off, error, timeout, zero suggestions, every
suggestion already applied). OUT of scope: any change to the header search, the ⌘K command menu,
`SearchMemories` itself, server-side `internal/understand`/`internal/decide` wiring (Phase 6's own
plan/research concern, not a UI contract), and a user-facing on/off toggle (enablement is
server/env-only, `ENGRAM_SEARCH_UNDERSTANDING`; the console has no settings surface for it).

| Role | Value | Usage this phase |
|------|-------|------|

| Chip label text | **default foreground** (unchanged, inherited — the same color `FacetStrip`'s neutral/unapplied chips already use) | Suggestion chip text. **Never** `--text-faint` here: this is the content the user reads and acts on, not decoration; dimming it would repeat the exact AA-contrast failure `04-A11Y-AUDIT.md` already found and fixed for row text (D-17 of Phase 4) |
| Chip border, resting | `var(--border)` (unchanged — the same token inputs and `.facet-chip` already use, not `--border-subtle`, which is reserved for dividers and was never vetted for the 3:1 non-text-contrast requirement an interactive control boundary needs) | `.suggested-chip` resting border |

**not** used for the chip's fill, its label text, or the row caption. No new destructive/warning/

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | None introduced. There is no page-level call to action this phase; accepting a suggestion chip is direct manipulation (click/Enter/Space on the chip itself), not a labeled button — same reasoning `02-UI-SPEC.md` gave for the results row. |
| Empty state heading | **N/A — deliberately absent, always.** Per D-12, the entire row (not a placeholder inside it) is omitted when understanding is off, the call errored or timed out, it returned zero suggestions, or every suggestion is already applied/dismissed. There is no "no suggestions" copy anywhere — an absent row IS the empty state. |
| Empty state body | N/A — see above; nothing renders, so there is no body copy to author. |
| Error state | **N/A — identical treatment to empty.** D-12/D-17: an error or timeout yields zero suggestions and the row is absent. No error banner, no retry affordance, no toast — a decision failure must be invisible to the operator, never surfaced as a failure of *their* search. |
| Destructive confirmation | N/A — dismissing a suggestion changes nothing server-side and loses no data; it needs no confirmation. Accepting a suggestion is exactly as reversible as manually adding the same filter chip (removable from `FacetStrip` afterward). |

### Suggestion chip label text (per D-03 oneof kind)

| Kind | Chip label | Notes |
|------|-----------|-------|
| `category` | The bare category name, e.g. `convention` | No count (a suggestion carries none — counts are a `FacetStrip` concept, not this row's). A small category-color dot precedes the label, `background: var(--cat-{category})`, the same decorative dot convention `ResultRow` uses for category identity — `(default)`, not locked by D-06, chosen for visual parity with the rest of the console rather than inventing a bare-word-only style. |
| `time_window` | The server's `label` string, rendered **verbatim** | e.g. `past week`, `today`, `past month`, `past year` — the client performs no bucket-name translation of its own; whatever `internal/understand` sends is what renders, per the honest-feedback "never paraphrase" convention. |
| `scope` | The scope string, in the default sans weight (not monospace) | `(default)` — a scope's full mono/type-badge treatment (`ScopeChip.svelte`) is reserved for places a scope is already an applied, identified filter; here it is still a suggestion, so the plain string is enough. |
| `tag` | `#{tag}` | Matches `FacetStrip`'s existing tag-chip format exactly (`#{t}`). |

Chips render in the exact order `UnderstandQueryResponse.suggestions` returns — **no client-side
re-sort** by kind. This is a deliberate default: re-sorting would imply the client knows something
about priority the server didn't already encode by putting it first, and D-03 states "one
suggestion per chip" with no ordering contract to second-guess.

### Accessible names (D-13, verbatim where quoted)

| Element | Copy |
|---------|------|
| Row caption (visible) | `Suggested` |
| Row container `aria-label` | `Suggested filters` `(default)` |
| Each chip's accept control `aria-label` | **`Suggested filter, not applied: {label}`** — quoted verbatim from D-13; `{label}` is exactly the visible chip label text from the table above |
| Each chip's dismiss control `aria-label` | `Dismiss suggested filter: {label}` `(default — naming pattern, not verbatim-locked)` |

## UI Considerations

Probe: `ui-consideration-probe` over 1 authored element (E1), `--auto`. 8 applicable
considerations, 0 unclassified, 8 resolved (8 explicit, 0 backstop). Empty/error COPY lives in the
Copywriting Contract above — rows here reference it rather than restating it.

Element: E1 Suggested filter chips row (`list-collection`, `interactive-control`) — the one and
only authored element this phase; the surface is small enough that a second element would just be
restating E1's own sub-parts.

| Category | Status | Truth |
|----------|--------|-------|
| empty | resolved (explicit) | Zero suggestions (any cause — off/error/timeout/all-applied/all-dismissed) renders **no row at all**, not an empty placeholder or "no suggestions" text (D-12). |
| loading | resolved (explicit) | The row is absent while the `UnderstandQuery` call is in flight; it appears only once resolved with ≥1 surviving suggestion — no skeleton, no spinner, ever, on this row. |
| error | resolved (explicit) | Identical to empty: a rejection or timeout yields an absent row, no error UI, no retry affordance (D-12, D-17) — a decision failure is invisible to the operator. |
| populated | resolved (explicit) | 1–N dashed-outline chips render left to right, in server response order, in a single line directly under `FacetStrip`, led by the `Suggested` caption. |
| partial | resolved (explicit) | A suggestion already reflected in the currently-applied filters is hidden client-side (D-12; see the exact per-kind hide rule in Interaction Notes below) — a 4-suggestion response with 1 already applied renders exactly 3 chips, never a disabled/"already applied" visual state for the 4th. |
| overflow | resolved (explicit) | The row is a single horizontally-scrollable line (`ScrollArea` + edge fade, identical mechanism to `FacetStrip`) — chips never wrap to a second line and the row never grows taller than one chip height regardless of suggestion count. |
| zero-one-many | resolved (explicit) | The row's layout is identical for 1 through N chips — there is no count-bearing sentence on the visible row (only the screen-reader-only announcement is count-agnostic-templated: singular at N=1, plural otherwise); zero is covered under empty (row absent, not "0 suggestions"). |
| long-text | resolved (explicit) | A chip's label (a long scope string, a long tag, an unusually long category name) ellipsizes within a max chip width (`calc(220 * var(--u))`, matching the console's other single-line chip max-widths) without wrapping or growing row height; the full text is available via the chip's native `title` attribute. |

## Interaction & Accessibility Notes

Not a template section, but load-bearing: the executor must build against these exactly, not
infer them from the CSS alone. This section extends `engram-console-conventions`'s keyboard model
rather than restating it in full.

### Trigger & eligibility (D-10)

Fires only when **all** of the following hold, evaluated against the classifier's output for the
**committed** query (`params.q`, not the debounced draft `inputText`):

1. `classifyInput(params.q).kind === 'text'`
2. The classified result carries **zero** operator chips (`classified.chips.length === 0`) — any
   `scope:`/`in:`/`tag:`/`#`/`is:` token in the box disqualifies the whole query, not just that
   token
3. The free-text portion is 2+ words (`classified.text.trim().split(/\s+/).length >= 2`)

An id/short_id-classified query, an operator-only query, or a single-word query never triggers a
call — the row simply never mounts for that query (indistinguishable from "resolved with zero
suggestions" to the user, but no RPC is made at all).

### Query-key pitfall — filters ride the request, never the key

`UnderstandQueryRequest` carries the query text **plus a snapshot of the currently-applied
filters** (scope/cross_spine/categories/tags/window) per D-03, so the server can skip questions
whose answer is already applied. This must **not** be read as "refetch whenever a filter
changes" — D-10 is explicit that the call fires **only** on a `q` change. The TanStack query key
is therefore `['understandQuery', q]` — filters are **not** part of the key. Toggling a facet
chip after the row has rendered must never re-trigger the RPC; it only ever changes which
already-fetched suggestions the client hides (the partial/hide rule below). Building the key from
`effective` (the full merged params object) instead of bare `q` is the one wiring mistake this
note exists to prevent — it would silently refetch on every facet click, unwiring D-10's own
firing rule.

### Session capability latch (D-04)

The first response's `enabled` field is authoritative for the rest of the page session. Once a
response arrives with `enabled: false`, no further `UnderstandQuery` call is made for any later
`q` change in that session (no `ListScopes`/`ListTags` work is even attempted server-side once
this is known, per D-04) — implement as a page-level `$state` boolean latched permanently to
`false` on that response, gating the query's own `enabled` option alongside the eligibility check
above. This is a runtime latch only (not persisted to `localStorage`), matching D-04's scope: "for
the rest of the session," not across reloads.

### Per-kind accept mapping — the exact `FacetStrip.onchange` path (D-11)

Accepting a chip **must** call the identical `onchange` callback `/search`'s page already wires to
`FacetStrip` (`onchange={(partial) => navigate({ ...partial, sel: '' })}`), with the same partial
shape a manual chip produces — this is what makes an accepted suggestion "exactly a manually added
chip" (D-11) rather than a second, parallel code path that happens to look the same:

| Suggestion kind | `onchange` partial (identical to the manual control that produces it) |
|---|---|
| `category` | `{ categories: [...params.categories, value] }` — same dedupe-by-inclusion shape as `FacetStrip.toggleCategory` |
| `time_window` | `{ createdAfter, createdBefore }` from the response's RFC3339 fields — same fields the created-window popover's date inputs write |
| `scope` | `{ scope: value, crossSpine: false }` — same shape `ScopeCombobox.onselect` produces |
| `tag` | `{ tags: [...params.tags, value] }` — same dedupe-by-inclusion shape `TagCombobox.onadd`/`FacetStrip`'s tag chips use |

### Per-kind "already applied" hide rule (D-12)

Evaluated reactively against `effective` (the merged, currently-applied params) on every render,
independent of the dismissed-set below:

| Suggestion kind | Hidden when |
|---|---|
| `category` | `effective.categories.includes(value)` |
| `tag` | `effective.tags.includes(value)` |
| `scope` | `effective.scope` is non-empty (**any** applied scope hides a scope suggestion, not just an exact-value match — the server only asked because no scope was applied at request time; a scope applied since then already answers the same question regardless of which one) |
| `time_window` | `effective.createdAfter \|\| effective.createdBefore` is non-empty (**any** applied window hides a time_window suggestion, same reasoning as scope) |

### Dismissal state (D-12)

A dismissed suggestion's identity (`kind` + `value`, e.g. `category:convention`, `tag:foo`,
`scope:<value>`, the literal string `time_window` since there is at most one per query) is added
to an in-memory `Set` scoped to the current `q`. The set is cleared whenever `q` changes — dismissal
is never written to the URL and never persisted across a query edit, per D-12's "held per `q` in
memory, not in the URL." A suggestion renders only when it is **neither** already-applied (above)
**nor** in this set.

### Roving-tabindex toolbar keyboard model (D-13)

The row is a toolbar (`role="toolbar" aria-label="Suggested filters"`) of accept controls, using
the standard WAI-ARIA APG Toolbar roving-tabindex pattern the term "roving-tabindex toolbar"
itself names — the toolbar as a whole is one `Tab` stop; arrow keys move focus **within** it:

| Key(s) | Action |
|---|---|
| `Tab` (into the row) | Focuses the currently-active chip's accept control (defaults to the first chip) |
| `←` / `→` | Move roving focus among chips' accept controls `(default — inherent to the named "roving-tabindex toolbar" pattern; not a new binding)` |
| `Home` / `End` | Jump to the first/last chip's accept control `(default, same pattern)` |
| `Enter` / `Space` | Accept the focused chip (D-13) |
| `Delete` / `Backspace` | Dismiss the focused chip (D-13) |
| `Tab` (out) | Leaves the toolbar; the dismiss `×` controls are **never** in the Tab/arrow sequence (see DOM shape below) |

Every visible chip additionally exposes a pointer-only `×` dismiss control (D-11) that is
**not** part of the roving set (`tabindex="-1"` always) — this mirrors the WAI-ARIA "tab with
close button" pattern (a close affordance reachable by click or by a key bound to the parent
control, never a separate Tab stop) rather than doubling the number of roving stops per chip.
DOM shape: a non-interactive wrapper (`<div>`, not a nested `<button>`) holding two sibling
`<button>` elements — the accept control (in the roving set) and the dismiss control
(`tabindex="-1"`, pointer/mouse only) — never a button nested inside a button.

Focus-visible treatment on the active chip reuses the console's one existing focus-ring pattern
(`border-color: var(--primary)` + `box-shadow: 0 0 0 calc(3 * var(--u)) var(--primary-soft)`),
the same CSS the header search input already applies — no new focus style is invented.

### Appearance transition

The row fades/slides in using the foundations' existing `0.15s ease` transition when it first
populates for a given `q` (no transition on subsequent accept/dismiss — those are instant, since
the remaining chips simply re-flow). There is no transition on disappearance beyond the row simply
unmounting — nothing lingers or fades to a "used up" state.
