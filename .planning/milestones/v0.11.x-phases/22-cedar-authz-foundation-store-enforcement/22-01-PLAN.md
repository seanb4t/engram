## Policy Reconciliation (LOAD-BEARING — read before authoring the .cedar files)

RESEARCH.md's Code Examples show ILLUSTRATIVE reference policy bodies (own_records with
`resource == Engram::OwnRecords::"bucket"`, and a BLANKET `forbid ... unless principal.owner != ""`).
Two of those illustrative bodies are INCORRECT for engram's behavior-preservation oracle (D-11)
and are corrected here. RESEARCH.md itself labels them "illustrative — exact Go types are Claude's
Discretion." The corrections below are grounded directly in the existing tests
`TestAnonBucketReadIsolation` and `TestAnonBucketWriteSemantics`
(`internal/store/store_test.go`), which D-11 requires to pass UNCHANGED.

Ground truth those tests fix:
- The anonymous caller (owner=="") MUST read/write/delete its own `owner==""` records (the
  anonymous bucket, auth-disabled deployments).
- The anonymous caller MUST NOT read another owner's `shared` record, nor any other owner's
  private record.
- An authenticated caller reads own (private + shared) records AND other owners' `shared` records.

Correction 1 — attribute-based, unified corpus. Policies match on resource ATTRIBUTES
(`resource.owner`, `resource.visibility`) rather than on distinct bucket entity types. This lets
ONE corpus serve both the bulk path (a canonical per-bucket probe resource) and the id-addressed
path (an `Engram::Memory` resource built from the fetched payload, per D-03). The
`OwnRecords`/`SharedRecords` names survive only as `Bucket` Go enum values and as reference names
in `schema.json` (D-06 reference-only).

Correction 2 — scoped forbid. A blanket `forbid ... unless principal.owner != ""` denies the
legitimate anonymous owner=="" bucket and breaks D-11. Scope it to non-empty-owner resources
(see defense_empty_owner below) so it blocks an empty-owner principal from reaching shared /
other-owner records WITHOUT denying the anonymous own bucket. This is exactly the defense-in-depth
STATE.md describes ("a second, independent backstop ... does not substitute for the Phase-23
upstream fix").

The four policy bodies (Cedar native `//`-comment syntax; describe in prose, author verbatim):
- own_records: a single `permit` with an empty head, gated `when { resource.owner == principal.owner }`
  — grants all five actions on records the principal owns; ""=="" naturally grants the anonymous
  bucket to the anonymous caller.
- shared_read: a `permit` scoped `action == Action::"read"`, gated
  `when { resource.visibility == "shared" && principal.owner != "" }` — read-only, non-empty-owner
  principals only (so anonymous never gains shared read).
- tenant_isolate: a `permit` gated
  `when { principal has tenant && resource has tenant && principal.tenant == resource.tenant }`
  — has-guarded, vacuous this phase (neither attribute is ever populated, D-06).
- defense_empty_owner: a `forbid` gated `when { resource has owner && resource.owner != "" }`
  and `unless { principal.owner != "" }` — denies an empty-owner principal on any non-empty-owner
  resource; does NOT fire on the owner=="" anonymous bucket.

The nil/unknown Subject fail-closed case is handled in the STORE (Plans 02/03), never by giving
Cedar an owner=="" principal — because own_records deliberately grants owner=="" (the anonymous
bucket). The store's condition builders keep an explicit nil guard (matchNothing / ErrNotFound)
before consulting the PDP.
