Expose the category filter on the MCP surface: a plural `categories []string` argument on
`search_memory` and `list_memory` (D-08), wired straight through to the transport-neutral core
requests with no lane-specific interpretation.

`coreListRequest.Categories` plus `deps.listMemory`'s threading already shipped in an earlier phase
— so the only genuinely missing plumbing on the list side is the MCP argument itself, and on the
search side it is the argument plus the one `coreSearchRequest` field assignment.

Output: two new struct fields with OR-explicit jsonschema descriptions, two closure wirings, and
three MCP-level tests covering the happy path plus the empty / unknown-value / ordering edges.
</objective>

`REQ-category-filter` empty edge and the empty-element-skipping behavior `categoryMatchCondition`

present in the scope must return the same ordered id slice as omitting the argument entirely.

deterministic for a fixed query and fixed candidate set, so an order difference is a real regression,
not flake.
