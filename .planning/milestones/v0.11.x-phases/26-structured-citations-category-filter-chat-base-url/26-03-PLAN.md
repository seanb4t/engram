  <decision>Publish `repeated string categories = 8` on `SearchMemoriesRequest` (D-10)</decision>
  <context>
This is the only **one-way** decision in Phase 26. A proto field number, once published in a tagged
release, can never be reused or removed without breaking wire compatibility for any client that
adopted it — reserve-and-deprecate is the only retreat. Everything else in this phase is reversible
or merely costly.

D-10 is already locked in `26-CONTEXT.md`; this checkpoint exists to make the one-way commitment
visible before the field ships, not to re-litigate the design. The engineering facts: field 8 is the
next free number on `SearchMemoriesRequest` (fields 1-7 are query, scope, k, tags, full,
created_after, created_before); additive fields are buf-lint- and buf-breaking-safe; and the buf
remote plugins are version-pinned, so regeneration is byte-identical apart from the new field.
  </context>
  <options>
    <option id="ship-field-8">
      <name>Ship it now as field 8 (D-10 as locked)</name>
      <pros>SC2's stated "MCP↔Connect parity" is actually true in both directions; the console and any Connect client can filter search by category; the field number is claimed while the message is still small and uncontested.</pros>
      <cons>Irreversible: field 8 is spent forever on this meaning.</cons>
    </option>
    <option id="defer-connect-search">
      <name>Defer Connect search-side parity to a later milestone</name>
      <pros>No one-way commitment this phase; the proto stays untouched and there is no codegen or drift surface.</pros>
      <cons>Leaves the mirror-image parity gap the phase goal explicitly set out to close (MCP search filters by category, Connect search cannot); a later phase pays the same one-way cost anyway, just later and with a larger message.</cons>
    </option>
  </options>
