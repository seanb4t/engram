<objective>
Publish the three-way exit-status taxonomy `engram setup` needs — total success, partial success,
total failure — and make the classification a pure, exhaustively-tested function over the per-runtime
outcome list.

Purpose: REQ-setup-partial-failure-legible requires a CI caller to distinguish the three cases
without parsing JSON. `exitCodeForConnectErr` structurally cannot produce either new code, so each
needs a named `nonConnectProducedCodes` allowlist entry — the same mechanism `exitFindings` already
uses — and the five sites that carry the taxonomy (`client_common.go`'s const block, `catalog.go`'s
`doc.ExitCodes`, `catalog_test.go`'s `wantExitCodes` and `nonConnectProducedCodes`, and
`testdata/catalog.golden`) must move in ONE commit, because the existing set-equality gate is
unsatisfiable while any subset of them lags.

Output: `exitPartial = 8` and `exitSetupFailed = 9` published end to end, `internal/setup.ExitClass`
proven over the full outcome-combination table, and `engram setup --apply` reporting every runtime's
own outcome before returning a typed exit status.
</objective>

  <action>
Add `internal/setup/exit.go` declaring an `ExitClass` type with three exported values —
`ExitTotalSuccess`, `ExitPartial`, `ExitTotalFailure` — and a pure
`Classify(results []Result) ExitClass`.

The classification rule, stated once here and encoded once there:
- An `attempt` is any `Result` whose `Outcome` is not `OutcomeNotPresent`. A `not-present` runtime is
  an expected outcome, never a failure (D-07): "there was nothing to do" must never be reported to a
  script as "I failed."
- A `failure` is any `Result` whose `Outcome` is `OutcomeFailed`.
- Zero failures -> `ExitTotalSuccess`, including the zero-attempts case (no runtime selected, or every
  selected runtime absent).
- At least one failure alongside at least one non-failed attempt -> `ExitPartial`.
- At least one failure and no non-failed attempt -> `ExitTotalFailure`.

`Classify` performs no I/O, takes no context, and touches neither the filesystem nor the network, so
the whole table is unit-testable with no fake and no harness. Follow `verifyFailOnErr`'s shape: a
pure function over an already-built report, returning a typed decision the caller maps to a process
exit code — never returning an `int` itself, so `internal/setup` stays free of `cmd/engram`'s exit-code
vocabulary and the leaf-purity gate keeps holding.

A `Result` carrying the zero-valued `Outcome` is a programming error, not a data case. Give
`Classify` an explicit guard that treats it as a failure and document why: silently bucketing an
unset outcome as success is exactly how an unreported error becomes an exit 0. Add a matching note to
`Outcome`'s doc comment in `plan.go`.
  </action>
