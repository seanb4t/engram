<objective>
Connect a value the PDP has been computing and discarding since Phase 22 to the operator who needs it.

`authz.Decision` already carries the full `cedar.Diagnostic` from `cedar.Authorize`, and
`internal/authz/authz.go:44-47` already says in a comment that the field "exists solely for future
debug-level logging / OTel span attachment by internal/store." This plan is that future. Nothing
about WHO is authorized changes; this phase reports decisions, it does not make them.

The design tension is entirely about disclosure. `cedar.Diagnostic` has exactly one field that can
embed evaluated entity values — `DiagnosticError.Message` — and D-02 excludes it, keeping only the
error COUNT. D-03 then insists that exclusion be structural: `diag` stays unexported and a narrow
accessor returns exactly the allowlisted fields, so a future `cedar.Diagnostic` field cannot leak
through a call site that meant well. Call-site discipline is the failure mode, not the mitigation.

Purpose: make a wrong allow as debuggable as a wrong deny, without turning the audit log into a
policy-evaluation transcript.
Output: a narrow accessor in `internal/authz`, a debug line at the two `internal/store` chokepoints,
and a negative gate proving the excluded half is genuinely unreachable.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `cedar.Diagnostic` -> operator log | Cedar's own evaluated-condition error text can embed entity attribute values. This is the only place in the phase where PDP-internal data crosses into a durable operator-visible sink. |
| `internal/authz` -> `internal/store` | The accessor is the entire API surface across this boundary for diagnostics. Whatever it returns is loggable; whatever it does not return is unreachable. |
