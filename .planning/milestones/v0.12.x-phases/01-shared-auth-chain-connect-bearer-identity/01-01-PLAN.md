<objective>
Wire one path end-to-end: a headless caller presents a bearer credential to the ConnectRPC
lane, the server verifies it through an injected expiry-enforcing verifier, records **which
lane** authenticated the request as a typed value, and the CSRF interceptor decides its
exemption from that record alone.

This is the phase's tracer slice and its security core. The lane-provenance stamp and the
CSRF exemption that reads it are **one atomic unit** (ROADMAP "why these four ship
together"): shipping the stamp without its reader would land a value nothing consumes.

Purpose: closes two defect classes that are invisible to a green test suite — `Expiration`
written by the verifier chain and read by nothing on this lane, and a CSRF exemption that
could be inferred from attacker-controlled request content.
Output: `internal/auth`'s transport-agnostic bearer policy, the Connect adapter and composed
resolver, the typed lane context key, and the lane-gated CSRF exemption.
</objective>

<assumption_delta_decision>
The detector fired `pluralization` on this phase scope, and the substantive delta is real: the
Connect lane has had exactly **one** identity mechanism (the session cookie) since it was
introduced, and this phase adds a second (bearer). The question the checkpoint asks — does the
current identity model still name the right noun? — has a concrete answer here.

- **Primary noun (generalized):** `auth.Lane` — *which credential family verified this request*.
- **Decision: `promote`.** The lane is promoted to an explicit, typed, compiler-enforced third
  return value on the resolver contract, and "cookie" is demoted to one variant of it
  (`auth.LaneCookie`). Every downstream cookie-lane side effect is re-keyed off the generalized
  noun rather than off "is there a cookie": the CSRF exemption (D-08) and session re-sealing
  (D-09) both branch on `auth.Lane` and on nothing request-derived. `auth.LaneUnknown` is the
  zero value and is invalid, so a future third lane cannot be added without declaring itself —
  the generalization cannot silently regress to the singular assumption.
- **Not `add-alongside`.** The rejected shape was carrying the lane as a key inside
  `mcpauth.TokenInfo.Extra` beside the existing owner claim, which would have left the old
  cookie-shaped assumption primary and the lane an optional detail a resolver could forget.
  CONTEXT.md D-07 rejected it for exactly that reason.
- **Invariant test encoding the generalized intent:** `TestCSRFLaneUnstampedFailsClosed` (Task 2)
  goes red the instant any future resolver returns an undeclared lane, and
  `TestResealGatesOnCookieLane` (Plan 02) goes red if a cookie-lane side effect is re-keyed off
  cookie presence again.
</assumption_delta_decision>

  <action>
Create `internal/auth/bearer.go` holding the whole transport-agnostic bearer policy (D-03 —
this package must not import `connectrpc.com/connect`).

Declare `type Lane int` with `LaneUnknown Lane = iota`, `LaneBearer`, `LaneCookie`, and a
`String()` method returning `"unknown"`, `"bearer"`, `"cookie"`. Mirror the shape of the
existing unexported `lane` enum in `chain.go:29-35`; the two types coexist deliberately —
`lane` discriminates bearer *shape* inside `ChainVerifier`, `Lane` records which *transport
credential family* authenticated a Connect request. Do not rename, merge, or otherwise touch
the existing `lane` type. Document the coexistence in the `Lane` doc comment, and document
that `LaneUnknown` being the zero value is load-bearing: an unstamped context yields it, and
D-08 rejects on it.

Declare `ExtractBearerCredential(authHeader string) (token string, ok bool)` reproducing the
go-sdk's `verify()` header parse exactly: `strings.Fields`, require exactly two fields,
`strings.EqualFold(fields[0], "bearer")`, and a non-empty `fields[1]`. Anything else returns
`("", false)`. This is the D-01/D-02 structural discriminator — a well-formed match commits
to the bearer lane, anything else means "not a bearer credential."

**Record the boundary policy in the doc comment (MED-5).** A credential value that *declares*
the bearer scheme but supplies a malformed credential — bare `Bearer`, `Bearer a b`, a
comma-coalesced pair — is **not** treated as a committed bearer attempt; it falls through to the
cookie lane exactly as a non-bearer scheme does. That is D-02, which is locked, and it is safe
in this direction only: the fallthrough goes toward the *more* restrictive lane, so such a
caller receives `auth.LaneCookie` and still faces the full CSRF check. The stronger "once the
scheme is declared, fail closed" reading would reject those callers outright; it is deliberately
not adopted here because D-02 names the opposite rule and because the permissive direction
cannot produce a bypass. State both readings in the comment so a future reader sees the choice
rather than inferring an accident.

Declare package-level sentinels `ErrTokenMissingExpiration = errors.New("token missing expiration")`
and `ErrTokenExpired = errors.New("token expired")`. **Those two message strings are load-bearing
and must match the go-sdk's own rejections at `auth/auth.go:131,:134` byte-for-byte** — see the
error-shape rule below.

Declare `EnforceExpiry(v mcpauth.TokenVerifier) mcpauth.TokenVerifier` returning a closure that
calls `v`, then:

  - verifier error non-nil → return it unwrapped and unmodified.
  - `TokenInfo` nil with a nil error → return `(nil, nil)` **unchanged, before touching any
    field** (MED-7). Do not dereference and do not synthesize a rejection: the SDK already
    rejects this case itself at `auth/auth.go:118-120` with a 500 `token validation failed`, and
    reshaping it into a 401 here would change the MCP wire response for what is a verifier
    *contract violation*, not a credential problem. The Connect adapter carries its own nil
    guard, so both lanes stay safe without either changing shape. Say this in the doc comment.
  - zero `Expiration` → reject with `ErrTokenMissingExpiration`.
  - `Expiration` before `time.Now()` → reject with `ErrTokenExpired`.

**Error shape (MED-8) — this deliberately departs from the local convention.** `chain.go:81,:85,:105`
and `static_token.go:59,:75` build denials with `errors.Join(mcpauth.ErrInvalidToken, <sentinel>)`,
whose `Error()` is the two messages separated by a newline. That is fine where it is the only
rejection, but it is wrong here: the SDK's `verify()` returns `err.Error()` verbatim as the 401
body when the verifier reports `ErrInvalidToken` (`auth/auth.go:107-112`), and it reaches that

## Flagged Assumptions

Surfaced, not silently resolved. Each needs a human read before the phase seals.

1. **Probe edge `REQ-connect-bearer-identity` / `unclassified` — unresolved.** The deterministic
   edge probe could not classify this requirement into any of its eight shape categories, so no
   acceptance criterion was auto-derived from it. Never auto-backstopped. The requirement is
   nonetheless covered by explicit criteria in this plan and Plans 02 and 03; this row records
   that the *probe* contributed nothing, not that the requirement is uncovered.
2. **Probe edge `REQ-connect-token-expiry` / `unclassified` — unresolved.** Same disposition; the
   requirement is covered by `TestEnforceExpiry`, `TestEnforceExpiryZero`, and `TestEnforceExpiryNoSkew`.
3. **D-12's "zero diff in `connectapi.go`" cannot be taken literally.** D-07 changes the
   resolver's return arity, and the `connectResolver` type is declared in `connectapi.go:360`, so
   the compiler forces a one-declaration edit there. The load-bearing half of D-12 — that
   `mountConnect`'s `resolve == nil` guard and interceptor ordering are untouched, leaving no
   boolean inside `mountConnect` to loosen with an `OR` — is preserved and gated explicitly in
   Task 1's acceptance criteria. This is a compiler-forced consequence D-12's prose did not
   anticipate, not a relaxation of the decision.
4. **`internal/auth` will contain both `lane` (unexported) and `Lane` (exported).** RESEARCH.md
   Open Question 2 recommends this shape, but the near-identical names are a readability hazard.
   Renaming the existing `lane` is out of this phase's scope; the coexistence is documented in
   the new type's doc comment instead.
5. **`EnforceExpiry` deliberately departs from the repo's `errors.Join` deny convention.**
   `chain.go` and `static_token.go` both build denials with
   `errors.Join(mcpauth.ErrInvalidToken, <sentinel>)`. This plan does not, because the go-sdk
   returns the verifier's `Error()` verbatim as the MCP 401 body before reaching its own expiry
   checks, so a joined message would change today's `token expired` response into a doubled one.
   The departure is scoped to `bearer.go`; the two existing files keep their convention. A
   reviewer who prefers uniformity should note that uniformity here costs a wire-contract change
   D-04's planner note explicitly forbids.
