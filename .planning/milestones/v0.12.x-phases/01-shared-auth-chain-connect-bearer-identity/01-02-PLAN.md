<objective>
Extend the lane marker from the CSRF exemption to the second cookie-lane side effect — session
re-sealing — so "the lane marker governs every cookie-lane side effect" becomes a uniform rule
rather than a CSRF-only special case. Then prove the bearer identity that Plan 01 introduced on
Connect resolves to the same actor and owner as the same token does on MCP.

Purpose: closes the narrow both-credentials case D-01 creates (a request carrying a valid
session cookie *and* a valid bearer token authenticates as bearer, yet `webauth.Reseal` reads
raw request headers and would otherwise refresh a session the request did not authenticate
with), and retires RESEARCH.md's Assumption A1 by measurement instead of by analogy.
Output: the `LaneCookie`-gated reseal interceptor and a bearer-lane parity test.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bearer-authenticated request → session cookie state | A request may carry both a bearer credential and a session cookie; the cookie is untrusted for this request's identity but is still a live credential the server could mutate. |
| verifier chain → per-lane identity derivation | `mcpauth.TokenInfo` crosses into `callerFromTokenInfo` on two different transports; a divergence there would attribute records to different actors for the same principal. |

## Flagged Assumptions

1. **RESEARCH.md Assumption A1 is retired by Task 2, not by this plan's authorship.** A1 claims
   Connect-bearer actor attribution will match MCP because both flow through
   `callerFromTokenInfo`. The plan does not assume that; it measures it and requires the outcome
   in writing. If the measurement refutes A1, that is a finding for the phase verifier, not a
   test to adjust until it passes.
2. **`TestResealSkippedForUnknownLane` is a defense-in-depth case, not a reachable path.** With
   Plan 01's D-08 CSRF arm in place, a write RPC stamped `auth.LaneUnknown` is rejected before
   the reseal interceptor runs. The case is kept because reseal is not procedure-gated (it runs
   for reads too) and because the repo's convention is to re-check invariants upstream already
   guarantees.
3. **This plan now edits a file it did not previously own.** `connectapi_service_auth_parity_test.go`
   is a v0.11.x artifact; the fixture change is one field on one struct literal. It is placed here
   rather than in Plan 01 because Plan 01's `EnforceExpiry` is not applied to that fixture — only
   this plan's parity tests wrap it — so the failure it prevents does not exist until Wave 2.
