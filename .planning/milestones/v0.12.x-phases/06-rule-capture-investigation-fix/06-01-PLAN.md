Open with the permission as the first sentence, in the imperative, before any qualification. The

State the two triggers as observable conditions. Present them as bold-lead bullets, matching the
`## Routing` idiom. Either one firing is sufficient:

- Repeat-hit on a footgun. The `search_memory` call you already make before every store surfaces an
  existing record describing the same problem you have just hit again. The store knew, and knowing
  did not prevent the hit — that gap is what a rule closes. Name that this trigger costs nothing new:
  the search-before-store step already runs and already returns the record.
- Normative phrasing at capture time. The `content` of the record you are about to write via
  `store_memory` or `schedule_memory` is phrased as a constraint on future behavior — MUST, MUST NOT,
  NEVER, ALWAYS, or a bare imperative with no exception. It is already a constraint; the only open
  question is whether it should be normative ground truth rather than a `gotcha`.

record's own content, at the moment you are about to write it. It does not apply to conversation,
to text you are quoting, or to a requirement you are restating. A trigger that fires on every
MUST-shaped sentence in a session is the nag that gets the whole mechanism turned off.

State the proposal protocol as a short numbered list, made inline at the moment the trigger fires —
never batched to a session-end sweep, because the justification for a candidate is strongest while
the context that produced it is live:

1. Say what you noticed and why it reads as normative. One or two sentences. This is a note, not a
   pitch.
2. Show the exact one-line `summary` you would store as the index entry, and the scope you would
   store it in (`rule:repo:*` for a repo constraint, `rule:project:*` for one that spans repos).
   Showing the actual index line is what lets the user judge it in one read.
3. Ask once, then stop. Do not re-ask within the session, do not restate the case after a no, and do
   not attach the proposal to an unrelated interrupt. **A user who has to argue you down will
   disable the trigger, and then the store gets nothing.**
4. On yes, call `store_rule` and cite the resulting `short_id`. On no, record the decline as below,
   then carry on with the `store_memory` you were about to make — the fact is still worth keeping as
   a `gotcha` or `convention`, it just is not normative ground truth.

`store_rule` must appear only inside step 4's accept branch. Nowhere in this subsection may the tool
name appear in a sentence that an agent could read as authorization absent an explicit user yes.

State the decline record precisely — this is the one new record shape the phase introduces, and
getting its content wrong makes a future agent read "declined" as "the gotcha is resolved":

On a decline, store an ordinary memory with `category: decision`, tag `rule-declined`,
`source: user-said`, in the spine scope. Its content states three things: what was proposed as a
rule, that the user declined **rule status** for it and when, and that the underlying fact remains
true and stays where it is. Name explicitly that it is `decision` and not `gotcha`: a decline filed
as a gotcha would be re-enumerated by the one-time backfill sweep and re-proposed, which is exactly
the nag this record exists to prevent.

Then close the loop back to the trigger: before proposing, if the `search_memory` you already ran
surfaced a record tagged `rule-declined` covering this concern, do not propose it again. Mention it
only if the user's own words reopen the question. State the honest limit in the same sentence — this
is a check, not a block; a user whose tolerance has changed can still be met, but the default is
silence.

Finish with a short "when not to propose" guardrail list, following the `### When not to use
cross-spine` shape (open with the failure mode of the thing being qualified): a fact scoped to one
file or one session is not normative; a candidate already declined is not re-proposable; two
proposals in one turn is one too many; and if you cannot state the constraint as a single index line,
you do not yet understand it well enough to propose it.

Do not restate the junk taxonomy or the routing table. Cross-reference them by name, as
`promoting-memory` and `migrating-from-beads` both do.
