**D-09 is honored but its scope is narrower than its wording, and this was verified in code.**

D-09 states: *"correction is delete-then-re-store, because rules cannot be superseded."* The premise
is exactly true — `supersedeMemory` rejects a rule target (`internal/server/tools.go:1724`), and so
does `setVisibility` (`:1655`), both via `errRuleImmutable`. But reading this session's tree turned
up two in-place paths D-09 does not account for, neither of which is supersession:

- `store_rule` accepts an optional `id` and performs an **ownership-validated in-place replace that
  carries the existing `short_id` forward** (`internal/server/rules.go:103-146`; documented at
  `docs-site/.../reference/tools.md:365`).
- `update_memory` **is permitted on a rule** for content, summary, and tags. It carries two guards
  and only two: the summary must stay a valid single-line index entry, and `shared: false` is
  rejected (`internal/server/tools.go:1501-1513`).

So delete-then-re-store is the correct and only path for **retirement or reversal** — the case D-09
is actually about — but it is the wrong path for a reworded or sharpened rule, where it would churn
the `short_id` other records and sessions may cite, for no gain.

The correction table in Task 1 therefore documents all four cases. It does not contradict D-09; it
states D-09's case precisely and adds the two D-09 did not consider. **If the user disagrees with
that reading, the fix is to drop the refine and replace-in-place rows from the table and leave only
retire — flag it before executing rather than after.**

**State the cadence before the checks**, so the discipline does not read as a per-session tax. Three

**Price the index honestly (D-11).** Session start loads only the compact `ruleView` — `short_id`,

split the three checks by whether the index is enough:

- Duplicates. Catchable from summaries alone, because a duplicate rule usually has a
  near-duplicate index line. Free — do it while reading the index you already have.
- Contradictions. **Not** catchable from summaries. Two rules can carry near-identical summaries and
  opposite content, or unrelated summaries and directly conflicting content. A real check needs full
  text.
- Rot. The constraint a rule names no longer exists — the path, command, tool, or workflow it
  constrains is gone or has changed. `created_at` in the index is the cheap aging signal; the check
  itself is against the current tree, not against the index.

Then price the full-text read exactly, because getting this wrong in either direction is the failure
mode D-11 asks you to avoid: it is **one `list_rules` call with `full: true`**, which returns the
whole set in a single response — not a `get_memory` per rule. The cost scales with total rule bytes,
not with a round trip per rule. At the three rules this repo has today it is free; at fifty the
response is large enough to be worth gating. Gate it behind the three cadence moments above and
nothing else — an unconditional full-text read every session is the habit this pricing exists to
prevent.

Say what the curation-smell advisory is and, in the same breath, what it is not: `list_rules`
returns a curation-smell advisory when a scope holds more than 50 rules (`ruleThreshold`, pinned by
`TestListRulesHandlerCurationAdvisory`). It is a **volume signal only** — it says nothing about
duplication or contradiction, and it cannot fire below 51 in a scope, so it will never fire at this
repo's current scale. Treat it as one input, never as the discipline.
