<objective>
Build the ranking variants D-06 says the eval must measure, under the pure (query, hits, k) contract `RerankHits` already uses:

- In `internal/store`, export `CandidateK` and add `VectorOrder`. These are the vector-only baseline and the no-op rank step D-08 ships if vector-only wins, so they belong to the shipped package.
- In `internal/retrievaleval`, add the eval-local comparison rankers `lexicalRerank` (a port of the shipped reranker), `cosineBlendRerank` and `overlapGateRerank`, parameterized for D-07's grid, with hermetic property tests.

**Placement decision (CONTEXT.md "Claude's Discretion" allows either location):** the comparison rankers live in the eval package, not in `internal/store` as RESEARCH.md suggested. D-08 deletes the lexical code from the shipped package if vector-only wins, but ROADMAP success criterion 3 and RANK-01 still require the eval to report a lexical-reranked row afterwards. Putting the comparison code in the eval package from the start satisfies both. In the likely D-05 outcome it needs no relocation step, and the ranker that ships is still measured through `SearchReranked` itself. If a tuned variant wins, plan 01-06 moves that one function into `internal/store`.

Purpose: plan 01-04's named-ranker roster needs these functions, and D-05's rule needs them measured over the same candidate pool `SearchReranked` sees.
Output: `CandidateK`/`VectorOrder` with tests, and `comparison_rankers.go` with tests.
</objective>
