<objective>
Provide the write-RPC mutation hooks the form/dialog/row layers consume, following the v6 options-as-thunk `createMutation` pattern with optimistic update + rollback (D-10):

- Memory (D-03): `useCreateMemory` (StoreMemory + optional shared composite), `useUpdateMemory` (UpdateMemory — content/tags/summary/shared via update_mask), `useDeleteMemory` (DeleteMemory), `useSetMemoryVisibility` (SetVisibility, Visibility enum), `useScheduleMemory` (ScheduleMemory with not_before/not_after + the SAME optional shared composite, since ScheduleMemoryRequest has no visibility field).
- Discovery (D-04): `useCreateDiscovery` (StoreDiscovery), `useDeleteDiscovery` (DeleteMemory by id — discoveries are records addressed by id), `useSetDiscoveryVisibility` (SetVisibility). No discovery edit (D-04 fence).

**Create-as-shared is a two-call composite (Codex+grok HIGH, verified against `proto/engram/v1/engram.proto`):** `StoreMemoryRequest`/`StoreDiscoveryRequest`/`ScheduleMemoryRequest` carry NO `visibility`/`shared` field (fields end at `summary`), and the server treats an unset visibility as PRIVATE (`connectapi.go:43` maps `m.Visibility` straight through; `''` is canonical private). So "create as shared" MUST perform the Store*/Schedule call, then — only after the ShareWarningInline acknowledgement — a SECOND `engramWrite.setVisibility({id, Visibility.SHARED})` call using the returned id. `useCreateMemory`/`useCreateDiscovery` accept a `shared: boolean` intent and sequence the two calls internally.

**Composite as an explicit STATE MACHINE with a DISCRIMINATED result (Codex round-3 HIGH — verified: `StoreMemoryRequest`/`ScheduleMemoryRequest` have no idempotency key and no id, `engram.proto:104,203`; responses are `{id, short_id}` only, `:116,222`).** A create-then-SetVisibility composite has three outcomes, and the SECONDARY (SetVisibility) failure MUST be caught inside the composite and converted to a discriminated result — it must NEVER surface as a raw auth `ConnectError` that the form's whole-create hard-auth resubmit path (D-09) would catch, because resubmitting the ORIGINAL create command would re-issue Store/Schedule with no dedup → a DUPLICATE record. The three states:
- **(a) primary Store*/Schedule failure** → propagate the error normally (nothing was created; the form's D-09 whole-create resubmit is safe and correct here — there is exactly zero created record).
- **(b) primary success + SetVisibility success** → return `{status: 'created_shared', id}`; toast `created`.
- **(c) primary success + SetVisibility failure (INCLUDING when SetVisibility returns Unauthenticated OR PermissionDenied)** → CATCH the secondary error inside the composite and return the discriminated `{status: 'created_private', id}`; toast `created (private) — sharing failed`. Do NOT auto-delete/rollback the created record (it genuinely landed); do NOT rethrow the secondary auth error; do NOT re-enter the whole-create resubmit path. The record is left PRIVATE and re-shareable through the ordinary row/detail Share action (`useSetMemoryVisibility` by id — a pure by-id SetVisibility that carries zero duplicate-create risk). This by-id re-share IS the "visibility-only continuation"; no separate whole-create replay is ever persisted or replayed. (Plan 05's form consumes this discriminated result: it treats `created_private` as SUCCESS — closes the sheet, clears any resume envelope — and only a state-(a) PRIMARY failure drives D-09.)

Each wrapper: options-as-thunk `createMutation(() => ({...}))`, `mutationFn` builds the request via `create(...Schema, {...})` and calls the matching `engramWrite` method, `onMutate`/`onError`/`onSettled` manage the cache (see cache rules below). Toasts use the lowercase one-word voice.

**Cache rules (Codex+grok MEDIUM):**
- Optimistic edit/delete/set-visibility use `getQueriesData`/`setQueriesData` with a PARTIAL query-key match (e.g. `{ queryKey: ['listMemories'] }`) — a single exact `getQueryData` cannot cover the parametrized `listMemoriesKey(scope, categories, visibility, limit, offset)` pages, the `['searchMemories', q, scope]`/`['searchDiscoveries', q, scope]` keys, or the different `{memories}` vs `{discoveries}` response shapes. `onMutate` snapshots ALL matching entries; `onError` restores each exact key/value pair.
- CREATE is invalidate-only: `StoreMemoryResponse`/`StoreDiscoveryResponse` return only `{id, short_id}`, so there is no server record to optimistically insert without a fabricated temp-id + reconciliation. Do NOT optimistically insert a create into list pages; `onSettled` invalidates the relevant keys and the refetch surfaces the new row.
- Filtered-cache membership (Codex round-2 MED): visibility is part of `listMemoriesKey(scope, categories, visibility, limit, offset)` (`queries.ts:34`), so a set-visibility change that merely flips `memory.visibility` in place leaves the record in an INCOMPATIBLE filtered list (e.g. a `visibility:'private'`-filtered page still shows a now-shared record) until refetch. On set-visibility, in each matched list/search cache entry REMOVE the record from any page whose visibility filter no longer matches the new value (rather than only flipping the field); on delete, also adjust the list `total`. Invalidate `['listScopes']` after create/delete/schedule (scope counts changed). `onSettled` invalidation of the touched keys remains the backstop.
- Dirty-mask (Codex round-2 MED): the `update_mask` must contain ONLY genuinely-changed fields. Re-sending unchanged content forces an unnecessary re-embed (`tools.go:1003` branches on pointer presence), and re-sending an unchanged auto-summary flips its provenance to client-authored (`store.go:1404`). `useUpdateMemory` builds the mask from the caller-supplied changed fields only; the form (Plan 05) computes the changed set by diffing against the original record and disables Save when that set is empty.

Purpose: one tested, reusable mutation surface so components never touch the transport or hand-roll cache bookkeeping.
Output: two mutation modules + node tests covering RPC shape and optimistic rollback (via extracted pure factories or a Svelte provider harness — see Task 1).
</objective>
