<objective>
Wire the write surfaces into the three list/detail routes so the operator can actually create/edit/delete/re-share/schedule end-to-end — the payoff plan that connects Plans 03/04/05.

Introduce `WriteSurfaces.svelte`, a route-level host component that owns the write UI state (which sheet is open, edit target, delete target, share target) and orchestrates: the `New memory`/`New discovery` toolbar entry point, `MemoryFormSheet`/`DiscoveryFormSheet` (create + edit), `DeleteConfirmDialog` (triggered by a delete callback), and `ShareWarningInline` (triggered by a share callback → `useSetMemoryVisibility`/`useSetDiscoveryVisibility`). Then wire each route (`observe`, `search`, `discovery`) to render `WriteSurfaces` and to pass `onedit`/`ondelete`/`onshare` down through `MemoryList` (and `MemoryDetail`) to the rows.

Entry points (Claude's discretion, per CONTEXT): `New memory` on the memory routes (observe/search) and `New discovery` on the discovery route, each as a least-intrusive toolbar button that opens the matching form sheet defaulted to the current scope (a `discovery:`-prefixed scope on the discovery route).

WriteSurfaces exposes an EXACT host API — `export function` instance methods (`openCreate()`/`openEdit(id)`/`requestDelete(id, kind)`/`requestShare(memory, kind)`) reached via `bind:this` — no vague "or equivalent". `openEdit` takes an **id** and fetches the FULL record via GetMemory before prefilling (Codex round-2 HIGH — row/search records are summary-shaped). `requestShare` takes the **Memory** (visibility-aware) and no-ops when already shared. The discovery route wires only delete/share (no edit — D-04).

WriteSurfaces also carries SC3 across the INLINE delete/share actions, not only the forms (Codex round-4 HIGH), and is the SOLE owner of dialog/banner closure (Codex round-5 HIGH): because the Plan-03 `DeleteConfirmDialog` no longer self-closes on confirm, the delete/share handlers await mutation settlement and close the surface only by clearing the target on success; on a terminal `Unauthenticated`/`PermissionDenied` they RETAIN the target so the dialog/banner STAYS VISIBLY OPEN and surface the same inline re-auth CTA the forms use (the Plan-03 `authFailure`/`onreauth` props → `/auth/login`) instead of a dead-end `write failed`. No resume envelope is needed (delete/share have no typed input) and no auto-replay occurs — the pending action stays visible for a deliberate, operator-initiated retry after re-auth, and delete/set-visibility are id-idempotent so a manual retry cannot duplicate a record. This retention is scoped to the in-SPA terminal-auth case (Codex round-5 MEDIUM): the `sessionStorage` resume envelope covers create/edit form input only; a delete/share that proceeds through the full `/auth/login` OIDC round-trip is NOT auto-reopened — the operator re-initiates the input-free, id-idempotent action after landing back on `/ui/`. An inline-action resume envelope is deliberately NOT added (nothing typed to preserve; it would introduce the auto-replay path the reviewers warned against).

This plan also completes the D-09 re-auth loop with a SINGLE-OWNER resume lifecycle (Codex round-3 HIGH): the OIDC callback lands on `/ui/` (not the originating route), so the `/ui/` root `+page.svelte` `peekResume()`s the envelope (`ui/src/lib/resume.ts`, Plan 05) on startup and `goto(base + normalizeReturnPath(env.returnPath))` — base-relative so it never double-prefixes to `/ui/ui/observe` (`base='/ui'`, `svelte.config.js:9`) — WITHOUT deleting the envelope. The destination route then peeks, calls `writeSurfaces.reopenFromResume(env)` (edit refetches the full record via GetMemory), passes `resumeValues`/`dirtyPaths` into the form as PROPS, and only `consumeResume()` (deletes) AFTER the form acknowledges applying them. The route/host is the sole envelope owner (the form never reads/deletes storage — Plan 05), eliminating the two-owner wipe-before-read race.

Finally, this plan ships the phase: after `pnpm test`/`pnpm check` are green, Task 3 runs `task ui:build`, commits the rebuilt `internal/webauth/static/` (the go:embed'd production console), and gates on the full `task` run — otherwise the shipped binary would not contain the write UX and CI ui-drift would reject (Codex HIGH).

Purpose: deliver SC1 as a working console flow AND ship it in the embedded binary, honoring D-02/D-06/D-07/D-10 and the D-04/D-05 fences.
Output: one host component + three wired routes + the rebuilt embedded SPA, with a browser test for the host's open/confirm orchestration.
</objective>
