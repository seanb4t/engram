      - Context — the read-only cookie lane hard-expired at a fixed 12h; the write lane (Phases 15-17) now needs a session to survive a long working session without dropping an in-flight write, but DEC-u9v forbids server-side session state. This ADR resolves how to keep sessions alive statelessly.
      - Decision — "Rotation" under statelessness is a sliding-expiry re-seal (D-10 point 1): on an authenticated Connect request whose remaining lifetime has crossed resealThreshold (= sessionTTL/2 = 6h, with a 60s resealSkew budget on the threshold comparison only), the server re-seals the {owner, expiry} AES-GCM cookie with a fresh absolute now+sessionTTL expiry and refreshes the readable engram_csrf cookie's Max-Age with the same HMAC(k_csrf, Owner) value (D-08). Zero server-side state; it is NOT a token store and NOT server-side revocation. Amends engram-u9v's "refreshes ... per request" clause (re-seal fires on a threshold, not every request; engram-8q3 already dropped tokens from the cookie).
      - Rationale — bullets: keeps write-capable sessions alive; stays stateless (DEC-u9v preserved); absolute now+TTL makes concurrent re-seals forward-monotonic (never shortens a session); refreshing both cookies prevents a mid-session engram_csrf lapse from silently breaking writes.
      - Alternatives Considered — Server-side session store / true revocation (instant revocation but reintroduces the operational dependency DEC-u9v/engram-8q3 deliberately avoid; its own ADR, not this milestone — Deferred). Per-request re-seal on every response (needless Set-Cookie churn; Rejected in favor of the ½-TTL threshold).
      - Consequences — Positive: long sessions never hard-drop mid-work; no new state, no new config var. Negative (state this PROMINENTLY per D-10 point 2): a stolen sealed cookie is valid up to a full sessionTTL, and because sliding re-seal EXTENDS the window while the cookie is actively used, an actively-abused stolen cookie never expires on its own. The ONLY kill-switch is rotating ENGRAM_UI_COOKIE_KEY (ui.cookie_key, internal/config/registry.go:56), which invalidates every sealed cookie at once — a detection/response gap, not a preventable one. Neutral (D-10 point 3): the hard-expiry check (resolver.go:49-51) stays fail-closed and byte-for-byte strict; the bounded resealSkew budget applies ONLY to the soft re-seal threshold, never to the hard-expiry check.
      - References — "Amends: engram-u9v"; "Governed by (unchanged): engram-8q3"; "Revisits: engram-1xv".

    Reference ONLY the real key ENGRAM_UI_COOKIE_KEY as the kill-switch — do NOT name the nonexistent session-key from the ROADMAP SC2 prose (D-10 flags it as a phantom).
