# Stack Research

**Domain:** Bounded reads over Qdrant gRPC + provider HTTP clients (Go backend)
**Researched:** 2026-09-18
**Confidence:** HIGH — every claim below is verified against the actual pinned source in
`go env GOMODCACHE` (`github.com/qdrant/go-client@v1.19.2`, `google.golang.org/grpc@v1.83.2`,
`connectrpc.com/connect@v1.21.0`, `github.com/testcontainers/testcontainers-go@v0.44.0` +
`modules/qdrant@v0.44.0`), not training-data recall.

## Recommended Stack

**Zero new Go dependencies.** Every capability this milestone needs already exists in the
pinned stack's own vocabulary — this is a within-API-surface milestone, not a new-library
milestone, matching the standing constraint every prior engram milestone has held (repo rule
`xvqj44e5mk`: prefer established idioms over hand-rolled ones, and the codebase's own
"zero new Go deps" norm).

### Core APIs (already-vendored, newly exercised)

| API | Package@Version | Purpose | Why Recommended |
|-----|------------------|---------|------------------|
| `qdrant.NewWithPayloadInclude(...string)` / `NewWithPayloadExclude(...string)` | `github.com/qdrant/go-client v1.19.2` | Shrink a `Scroll`/`Get` response to only the payload keys a read path actually needs | Already proven in this repo: `Store.ListScopes` (`internal/store/store.go:1673`) uses `NewWithPayloadInclude("scope")` specifically because a full-payload scan overflowed the 4 MiB gRPC receive cap in production (#583, `TestListScopesFullPayloadsOverGRPCLimit`). This is the established, idiomatic fix — apply the identical pattern to `Store.List`'s offset/deep-offset paths and the 256-record operator sweeps, which currently request `NewWithPayload(true)` (full payload) unconditionally. |
| `qdrant.Config.GrpcOptions []grpc.DialOption` | `github.com/qdrant/go-client v1.19.2` | Pass raw `grpc.DialOption`s (e.g. `grpc.WithDefaultCallOptions(grpc.MaxCallRecvMsgSize(n))`) into the client's underlying `grpc.NewClient` dial | Verified in `qdrant/grpc_client.go:34-56`: the client builds its own default dial options (creds, metadata/rate-limit interceptors, keepalive) then appends `config.GrpcOptions` **last**, with the comment "we append config.GrpcOptions in the end so that user's explicit options take precedence." `internal/server/tools.go`'s `storeFromConfig` already threads `GrpcOptions` (currently just an OTel stats handler) — raising `MaxCallRecvMsgSize` is a one-line addition at that exact call site. The milestone's own PROJECT.md is explicit that this is **defense in depth only** (#583 rejected it as *the* fix) — it does not replace payload-selector/paging bounds, it just moves the ceiling so an unbounded read fails later/larger instead of at exactly 4 MiB. |
| `google.golang.org/grpc/status` + `google.golang.org/grpc/codes` | `google.golang.org/grpc v1.83.2` | Detect a gRPC `ResourceExhausted` status returned by an oversized `Scroll`/`Get`/`Count` response and map it to a distinct Connect code | Verified in `grpc@v1.83.2/rpc_util.go:795-798`: an over-cap receive returns `status.Errorf(codes.ResourceExhausted, "grpc: received message larger than max (%d vs. %d)", ...)`. `internal/store/store.go` already imports both packages (`grpccodes "google.golang.org/grpc/codes"`, `"google.golang.org/grpc/status"`) and already pattern-matches on `status.FromError(err).Code() == grpccodes.AlreadyExists` at `store.go:591` — the identical idiom extends to `ResourceExhausted`. No new import needed beyond what the file already has. |
| `connect.CodeResourceExhausted` | `connectrpc.com/connect v1.21.0` | The Connect-side code a `ResourceExhausted` gRPC status should map to, instead of falling through `connecterror.go`'s `default` arm to `CodeInternal` | Verified in `connect@v1.21.0/code.go:67-70` (`Code = 8`) and `protocol_connect.go:1297` — Connect's own protocol translator already maps `CodeResourceExhausted` to HTTP 429, and connect-go itself raises this exact code internally for its own oversized-message guards (`envelope.go:163-173`, `error.go:466`). This is the single missing `case` in `internal/server/connecterror.go`'s exhaustive sentinel switch (currently ends at `context.DeadlineExceeded` before the generic `default`). |
| `io.LimitReader` / `io.CopyN` | stdlib | Bound HTTP response-body reads (both the success-path decode and the non-2xx error-body read) and bound the post-error drain independently of `http.Client.Timeout` | `internal/embed/embed.go` and `internal/summarize/summarize.go` **already use this idiom** for both the success-path decode (`json.NewDecoder(io.LimitReader(resp.Body, c.maxResponseBytes))`) and the non-2xx error-body read (`io.ReadAll(io.LimitReader(resp.Body, maxErrorBodyBytes))`, 4096 bytes in both clients) — issue #347 ("embed discards provider error body") is functionally addressed by this existing code (though the tracking issue is still open; verify with the phase owner whether #347 needs only a regression test, not a code change). The **actual gap** is #457: the connection-reuse drain immediately after (`io.Copy(io.Discard, resp.Body)`, `embed.go:295` / `summarize.go:182`) is **unbounded** — it relies entirely on `http.Client.Timeout`, and `WithTimeout(0)` is a documented, supported escape hatch (mirrors `embedTimeout`/`summaryTimeout`'s "0 = infinite" convention in `internal/server/tools.go`) that removes that bound entirely. Fix: replace both `io.Copy(io.Discard, resp.Body)` calls with `io.CopyN(io.Discard, resp.Body, maxDrainBytes)` (or `io.Copy(io.Discard, io.LimitReader(resp.Body, maxDrainBytes))`) — pure stdlib, no new import beyond `io` (already imported in both files). |
| `qdrant.GetPoints` / `Client.Get` | `github.com/qdrant/go-client v1.19.2` | Batch point-ID retrieval as an alternative to `Scroll` when a caller already has bounded set of IDs | Verified struct at `points.pb.go:1754` (`CollectionName`, `Ids []*PointId`, `WithPayload`, `WithVectors`, no numeric size other than `len(Ids)`). Not currently used by any of the milestone's five read paths (`List`, `ListScheduled`, `Search`, the operator sweeps) — all of them iterate an unbounded/filtered scope, not a known ID set — so this is **not a fix ingredient** for #585's siblings. Documented here only because the question asked about it explicitly; do not introduce it as a new pattern this milestone. |
| `qdrant.ScrollPoints.OrderBy` / `StartFrom` | `github.com/qdrant/go-client v1.19.2` | Keyset ("deep") pagination ordered by a payload field | Verified at `points.pb.go:4491-4515` and `oneof_factory.go:629-666` (`NewStartFromDatetime`, `NewStartFromFloat`, `NewStartFromInt`, `NewStartFromTimestamp`). `Store.listByCursor` (`store.go:1463`) already uses this correctly with `maxListLimit = 1000`. Confirms the store.go comment: `ScrollPoints.Offset` is a `*PointId` (start-after-this-point), **not a numeric skip-count** — Qdrant has no numeric OFFSET, which is exactly why `Store.List`'s offset/"all" mode (`opts.Limit == 0`) must over-fetch `fetch := opts.Offset + opts.Limit` (or `total` for "all") in one `Scroll` call with `WithPayload(true)` and is therefore the primary #585 overflow site. |

## Alternatives Considered

| Recommended | Alternative | When to Use Alternative |
|--------------|-------------|--------------------------|
| Payload selectors (`NewWithPayloadInclude`) + explicit paging caps as the **primary** fix for #585 | Raising `grpc.MaxCallRecvMsgSize` alone | Never as the sole fix — PROJECT.md records that #583 explicitly rejected this ("Raising `MaxCallRecvMsgSize` alone only moves the ceiling... it is defense in depth at most"), because `content` has no server-side size bound, so a wider ceiling just changes which page size first overflows. Use it *additionally*, as a second line of defense, once the payload-shape and paging-cap fixes are in place. |
| `io.LimitReader`/`io.CopyN` for bounded HTTP reads | A third-party bounded-reader library (e.g. wrapping `http.MaxBytesReader`) | `http.MaxBytesReader` is server-side only (it needs an `http.ResponseWriter` to call `.CloseNotify`/reject via); engram's embed/summarize clients are HTTP **clients** reading a server's response, so the correct idiom is `io.LimitReader` on `resp.Body`, which the codebase already uses in exactly this shape. Do not introduce a wrapper type. |
| `status.FromError` + `grpccodes.ResourceExhausted` in `connecterror.go`'s existing sentinel switch | A generic byte-size check before every `Scroll`/`Get` call | Pre-flight size estimation is unreliable (Qdrant doesn't report response size before transfer) and duplicates logic already present in grpc-go's own decode path; mapping the *status the transport already produces* is strictly simpler and matches the file's existing "typed sentinels via `errors.Is`/`errors.As`, never strings" design contract (`connecterror.go:16-21`). |
| `testcontainers.WithAdditionalWaitStrategy` for local-dev container hardening | Rewriting the CI job's `services:` health-check | Out of scope: the CI shared-Qdrant-service stability fix (single `services:` container + `/dev/tcp` health-cmd) already shipped in a prior milestone (`.github/workflows/ci.yaml:27-63`, "One shared Qdrant serves the whole job (#497)"). What THIS milestone can still affect is (a) whether the *local* testcontainers-go fallback path used by `go test ./...` off-CI needs a stronger startup signal or resource cap given new >4 MiB regression tests, and (b) whether the CI job's qdrant `services:` `options:` needs an explicit `--memory`/`--cpus` cap added (a workflow-YAML change, not a Go dependency) if the new tests push memory pressure back into #497's territory. |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|--------------|
| Any new third-party pagination/streaming library | Zero-new-deps is this repo's explicit, repeatedly-held constraint across every prior milestone (see PROJECT.md "Standing constraints held" for v0.8.x through v0.17.0); Qdrant's own `Scroll`+`OrderBy`+`StartFrom` keyset paging (already implemented in `listByCursor`) is a complete, idiomatic paging primitive. | The existing `qdrant.ScrollPoints` + `OrderBy`/`StartFrom` combination, extended to the sibling call sites that currently skip it (offset mode, `ListScheduled`, operator sweeps). |
| `qdrant.GetPoints`/`Client.Get` as a #585 fix | It retrieves by a known ID set; none of the five overflow-prone call sites (`List` offset mode, `ListScheduled`, full-payload `Search`, the 256-record operator sweeps) start from a known ID set — they all filter/scan a scope. Introducing it here would be solving a different problem than the one specified. | Payload selectors on the existing `Scroll` calls. |
| A hand-rolled bounded `io.Reader` wrapper type for HTTP client responses | The repo already has the correct, tested idiom (`io.LimitReader` composed with `json.NewDecoder`/`io.ReadAll`/`io.CopyN`) in two files; a new wrapper type would duplicate it under a different name for no behavioral gain, and this milestone's own instructions call for "established OSS/idiomatic solutions over hand-rolled ones." | `io.LimitReader(resp.Body, n)` for decode/error-body reads; `io.CopyN(io.Discard, resp.Body, n)` for the bounded drain. |
| Retrying `MaxCallRecvMsgSize` tuning per-RPC via `grpc.CallOption` on every `Scroll`/`Count`/`Get` call | `qdrant.Client`'s own methods (`Scroll`, `Get`, `Count`, ...) do not accept variadic `grpc.CallOption` — they wrap the generated `pointsClient`/`collectionsClient` internally (verified: `Client.Get`/`Client.Scroll` signatures in `points.go` take only `(ctx, request)`). A per-call override is not reachable through the public `*qdrant.Client` API surface. | `qdrant.Config.GrpcOptions` at client construction (`grpc.WithDefaultCallOptions(grpc.MaxCallRecvMsgSize(n))`), which applies to every RPC issued by that client — the only reachable seam. |

## Stack Patterns by Variant

**If a read path has a caller-supplied `Limit`/`k` (e.g. `Search`, cursor-mode `List`):**
- Cap it server-side to a fixed maximum (mirroring `maxListLimit = 1000` already in `store.go:1458`) before it reaches `ScrollPoints.Limit`/`QueryPoints`.
- Because an unbounded caller-supplied limit is exactly the shape `TestListScopesFullPayloadsOverGRPCLimit`-style regression tests must reproduce and RED against.

**If a read path computes its own fetch size internally (offset mode's `fetch := opts.Offset + opts.Limit`, or `Limit: 0` == "all" meaning `fetch = total`):**
- Either bound `fetch` to a hard ceiling and paginate internally (multiple bounded `Scroll` calls, results accumulated in Go), or narrow `WithPayload` to only the fields the caller's response shape actually needs, or both.
- Because these are the two shapes PROJECT.md names explicitly as #585's remaining overflow sites, and the "Open for discuss-phase" note in PROJECT.md ("whether Connect `ListMemories` keeps `limit: 0` = all with numeric offset paging... or moves to a hard cap plus cursor paging") signals this is a real, not-yet-decided design fork for `discuss-phase` — this research file documents the *available primitives* for both branches of that fork rather than pre-deciding it.

**If a 256-record operator sweep (`migrate`, `revert`, `summarize-missing`, `spine-review`, `reindex`) needs the record's full `content` to do its work (e.g. summarize-missing must read content to summarize it):**
- A payload-selector narrowing (like `ListScopes`'s `scope`-only fetch) is not available — the sweep genuinely needs `content`. The available bound is a smaller per-page `Limit` (below 256) computed adaptively, or accept that these sweeps need `MaxCallRecvMsgSize` raised as the defense-in-depth measure PROJECT.md describes, since payload narrowing cannot apply when the field itself is the one being read.
- Because a size bound imposed by dropping the field you need to process is not a fix — this is the one call-site family where `MaxCallRecvMsgSize` legitimately does more than "move the ceiling."
